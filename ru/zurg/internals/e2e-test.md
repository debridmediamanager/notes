# E2E-тестирование {#e2e-testing}

Сквозные тесты, которые проверяют, что zurg работает правильно после развёртывания.

## Тест воспроизведения в Plex {#plex-playback-test}

Проверяет, что контент действительно воспроизводится через Plex: выбирает случайный фильм и тестирует весь путь воспроизведения.

### Запуск теста {#run-the-test}

```bash
./scripts/plex-e2e-test.sh
```

Скрипт автоматически читает `plex_server_url` и `plex_token` из `config.yml`.

Чтобы переопределить их своими настройками:
```bash
PLEX_URL="http://your-plex:32400" PLEX_TOKEN="your-token" ./scripts/plex-e2e-test.sh
```

### Что он проверяет {#what-it-tests}

| Step | Description |
|------|-------------|
| 1 | Найти библиотеку Movies через Plex API |
| 2 | Получить общее количество фильмов |
| 3 | Выбрать случайный фильм |
| 4 | Получить URL потока для фильма |
| 5 | Проверить, что поток доступен (HTTP 200) |
| 6 | Декодировать 3 секунды видео с помощью ffmpeg |
| 7 | Создать и проверить отслеживание сессии в Plex |

### Требования {#prerequisites}

- Сервер Plex запущен и доступен
- `plex_server_url` и `plex_token` настроены в `config.yml`
- Установлены `curl`, `jq` и `ffmpeg`

### Устранение неполадок {#troubleshooting}

| Ошибка | Причина | Решение |
|-------|-------|-----|
| No movie library found | Неверный тип библиотеки или она пустая | Проверьте, что в Plex есть библиотека "Movies" |
| Stream not accessible (HTTP 4xx) | Проблема с авторизацией или путём | Проверьте токен и что файл существует |
| Failed to decode video frames | Повреждённый файл или проблема с сетью | Проверьте логи zurg, попробуйте другой фильм |
| Session not detected | Таймаут сессии Plex | Проверьте логи Plex |

## Интеграционный набор {#integration-suite}

```bash
ssh zen
cd /path/to/isolated/zurg/source
make integration-test
```

**Запускайте его на изолированной цели на `zen`.** Установите там набор инструментов Go, shellcheck, rclone и утилиту .NET move probe. Набор тестов сам создаёт свои процессы zurg и монтирования; ему не нужно заменять обычный сервис zurg или монтирование на zen. Используйте отдельный исходный каталог, `TMPDIR`, конфиг, порт и `MOUNT_PATH`. Перед запуском проверьте временный конфиг и сохраните общесистемный `INTEGRATION_LOCK_FILE=/tmp/zurg-integration-rd.lock`, даже если у вас свой `TMPDIR`, чтобы другие сеансы по-прежнему выстраивались в очередь вместе с вашим.

Тесты, у которых не хватает предусловий, могут пропуститься с кодом успешного выхода. Читайте их вывод, чтобы убедиться, что FUSE, rclone, Plex и NNTP действительно запустились.

| Тест | Нужен FUSE | Нужен Plex | Нужен аккаунт Usenet |
|------|:----------:|:----------:|:--------------------:|
| `refresh_repair_integration.sh` | | | |
| `network_test_cache_integration.sh` | | | |
| `rclone_mount_integration.sh` | да | | |
| `magic_mount_integration.sh` | да | | |
| `magic_move_refusal.sh` | да | | |
| `magic_library_move_integration.sh` | да | | |
| `plex_integration.sh` | да | да | |
| `nzb_bench_integration.sh` | | | да |

`force_location_integration.sh` **не** входит в набор — он проверяет сетевой путь этого хоста до CDN Real-Debrid, а не zurg, поэтому падает там, где этот путь не отвечает, независимо от изменения, которое тестируется. Запускайте его намеренно командой `make force-location-test` на хосте с рабочим IPv4 до нужного региона. См. [Тест интеграции Force Location](#force-location-integration-test).

Пять тестов, которые используют Real-Debrid, работают с одним и тем же аккаунтом — см. [аккаунт общий](#the-real-debrid-test-account-is-shared). Бенчмарк вместо этого использует аккаунт новостного сервера и вообще не трогает Real-Debrid, но он берёт ту же общесистемную блокировку, что и остальные: замер, проведённый параллельно с чтением другого набора, на самом деле измеряет этот другой набор.

Тест монтирования работает и на Mac, если установлен macFUSE — проверено на macFUSE и Linux `fusermount`. Тесту Plex нужны `plex_server_url` и `plex_token` во временном конфиге, и Plex должен иметь возможность проходить каждый родительский каталог временного монтирования. Монтирование внутри личного домашнего каталога может работать для тестового пользователя, но оставаться недоступным для Plex.

`make integration-test` собирает zurg, запускает shellcheck по скриптам, самопроверку `lib.sh` и модульные тесты `integration/nzbbench`, затем запускает все семь, от самых дешёвых: кэш сетевых тестов, монтирование rclone, Plex, монтирование `__magic__`, отказ в перемещении .NET, refresh/repair и в конце бенчмарк Usenet. Последние два — самые дорогие: refresh/repair ждёт полного сканирования библиотеки, а бенчмарк читает гигабайты с новостного сервера дважды, поэтому ошибка в любом другом тесте не должна заставлять ждать это, чтобы её обнаружить. `make integration-test-media` запускает тесты монтирования rclone, Plex и `__magic__`, а `make nzb-bench-test` — только бенчмарк.

Каждый скрипт владеет рабочим каталогом внутри `$TMPDIR`, собственным портом и пишет туда лог zurg; набор запускается с `STREAM_LOGS=false`, поэтому в терминал попадают только собственные проверки теста. Установите `STREAM_LOGS=true`, чтобы следить за логом zurg в stderr во время отладки.

Общие вспомогательные функции находятся в `integration/lib.sh` (управление процессами, API Real-Debrid, запросы к библиотеке на диске) и `integration/lib_media.sh` (FUSE и Plex). Чтобы добавить тест, подключите их через source, а не копируйте другой скрипт.

`integration/lib_test.sh` проверяет сами вспомогательные функции: не нужны ни аккаунт, ни сеть, занимает около секунды. `integration/nzb_bench_timing_gate_test.sh` проверяет, как обёртка бенчмарка переводит код выхода инструмента в язык набора тестов, работая на урезанном реальном отчёте из `integration/testdata/`; оба запускаются через `make test-integration-lib`.

### Тестовый аккаунт Real-Debrid общий {#the-real-debrid-test-account-is-shared}

Набор тестов работает с одним тестовым аккаунтом Real-Debrid, и этот аккаунт не приватный. Продакшн-zurg на `zen` следит за той же библиотекой, поэтому он видит и обновляет именно те торренты, которые тест только что добавил. Любой инстанс на этом аккаунте **с включённым repair** тоже проверяет, чинит и наводит порядок в них.

Оба сбоя ниже были диагностированы 2026-08-23, когда zurg на `macmini` работал с этим аккаунтом и делал repair каждые 10 минут. Этот инстанс остановили 2026-08-29, и за ним никто не присматривает, а прогоны на `zen` идут с `enable_repair: false`, так что на 2026-09-01 у обоих сбоев нет живого источника. Они вернутся, как только repair включат где-нибудь на этом аккаунте, поэтому последовательный запуск, описанный ниже, остаётся в силе.

Что это делает с прогоном, когда четыре из шести скриптов упали и на тестируемой сборке, *и* на её базовой версии:

- **Фикстура, которая так и не появляется.** Real-Debrid дедуплицирует download id для каждой ссылки, а удаление строки в downloads отзывает этот код у всех, кто его держит. Чистка другого инстанса отзывает код, который этот прогон только что разрешил; проверка прогона отвечает `404 invalid_download_code`, и zurg помечает файл как сломанный. Сломанный торрент скрывается из всех списков. Тест тогда пишет `zurg serves the fixture over HTTP but it never appeared under .../mnt/movies within 180s`, что выглядит как баг монтирования или dircache, хотя это не так.
- **Удаление, которое откатывают.** Инстанс с repair заново добавляет торрент, который этот прогон только что удалил, поэтому `refresh never dropped <hash> after it was deleted from the account` падает на библиотеке, которая показывает реальное положение дел верно.

Больше всех страдают проверки удаления и repair. Прежде чем винить изменение, прочитайте контекст сбоя, описанный ниже. А если прогон должен быть чистым, сначала остановите repair на других инстансах.

**Два этих скрипта не могут работать одновременно**, ни на этом хосте, ни из другой сессии на нём. Они делят поминутный лимит API аккаунта, поэтому пара получает `API rate limit (code=34)`, и проверки начинают падать из-за трафика, а не из-за поведения (замерено на `fun`, два параллельных прогона). Кроме того, каждый скрипт удаляет торренты *по хешу*, так что чистка одного прогона с радостью удалит фикстуру другого. Поэтому каждый скрипт берёт общесистемную блокировку в начале `main`, до первого вызова API, и держит её до выхода.

| Переменная | По умолчанию | Описание |
|----------|---------|-------------|
| `INTEGRATION_LOCK_FILE` | `$TMPDIR/zurg-integration-rd.lock` | Блокировка. `flock`, где он есть, иначе каталог `.d` с pid внутри (в macOS `flock` нет) |
| `INTEGRATION_LOCK_WAIT` | `0` | Сколько секунд ждать в очереди за идущим прогоном. `0` сразу отказывает, и это то, что нужно: альтернатива — час простоя за холодным сканированием |

Блокировка, оставшаяся от убитого прогона, забирается автоматически: в каталоге записан pid владельца, а `flock` снимает ядро. Разумеется, блокировка ничего не говорит `zen` или `macmini`. Она только разводит прогоны этого хоста.

**Как читать сбой.** Каждый `fail` теперь выводит из лога zurg этого прогона: количество каждого симптома общего аккаунта (`invalid_download_code`, `hoster_unavailable`, строки о лимите запросов, `code=34`, `Link verification failed`, `keeping files as broken`, `broken_file]`, `Deleted downloads entry`), затем последние десять таких строк и последние несколько строк с именем тестируемой фикстуры. Строка `none present, so this failure is probably zurg's own and not the account's` означает, что пора смотреть код.

В `docs/realdebrid-behavior.txt` описана семантика ссылок, на которой всё это держится: какие ссылки с какого аккаунта активируются и почему `unavailable_file` и `hoster_unavailable` означают разное.

### Время выполнения {#runtime}

Первый запуск для конкретной рабочей папки (work dir) платит за холодное сканирование библиотеки: один вызов info и одну проверку ссылок на каждый торрент, с темпом, который задаёт API-бюджет аккаунта. На аккаунте с несколькими тысячами торрентов это десятки минут. На этом аккаунте было 3 361 торрент на 2026-08-29, этого хватило, чтобы получить устойчивый `code=34` и потратить около двадцати минут на один скрипт. Между запусками рабочая папка хранит три кэша, поэтому следующие запуски их пропускают: `info/`, `linkcache/` и результаты тестов сети. Чтобы принудительно пройти холодный путь, удалите рабочую папку.

`linkcache/` — это то, что сохраняет `internal/debrid.LinkCache`, по одному файлу на каждый экземпляр провайдера. Именно эта часть убирает те двадцать минут: при первом появлении торрента одна из его ссылок разрешается, чтобы её проверить. Это один вызов `unrestrict/link` на торрент, когда кэш пустой, и бесплатно, когда кэш уже прогрет. Выигрыш ограничен TTL кэша в 4 часа, так что перезапуск набора на следующий день снова будет холодным. Поэтому эта часть ускоряет итерации, но не первый запуск.

Ни `info/`, ни `linkcache/` не лишены ссылок, и в обоих лежат коды, которые другой экземпляр на том же общем аккаунте может отозвать. `.zurginfo` — это дословный `TorrentInfo`, так что в нём есть Real-Debrid коды `/d/` торрента, а `linkcache/` хранит то, во что эти коды разрешились. Оба всё равно сохраняются. Пересборка этих кэшей и стоит десятков минут. Отозванная запись при этом не даёт неверного ответа: проверка получает `404 invalid_download_code`, zurg инвалидирует эту запись и выпускает новую. Поэтому платят вызовом только отозванные записи. Ожидайте, что их будет немного в каждом запуске, и что ускорение будет зависеть от их количества.

Фикстура ещё уже. `clean_state_for_hash` удаляет те записи `info/`, у которых хеш совпадает с её хешем, так что список ссылок всегда заново запрашивается с аккаунта. `linkcache/` же ключуется по ссылке, а не по хешу, и на каждую фикстуру не очищается. Поэтому *разрешение* одной из таких ссылок может остаться от предыдущего запуска. На это ни одна проверка здесь не опирается: фикстуры проверяют обновление, маршрутизацию, монтирование и ремонт. Устаревшее разрешение не проходит верификацию, и его перевыпускают до того, как его увидит любой из тестов.

### Интеграционный тест Refresh/Repair {#refreshrepair-integration-test}

```bash
./integration/refresh_repair_integration.sh
```

Автоматическое восстановление в тестовом конфиге остаётся выключенным. Два явных запроса `/manage/{hash}/repair` обходят эту настройку и чинят свои фикстуры.
Если включить восстановление без участия пользователя, zurg начнёт сканировать и менять несвязанные записи в общем аккаунте, и на это уйдёт бюджет API, который нужен для проверок.
`refresh_repair_config_test.sh` проверяет сгенерированный конфиг без обращений к провайдеру, используя отредактированный тестовый входной файл, снятый с сбоя от 2026-09-10.

| Сценарий | Описание |
|----------|----------|
| 1. Автоматическое обновление (добавление) | Добавляет торрент через RD API и ждёт, пока цикл обновления его заметит. Без перезапуска, иначе тест проверял бы путь холодной загрузки |
| 2. Назначение директорий и маршрутизация | Проверяет, что файлы появляются в виртуальных директориях HTTP/DAV |
| 3. Сохранение данных (перезапуск) | Перезапускает zurg и проверяет, что кэшированное состояние сохраняется |
| 4. Автоматическое обновление (удаление) | Удаляет торрент и ждёт, пока очистка устаревших ключей его уберёт |
| 5. Запуск восстановления | Запускает восстановление через Manage API, проверяет, что zurg записал в лог, что принял запрос, и ждёт `ok_torrent` с 0 битыми файлами |
| 6. Проверка восстановления | Восстанавливает второй торрент и запрашивает диапазон байтов видеофайла из него |

### Интеграционный тест Force Location {#force-location-integration-test}

```bash
make force-location-test
```

Не входит в `make integration-test`, запускается только вручную. Замер на `fun` 2026-08-29 показал: принудительные хосты `nyk` резолвятся в AAAA-записи, а клиент загрузки подключается по `tcp4`, поэтому каждый HEAD заканчивался ошибкой `no suitable address found`. При трёх повторах на каждый запрос сканирование библиотеки, которое ждёт этот тест, висит почти час, прежде чем упасть из-за сети хоста, а не из-за zurg. Тест уже пропускается, если регион нездоров (см. ниже), но эта проверка не покрывает хост, который не может достучаться до *здорового* региона по IPv4.

Заполняет сетевой тестовый кэш, закреплённый за `LOCATION` (по умолчанию `nyk`), а затем проверяет, что ссылка, полученная через эндпоинт zurg `/strm/`, перенаправляет на хост загрузки в этом регионе. `MAX_GEO_PROBES` (по умолчанию `4`) ограничивает, сколько гео-серверов проверяет шаг заполнения кэша.

Если задан `cdn_host_preference`, каждая ссылка, которую проверяет zurg, идёт через принудительный регион, так что при нездоровом регионе список остаётся пустым, и выглядит это как баг zurg. Поэтому тест сначала проверяет регион и пропускается, а не падает, если Real-Debrid не выдаёт для него ссылку или хост, который её отдаёт, не отдаёт байты.

### Интеграционный тест Rclone Mount {#rclone-mount-integration-test}

```bash
./integration/rclone_mount_integration.sh
```

Проходит по тому пути, по которому на самом деле идёт плеер: FUSE → zurg HTTP → Real-Debrid:

| Шаг | Проверка |
|------|-----------|
| 2 | zurg поднимает собственный маунт и пишет в лог `Mount verification successful` |
| 3 | настроенные директории видны в корне маунта |
| 4a–4c | фикстура попадает в библиотеку, отдаётся по HTTP и появляется в маунте. Шаги разбиты так, чтобы при сбое было видно, на каком именно переходе всё сломалось, а не просто «нет в маунте» |
| 5 | чтение файла через FUSE возвращает настоящие байты |
| 6 | после остановки zurg маунт освобождается |

Шаг 4c — это проверка VFS dircache: фикстура попадёт в маунт, только если список директории был сброшен, а не взят из кэша, сохранённого до появления торрента.

Библиотеку сужает регулярное выражение, которое строится из имени самой фикстуры. Так в маунте оказывается один релиз, а не весь аккаунт. `MOUNT_PATH` по умолчанию равен `$WORK_DIR/mnt`, но никогда не `/mnt/zurg` из продакшена. `RCLONE_BIN` по умолчанию равен `$(pwd)/bin/rclone`.

### Интеграционный тест Plex {#plex-integration-test}

```bash
./integration/plex_integration.sh
```

| Шаг | Утверждение |
|------|-------------|
| 2 | zurg пишет в лог `Successfully connected to Plex server` |
| 3 | фикстура попадает в библиотеку, и если она ещё появляется в маунте, её должно быть можно прочитать (Plex читает её как свой собственный пользователь) |
| 4 | создаётся новая одноразовая секция поверх `$MOUNT_PATH/movies` |
| 5 | zurg сопоставляет путь своей библиотеки с этой секцией и ставит в очередь обновление **для пути фикстуры** |
| 6 | Plex в итоге индексирует этот элемент |

То, что фикстура появилась в маунте, здесь скорее предусловие, а не проверка: если Plex настроен, zurg ещё и прогоняет свой matcher по всей библиотеке Plex. Это конкурирует с обновлением, так что листинг VFS может сильно отставать. Тест об этом сообщает и продолжает работу после истечения `MOUNT_VISIBLE_TIMEOUT` (по умолчанию `420`). Шаги 5 и 6 всё равно упадут, если Plex не видит файл, а проверка того, что инвалидация работает, — задача теста маунта. `PLEX_URL` и `PLEX_TOKEN` переопределяют `plex_server_url`/`plex_token` из конфига.

Plex автоматически сканирует новую секцию и может закончить раньше, чем создание вернёт управление. Тест записывает это начальное количество. Шаг 5 отдельно проверяет, что zurg ставит в очередь правильный путь после явного запроса manage.

Секция создаётся с `agent=tv.plex.agents.none` и сканером `Plex Video
Files`, поэтому Plex индексирует всё локально и не обращается к онлайн-агенту метаданных. По пути наружу секция удаляется, в том числе при ошибке, из ловушки EXIT. При SIGKILL ничего не выполняется, так что после убитого запуска проверяйте и удаляйте только свою секцию. Существующие секции харнес не трогает, потому что они могут принадлежать другой сессии. Существующие библиотеки не затрагиваются никогда.

Шаг 5 просит zurg выполнить побочные эффекты через `POST /manage/{hash}/scan`, а не ждать очередного прохода обновления. Триггер назначения папки срабатывает один раз, когда торрент обнаруживается, а это неизбежно происходит раньше, чем появляется секция. Ждать следующего полного прохода — это десятки минут на аккаунте с несколькими тысячами торрентов. Проверяемое сопоставление при этом не меняется: zurg по-прежнему должен сам сопоставить путь своей библиотеки с нужной секцией.

### Регрессия бенчмарка Usenet {#usenet-benchmark-regression}

```bash
./integration/nzb_bench_integration.sh
make nzb-bench-test
```

Ничто другое в наборе тестов не читает ни байта по NNTP. Изменение в загрузчике статей, декодере yEnc, восстановлении PAR2 или читателе архивов может вдвое снизить пропускную способность, вдвое увеличить потребление памяти или начать отдавать тишину вместо статьи, которой больше нет. Все остальные тесты при этом всё равно пройдут. Этот тест читает четыре подготовленных релиза через временный zurg и проверяет и цифры, и байты.

**Почему это A/B, а не сохранённое число.** Скорость на живом новостном сервере плавает на 10–20% в течение вечера: шесть чтений одного релиза за один сеанс дали от 34 до 50 МБ/с. Поэтому узкий допуск относительно цифры, записанной на прошлой неделе, упал бы из-за погоды, а не из-за кода. Тест измеряет два бинарника в одном временном окне на одном хосте, меняет порядок от повтора к повтору, чтобы прогрев на стороне провайдера достался обоим, и сравнивает их медианы.

A — базовая версия: по умолчанию это самый новый тег `*-nightly`, доступный из `HEAD`. Она извлекается через `git archive`, собирается один раз и кэшируется в рабочей папке, чтобы следующие запуски её переиспользовали. B — кандидат, `zurg`, который этот репозиторий только что собрал. **Метрика падает, когда B хуже A больше чем на 5%** (`BENCH_TOLERANCE`). Если B лучше, это отмечается как улучшение. Метрика, которой нет на одной из сторон, получает `n/a`, а не статус регрессии.

За каждый повтор тест замеряет: холодное открытие, время до первого байта, чтение 64 MiB и повторное чтение тех же 64 MiB из кэша, скраб из восьми точек, чтение 256 MiB с секундами CPU на гигабайт и пиковым RSS рядом (только Linux, оба значения берутся из `/proc`), а также длительность контейнера, которую выдаёт `ffprobe`.

Корректность проверяется только у кандидата и никогда по часам. Каждое чтение записывает md5, который должен совпасть с записанной константой и совпасть у двух бинарников. Повреждённый релиз должен отдать либо оригинальные байты, либо тишину, и ничего другого. Ремонт затем должен дойти до оригинала и остаться корректным после перезапуска.

Корпус лежит в `integration/nzbbench/corpus/`: шесть NZB на шесть вопросов.

| NZB | Что это | Для чего он нужен |
|-----|---------|-------------------|
| `ToyStory5.nzb` | WEB-DL на 6.61 GB, 1,576 × 4 MiB статей | каждая цифра скорости и задержки, а также проверка длительности через ffprobe |
| `ToyStory5Damaged.nzb` | тот же релиз, но message-id статьи 21 испорчен, так что любой сервер отвечает `430` | дыра должна читаться как оригинальные байты или как тишина, всё остальное — ошибка корректности. Затем PAR2 должен её починить, и ремонт должен пережить перезапуск |
| `Obfuscated.nzb` | тот же фильм, выложенный семью файлами под `<hex> [n/7] yEnc`, его настоящее имя можно восстановить только из индекса PAR2 | проверка переименования: он должен отображаться под настоящим именем `.mkv` правильного размера, и ни одного `.par2` не должно быть видно |
| `FatherBrown.nzb` | RAR из 11 томов с одним эпизодом, папка `Sample/` и nfo | читатель архивов: структура папок должна сохраниться, а чтения внутри архива получают собственную цифру скорости (`rar_read_MBps`, одно чтение за повтор) |
| `WrongTurn3.nzb.gz` | 7z без сжатия на 58 GB в 54 томах по 1 GiB (последний короче) плюс семь файлов PAR2, полное дерево UHD BluRay; сжат gzip, потому что NZB без сжатия весит 7 MB | читатель разбитого 7z: тома должны быть склеены, а заголовок в конце последнего тома прочитан до того, как что-либо начнёт перечисляться. Именно это перечисление и замеряется (`sevenzip_list_s`, одно за повтор с очищенной раскладки). Затем поток фильма на 57.6 GB должен отдать 16 MiB на смещении 8 GiB с записанным md5. Это проверка корректности, а не времени. Цифры скорости нет: у каждого тома этого релиза у данного провайдера не хватает около пятой части статей, так что замер чтения измерял бы поиск дыр |
| `NestedRar.nzb` | двухдисковый XviD-репост: один внешний набор томов RAR5, чьи члены — тома ещё двух RAR-наборов в `CD1/` и `CD2/`, плюс клип в `Sample/` и nfo | читатель вложенных архивов: оба внутренних набора должны открыться. Плоский тест отказывается от двух сравнимых наборов, а каталоги постера как раз и группируют их. Оба фильма должны отображаться с настоящими размерами и с собственной цифрой скорости (`nested_read_MBps`, одно чтение за повтор) |

**Один аккаунт, один экземпляр.** Второй zurg на том же новостном аккаунте конкурирует с первым за его лимит соединений, и сервер отказывает *более старому*. На `fun` production `zurg-usenet` держит все соединения, которые позволяет тариф аккаунта, поэтому бенчмарк работает на 10 (`BENCH_NNTP_CONNECTIONS`). Отказ `Too many connections` сообщается как **пропуск, а не провал**. То же касается недоступного сервера или отклонённого `AUTHINFO`: окружение не смогло ответить на вопрос, и тест так и пишет, вместо того чтобы винить сборку.

Около 15–20 минут при стандартных четырёх повторах, плюс разовые несколько минут при первой сборке базовой версии.

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `PORT` | `12358` | Порт для экземпляров zurg бенчмарка (по одному за раз) |
| `WORK_DIR` | `$TMPDIR/zurg-nzb-bench` | Хранит сгенерированный конфиг, рабочие папки и логи обоих бинарников, `report.json` и закэшированный базовый бинарник. Сохраняется между запусками: персистентная `data/` как раз и делает так, что последующие повторы измеряют перезапуск, а не холодное обучение |
| `BENCH_ENV_FILE` | `~/.config/zurg/bench-account.env` | Файл аккаунта, подключается, если существует. Строки `KEY=value` для переменных `BENCH_NNTP_*`. **Поддерживаемый способ дать бенчмарку собственный аккаунт.** Он не даёт учётным данным попасть в репозиторий или в историю shell |
| `CONFIG_PATH` | `config.yml` | Конфиг, из которого заимствуется новостной аккаунт, если ни окружение, ни файл аккаунта его не указывают: блок `nntp:` первого провайдера `type: nzb`. Заимствование отклоняется, если у этого аккаунта уже открыты соединения отсюда (см. ниже) |
| `BENCH_NNTP_HOST` / `_PORT` / `_TLS` / `_USER` / `_PASS` | *(из `BENCH_ENV_FILE`, затем `CONFIG_PATH`)* | Новостной аккаунт. Экспортированное значение важнее файла аккаунта. Ничего не найдено нигде: пропуск |
| `BENCH_NNTP_CONNECTIONS` | `10` | Соединения, которые открывает бенчмарк. Это предел: аккаунт, настроенный на меньшее число, сохраняет своё число |
| `BENCH_ALLOW_SHARED_ACCOUNT` | *(не задано)* | Установите `1`, чтобы мерить на заимствованном аккаунте, у которого уже есть открытые соединения. Делайте это, только если убедились, что на аккаунте достаточно места |
| `BASELINE_REF` | самый новый `*-nightly`, доступный из `HEAD` | С чем сравнивать. Определяется после `git fetch --tags` по возможности |
| `BASELINE_BIN` | *(собирается из `BASELINE_REF`)* | Готовая базовая версия, используется как есть. Способ сравниться с тем, что здесь уже не собирается |
| `BENCH_REPS` | `4` | Повторы на каждый бинарник. Медианы берутся по ним |
| `BENCH_TOLERANCE` | `0.05` | Насколько B может быть хуже, прежде чем это станет регрессией |

`report.json` содержит каждую строку по каждому повтору для обоих бинарников, медианы, вердикты по каждой метрике, вывод `version` обоих бинарников, а также хост и ОС. Так любое число в нём можно сопоставить с кодом, который его выдал. Чтобы записать набор чисел без сравнения, вызовите инструмент напрямую с одним `--bin`: он замерит, запишет JSON и завершится с кодом 0:

```bash
cd integration/nzbbench && go build -o /tmp/nzbbench . && cd -
/tmp/nzbbench --config /path/to/a-config-with-an-nzb-provider.yml --port 12358 \
  --corpus integration/nzbbench/corpus --work /tmp/nzbbench-record \
  --bin candidate=./zurg --out /tmp/record.json
```

Конфиг должен быть вашим собственным: тот, что генерирует обёртка, содержит пароль от новостного аккаунта в открытом виде и удаляется по окончании запуска.

`integration/nzbbench/README.md` описывает собственные флаги инструмента и коды выхода.

**Коды выхода `nzb_bench_integration.sh`.** `0` сравнение выполнено и прошло успешно, либо хост вообще не может запустить бенчмарк и запуск пропущен; `1` функциональная проверка не прошла или метрика ухудшилась; `4` все функциональные проверки прошли, но временной гейт **не был оценён** -- новостной сервер вышел за предел стабильности инструмента в течение окна, поэтому сравнение пропускной способности и задержки было отброшено. Код 4 намеренно не совпадает ни с 1 при сломанной сборке, ни с 0 при пропуске: решения по производительности не принято, нужен повторный запуск в более спокойное время, а запуск выводит баннер с названием гейта и разбросами значений, которые его сломали. `make integration-test` превращает любую упавшую строку рецепта в собственный код выхода make, то есть 2, поэтому при запуске набора тестов вы увидите ненулевой код make и этот баннер вместо строки цели "All integration tests passed.". Если нужно ветвление именно по коду 4, вызывайте скрипт напрямую.

### Дайте бенчмарку собственный аккаунт новостей {#give-the-benchmark-its-own-news-account}

Лимит подключений принадлежит **аккаунту**, а не процессу. Если направить бенчмарк на тот аккаунт, на котором уже работает продакшен-инстанс, вместе они превысят лимит тарифа, и сервер отключит *более старого* держателя подключения, то есть продакшен, который ничего не знает о бенчмарке, из-за которого это случилось.

Поэтому бенчмарк берёт аккаунт из `CONFIG_PATH` только как запасной вариант и **отказывается брать аккаунт, на котором на этом хосте уже открыты подключения**. Лучше дай ему свой собственный аккаунт в `~/.config/zurg/bench-account.env`:

```
BENCH_NNTP_HOST=news.example.net
BENCH_NNTP_PORT=563
BENCH_NNTP_TLS=true
BENCH_NNTP_USER=...
BENCH_NNTP_PASS=...
BENCH_NNTP_CONNECTIONS=25
```

Выбери аккаунт с запасом, от которого ничего не зависит. Это сервер, измеренный предел которого намного выше того, что настроено для любого инстанса, чтобы бенчмарк не мог оставить читателей без подключений.

Всё, что экспортировано в командной строке, всё равно важнее файла, а `BENCH_ALLOW_SHARED_ACCOUNT=1` отменяет отказ, если ты уже убедился, что запас есть.
