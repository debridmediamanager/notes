Выравнивание очистки корзины Plex с собственным статусом файлов zurg

Назначение этого документа

Сейчас Plex trash sweep решает, что удалить из библиотеки Plex, по отсутствию файла плюс таймеру возраста. zurg уже знает кое-что куда лучше: можно ли починить контент, стоящий за этим файлом, или он безвозвратно мёртв. Но sweep это не спрашивает.

Этот документ описывает план замены таймера этими данными. Его нужно проверить до того, как будет написан какой-либо код, потому что изменение решает, что удаляется из медиатеки. Текущее поведение ошибочно в обе стороны: оно ждёт две недели, прежде чем удалить контент, который мёртв уже в первый день, и удаляет контент, который zurg всё ещё активно чинит.

Здесь зафиксировано, что проверено в коде и на живой библиотеке, что предлагается и что намеренно оставлено как есть. Всё, что ниже утверждается как факт, проверено на работающей системе 2026-08-16, а не выведено по названиям.

Охват: internal/plexsweep, internal/plexdb и новый запрос только для чтения в internal/torrent. Сама логика починки не меняется.

1. Предыстория — что уже выпущено и почему это нужно пересмотреть

Коммит Что
4737b677 Предупреждение, если в Plex включён autoEmptyTrash
020042a3 Очистка: обнаружение, защитные проверки, ремонт, удаление по отдельным элементам
51cc9f69 Интерфейс настроек в Dashboard и документация
1a481a8f Ремонты учитываются в лимите, а не только удаления
c6f41621 plex_trash_sweep_min_age_days, по умолчанию 14

Главный инвариант очистки не меняется и остаётся в силе: ничего, что ещё имеет файл, никогда не удаляется. Элементы с живым файлом либо ремонтируются, либо остаются нетронутыми со своим значком корзины. Сериалы и сезоны с живыми эпизодами не трогаются вообще. Удаление происходит по отдельным элементам, а не через emptyTrash на уровне всей секции в Plex.

Пересматривается только правило того, когда можно удалять действительно отсутствующую запись.

Таймер — это заменитель вопроса, на который zurg может ответить напрямую

plex_trash_sweep_min_age_days ждёт 14 дней, прежде чем удалить запись, исходя из того, что красная иконка корзины — единственное уведомление, которое получает оператор о том, что контент пропал, а удаление записи уничтожает это уведомление.

Сама идея верная, а механизм — догадка. Он ошибается в обе стороны:

  • Торрент с пометкой infringing torrent сразу известен как мёртвый. Держать его запись в Plex две недели никому не помогает — ожидание его не вернёт.
  • Торрент, который всё ещё перепроверяется, может вернуться дольше чем через 14 дней. Таймер удалит его запись, пока zurg ещё с ним работает. Это худшая ошибка, потому что она уничтожает запись в библиотеке для контента, который потом возвращается.

2. Проверенные факты

2.1 Модель состояний zurg

Существует три состояния файла и два состояния торрента (подсчитано по internal/torrent, без тестов):

Уровень Состояния
File.State ok_file, broken_file, deleted_file
Torrent.State ok_torrent, broken_torrent

Оба — машины pkg/fsm. FSMWithTime записывает unix-метку времени каждого перехода и поддерживает SinceWhen, так что ответ на вопрос «как давно это сломано» уже есть, ничего добавлять не нужно.

Один сломанный файл обрекает весь торрент. MarkFileBrokenAndEnqueueRepair (internal/torrent/hooks.go:215-234):

changed := file.State.Set("broken_file", torrent.State.GetMutex()) == nil
...
if err := torrent.State.Set("broken_torrent"); err == nil {
    t.repairLog.Infof("Torrent state changed: %s [? -> broken_torrent] (has broken file)", ...)
}

В логе написано "has broken file", в единственном числе. Один сломанный из десяти и все десять сломанных дают одинаковое состояние торрента. Состояния файлов нигде не агрегируются.

Unfixable агрегирует по аккаунтам, а не по файлам. markAsUnrepairable (internal/torrent/unplayable_unrepairable.go:44-71):

if cp != nil {
    cp.SetUnrepairableReasonIfEmpty(reason)      // one account's copy
    entryCondemned = t.repairableCopy(torrent) == nil
}
if entryCondemned {
    torrent.SetUnrepairableReasonIfEmpty(reason) // the entry
}

Запись обрекается, когда не остаётся ни одной копии, которую можно починить. Намеренно выбрано не «у каждой копии есть причина»: копия, которую всё равно никогда не починить (у бэкенда Usenet нет magnet-адаптера), иначе держала бы мёртвый релиз в очереди на починку вечно. В File вообще нет поля unrepairable (internal/torrent/file_types.go).

Итак, три уровня отвечают на три разных вопроса, и ни один из них не отвечает на вопрос о масштабе:

Уровень Что сообщает Чего не сообщает
File.State этот файл ok / broken / deleted останется ли он мёртвым навсегда
TorrentCopy.UnrepairableReason мёртва ли копия этого аккаунта ничего о других аккаунтах
Torrent.UnrepairableReason ни один аккаунт не может починить это какая часть релиза затронута

2.2 Живые измерения (производственная библиотека, 2026-08-16)

Доли ниже — от сломанных торрентов, которые составляли около 3% библиотеки.

Почти у всех сломанных (98%) есть причина Unfixable:

Причина Доля от сломанных
stalled download 38%
infringing torrent 37%
repair failed 15%
duplicate file IDs (pack torrent) 4%
rar'ed by RD 1%
repair failed, no seeders 1%
the lone cached file is broken under 1%
invalid file ids under 1%
repair failed, download status: error under 1%
provider cannot re-add torrents under 1%

Остальные (2%) сломаны без причины — но их всё ещё можно починить.

Но Unfixable — это не то же самое, что мёртвый. zurg уже делит эти причины на постоянные и восстанавливаемые (internal/torrent/unrepairable_reasons.go:44-70). В permanentReasons лежат восемь вердиктов, которые никакой повтор не изменит: infringing, unsupported, unavailable, invalid, too big, not allowed, no repairable files, invalid file ids — плюс любая причина с префиксом repair failed, download status:. Всё остальное, включая два самых больших варианта выше, явно считается временным: stalled download, repair failed, duplicate file IDs, rar'ed by RD, not cached, the lone cached file is broken, full torrent repair failed.

repair failed, no seeders был девятым, когда брали доли выше, и записи с этой причиной здесь — как раз причина, по которой он больше им не является: ни один бэкенд, с которым работает zurg, не сообщает сиды, так что этот вердикт никогда ничем не измерялся — его вывели из того, что ремонт не уложился во время. Теперь он временный и, к тому же, его нельзя записать (verdictClaims), так что такие записи выходят из списка и пробуются снова, как и все остальные.

Применим это разделение к долям выше:

  Доля от сломанных
Постоянно неремонтируемые 39%
Неремонтируемые, но восстанавливаемые 59%
Сломаны, пока без причины 2%

Нераспознанная причина (provider cannot re-add torrents, одна запись здесь) не попадает ни в один список, и IsPermanentlyUnrepairable для неё возвращает false — осторожный ответ, именно он нам и нужен.

Это самый важный вывод для дизайна: правило, которое смотрит только на то, установлен ли Unfixable, удалило бы записи Plex в два с половиной раза больше релизов, чем на самом деле мертвы.

Теперь важно, где эти сломанные торренты находятся относительно маунта:

  Доля от сломанных Что видит Plex
Сломаны, всё ещё на маунте примерно три из четырёх Файл как будто существует → никогда не помечается tombstone. Иконки корзины нет; ломается только при воспроизведении
Сломаны, пропали с маунта примерно один из четырёх Файла нет → помечен tombstone → это и есть кандидаты для sweep

Это ключевой замер. Это значит, что sweep встречает только вторую группу, а для неё zurg обычно уже имеет вердикт.

Со стороны Plex, на том же хосте: накопилась очередь удалённых leaves, ни один из которых не старше 14-дневного окна (самый старый tombstone — 2026-08-11). Плюс несколько пустых оболочек сериалов и несколько десятков пустых оболочек сезонов.

3. Разрыв

broken_torrent означает «что-то в этом торренте сломано». Для очистки это неправильная детализация.

Вот пример: в паке из десяти эпизодов файл одного эпизода насовсем пропал, но торрент в целом всё ещё можно восстановить. Если спросить у торрента, он ответит «всё ещё восстановим», и очистка будет вечно хранить запись в Plex для этого мёртвого эпизода.

Нет состояния, которое означало бы «весь этот релиз мёртв» в отличие от «что-то в этом релизе сломано».

4. Дизайн

4.1 Не добавлять четвёртое сохраняемое состояние

Очевидный ход — новое состояние торрента, например dead_torrent. Отклонено.

Каждому сайту, который переводит торрент из одного состояния в другое, пришлось бы это поддерживать, а устаревший флаг «все файлы сломаны» хуже, чем отсутствие флага, потому что он даёт право на удаление. Нужная информация уже есть в состояниях файлов, просто она нигде не собирается воедино.

Вместо этого вычисляем её на лету:

// AllFilesBroken reports whether nothing in this release still reads.
// Derived from the file states rather than stored, so it cannot go stale
// and needs no migration or new transitions.
func (t *Torrent) AllFilesBroken() bool

Так дешевле, всегда согласованно, и это можно показать на дашборде без хранения в базе.

Определение, которое нужно уточнить при реализации: deleted_file должен считаться как «не читается» наравне с broken_file, а торрент с нулём файлов должен возвращать false, а не true по пустой логике. Пустой релиз не доказывает, что он мёртв.

4.2 Спросить у файла, при необходимости вернуться к торренту

Очистка сопоставляет путь Plex с файлом zurg и затем применяет:

Вердикт zurg Очистка
файл ok_file оставить — на самом деле он не пропал
broken_file, у торрента нет причины невосстановимости оставить — ремонт может вернуть файл, как бы долго он ни длился
broken_file, причина указана, но не постоянная оставить — zurg всё ещё считает файл восстановимым
broken_file, причина постоянная (невосстановимо навсегда) удалить — никакая повторная попытка не изменит этот вердикт
у zurg нет торрента для этого пути использовать окно по возрасту

Проверка на постоянность — это IsPermanentlyUnrepairable(reason) (internal/torrent/unrepairable_reasons.go:59), она используется ровно так же, как её использует ForceRepairTorrent. Важно переиспользовать её, а не заново собирать список: если позже в permanentReasons добавят новую причину, поведение очистки должно поменяться автоматически, а неизвестная причина должна оставаться непостоянной.

AllFilesBroken() сама по себе не даёт права на удаление — релиз, который полностью сломан, но с восстановимой причиной, всё равно обрабатывается. Эта функция уточняет отчёты и дашборд и помогает человеку, читающему лог, отличить «пропала одна серия из десяти» от «пропал весь пак».

Последняя строка объясняет, почему plex_trash_sweep_min_age_days остаётся. Когда торрент полностью исчезает из аккаунта, его .zurgtorrent исчезает вместе с ним, и zurg больше не может ничего сказать. Таймер перестаёт быть основным правилом и становится запасным вариантом именно для случая, когда лучшего варианта нет.

Это также понижает настройку в интерфейсе, что решает отдельную жалобу на то, что её подпись («Keep Broken Entries Visible») описывает побочный эффект, а не действие.

4.3 Поиск путь → торрент → файл

Существующий матчер Plex работает в обратную сторону: buildPlexDirIndex (internal/plex/matcher.go:539) индексирует компоненты пути Plex и ищет их по ключу торрента. Для sweep нужна обратная логика, построенная на той же идее:

  1. Построить map[strings.ToLower(GetKey(torrent))] *Torrent из DirectoryMap.Get(INT_ALL).

  2. Разбить путь Plex на компоненты с той же нормализацией, что и splitPathComponents (matcher.go:525), и проверить каждый компонент по этой карте. Каталог релиза — это компонент, который совпал.

  3. Внутри этого торрента сопоставить оставшуюся часть пути с File.Path (internal/debrid/types.go:133), чтобы найти конкретный файл.

Работать нужно через TorrentManager, а не сравнивать строки с data/*.zurgtorrent. Причины: различаемые имена (Some.Release {a1b2c3}), копии на нескольких аккаунтах и переименования корректно определяются только через GetKey.

Неудачный поиск — не повод что-то удалять. Если путь не определился, считаем, что zurg «не имеет мнения», и переходим к запасному варианту с окном по возрасту.

4.4 Что не меняется

  • Инвариант: ничего, у чего есть живой файл, не удаляется.
  • Сериалы и сезоны с живыми потомками никогда не трогаются.
  • Удаление по одному элементу через DELETE, никогда не emptyTrash.
  • Защитные проверки: rclone под управлением и запущен, монтирование читается, Plex не сканирует.
  • Снимок перед любыми изменениями; лимиты действуют и на исправления, и на удаления.

Новые правила только делают очистку более осторожной или более точной — они никогда не разрешают удаление, которое текущий код бы отклонил.

5. План реализации

# Шаг Файлы
0 Убедитесь, что разделение на постоянные/восстанавливаемые — правильный фильтр: сделайте пробный подсчёт (dry-run) на живой библиотеке до того, как что-то будет удалено —
1 AllFilesBroken() + юнит-тесты (пустой релиз, смешанный, все сломаны, все удалены) internal/torrent/
2 Поиск статуса только для чтения: путь → торрент → файл, возвращающий небольшое значение-вердикт новый файл в internal/torrent/ или internal/plexsweep/
3 Определите тип вердикта (StatusOK, StatusRecoverable, StatusPermanentlyDead, StatusUnknown), чтобы sweep никогда не работал с внутренностями zurg напрямую internal/plexsweep
4 Подключите поиск к Sweeper через интерфейс, как уже сделано для Mount/Library/Trash internal/plexsweep/sweep.go
5 Примените таблицу решений; оставьте окно по возрасту как запасной вариант для StatusUnknown internal/plexsweep/sweep.go
6 Передайте TorrentManager в точке вызова internal/app.go
7 Тесты: по одному на каждую строку таблицы решений, плюс тест на ошибку поиска, который доказывает, что неразрешимый случай никогда ничего не удаляет internal/plexsweep/sweep_test.go
8 Документация: docs/config.md, config.example.yml, docs/CHANGELOG.md, и перепишите подпись на дашборде документация + шаблоны

Порядок: шаги 1–3 — чисто добавления без изменения поведения, их можно включить одним коммитом; шаг 5 — единственный, который меняет, что будет удалено.

6. Риски и открытые вопросы

  1. Порядок инициализации. Подтверждено: startPlexTrashSweep вызывается в internal/app.go:268, а TorrentManager создаётся в internal/app.go:285, то есть уже после него. Вызов нужно перенести ниже или использовать сеттер. Нужно проверить, не зависит ли от текущего места что-то ещё.
  2. Неоднозначность поиска. Два торрента могут иметь ключи, которые совпадают по одному и тому же компоненту пути. Решение: если подходит больше одного кандидата, считать StatusUnknown, а не выбирать один из них.
  3. only_show_the_biggest_file. В каталоге фильмов часть файлов скрыта, поэтому путь в Plex может указывать на файл, который zurg не отдаёт. Поиск не должен считать, что имя файла из Plex дословно есть в File.Path.
  4. Стоимость. Построение индекса ключей на каждом проходе зависит от размера библиотеки, O(размер библиотеки). При нескольких тысячах торрентов это несущественно, а проход запускается раз в день. Индекс нужно строить на каждый проход, а не на каждый элемент.
  5. Снимается ли Unfixable когда-либо? Решено: да. refresh.go:851-857 снимает его, когда торрент проходит проверку и возвращается в ok_torrent ("all links intact, no broken files"). repair.go:165-181 снимает его (запись и все копии) при принудительном восстановлении. Поэтому восстановленный релиз не несёт устаревшей пометки, и дизайн не должен от неё защищаться.
  6. Битые, но присутствующие торренты. Это вне рамок данной задачи: Plex никогда не помечает их как удалённые, поэтому проход их не видит. Стоит отметить, что до момента сбоя воспроизведения они невидимы и для Plex, и для этой функции.

7. Как это было реализовано (2026-08-16)

Внесено как feat: decide plex trash sweep removals from zurg's repair verdicts. Там, где реализация решила вопрос, который этот документ оставлял открытым, или отошла от §4, указаны решение и причина:

  • Поиск сопоставляет родительский каталог пути точно с DirectoryMap[INT_ALL], вместо перебора всех компонентов пути (§4.3). Монтирование раскладывает релиз плоско: <library dir>/<key>/<visible name>. Plex записал путь из монтирования, которое отдаёт ключ как есть. Если точного совпадения нет, ответ — unknown, и неоднозначность из-за коллизий ключей (риск 2) исчезает, потому что точные ключи не могут совпасть.
  • Строка 1 таблицы решений изменилась. ok_file, которого при этом нет в монтировании, — это файл, который скрывают фильтры, а не «на самом деле не потерян». Если оставить его навсегда, после смены фильтра останется постоянная иконка корзины. Теперь такой случай откатывается к окну по возрасту.
  • deleted_file учитывается наравне с broken_file во всех правилах, а не только в AllFilesBroken(). Строки таблицы читаются как «не ok_file».
  • Элементы с несколькими версиями оцениваются целиком. Таблица была поштучной, а единица работы sweep — элемент Plex с частями. Если восстанавливается одна часть, сохраняется весь элемент. Элемент считается мёртвым, только если мертвы все части. Любое другое сочетание уходит в окно по возрасту.
  • Имя файла, которое указывает на торрент, но не на файл (переименование, листинг архива, only_show_the_biggest_file, риск 3), считается мёртвым, только если причина записи постоянная и AllFilesBroken(). Восстанавливаемым оно считается, если торрент сломан без постоянного вердикта. Во всех остальных случаях ответ — unknown. Несопоставленное имя никогда не осуждается по ассоциации, пока какой-либо файл ещё читается.
  • Подключение (риск 1): startPlexTrashSweep перенесён ниже создания менеджера в internal/app.go. Ничто не зависело от его прежнего места. Вердикты попадают в sweep через plexsweep.Verdicts, который реализует TorrentManager.FileStatusForMountPath. Пока первое обновление не заполнило INT_ALL, каждый поиск отвечает unknown, и sweep ведёт себя точно так же, как версия с окном по возрасту.

8. Явно вне рамок

  • Пустые оболочки сериалов и сезонов. Очистка удаляет только конечные файлы, поэтому полностью мёртвый сериал оставляет после себя пустую оболочку (в измеренной библиотеке таких сериалов несколько, а сезонов — несколько десятков). Это отдельная задача, которой нужна аккуратная последовательность действий: удалить конечные файлы, перепроверить родительский каталог и удалять его только тогда, когда у него не осталось дочерних элементов.
  • Любые изменения в поведении ремонта, в очереди ремонта или в том, когда zurg помечает что-то как неремонтопригодное.
  • Собственный autoEmptyTrash в Plex, который уже учтён предупреждением в 4737b677.
  • Существующий накопившийся объём в измеренной библиотеке: его намеренно оставили для ручного решения.
