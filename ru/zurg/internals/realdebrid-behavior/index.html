Торренты

Real-Debrid поддерживает загрузку неограниченного количества торрент-файлов и magnet-ссылок, а также выбор отдельных файлов из них для скачивания. Если торрент-файл или magnet-ссылку уже скачал другой пользователь, такой торрент считается «cached», и Real-Debrid сразу отдаёт вам готовую ссылку. Если нет, сервис попытается скачать magnet-ссылку из публичных трекеров или через DHT/PEX. Если это торрент-файл с информацией о трекерах, будут использованы именно эти трекеры. Это полезно для приватных трекеров (к сожалению, многие приватные трекеры блокируют серверы загрузки Real-Debrid). Если у торрента больше нет сидеров и личеров и скачать все его части невозможно, появится ошибка. После скачивания вы также получите кешированные ссылки вида https://real-debrid.com/d/DOWNLOADCODE DOWNLOADCODE — это уникальный ID конкретного файла длиной ровно 13 символов (всё, что идёт после 13-го символа, игнорируется).

Выбор файлов

Как уже говорилось, внутри торрента можно выбрать только те файлы, которые вы хотите скачать. Если в торренте есть файлы A, B и C, и вы выбираете A и B, будут скачаны только A и B. Статус кэша торрента на самом деле зависит от этого уникального выбора файлов. Возвращаясь к торренту с файлами A, B и C: для A, B или B (single), A+B, B+C, A+C (pair) или A+B+C (all files) статус кэша будет разным. Каждый уникальный выбор заново скачивает торрент с трекеров и возвращает другую ссылку на кэш, даже для одного и того же файла.

Кешированные ссылки

Кэшированные ссылки не скачиваются. По сути это просто контейнер для ЗАГРУЗОЧНЫХ КОДОВ в Real-Debrid. Чтобы получить настоящую ссылку для скачивания или стриминга, её нужно "unrestrict" (превратить) через Real-Debrid. Такая ссылка действует 7 дней. Сами кэшированные ссылки живут дольше 7 дней. Если у торрента есть рабочие кэшированные ссылки (то есть их можно успешно unrestrict), значит, он всё ещё в кэше Real-Debrid. Точно не известно, но весьма вероятно, что статус кэша торрента можно продлить, если больше пользователей будут делать unrestrict его кэшированных ссылок.

Имейте в виду, что проверить, работает ли кэшированная ссылка, можно только одним способом: сделать unrestrict и проверить первый байт полученной ссылки с помощью HTTP-заголовка Range. zurg поддерживает две проверки: по HEAD (по умолчанию, быстро) и на основе Range (GET bytes=0-0, более тщательно). Выбор делается опцией конфигурации use_range_verification.

Совместное использование кешированных ссылок между аккаунтами (измерено 2026-08-19)

RD возвращает ID ссылок двух длин: 13 символов (70%) и 16 символов (30%). Эти лишние 3 символа меняют то, кто может разблокировать ссылку:

  • Если обрезать ID до первых 13 символов, ссылка /d/ разблокируется с ЛЮБОГО премиум-аккаунта, а не только с того, который её создал. Торрент-библиотека вызывающего не трогается. Единственный побочный эффект: запись в истории загрузок вызывающего.
  • Если отправить полный 16-символьный ID, та же ссылка разблокируется ТОЛЬКО с аккаунта, который её создал. Все остальные аккаунты получают "unavailable_file". Так происходит, даже пока торрент-источник жив, даже если у вызывающего есть тот же infohash в его собственной библиотеке, и независимо от параметра ip. Поэтому всегда обрезай ID до 13 символов перед разблокировкой сохранённой ссылки. Тесты с полными ID ложно "доказывают", что делиться ссылками нельзя.

Кэшированные ссылки переживают удаление торрента создавшим аккаунтом, но умирают от старости. По результатам выборки в большом масштабе: ссылки, созданные 1–2 месяца назад, всё ещё разблокировались с других аккаунтов. Ссылки старше ~3 месяцев все возвращали "hoster_unavailable". Отдельно RD может удалить сам контент из своего кэша. Хэш, который месяц назад был в кэше, на следующий месяц может висеть в downloading с 0 сидами. Тогда ссылка возвращает "unavailable_file" для всех, включая создавший аккаунт.

Как разбирать ошибку разблокировки для сохранённой кэшированной ссылки:

  • ссылка 13 символов + hoster_unavailable -> ссылка состарилась; повторное добавление торрента с тем же выбором создаст свежие ссылки (см. восстановление ниже)
  • ссылка 13 символов + unavailable_file -> RD полностью удалил контент; для свежих ссылок нужна настоящая перезакачка с сидов
  • ссылка 16 символов + unavailable_file -> это ни о чём не говорит про доступность: ты просто не тот аккаунт, который её создал. Обрежь ID и повтори

Разблокированные ссылки (URL-адреса хостов *.download) привязаны к IP серверным трекингом, а не отказом: CDN спокойно отдаёт 206 чужому IP, но real-debrid записывает IP загрузок. Использование ссылок одного аккаунта с нескольких IP приводит к предупреждению о шеринге аккаунта. Передавай IP загрузчика в unrestrict/link (параметр ip), чтобы ссылка создавалась для того IP, который будет качать файл.

Восстановление повреждённых кешированных ссылок

Иногда кэшированная ссылка или даже разблокированная ссылка на файл внутри торрента перестаёт работать. Это может быть из-за ошибки unrestrict API или потому что разблокированная ссылка возвращает HTTP-ошибку. Чтобы это исправить, нужно заново скачать торрент и сгенерировать новые, свежие кэшированные ссылки. Можно попробовать перезагрузить торрент с тем же самым выбором файлов и посмотреть, появятся ли новые, свежие кэшированные ссылки. Если это не помогло, значит, нужно выбрать другой набор файлов в этом торренте. Например, если в торренте с несколькими файлами сломан только один файл, выберите только этот сломанный файл. Если всё равно возвращается сломанная кэшированная ссылка, попробуйте добавить в выбор ещё один файл. Повторяйте это, пока не получите свежую рабочую кэшированную ссылку.

Поведение RAR

Real-Debrid имеет особенность: если выбрать тип файла, который нельзя стримить, торренты сохраняются в RAR-архивы (без сжатия).

Подтверждённые типы видеофайлов: .avi .flv .m2ts .m4v .mkv .mov .mp4 .mpg .mpeg .ts .webm .wmv Подтверждённые типы аудиофайлов: .mp3 .flac .m4a

Если выбрать файлы этих типов, Real-Debrid отдаёт отдельные ссылки на каждый файл, и их можно стримить. Если выбрать что-то другое, то Real-Debrid точно упакует всё в RAR-архив. Например, если выбрать .mkv видео и .sub субтитры, файлы будут упакованы в RAR. То же самое, если выбрать только .jpg постер: он тоже уйдёт в RAR.

Торрент, даже с несколькими файлами, если он упакован в RAR, вернёт только одну кэшированную ссылку (которая указывает на RAR-файл). Если выбрать только подтверждённые типы видео/аудио, архивирования не будет, и вы получите кэшированную ссылку на каждый выбранный файл.

Удаление строки в списке загрузок отзывает URL, который она создала

Замерено 2026-08-22 на тестовом аккаунте, по одному unrestrict на каждый случай.

Unrestrict создаёт запись в /downloads и URL на одном пронумерованном хосте, например https://124-4.download.real-debrid.com/d/<13-char code>/. Код не привязан к хосту: до удаления записи тот же код отвечает 200 на 44-4, 125-4 и на собственном 124-4. Завершающий сегмент с именем файла необязательный везде; zurg его убирает, и обе формы отвечают одинаково.

DELETE /downloads/delete/ отзывает этот код, а то, что останется рабочим, зависит от того, какие хосты уже отдавали файл:

  • Запись удалена, URL так и не запрашивали: все хосты отвечают 404 с X-Error: invalid_download_code. Через 30 с всё ещё 404, так что не устаканивается.
  • Запись удалена после одного запроса через 44-4: 44-4 продолжает отвечать 200, а хост 124-4, который выдал код, и нетронутый 125-4 отвечают 404 invalid_download_code.

Выходит, что запрос к файлу активирует код на том хосте, который его отдал, а запись как раз и держит остальные хосты рабочими. Это противоположно предположению, на котором написана очистка списка downloads, и это важно, потому что zurg выбирает хост для загрузки на каждый запрос (ensureReachableDownloadServer переписывает на один из N самых быстрых хостов): хост, на который пришёл проверочный HEAD, не обязательно тот, который выберет следующий запрос. Поэтому ресолв, оставшийся в кеше ссылок после удаления записи, почти на каждом последующем запросе отвечает 404 invalid_download_code. Это выглядит как сломанная ссылка и помечает здоровый релиз как битый.

Повторный unrestrict той же ссылки после удаления в итоге выдаёт новый id на новом хосте и работает нормально. Id не переиспользуются.

Но не сразу, и первое измерение здесь говорило «не затронуто», потому что его сняли через несколько минут. Повторно замерено 2026-08-23 на тестовом аккаунте: после DELETE /downloads/delete/ unrestrict/link 75 секунд возвращал тот же мёртвый id и выдал новый только на t+81s.

Из этого следуют два вывода, и оба отражены в коде. downloadsCleanupMinAge держит запись две минуты перед удалением, поэтому соседний экземпляр, который ресолвит ту же ссылку в этом окне, получает живой код. А цепочка повторных unrestrict в пути отдачи (четыре попытки примерно за шесть секунд) целиком укладывается в это окно, так что её исчерпание ничего не говорит о файле. Когда каждый ресолв возвращает тот же URL, который только что ответил 404, zurg отказывает в чтении с Retry-After вместо того, чтобы помечать релиз битым.
