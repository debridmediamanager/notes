# Список изменений {#changelog}

## zurg находит аниме, ежедневные шоу и спешлы для Sonarr {#zurg-finds-anime-daily-shows-and-specials-for-sonarr}

Раньше источник Sonarr пропускал ежедневные сериалы, аниме и спешлы сериалов, и на каждый тип выводилось по одному предупреждению. Теперь недостающие серии ежедневных шоу тоже запрашиваются по дате выхода (`The Daily Show 2026.11.03`), серии аниме по номеру, который шоу использует в счёте (`Jujutsu Kaisen 30` — это шестая серия второго сезона), а спешлы как сезон `00`, наряду с обычным поиском по сезону и серии. Парсер самого Sonarr определяет, какая серия в каждом релизе, как и для любого сериала, а профиль качества оценивает его по-прежнему. Видео, которое кладётся для аниме или ежедневного шоу, называется `JUJUTSU KAISEN - S02E06 - <the release's own name>`, потому что пересканирование Sonarr читает файл только по его имени и положил бы `2nd Season - 06` в сезон 1. Видео обычных сериалов и спешлов сохраняют свои имена. Спешлы кладутся в папку, которую задаёт **Specials Folder Format** в Sonarr, и подойти к ним может только релиз с именем `S00Exx`. Подробнее: [Что zurg запрашивает у Sonarr](../guides/acquisition.md#what-zurg-asks-sonarr-for).

## Держать искомый фильм в 1080p и в 4K {#keep-a-wanted-film-at-1080p-and-at-4k}

`quality: [1080p, 4k]` в блоке `acquisition:` оставляет по две копии каждого фильма в вашем списке желаемого DMM, чтобы телевизор 1080p мог воспроизводить одну из них без транскодирования файла 4K. Каждая копия берёт лучший релиз с разрешением не выше своего и сама обновляется до него. Пока нет ничего лучше 1080p, обе копии используют один экземпляр. Сериалы и все остальные источники по-прежнему получают одну копию. См. [копия на каждое из нескольких разрешений](../guides/acquisition.md#a-copy-at-each-of-several-resolutions).

## zurg update работает после установки в одну строку {#zurg-update-works-after-the-one-line-install}

Однострочные установщики входят в GitHub через GitHub CLI. Они скачивали его только для этого и удаляли после завершения. Поэтому `zurg update` искал GitHub CLI, не находил его и останавливался с ошибкой "no GitHub credential found", хотя ваша авторизация всё ещё была сохранена. Старый GitHub CLI из репозитория Ubuntu не может передать авторизацию, и обновление там тоже останавливалось так же.

Теперь `zurg update` также использует GitHub CLI, который установщики хранят в `bin` рядом с zurg. Авторизация, сохранённая GitHub CLI без keyring, теперь работает, даже если сам CLI удалён. Если авторизация всё равно не найдена, команда выведет одну команду, которая это исправит. Запустите обновление через установщик один раз, и все последующие `zurg update` будут входить сами.

## Много старых ссылок Real-Debrid, которые падают сразу, больше не называется сбоем сервиса {#many-old-real-debrid-links-failing-at-once-is-no-longer-called-an-outage}

Ссылки Real-Debrid перестают работать через несколько месяцев после создания, поэтому релизы, добавленные примерно в одно время, перестают воспроизводиться тоже примерно в одно время. Когда за один проход восстановления выходило из строя больше пяти таких релизов, zurg записывал в лог "suspected provider-wide outage" и придерживал восстановление всех, кроме пяти. Из-за этого большая партия оставалась сломанной гораздо дольше и выглядела так, будто Real-Debrid лёг. Теперь zurg сначала спрашивает Real-Debrid про релиз на том же аккаунте, который ещё воспроизводится. Если он воспроизводится, значит, сбойные ссылки просто старые, и все релизы восстанавливаются как обычно. Только если Real-Debrid отказывает и в рабочих ссылках, zurg считает это сбоем и ждёт.

## Ссылки на сессии Emby на панели открывают панель Emby {#the-dashboards-emby-session-links-open-embys-dashboard}

Ссылки «active sessions» и «transcodes» на панели Emby в дашборде открывали `/web/#/dashboard`, то есть адрес Jellyfin для этой страницы, и Emby там навсегда застревал на заставке. Теперь обе ссылки ведут на `/web/index.html#!/dashboard`, адрес, который Emby использует сам. Ссылки на панели Jellyfin не изменились.

## Отсутствие .nfo больше не отправляет релиз Usenet на repair {#a-missing-nfo-no-longer-sends-a-usenet-release-to-repair}

Старые посты в Usenet часто теряют свой .nfo, а все видео- и архивные части остаются на месте. zurg принимал это за повреждение всего релиза. Каждый раз, встретив такой .nfo, он запускал восстановление, и так повторялось после каждого перезапуска. Настоящие восстановления из-за этого ждали в очереди за сотнями бессмысленных. Некоторые релизы, которые нормально проигрывались, помечались как невосстановимые, и единственным способом вернуть их было удалить .nfo.

Теперь отсутствующий .nfo или другой небольшой файл рядом с видео считается пустым и не запускает восстановление. Такой файл больше не помечает релиз как невосстановимый. Поврежденное видео можно снова восстановить, если рядом с ним нет .nfo. Релизы, которые уже были помечены невосстановимыми по этой причине, перепроверяются примерно в течение дня и возвращаются сами по себе.

## Файлы Usenet больше не проигрывают тишину там, где сервер отдал статью другой загрузки {#usenet-files-no-longer-play-silence-where-a-server-sent-another-uploads-article}

Некоторые новостные серверы на запрос одной статьи вашего файла отвечают статьёй из другой загрузки с тем же номером. zurg заметил это только тогда, когда у другой загрузки статей было меньше, чем у вашего файла. На коротких файлах, например на томах RAR и коротких сериях, он брал не ту статью и на этом участке проигрывал тишину. В логе это называлось `an internal mapping failure in zurg`, а смещение «falls between two articles that are both present and neither covers». Теперь zurg также проверяет размер файла, который указывает каждая статья. Он отказывается от статьи из другого файла и запрашивает настоящую у других ваших новостных аккаунтов. Статьи, которые старая сборка уже сохранила в кэше статей, тоже отбрасываются. Если у вас один аккаунт, этот участок всё равно будет проигрываться как тишина. Теперь в логе записано, что сервер отправил статью другого файла, а не то, что проблема в zurg.

## Соединения Usenet снова работают на полной скорости, когда другое приложение перестаёт использовать аккаунт {#usenet-connections-come-back-at-full-speed-after-another-app-stops-using-the-account}

Если ваш провайдер новостей когда-либо отказывал zurg из-за слишком большого числа подключений, например пока другая программа или более ранний zurg ещё занимали часть из них, zurg продолжал добавлять подключения по одному в секунду всё время работы, даже когда свободные места уже появились. После каждого затишья пачка загрузок снова начиналась с двух «тёплых» подключений, поэтому большому аккаунту требовалось больше минуты, чтобы вернуться к полной скорости, а импорты стояли в очереди за ним, с записью «waited 5s for a connection (queued for the account's allowance)» в журнале отладки. Теперь, как только провайдер снова принял подключение и минута прошла без новых отказов, zurg открывает нужное количество сразу.

## Отладочный лог показывает, когда загрузка ждёт соединения при настроенных нескольких новостных серверах {#the-debug-log-says-when-a-fetch-waits-for-a-connection-with-several-news-servers-configured}

С одним сервером Usenet, если загрузка ждала соединения дольше пяти секунд, в отладочном логе появлялась строка об этом. С двумя и более серверами такой строки не было никогда, так что добавление второго сервера убирало её, даже если ожидание на самом деле не прекращалось. Теперь строка появляется и в конфигурациях с несколькими серверами, и в ней указаны серверы, на которые ждала загрузка.

## Захват Usenet без файлов для repair и с мёртвой первой статьёй сразу завершается ошибкой {#a-usenet-grab-with-no-repair-files-and-a-dead-first-article-fails-at-once}

Релиз, выложенный без файлов PAR2, у которого первая статья отсутствовала на всех новостных серверах, раньше держался пять минут, прежде чем Radarr или Sonarr узнавали, что загрузка провалилась: всё это время ждали восстановления, из которого нечего было восстанавливать. Теперь zurg видит, что данных для восстановления нет, и сразу сообщает, что загрузка не удалась, поэтому клиент добавляет релиз в blocklist и переходит к следующему.

## Захват Usenet, который исправил repair, больше не помечается как неудачный через пять минут {#a-usenet-grab-that-repair-fixed-is-no-longer-reported-failed-five-minutes-later}

Когда в загрузке не хватало нескольких статей, а её PAR2-файлы могли их восстановить, zurg чинил её. Но опережающее чтение, которое работало во время починки, могло снова запросить недостающие статьи и получить отказ сразу после того, как починка заканчивалась. Этот отказ возвращал релиз в список повреждённых, поэтому загрузку держали пять минут, а потом помечали как неудачную, и Radarr или Sonarr добавляли в блоклист релиз, который на самом деле нормально воспроизводился. Отказ по статье, которую починка уже восстановила, больше не считается повреждением.

## Обновлённые загрузки, которые пришли с .nfo или субтитрами, тоже удаляются {#upgraded-downloads-that-came-with-an-nfo-or-subtitles-are-deleted-too}

С `magic.allow_delete` включённым, удалённое видео, которое не было внутри RAR-архива, раньше удалялось само по себе. `.nfo`, субтитры и постер, лежавшие рядом с ним, оставляли загрузку в библиотеке. NZB-файл оставался в `nzbs/`, а торрент — на вашем аккаунте debrid. Каждое обновление такой загрузки оставляло после себя такой же мусор. Теперь вся загрузка удаляется, как только ничего в `__magic__` её больше не использует. Загрузка остаётся, пока другой эпизод из неё всё ещё в библиотеке или ждёт импорта в своей папке. Субтитры, которые Sonarr или Radarr импортировали рядом с видео, тоже её держат, пока их не удалят.

## Заменённые и неудачные загрузки Usenet больше не копятся {#replaced-and-failed-usenet-downloads-no-longer-pile-up}

С включённым `magic.allow_delete` удалённый эпизод или фильм, который был извлечён из RAR-архива, просто скрывался. Загрузка, из которой он взялся, оставалась в библиотеке, а её NZB навсегда оставался в `nzbs/`. Когда вы обновляли отдельные эпизоды до сезонного пака, для каждого эпизода оставалась такая запись. Теперь вся загрузка удаляется, как только ничто в `__magic__` её больше не использует. Загрузка остаётся, пока в библиотеке есть другой эпизод из того же архива. Она также остаётся, пока в её папке есть что-то для импорта.

Sonarr и Radarr при удалении неудачной загрузки просят удалить её файлы. zurg всё равно сохранял NZB. Теперь он удаляет его, если из этого релиза ничего не было импортировано. Загрузка, которая завершилась и была импортирована, сохраняет свой NZB, как и раньше, потому что импортированный файл всё ещё воспроизводится из него.

## zurg теперь сообщает, когда библиотека закончила загрузку {#zurg-now-says-when-the-library-has-finished-loading}

Docker считает zurg здоровым сразу после запуска. Большая библиотека может грузиться после этого больше часа. Всё это время папки в маунте выдают `Input/output error`, и кажется, что установка сломана. Новый адрес `/ready` помогает различить эти два случая. Он отвечает 503, пока библиотека не загрузится, и 200, когда загрузка закончится. Пароль для него не нужен. Внутри контейнера `/app/healthcheck.sh --ready` проверяет то же самое. Собственная проверка здоровья контейнера по-прежнему только смотрит, запущен ли zurg. Так долгая первая загрузка не сможет привести к перезапуску контейнера или задержать маунт, который от него зависит. Проверка здоровья теперь ещё и читает переменную окружения `PORT`. Раньше контейнер с заданным `PORT` проверялся не на том порту.

## Захват может пропускать релизы по словам в их названиях {#acquisition-can-skip-releases-by-words-in-their-names}

Задайте `exclude_words` в блоке `acquisition:`, и zurg никогда не возьмёт релиз, в названии которого есть одно из этих слов. `exclude_words: [DV, HDR10+]` не даёт попасть на телевизор, который не умеет воспроизводить Dolby Vision и HDR10+, но при этом всё равно берёт 4K с обычным HDR. Работает для Plex watchlist, Seerr, Radarr и Sonarr, а также для Usenet и торрентов. Сравнение только по целым словам. `DV` не поймает `DVDRip` или фильм под названием Adventures. `DV`, `DoVi` и `Dolby Vision` означают одно и то же, как и `HDR10+` и `HDR10Plus`. Radarr и Sonarr никогда не спрашивают про исключённый релиз.

## Radarr и Sonarr могут брать лучшее качество из профиля первым {#radarr-and-sonarr-can-take-the-profiles-best-quality-first}

Продукт zurg обычно берёт разрешённый релиз, который быстрее всего проверить. Для фильма это обычно 1080p WEB-DL. Затем проход обновления движется к cutoff вашего профиля. Для сериалов сначала берётся пак сезона, а уже потом отдельные серии. Поэтому 1080p-пак может заполнить сезон, даже если были доступны серии в 2160p. Установите `best_first: true` в разделе `acquisition:`, и первая загрузка будет следовать вашему профилю качества в Radarr или Sonarr. Сначала берётся лучшее разрешение из разрешённых. Всё, что соответствует cutoff или выше, считается достаточно хорошим. Если релиз оказывается недоступен, zurg идёт вниз по профилю. Первый файл может прийти дольше, потому что лучшие релизы часто являются большими многотомными постами. По умолчанию эта опция выключена.

## Результаты торрентов больше не вытесняют NZB там, где ни один аккаунт не принимает торренты {#torrent-results-no-longer-crowd-out-nzbs-where-no-account-takes-torrents}

На инстансе с NZB-провайдером, но без аккаунта debrid, который принимает торренты, acquisition всё равно искал по твоим Torznab-индексаторам, и каждый найденный торрент съедал одну из трёх попыток, которые даются релизу эпизода или пака сезона. С `prefer: torrents` или когда 4K-торренты стояли выше 1080p NZB, NZB так и не пробовались, и эпизод падал. Теперь Torznab-индексаторы там пропускаются, а в логе появляется одна строка об этом. Релиз, который инстансу некуда положить, больше не считается попыткой. Фильмы тоже больше не спрашивают Radarr о таких торрентах.

## Захват больше не считает NZB готовым там, где нечего проиграть {#acquisition-no-longer-counts-an-nzb-as-done-where-nothing-can-play-it}

На инстансе с аккаунтом debrid и без провайдера nzb поиск при получении всё равно обращался к вашим индексаторам Newznab, а загруженный NZB считался готовым без какой-либо проверки. Из-за этого название из списка Plex могло быть удалено из списка для файла, который ни один инстанс не может воспроизвести. Теперь на таком инстансе индексаторы Newznab пропускаются, и в логе появляется одна строка об этом. NZB никогда не считается готовым на инстансе без провайдера nzb.

## Релиз без чего-либо для проигрывания сообщается один раз, а не каждый день {#a-release-with-nothing-left-to-play-is-reported-once-instead-of-every-day}

Когда у релиза удалялись все воспроизводимые файлы, zurg каждый день снова выдавал предупреждение, что он «has no playable file that still reads». В библиотеке со ста такими релизами в день записывалось сто таких предупреждений для релизов, к которым никто не прикасался. Теперь предупреждение появляется один раз, а релиз снова проверяется только тогда, когда с ним что-то меняется. Восстановление файла по-прежнему возвращает его сразу.

## Битые релизы на AllDebrid и TorBox возвращаются, когда файлы всё ещё проигрываются {#broken-releases-on-alldebrid-and-torbox-come-back-when-the-files-still-play}

Релиз, который есть только у AllDebrid, TorBox, Premiumize, Offcloud или Debrid-Link, мог неделями оставаться сломанным и скрытым, хотя аккаунт всё ещё его отдавал. Repair сам по себе не добавляет заново релизы на этих сервисах, потому что они намеренно удаляют контент, а больше ничего не проверяло, начали ли файлы работать. Теперь Repair раз в день спрашивает аккаунт, воспроизводятся ли ещё файлы сломанного релиза, и возвращает те, которые воспроизводятся, ничего не добавляя. Всё, что аккаунт действительно удалил, по-прежнему требует кнопки Repair. Прогноз MCP repair говорит то же самое, а не сообщает, что ни одна проверка никогда не сработает по этому релизу.

## Загрузки TorBox, которые ставятся в очередь за свободным слотом, теперь показываются как в очереди и доходят до конца {#grabs-torbox-queues-for-a-free-slot-show-as-queued-and-finish}

Когда все слоты загрузки на аккаунте TorBox были заняты, TorBox ставил новые захваты из Sonarr и Radarr в свою очередь, и zurg терял их из виду. Захват показывался как fetching metadata примерно десять минут, а потом как ошибка, и Sonarr с Radarr его сбрасывали. Когда TorBox позже загружал его, ничего не импортировало файл. Теперь zurg следит за захватом из очереди до того, как TorBox его запустит, и до конца загрузки. Пока он ждёт, он показывается как queued, а таймаут отсутствия прогресса не запускается, пока TorBox не начнёт загрузку.

## Можно искать один релиз на странице `__magic__` {#you-can-search-for-one-release-on-the-__magic__-page}

На библиотеке, которую организуют Sonarr или Radarr, после каждого импорта остаётся скрытая рабочая папка, а страница `__magic__` показывает только первую тысячу сохранённых строк. Нужный тебе релиз обычно в этот список не попадал, поэтому его кнопки Unhide и Reset были недоступны, а заметка под списком отправляла в data/magic.json. Редактировать этот файл, пока работает zurg, нельзя: при остановке zurg записывает его заново из памяти, и строки возвращаются после перезапуска.

Теперь у сохранённых строк и висячих страниц есть поле поиска. Введи название релиза, путь из своего mount или хеш, и все строки, сохранённые для этого релиза, появятся вместе с кнопками, сколько бы ни было записей в таблице.

Так же можно вернуть релиз, который есть в `__all__`, но никогда не появляется в `__magic__/__all__.` Если удалить релиз и добавить его заново или вернуть из DMM, его хеш сохраняется, и он возвращается со всем, что `__magic__` хранил о нём, включая папку задания, удалённую после импорта. Найди его через поиск и нажми Unhide в строке release-tombstone.

## `__magic__` на Windows перестаёт бесконечно расти журнал {#__magic__-on-windows-stops-growing-its-journal-forever}

On Windows, zurg logged `cannot truncate data\magic.journal ... Access is
denied.` every time it tried to tidy the file where `__magic__` records your
moves and folders. The file was never emptied, so it grew with every change
and every start read all of it again. After a few thousand changes in one run,
each further change also rewrote the whole saved layout. zurg now empties it
on Windows as it always did elsewhere, and the first start after updating
clears what has piled up. If tidying ever fails, zurg tries again after more
changes instead of on every one.

## Восстановление файла через MCP сразу возвращает его релиз {#restoring-a-file-over-mcp-puts-its-release-back-right-away}

Восстановление файла с помощью MCP-инструмента `zurg_release_file_restore` возвращало файл на место, но релиз оставался помеченным как неисправный и лежал в `__unplayable__` до следующего обновления библиотеки. Теперь инструмент делает то же, что кнопка Restore в торрент-менеджере: релиз выходит из `__unplayable__`, возвращается в свои папки вместе со своими .strm-файлами и сохраняется в таком виде. Как и раньше, он не просит Plex, Jellyfin или ваш скрипт on_library_update пересканировать библиотеку.

## Вернуть файлы, которые скрыл неудачный repair {#bring-back-files-a-failed-repair-hid}

Старые сборки помечали файл удалённым, когда ремонт сдавался на одном аккаунте, даже если другой аккаунт ещё мог его воспроизвести, и релиз тогда пропадал из всех папок. В менеджере торрентов появился новый фильтр "Deleted, still served": он показывает релизы, у которых ничего не осталось для воспроизведения, но удалённый файл всё ещё отдаёт какой-то аккаунт. Если зажать кнопку Restore, zurg проверит ссылку каждого файла и вернёт в папки те, что воспроизводятся, так же как если бы вы нажали Restore на каждом файле по отдельности.

zurg сам по себе этого не делает. Файл, который вы удалили намеренно, хранится точно так же, поэтому просмотрите список и восстанавливайте только то, что вы не удаляли. Релизы, которые всё ещё что-то воспроизводят, в список не попадают, так как удаление лишней серии или эпизода — это обычное намеренное удаление.

## Захват смотрит дальше первой страницы результатов поиска {#acquisition-looks-past-the-first-page-of-search-results}

Раньше acquisition читал только первую страницу, которую возвращал индексатор. С DMM, который отдаёт по десять результатов на страницу, самые большие сначала, ограничение по размеру могло отсеять все они, и фильм падал с ошибкой "no eligible releases" каждые несколько часов, хотя более мелкие релизы были на следующих страницах. Теперь он продолжает запрашивать страницы, пока не наберёт достаточно релизов, подходящих под твои ограничения, но не больше десяти страниц. Для сериалов эпизод, который не нашёлся в поиске по сезону (обычно это более старый эпизод, когда в результатах доминирует самый новый), теперь ищется отдельно.

## Мёртвые файлы в папках фильмов и сериалов `__magic__` теперь выпадают, чтобы Radarr и Sonarr их заметили {#dead-files-in-__magic__-movie-and-show-folders-now-drop-out-so-radarr-and-sonarr-notice}

Файл, который Radarr или Sonarr импортировали в папку под `__magic__`, после того как релиз перестал работать, продолжал показываться в полном размере, поэтому повторное сканирование всё ещё его видело, и фильм или серия так и не возвращались в состояние wanted. Теперь он исчезает из папки в тот же момент, что и из всех остальных списков: как только ремонт больше не может его восстановить, или через день после поломки, если ремонт выключен. При следующем сканировании он помечается как missing, и acquisition ищет замену. Если файл снова начинает работать, он появляется на прежнем месте.

## Season Fix сортирует пакеты из нескольких сезонов и пронумерованные экстры {#season-fix-sorts-multi-season-packs-and-numbered-extras}

Season Fix теперь сам определяет сезон по названию каждого файла, поэтому раздача вроде `Full Metal Panic S2 - 01`, `Bakuman II - 01`, `KonoSuba 2 - 01` или `Demon Slayer Mugen Train Arc - 01` больше не сваливает все серии в один сезон 1, и каждая серия получает свой сезон. Раздачи с названиями в ромадзи или с суффиксом, например `Sergeant Keroro 001-358` или `Dragon Ball Z COMPLETE`, распознаются, если их файлы имеют одно общее название. Имена с подчёркиваниями, `Ep01`, `1.01.` или число внутри названия серии теперь читаются так, как и задумано.

Пронумерованные дополнительные материалы, например `Special 01`, `OVA 01`, `- 11 (OVA)` и выпуски-пересказы `24.5`, раньше попадали к настоящей серии как вторая версия, и Play мог выбрать именно дополнительный материал. Теперь их переименовывают с суффиксом Plex `-other`, поэтому они отображаются как extras.

## Мёртвая ссылка Real-Debrid больше не держит скан библиотеки на несколько минут {#a-dead-real-debrid-link-no-longer-holds-a-library-scan-for-minutes}

Когда Real-Debrid продолжает отдавать файл с той же отозванной ссылкой, zurg ждёт несколько минут, потому что это нормально сразу после удаления загрузки. Если файл всё ещё отклоняется таким образом через пять минут, он теперь считается битой ссылкой и отправляется на repair, вместо того чтобы просить пользователя прийти позже. Раньше один мёртвый файл мог задерживать сканирование Plex примерно на десять минут.

## Зависшие и неудачные задания Usenet можно очистить на странице `__magic__` {#failed-and-stuck-usenet-jobs-can-be-cleared-from-the-__magic__-page}

Задание со статусом Failed или Stuck в списке SABnzbd оставалось там навсегда, как только Sonarr или Radarr переставали использовать zurg как клиент загрузки. Перезапуск его не убирал. Единственный способ был удалить `data/sabnzbd-jobs.json` вручную. На странице `__magic__` теперь у каждого задания со статусом Failed или Stuck есть кнопка **Clear**, а над списком есть кнопка, которая очищает их все сразу. Удерживайте её, пока полоса не заполнится. Задания в статусе Queued и Completed не трогаются. NZB-файл задания тоже удаляется, если только импорт в `__magic__` не использует этот релиз.

## Аддон Stremio сообщает, когда ему нужен https {#the-stremio-addon-says-when-it-needs-https}

Stremio загружает аддон по простому http только на том компьютере, где он запущен. На телевизоре, телефоне или другом компьютере адрес http не работает и выдаёт "failed to load manifest", даже если устройство может достучаться до zurg. Страница настроек теперь показывает это прямо рядом с адресом аддона, если вы открыли её по http с таким адресом. В руководстве по Stremio показаны три способа поставить zurg за https: Tailscale Serve, свой обратный прокси и туннель Cloudflare.

## Plex подхватывает фильм или серию сразу, как только Radarr или Sonarr импортирует их в `__magic__` {#plex-picks-up-a-movie-or-episode-as-soon-as-radarr-or-sonarr-imports-it-into-__magic__}

После того как Radarr или Sonarr переносили файл в папку внутри `__magic__`, zurg просил Plex просканировать сам файл. Plex сканирует только папки, поэтому он отвечал, что всё в порядке, и ничего не добавлял. Фильм при этом оставался пропавшим до следующего планового сканирования Plex. Теперь zurg просит Plex просканировать папку, в которую попал файл. То же касается файла, который заменяет обновление, чтобы старая версия исчезала из библиотеки. Это относится и к ручным эндпоинтам сканирования, инструменту MCP `zurg_plex_scan_releases`, сканированию после переименования или удаления файла, а также путям, которые передаются в `on_library_update`.

## Страница Manage показывает дубликаты релизов и тот, который использует Radarr или Sonarr {#the-manage-page-lists-duplicate-releases-and-which-one-radarr-or-sonarr-uses}

Обновление заменяет релиз, который был до него, но тот остаётся в вашей библиотеке. А если загрузки идут с разных индексеров, у вас может оказаться несколько копий одного фильма или сезона. Новое представление Duplicates на странице Manage группирует релизы, в которых лежат один и тот же фильм или одни и те же эпизоды, и показывает, какой из них использует Radarr или Sonarr. zurg определяет это по тому, где лежит файл в `__magic__`, а не по названиям релизов.

Для сезона он перечисляет каждый эпизод, который есть в более чем одном релизе, и тот релиз, в котором находится файл Sonarr. Поэтому пак, из которого Sonarr берёт всего несколько эпизодов, всё равно показывается как используемый. Все остальные релизы помечаются как "No reference found" или "Unknown" с указанием причины. Выберите те, которые хотите удалить, и zurg перед удалением заново запросит данные из Radarr и Sonarr, пропустив всё, что начало использоваться с тех пор. Ничего не удаляется автоматически.

## Занятые слоты загрузок TorBox считаются так же, как их считает TorBox {#torboxs-busy-download-slots-are-counted-the-way-torbox-counts-them}

Перед тем как восстановление или первое воспроизведение добавит торрент в TorBox, zurg проверяет, есть ли на аккаунте свободный слот для загрузки. Раньше он считал все торренты, которые не были полностью загружены. Из-за этого пропускались торренты, которые раздаются (seeding), а TorBox засчитывает их в лимит тарифа на срок до 30 дней, и при этом учитывались торренты, срок хранения контента которых истёк, а они слот вообще не занимают. Из-за нескольких истёкших торрентов в библиотеке восстановление могло ждать так, будто все слоты заняты.
Теперь zurg считает именно те торренты, которые TorBox помечает как active.

## TorBox может раздавать для приватных трекеров {#torbox-can-seed-for-private-trackers}

Новая настройка `tb_seed_torrents` определяет, будет ли zurg раздавать торренты, которые он добавляет в TorBox. По умолчанию она стоит на `never`, так что если вы её не трогаете, ничего не меняется. Поставьте `always`, если приватному трекеру нужен ваш рейтинг, или `auto`, чтобы решение принимал параметр раздачи в вашем аккаунте TorBox. Её можно поменять в разделе Health & Repairs на панели управления, и она начинает работать при следующем добавлении.

Торрент, который раздаётся, занимает один из активных слотов вашего тарифа TorBox, пока раздача идёт, до 30 дней на Pro. Если раздающиеся торренты заполняют все слоты, новым загрузкам и ремонтам на этом аккаунте приходится ждать, пока какой-то слот освободится.

## Наборы RAR, у которых тома названы не по порядку, теперь проигрываются {#rar-sets-whose-volumes-are-named-out-of-order-now-play}

Релиз, у которого каждый том RAR называется по-своему, например случайным именем или `Movie 2026 part1.rar`, раньше показывался как отдельный архив на каждый том. Первый из них показывал фильм, но после первой части перестава работать, а остальные ничего не показывали. Теперь zurg сам читает из самого тома, к какой части он относится, и собирает набор обратно. Раньше это приходилось делать вручную, переименовывая тома в `part001.rar` и далее. Это работает только тогда, когда тома пронумерованы и образуют один полный набор. Если какого-то тома не хватает или два тома претендуют на одно и то же место, релиз остаётся как был, а в логе написано почему. Сжатые архивы, тома которых выложены не по порядку, теперь тоже воспроизводятся.

## Скан Plex, который ещё анализирует, больше не помечается как зависший {#a-plex-scan-that-is-still-analysing-is-no-longer-reported-as-stuck}

Plex во время анализа файлов, которые нашёл скан библиотеки, не меняет ни прогресс скана, ни текущую папку. На большой или удалённой библиотеке этот анализ может занимать очень много времени. Раньше дашборд принимал это за зависший скан и советовал перезапустить Plex прямо в процессе. Теперь zurg слушает собственный канал обновлений Plex и считает элементы, над которыми Plex сообщает, что работает. Поэтому помечается только скан, который действительно остановился.

## Загрузки торрентов только из кэша сохраняют отказ при добавлении у провайдеров с ограничением скорости {#cached-only-torrent-uploads-preserve-the-refusing-add-on-rate-paced-providers}

Файл `.torrent`, отправленный в режиме cached-only, теперь доходит до отказного добавления TorBox, даже когда его почасовой лимит добавлений переполняет бэкенд. Промах по кэшу не создаёт передачу и не занимает активный слот, но всё равно тратит одно из 60 некэшированных добавлений TorBox в час. Обычные добавления продолжают загружать исходный файл. В руководстве по qBittorrent теперь перечислены все шесть провайдеров загрузки торрент-файлов, а также описаны отдельные пути cached-only для Debrid-Link и TorBox.

## Файл, который вы удаляете во время восстановления, остаётся удалённым {#a-file-you-delete-while-it-is-being-restored-stays-deleted}

Удаление файла или релиза, пока восстановление всё ещё проверяет его ссылку, теперь ждёт завершения этой проверки и затем побеждает. Обновление библиотеки, которое уже шло, больше не может вернуть релиз, который вы только что удалили.

## Перемотка далеко внутрь сжатого архива больше не вешает читалку {#a-seek-far-into-a-compressed-archive-no-longer-hangs-the-reader}

Файл внутри сжатого RAR или zip можно декодировать только с начала, поэтому чтение ближе к концу большого архива раньше ждало весь архив и не получало никакого ответа. Plex мог висеть на таком чтении больше часа, а этого хватало, чтобы заблокировать его базу данных. Теперь zurg отвечает в течение 20 секунд, сохраняет уже пройденный прогресс и готовит конец файла в фоне, поэтому следующее чтение этой части происходит сразу.

## Отказы Real-Debrid следуют опубликованным правилам имён файлов {#real-debrid-refusals-follow-the-published-filename-rules}

Когда Real-Debrid отказывает в повторном добавлении релиза во время repair, zurg теперь проверяет название релиза и названия его файлов по опубликованным правилам именования. Если релиз блокируется этими правилами, он помечается как infringing навсегда. Любой другой отказ воспринимается как то, что Real-Debrid замедляет добавления, и релиз остаётся в очереди на следующий проход repair, а не снимается.

## Восстановление файла сразу возвращает его на место {#restoring-a-file-puts-it-back-where-it-belongs-straight-away}

Действие Restore на странице управления релизом теперь перекладывает релиз в нужные директории, сохраняет восстановленное состояние и записывает его STRM-файл сразу, как только файл проходит проверку. Восстановленный файл больше не остаётся в директории unplayable до следующего обновления провайдера, а релиз, у которого последний битый файл был восстановлен, после перезапуска не помечается как сломанный. Удалённые файлы остаются удалёнными, пока вы их не восстановите.

## Отбрасываем чужие статьи Usenet до отдачи байтов {#reject-foreign-usenet-articles-before-serving-bytes}

Отклоняйте статьи Usenet с тем же номером, у которых положительный общий размер yEnc меньше наибольшего номера, указанного в NZB, включая сохранённый кэш и progressive-пути, чтобы рабочие резервные аккаунты подставляли байты.

## Сохраняем классификацию отказов RD, подкреплённую доказательствами {#preserve-evidence-backed-rd-refusal-classification}

Не записывать ответы addMagnet 451 как отказы релиза, пока доказательства ограничения на уровне аккаунта не охватывают всю операцию, и сохранять временные ошибки при repair.

## Уточнили окна чтения для истёкших и повреждённых файлов {#clarify-expired-broken-file-read-windows}

Сообщите о том, что окно повторных попыток чтения битого файла истекло, но не говорите, что восстановление сдалось.

## Отдаём записанное состояние файла в MCP {#expose-recorded-file-health-in-mcp}

Покажи записанные по каждому файлу счётчики состояния в представлениях релизов MCP и сделай так, чтобы таблицы файлов с ленивой загрузкой можно было безопасно просматривать, не выдавая состояние жизненного цикла за живую проверку раздачи.

## Обрабатываем повторяющиеся операции с sidecar-файлами {#handle-duplicate-sidecar-operations}

Распознавать типизированные ответы «источник не найден» от дублирующихся WebDAV-алиасов, при этом сохраняя настоящие ошибки «все неудачно» и ошибки доступа.

## Перезагрузка под тем же именем восстанавливается, а не помечается как ошибка {#a-re-grab-under-the-same-name-is-repaired-instead-of-failed}

Повторное скачивание NZB под именем, которое zurg уже хранит, больше не проверяет и не восстанавливает старую копию, пока читается новая. Скачивание ждёт новый файл, поэтому релиз с пропущенной статьёй, которую PAR2 может восстановить, восстанавливается и доводится до конца, а не помечается как неудачный.

## Сбои восстановления больше не выдаются за удаления пользователем {#repair-failures-no-longer-masquerade-as-user-deletions}

Ошибки автоматического восстановления теперь помечают как сломанный только тот источник провайдера, который дал сбой. Исправные альтернативные копии сохраняются, а при следующем обновлении провайдеров видимость файла может вернуться.

## Торренты без IMDb id определяются по имени релиза через DMM {#torrents-without-an-imdb-id-are-identified-by-release-name-through-dmm}

Если задан `dmm_metadata_secret`, задача IMDb больше не требует ключа OpenSubtitles. Торренты без id или только с маркером промаха от OpenSubtitles определяются при запуске по тегу `imdb-tt…` в их названии. Если тега нет, их пытается определить резолвер DMM, но он отвечает только тогда, когда название точно совпадает ровно с одним тайтлом. Фансаб-романизации вроде "Kaijuu 8-gou" находятся через алиасы DMM и совпадают с Kaiju No. 8, а название, которое есть у нескольких сериалов, не трогается. Торрент, который DMM не может назвать, сохраняет пустой id, чтобы Plex-совпадение всё равно могло его заполнить.

## Фильм Radarr, который ни один индексатор не знает по id, ищется по названию {#a-radarr-movie-that-no-indexer-knows-by-id-is-searched-for-by-name}

Многие посты в Usenet индексируются без IMDb или TMDB id. zurg искал фильм для Radarr только по id, поэтому документалка, по которой ни один индексатор не вернул ничего по id, падала с ошибкой "no eligible releases", хотя встроенный поиск Radarr по названию находил нормальный релиз. Если поиск по id ничего подходящего не нашёл, zurg теперь ищет и по названию с годом, а встроенный парсер Radarr всё равно решает, является ли каждый результат нужным фильмом. Поиск по названию запускается только тогда, когда поиск по id вообще ничего не нашёл: если фильм по id найден, он индексируется по id, а повторный запрос по названию просто принёс бы те же самые посты.

## NZB, найденные через Prowlarr, теперь можно скачать {#nzbs-found-through-prowlarr-can-be-downloaded}

Prowlarr передаёт каждый Usenet NZB через редирект на индексатор, и отключить это нельзя. zurg раньше следовал редиректу только на тот же хост, поэтому при индексаторах, настроенных через Prowlarr, каждая загрузка NZB завершалась ошибкой "answered 301 Moved Permanently", и ничего не скачивалось. Теперь редирект отрабатывается. API-ключ из самой ссылки по-прежнему не передаётся на другой хост, а редирект с HTTPS на обычный HTTP по-прежнему блокируется.

## Индексатор, который отказывает часами, больше не тормозит получение {#an-indexer-that-refuses-for-hours-no-longer-stalls-acquisition}

Prowlarr отвечает на поиск по отключённому индексатору кодом `429` и заголовком `Retry-After` на много часов. zurg ждал две минуты и спрашивал снова, три раза, так что каждый поиск тратил шесть минут на один этот индексатор. Acquisition сдавался по каждому тайтлу после пяти попыток и выбрасывал всё, что уже ответили остальные индексаторы, поэтому ничего не добавлялось, пока индексатор не вернётся. Теперь индексатор, который просит оставить его в покое дольше двух минут, пропускается до назначенного им времени, а поиск идёт по остальным.

## Название, удалённое после получения, ищется снова {#a-title-deleted-after-acquisition-is-searched-for-again}

Когда файл, который zurg добавил по запросу Sonarr или Radarr, удалили (потому что это была не та версия или по другой причине), и тайтл снова появился в списке missing, zurg отвечал "completed without a search, the release was already held" и больше не искал его. Теперь zurg сначала проверяет папку сезона или фильма в `__magic__`. Эпизод или фильм, у которого видеофайла уже нет, ищется заново. Тот, у которого видео ещё есть, что происходит, пока Sonarr не сделал рескан, оставляется как есть.

## «Scan in Plex» в списке нераспознанных теперь ждёт результата {#scan-in-plex-on-the-undetected-list-waits-for-the-result}

Кнопка сканирования по удержанию в списке необнаруженных перезагружала страницу через две секунды после нажатия, хотя сопоставление с Plex ещё не начиналось. На большой библиотеке оно занимает минуты, поэтому список всегда возвращался без изменений, и казалось, что кнопка ничего не делает. Теперь кнопка показывает, что сопоставление идёт, ждёт его окончания, сообщает, сколько релизов удалось сопоставить, и только после этого перезагружает страницу.

## Релиз, чьё имя заканчивается пробелом, сопоставляется с Plex {#a-release-whose-name-ends-in-a-space-is-matched-to-plex}

Релиз, у которого в имени файла есть пробел перед расширением, например
`... [Hurtom] v2 .mkv`, получает папку, название которой заканчивается пробелом. Plex находил её, но zurg так и не мог её сопоставить, поэтому она оставалась в списке необнаруженных после каждого сканирования. Теперь сопоставление работает.

## Удаление файла на странице manage сохраняет вашу позицию {#deleting-a-file-on-the-manage-page-keeps-your-place}

Раньше при удалении, восстановлении, переименовании или принудительном показе одного файла на странице управления релизом страница перезагружалась в самом верху, поэтому при чистке большого пака после каждого клика приходилось снова прокручивать вниз. Теперь страница возвращается к строке этого файла и подсвечивает её.

## Панель принимает путь монтирования, набранный в кавычках {#the-dashboard-takes-a-mount-path-typed-with-quotes}

Путь монтирования, вставленный в панель управления так, как его пишет config.yml, например `"/Users/me/Plex Media Server/ZurgMount"` или `'Z:\'`, отклонялся с ошибкой "mount path should be absolute", потому что кавычки считались частью пути. Теперь панель управления убирает парные кавычки вокруг значения и сохраняет путь без них.

## Сбой загрузки списка Plex watchlist теперь объясняет причину {#a-failed-plex-watchlist-fetch-says-why}

Когда Plex отклоняет запрос списка желаний, в логе теперь есть его собственная причина, например `unexpected status: 401: Invalid token`, а не только код статуса. Если вы всё ещё видите `Failed to fetch watchlist: ... unexpected status: 400`, эта формулировка пришла из сборки старше августа. Обновите zurg: текущие сборки запрашивают список желаний страницами, которые Plex принимает.

## Релиз, слишком повреждённый для памяти repair, сразу помечается как ошибка {#a-release-too-damaged-for-repairs-memory-fails-at-once}

Когда у релиза Usenet не хватает больше, чем PAR2 может восстановить, помещаясь в память за один раз, zurg теперь сообщает об этом и останавливается, а Sonarr или Radarr выбирают другой релиз. Раньше он держал захват в ожидании, а затем пробовал снова каждые несколько минут, каждый раз заново проверяя весь релиз и получая тот же ответ. Повреждения, которые ещё не подтверждены как окончательные, например статьи, на которые сервер не ответил, по-прежнему повторно запрашиваются.

## Setup проходит мимо пустого конфига и сообщает, когда поле токена скрыто {#setup-gets-past-an-empty-config-and-says-when-the-token-prompt-is-hidden}

`zurg setup` и установщики, которые его запускают, отказывались продолжать работу, если в папке лежал пустой `config.yml`, и выводили ошибку, которая заканчивалась пустым местом. Теперь пустой конфиг заменяется. Файл с содержимым по-прежнему никогда не перезаписывается, а в ошибке теперь написано, какой это файл и как начать заново. Подсказка для ввода токена говорит, что введённое или вставленное значение будет скрыто, из-за чего раньше казалось, что терминал не принимает ввод. Опечатка в `config.yml` теперь помечается как ошибка в `config.yml`, а не во внутреннем "outbound identity config".

## Резервный сервер новостей теперь восполняет статьи, которые основной отдаёт неверно {#a-backup-news-server-now-fills-in-articles-the-main-server-answers-wrongly}

Некоторые новостные серверы на запрос одной статьи отвечают куском другой загрузки. zurg распознавал неправильный кусок, но никогда не просил резервный сервер о нужном. Из-за этого пропуск воспроизводился как тишина, или файл не открывался, даже если резервный сервер его имел. Теперь zurg запрашивает следующий сервер, как это делает SABnzbd.

## RAR-релиз Usenet попадает в свою папку без перезапуска {#a-rard-usenet-release-reaches-its-directory-without-a-restart}

Релиз, выложенный набором RAR, раскладывается по директориям по именам его томов, пока архив не открыт, а после открытия — по файлам внутри. Раньше после открытия архива никто не перераскладывал его заново, поэтому директория, которая ищет `.mkv` или номера эпизодов, пропускала только что загруженный релиз в RAR, пока zurg не перезапустят, и Plex с Jellyfin его там не видели. Теперь релиз перемещается в нужные директории сразу, как только его архив впервые просмотрен.

## Фильм, выложенный под случайным именем, называется по своему релизу {#a-movie-posted-under-a-random-name-is-named-after-its-release}

Некоторые посты в Usenet дают фильму случайное имя, например `eq5KVi5Y3iTwFEn1Nub8yPY9yd6oUzTu.mkv`, и повторяют его во всех местах поста, где может быть настоящее. zurg сохранял это имя, поэтому у Radarr и Sonarr в имени файла не было ничего, за что можно зацепиться. Теперь zurg называет файл по имени релиза, как это делает SABnzbd: только когда это явно один большой файл релиза, только для видеофайла и никогда для структуры диска или архива. Это касается релизов, которые будут загружены с этого момента; тот, что уже есть в библиотеке, сохраняет своё имя.

## Правила по размеру теперь применяются к файлам внутри архивов {#size-rules-now-apply-to-files-inside-archives}

Фильм из Usenet, выложенный как набор RAR, показывается как файлы внутри архива. Эти файлы обходили настройки директории `only_show_the_biggest_file` и `only_show_files_with_size_gte`/`_lte`, поэтому всё остальное, что было в посте, оставалось видимым рядом с фильмом. Во многих постах есть маленькая картинка с именем фильма и набор кадров с временными метками, и Jellyfin использовал её как постер. Теперь настройки размера применяются к содержимому архивов так же, как и ко всем остальным файлам.

## Релизы Usenet, где самый большой файл PAR2 больше 512 МБ, можно восстановить {#usenet-releases-whose-largest-par2-file-is-over-512-mb-can-be-repaired}

Когда в релизе не хватает частей, zurg восстанавливает их из собственных PAR2-файлов релиза. Раньше он отказывался читать любой PAR2-файл больше 512 MB. А в большом релизе именно этот файл содержит больше всего данных для восстановления, и часто он единственный. Из-за этого такой релиз нельзя было починить, сколько бы частей ни не хватало. zurg снова и снова пытался, каждый раз скачивая все свои более мелкие PAR2-файлы, и только потом сдавался. Теперь zurg читает PAR2-файл любого размера.

Если повреждений в релизе больше, чем одно восстановление может удержать в памяти, он сразу отклоняет такой релиз, как только подсчитает повреждения, ещё до скачивания каких-либо его PAR2-файлов.

## Sonarr может передать свои недостающие эпизоды в zurg {#sonarr-can-hand-its-missing-episodes-to-zurg}

zurg теперь умеет брать список и из Sonarr. Добавь источник `sonarr` в `acquisition.sources`, укажи URL Sonarr и API-ключ. zurg затем проходит по эпизодам, которых не хватает в Sonarr, и по файлам эпизодов, которые нужно апгрейдить. Он ищет по твоим индексаторам и проверяет, что новостные серверы всё ещё хранят релиз. Каждый эпизод он кладёт в папку его сезона внутри `__magic__` и просит Sonarr пересканировать сериал. Для этого Sonarr не нужны ни индексаторы, ни клиент загрузки.

Сезон, который отсутствует целиком и уже закончил выходить, может прийти одним сезонным паком. Всё остальное приходит по одному эпизоду. Каждый релиз сначала проходит через собственный парсер Sonarr. Он должен быть от нужного сериала и про нужный эпизод, и он должен подходить под профиль качества сериала. Апгрейды заменяют только тот эпизод, который обновляют. Если для одного эпизода сезона релиза пока нет, остальные всё равно размещаются, и Sonarr пересканирует их. Ежедневные сериалы и аниме пока пропускаются, в логе появляется заметка. Настройку стороны Sonarr описывает `docs/acquisition.md`.

## Получение работает со многими тайтлами одновременно {#acquisition-works-on-many-titles-at-once}

Раньше названия из списка просмотра или сервиса запросов обрабатывались одно за другим, поэтому длинный список занимал столько же времени, сколько все его названия вместе. Теперь zurg работает сразу с восемью названиями, это задаёт `acquisition.concurrency`. Название, которое появилось в списке поздно, больше не ждёт, пока завершатся все впереди него.

Новый релиз теперь не лежит по две минуты, прежде чем zurg его проверит. zurg проверяет каждую секунду, пока релиз не появится в библиотеке, но не дольше полутора минут. Если серверы новостей больше не хранят релиз, zurg сразу переходит к следующему кандидату, а не повторяет попытку через пять минут. Проверка релиза больше не должна укладываться в то время, которое осталось после поиска, поэтому медленный поиск по длинному списку больше не задерживает названия на минуты. Обновления для названий, которые у вас уже есть, теперь ждут, пока не будут готовы недостающие названия из того же списка, так что они не конкурируют с ними за вызовы индексаторов и подключения к новостным серверам.

## Релиз Usenet, восстановленный через PAR2, остаётся восстановленным при чтении {#a-usenet-release-repaired-with-par2-stays-repaired-while-it-is-read}

Когда некоторых частей релиза нет на новостных серверах, zurg восстанавливает их из PAR2-файлов релиза и отдаёт восстановленные байты. Часть zurg, которая забирает данные заранее, до того как их запросит плеер, не знала о восстановленных кусках. Поэтому она снова запрашивала у серверов отсутствующие статьи. Их там по-прежнему не было, и zurg снова отмечал релиз как повреждённый, хотя все отданные им байты были правильными. Релиз, восстановленный во время импорта, мог через пару мгновений снова получить статус сбоя, а download client выбрасывал хорошую копию и скачивал другую. Теперь zurg ничего не запрашивает у серверов, если уже восстановил это сам.

## Radarr может передать свои нужные фильмы в zurg {#radarr-can-hand-its-wanted-movies-to-zurg}

zurg теперь умеет брать список фильмов из Radarr. Добавь источник `radarr` в `acquisition.sources`, укажи URL Radarr и его API-ключ. Тогда zurg будет перебирать фильмы, которых Radarr не хватает или которые можно улучшить. Он ищет релизы через твои индексаторы, проверяет, что новостные серверы ещё держат нужный релиз, кладёт видеофайл в папку фильма внутри `__magic__` и просит Radarr пересканировать этот фильм. Для этого Radarr не нужны ни индексаторы, ни клиент загрузки. Каждый релиз, который берёт zurg, сначала проходит через собственный парсер Radarr, так что это точно нужный фильм и он подходит под профиль качества: разрешённое качество, минимальный балл Custom Format, ограничения по размеру и улучшение только до cutoff. zurg берёт первый разрешённый релиз, который быстрее всего проверить, сначала веб-релизы, а предпочтительные качества профиля оставляет следующему шагу улучшения. Radarr zurg спрашивает только тогда, когда собирается проверить релиз, по одному за раз. Он никогда не спрашивает о релизе, в названии которого указано разрешение, для которого в профиле нет качества. Поэтому занятый Radarr обычно отвечает на один-три вопроса на фильм, а не на каждый результат поиска. Если Radarr видит маунт zurg по другому пути, укажи в `library_path` путь, по которому Radarr видит `__magic__`. На новой странице Acquisition на дашборде показаны все тайтлы, над которыми работает zurg, что он делает прямо сейчас и куда положен каждый релиз. Настройку со стороны Radarr описывает `docs/acquisition.md`.

## Получение выбирает релиз Usenet, который быстрее всего подтвердить {#acquisition-picks-the-usenet-release-that-is-quickest-to-confirm}

Когда zurg добавляет фильм, он сначала смотрит на посты, в которых только один видеофайл. Такие посты гораздо чаще остаются целыми на новостных серверах, и чтобы это подтвердить, нужно всего два чтения статей. Для каждого кандидата zurg читает NZB до того, как что-то сохранить. Он сохраняет первый найденный пост с одним видео и переходит к наборам многотомных архивов, только если подходящих постов нет. Берутся наборы от самого маленького, и одновременно обрабатывается не больше шести. Результаты, названные по одной части разбитого на части поста, пропускаются. В тестах на IMDb Top 100 такой выбор сократил количество NZB, которые zurg должен был загрузить, с 517 до 156. Поиск и загрузка NZB теперь делят общий лимит одновременных запросов на каждый индексер, и если индексер сообщает, что он занят, zurg ждёт. Запрос на фильм без quality profile всё равно сначала получает то разрешение, которое было запрошено. Получение сериалов не изменилось.

## Получение проверяет релиз, как только zurg узнает его размеры {#acquisition-checks-a-release-once-zurg-knows-its-sizes}

zurg раньше проверял новый релиз на новостных серверах сразу, как только он появлялся в библиотеке, и в то же время читал этот же релиз, чтобы узнать размеры его файлов. Оба процесса запрашивали одни и те же статьи по одним и тем же подключениям, поэтому на длинных списках всё шло очень медленно. В списке из 99 фильмов последний попадал в Radarr почти через девять минут. Теперь zurg проверяет релиз, когда его размеры уже известны, так же как это уже делается для Sonarr и Radarr через эндпоинт SABnzbd. Одновременно проверяется не больше шести релизов, а первая статья, которую уже скачала проверка размеров, повторно не запрашивается, если она ещё сохранена. Пачка сохранённых релизов теперь приводит к одному обновлению библиотеки, а не к обновлению на каждый релиз.
Проверка релиза теперь выполняется раньше проверок размеров других релизов, но никогда раньше воспроизведения. Если у аккаунта больше двенадцати подключений, он теперь узнаёт размеры до шестнадцати релизов одновременно, а не восьми.

## Скачанный релиз Usenet с несколькими пропавшими кусками сначала восстанавливается, а потом помечается как ошибка {#a-grabbed-usenet-release-with-a-few-missing-pieces-is-repaired-before-it-is-failed}

Перед тем как сообщить Radarr или Sonarr, что загрузка завершена, zurg проверяет, что все части релиза всё ещё есть на новостных серверах. Раньше, если эта проверка находила пропавшие части, zurg сразу помечал загрузку как неудачную, даже когда PAR2-файлы самого релиза могли восстановить то, что пропало. Radarr тогда выбрасывал релиз и искал другой, часто более худший. Теперь zurg сначала восстанавливает недостающие части и сообщает об ошибке загрузки, только если это не помогло. За неделю реальных загрузок большинство релизов, которые так провалились, имели PAR2-файлы, которые могли бы их спасти.

## Повреждённые релизы Usenet ждут своей очереди на восстановление, а не сразу помечаются как ошибка {#damaged-usenet-releases-wait-their-turn-for-a-repair-instead-of-being-failed}

zurg чинит одновременно не больше двух повреждённых релизов, а одна починка может занять от пары минут до часа с лишним. Третья повреждённая загрузка получала всего пять минут на старт, прежде чем zurg сообщал Radarr или Sonarr, что она провалилась. Поэтому, когда приходило несколько сразу, всё кроме двух выбрасывалось, так и не попытавшись починить, и в логе об этом ничего не было. Теперь zurg держит загрузку в ожидании, пока её починка стоит в очереди, до трёх часов, а в логе пишется, что починка ждёт своей очереди.

## Загрузка Usenet больше не ждёт вечно размеры файлов, которые никто не узнает {#a-usenet-download-no-longer-waits-for-ever-on-file-sizes-nothing-is-going-to-learn}

Zurg задерживает готовую загрузку в Radarr и Sonarr, пока не узнает точный размер каждого файла, потому что клиенты проверяют размер при импорте. После некоторых повторных загрузок zurg мог перестать пытаться определить размеры, но продолжал их ждать, поэтому загрузка висела в очереди, пока клиент не сдавался, часто через два часа. Теперь zurg заново определяет размер для таких релизов, а если дальнейшее определение невозможно и все части релиза лежат на новостных серверах, сообщает клиенту, что загрузка готова.

## Релизы Usenet, где постер переименовал только первый том архива, снова воспроизводятся {#usenet-releases-whose-poster-renamed-only-the-first-archive-volume-play-again}

Некоторые аплоадеры переименовывают первый том архива в название релиза, а остальные оставляют под исходными именами, поэтому релиз приходит как `Show.S02E03.part03.rar` плюс `show.203.r00` … `show.203.r19`. zurg группировал тома по имени, видел два неполных архива и не мог открыть ни один из них. Теперь он читает заголовок первого тома, определяет, к каким томам он относится, и переименовывает его соответственно, так что эпизод воспроизводится и импортируется. Если в папке действительно не хватает тома архива, zurg теперь выводит понятное сообщение, а не общую ошибку сервера.

## Обфусцированные релизы Usenet, у которых тома просто пронумерованы, теперь воспроизводятся {#obfuscated-usenet-releases-whose-volumes-are-just-numbered-now-play}

Некоторые релизы прячут все имена файлов за случайной строкой и номером, так что фильм приходит как `f342c135….01`, `….02` и так далее, а текстовые файлы и обложки идут вперемешку с ними с собственными номерами. zurg не распознавал их как части одного архива, показывал как отдельные файлы, и Radarr с Sonarr ничего не находили для импорта. Теперь zurg читает начало каждого пронумерованного файла, собирает части архива в правильном порядке (даже если первую часть залили последней) и не включает в архив текстовые файлы и изображения.

## NZB сезонных паков больше 32 МБ принимаются {#season-pack-nzbs-over-32-mb-are-accepted}

zurg отказывался принимать любые NZB больше 32 МБ, которые присылались через его endpoint SABnzbd, и отвечал "request body too large". NZB для больших сезонных пачек часто бывают больше этого: сезон на 526 ГБ пришёл как NZB на 49 МБ. Теперь zurg принимает NZB до 256 МБ. NZB на 49 МБ с почти полумиллионом частей загружается меньше чем за полминуты.

## Файлы из обёрнутых постов Usenet сохраняют свои настоящие имена {#files-from-wrapped-usenet-posts-keep-their-real-names}

Некоторые инструменты для публикации оборачивают каждое имя файла в тему письма, например `[PRiVATE]-[EnCrYpTnZb]-[Show - 48.mkv]-[3/4]`, и оставляют обычное имя файла в кавычках пустым. zurg сохранял обёртку как часть имени, поэтому эпизоды отображались как `[PRiVATE]-[EnCrYpTnZb]-[Show - 48.mkv`, и Sonarr и медиасерверы не могли их сопоставить. Теперь zurg вынимает имя из обёртки. Релизы, которые уже есть в библиотеке, перечитываются один раз, чтобы подхватить исправленные имена.

## Загрузки, уже отмеченные как неудачные, больше не занимают слоты ремонта у новых {#downloads-already-reported-failed-no-longer-take-repair-slots-from-new-ones}

Как только zurg сообщает Radarr или Sonarr, что загрузка не удалась, клиент её удаляет и ищет другую. Раньше zurg всё равно пытался восстанавливать такие загрузки при каждом перезапуске. Эти бессмысленные восстановления могли занимать оба слота для ремонта, и в это время новая загрузка, которую ещё можно было спасти, ждала своей очереди. Теперь zurg перестаёт восстанавливать загрузку, как только сообщил о её неудаче.

## Отчёты о повреждениях называют каждый файл {#damage-reports-name-every-file}

Когда в релизе Usenet не хватало частей, в сообщении zurg об ошибке файлы перечислялись по имени, и файл, который пост вообще не называл, выводился пустым: "across 4 file(s): , , , ". Теперь такой файл указывается по его месту в релизе, например "file 12 of 73", поэтому в сообщении видно, какие файлы затронуты.

## Stremio пропускает релиз, видео которого начинается с пустоты {#stremio-skips-a-release-whose-video-starts-with-nothing}

Когда начало видео из релиза Usenet пропадает с новостных серверов, zurg заполнял его тишиной и отдавал Stremio так, будто всё в порядке. Плеер ничего не показывал, и фильм выглядел сломанным. Теперь zurg перед началом воспроизведения проверяет первые байты. Если там нет ничего настоящего, он переходит к следующему релизу в списке, так же как уже делает для релиза, в котором нет ничего воспроизводимого. Фильм с пропуском где-то дальше всё равно проигрывается.

## Битые файлы остаются в библиотеке, пока zurg всё ещё будет их повторно пробовать {#broken-files-stay-in-the-library-while-zurg-will-still-retry-them}

Когда zurg не смог починить битый файл с первой попытки, он убирал файл из маунта, даже если через день собирался повторить попытку. Plex воспринимает пропавший файл как удалённый, поэтому одно сканирование библиотеки могло отправить эпизоды, сезоны и целые сериалы в корзину. Теперь битый файл остаётся в маунте, пока zurg планирует очередную попытку починки. Он уходит только тогда, когда zurg уверен, что содержимое пропало, например если сервис полностью отказывается от релиза или в нём не осталось ничего, что можно воспроизвести.

## Radarr и Sonarr выполняют поиск заново, когда релиз, который они взяли дважды, мёртв {#radarr-and-sonarr-search-again-when-a-release-they-grab-twice-is-dead}

Когда первый релиз, который Radarr захватил, оказался нерабочим, его следующий поиск часто находил тот же релиз у другого индексатора, под тем же именем. zurg записывал этот второй захват под ID задачи первого. Radarr и Sonarr помнят каждую загрузку, которая у них уже провалилась, по этому ID, поэтому они принимали новый захват за старый провал и больше его не проверяли: ни провала, ни blocklist, ни нового поиска. Фильм просто переставал двигаться. В прогоне IMDb Top 100 через Radarr 25 фильмов закончили именно так.

Захват релиза, который zurg уже ответил «пока что», теперь получает свой собственный ID задачи, так же как сам SABnzbd называет каждую загрузку. Если и он окажется нерабочим, Radarr получит второй провал, добавит его в blocklist и выполнит новый поиск.

## Мёртвые релизы Usenet помечаются как неудачные за минуты, а не за полчаса {#dead-usenet-releases-are-reported-failed-in-minutes-instead-of-up-to-half-an-hour}

zurg проверяет статьи загруженного релиза, прежде чем сообщить Radarr или Sonarr, что он готов, и перед этим ждёт, пока размеры файлов релиза не установятся. Мёртвый пост как раз тот релиз, у которого размеры так и не приходят, поэтому проверка статей простаивала за тридцатиминутным ожиданием, пока клиент ждал ответа. Теперь, если zurg не смог узнать размеры релиза, он сразу проверяет статьи. Если статей уже нет, релиз помечается как failed, и клиент переходит к другому.

Релиз, в котором при чтении нашли повреждение, тоже держали пять минут для восстановления PAR2, даже при `enable_repair: false`, когда восстановление вообще не запускается. Теперь это ожидание пропускается, если восстановление всё равно не может начаться.

В прогоне IMDb Top 100 через Radarr, где больше половины загруженных релизов были мёртвыми, эти два ожидания занимали большую часть времени, которое фильм проводил в zurg.

## Релиз, оказавшийся повреждённым при импорте, помечается как неудачный, и Radarr берёт другой {#a-release-that-turns-out-damaged-during-import-is-failed-so-radarr-grabs-another}

zurg проверяет одну статью на каждый файл, прежде чем сообщить Radarr, что релиз готов, поэтому релиз с пропуском в середине файла может пройти проверку. Когда импорт Radarr дошёл до пропуска, zurg отказался переносить файл, и это правильно, но при этом загрузка выглядела незавершённой, а не проваленной. Radarr перевёл фильм в статус "import blocked" и больше не искал другую копию. В ходе прогона IMDb Top 100 через Radarr пять фильмов застряли таким образом.

Теперь при отказе в импорте загрузка помечается как failed. Radarr добавляет этот релиз в blocklist и ищет другой.

## Полностью обфусцированный релиз больше не выходит с видеофайлом без имени {#a-fully-obfuscated-release-no-longer-comes-out-with-a-nameless-video-file}

Когда в Usenet-посте скрыты все имена файлов, zurg определяет основной файл по его первым байтам и называет его по имени релиза, как это делает SABnzbd. Эта проверка выполнялась последней в проходе с ограничением в девяносто секунд, и когда заявки приходили пачкой, лимит мог закончиться раньше. Тогда видеофайл публиковался под именем релиза без расширения вообще, а Radarr и Sonarr такие файлы пропускают, поэтому загрузка висела в их очереди и ждала файл, который они могли бы импортировать.

Теперь релиз переименовывается заново до трёх раз, пока zurg не получит возможность просмотреть файл, и только после этого он показывается вашей библиотеке и вашим *arr. В одном прогоне IMDb Top 100 через Radarr это был Seven Samurai, файл .mkv размером 42 GB.

## Релизы с акцентами или CJK в именах файлов сохраняют свои полные названия {#releases-with-accents-or-cjk-in-their-filenames-keep-their-whole-names}

Релиз, чьи файлы называются чем-то, кроме обычных английских букв, выходил из zurg с отрезанным началом каждого имени. `Détective Conan S11E01 - 286 [MULTI] [AVC].mkv` отдавался как `tective Conan S11E01 - 286 [MULTI] [AVC].mkv`, а китайское или японское название теряло ещё больше, потому что обрезалось всё до последнего такого символа включительно.

Sonarr и Radarr не могли ничего с этим сделать. Имя вроде `tective Conan S11E01` не совпадает ни с одним сериалом, поэтому они переходили к истории граббов загрузки, отказывались импортировать только на этом основании и ставили элемент на паузу с сообщением "release was matched to series by ID. Automatic import is not possible." Релиз висел в очереди, и ничего его не двигало.

Из-за этого можно было потерять файлы. Если единственное, что отличает два файла друг от друга, стоит после последнего символа с диакритикой, у обоих получается одинаковое имя, а имя и есть путь. У одного французского релиза с десятью томами восстановления все десять сократились до одного имени, и в итоге опубликовалось четыре файла вместо тринадцати, которые лежат в посте. Данные для восстановления оказались недоступны.

Теперь zurg считает частью имени файла любой символ выше простого ASCII, и это правильно, ведь так оно и есть. Счётчики частей, маркер `yEnc`, скобки и расширения файлов, которые ставят постеры, все написаны простым ASCII, так что всё остальное относится к названию. Релизы с именами в простом ASCII не затронуты и выходят точно так же, как раньше.

Релизы, которые уже есть в вашей библиотеке, сохраняют имена, под которыми были записаны, потому что zurg не пересматривает список файлов, который уже зафиксировал. Чтобы получить исправленные имена, добавьте затронутый релиз заново.

## Название, написанное на японском, корейском, китайском, тайском или арабском, остаётся без изменений {#a-name-written-in-japanese-korean-chinese-thai-or-arabic-is-left-alone}

zurg переименовывает файл внутри архива, если его имя ничего не говорит о содержимом. Так релиз, выложенный под хешем, появляется под собственным названием. Чтобы это определить, раньше сравнивали заглавные и строчные буквы, но многие письменности вообще не делят буквы на регистры. Файл `오징어 게임 S01E01` получал ноль и тех, и других, не проходил проверку на обычное имя и переименовывался так, будто это хеш, вместе с S01E01. Страдали все: хань, кана, хангыль, тайский, иврит и арабский.

Теперь буква без регистра сразу решает вопрос, а не проваливает проверку. Имена на этих письменностях сохраняются как есть, а хеши переименовываются точно так же, как и раньше.

Теперь zurg также пишет в лог, если в одном релизе два файла получили одинаковое имя. Имя это путь, поэтому в таком случае релиз тихо показывает меньше файлов, чем есть на самом деле, а лишние нельзя открыть вообще. Раньше об этом ничего не сообщалось, поэтому баг с именами файлов с диакритикой из предыдущей записи остался незамеченным: единственным признаком был список папки, в котором строк было меньше, чем ожидалось.

## Исправления имён файлов теперь применяются и к релизам, которые у вас уже есть {#the-filename-fixes-now-reach-releases-you-already-have}

Две записи выше изменили то, как zurg читает имя файла из Usenet-поста, но zurg хранит результат чтения каждого NZB и переиспользует его при каждом запуске, вместо того чтобы заново проходить весь ваш каталог наблюдения. Сохранённые результаты были по-прежнему старыми, поэтому после обновления релиз, который у вас уже был, продолжал показывать то же неправильное имя, что и раньше. Исправленное имя получил только недавно добавленный NZB.

Теперь zurg замечает, что читает посты иначе, чем были записаны сохранённые результаты, и читает их заново. При первом запуске после обновления zurg один раз перечитает каждый NZB в вашем каталоге наблюдения. Это займёт немного больше времени, чем обычно, а потом всё вернётся в норму. Ничего не скачивается заново и статьи не загружаются; перечитываются только файлы, которые уже лежат на вашем диске.

Если релиз был затронут, его файлы вернутся под именами, которые дал им пост. Но ваш download client может всё ещё хранить неудачный импорт от прошлого раза, поэтому релиз, который застрял в Sonarr или Radarr из-за невозможности импорта, нужно сначала удалить из очереди, и только тогда он снова попробует импортироваться.

## Названия с знаками препинания тоже сохраняют свои полные имена {#titles-with-punctuation-in-them-keep-their-whole-names-too}

Исправление имени файла выше по списку перестало обрезать имена на символах с акцентами и китайских иероглифах, но этого оказалось мало. zurg определял, что такое имя файла, перебирая символы, которые в нём разрешено использовать, и в этом списке не хватало двадцати обычных знаков. Поэтому название с таким знаком обрезалось в том же месте, что и раньше:

    Tom & Jerry - The Movie.1992.1080p.mkv   ->   Jerry - The Movie.1992.1080p.mkv
    Mairimashita! Iruma-kun (2026) [22].mp4  ->   Iruma-kun (2026) [22].mp4

Так же обрезалось из-за `!`, `&`, `#`, `$`, `%`, `@`, `~`, `;`, `=` и `^`.

Перебирать разрешённые символы — дело безнадёжное, поэтому zurg больше так не делает. Имя — это имя файла, и единственные символы, которых точно не может быть в имени, — те, что не принимает ни одна файловая система: `/ \ : * ? " < > |`. Всё остальное теперь относится к названию.

Проверил на всех NZB в большой папке для наблюдения: из subject-ов, которые являются обычным именем файла, почти у всех, что раньше обрезались, теперь сохраняется полное имя. Короткими остаются только те, у которых убирается штамп индексатора для каждой загрузки, и это правильно.

## Релиз, у которого переименовали файлы, сам подхватывает новые имена {#a-release-whose-files-were-renamed-picks-the-new-names-up-on-its-own}

Изменения в именах файлов, сделанные выше, поменяли то, как zurg называет файлы внутри релиза Usenet, но релиз, уже находящийся в вашей библиотеке, не всегда это замечал. zurg сопоставляет уже известный ему релиз со свежим списком по ссылке, которую он сохранил для каждого файла, а ссылка Usenet содержит позицию файла внутри релиза. Когда исправленное имя сортируется иначе, чем старое, эта позиция сдвигается, сохранённая ссылка больше не указывает на тот же файл, и сопоставлять стало не по чему, поэтому старое имя оставалось.

Теперь zurg использует для сопоставления размер файла, который не меняется. Если в релизе ровно один файл такого размера, то это и есть нужный файл, и имя обновляется. Если два файла одинакового размера, zurg ничего не переименовывает, а не угадывает, чтобы не записать один эпизод под именем другого.

Релизы, у которых позиция не сдвинулась, и так получали новые имена и не затронуты. Не затронут и любой бэкенд, кроме Usenet, потому что его ссылки не меняются при переименовании файла.

## Файл, который монтирование не может прочитать, перестаёт задерживать всё остальное {#a-file-the-mount-cannot-read-stops-holding-everything-else-up}

Когда чтение не удалось по причине, которую zurg не смог определить, он говорил клиенту попробовать снова и продолжал повторять это, пока файл продолжал падать. rclone воспринимает это всерьёз: одно чтение такого файла занимало 55 секунд и три десятка запросов, прежде чем сдавалось. Поскольку rclone замедляет всё соединение с сервером, который продолжает возвращать ошибки, следующий здоровый файл открывался за 3.66 секунды вместо 0.04.

Теперь повторные попытки прекращаются через минуту одной и той же ошибки. На чтение отвечают так же, как раньше отвечали на чтение сломанного файла. Файл остаётся в списке вашей библиотеки, а то же самое чтение занимает полсекунды.

zurg по-прежнему пытается скачать файл при каждом чтении, так что если файл снова заработает, следующее чтение его подхватит.

## Монтирование прекращает загрузку, как только вы перестаёте читать {#the-mount-stops-downloading-once-you-stop-reading}

Сканирование библиотеки, проверка субтитров или любая другая операция, которая ненадолго затрагивает много файлов, тянула с вашего debrid-аккаунта гораздо больше данных, чем читала.

rclone 1.74 начал продолжать загрузку файла ещё пять секунд после того, как последняя программа его закрыла. Ничего не ждало этих байтов, а на быстром аккаунте пять секунд — это несколько сотен мегабайт на файл. Чтение 1 MiB из каждого из двадцати файлов тянуло 4.2 GiB вместо прежних 80 MiB.

zurg теперь это отключает. Монтирование на rclone 1.73 и более старых версиях не затронуто и не меняется, потому что этой опции там нет.

Если вы запускаете свой rclone, а не монтирование zurg, добавьте `--vfs-handle-caching 0` в команду монтирования на rclone 1.74 или новее. Подробности есть в README.

## Релиз, потерявший один архивный том, больше не теряет остальные {#a-release-that-loses-one-archive-volume-no-longer-loses-the-rest}

Релизы из Usenet, которые выложены как многотомный набор rar или 7z, могли вообще перестать импортироваться. Sonarr и Radarr висели на "Waiting for import" и не двигались с этого места, а папка релиза либо содержала только части rar, либо пропадала совсем.

Когда zurg не мог прочитать один том набора, он откладывал этот том в сторону и позволял следующему обновлению списка идти без него. Это обновление видело набор без одного тома, останавливалось на томе, который шёл за ним, и тоже откладывало его. Релиз терял тома по одному за обновление, примерно каждые десять минут, и когда томов не осталось, он выпадал из библиотеки и из папки, откуда клиент загрузок импортирует файлы. Путь, которого нет, для Sonarr — это не пустая папка, а импорт, который падает навсегда.

Том, про который известно, что он нечитаемый, теперь остаётся в своём наборе. Каждое обновление списка останавливается на одном и том же томе и сообщает о нём одно и то же, поэтому релиз, у которого не хватает части поста, отмечается как такой один раз, и ваш клиент может добавить его в блоклист и поискать другую копию. Релизы, у которых все тома читаемы, не затрагиваются.

## Сканирование следует за библиотекой в её новое расположение под `__magic__` {#scans-follow-the-library-into-its-new-home-under-__magic__}

Зеркало вашей библиотеки переехало из `__magic__` в `__magic__/__all__` в 2026.09.17.2240-nightly. Часть zurg продолжала использовать старый путь.

Когда выходил новый релиз, сканирование, которое zurg запрашивал у Plex или Jellyfin, указывало на папку, которой с того релиза уже не существовало. Поэтому ничего не ставилось в очередь, и новый контент ждал планового сканирования самого медиасервера. То же самое получал и любой, кто использовал скрипт `on_library_update`.

Теперь всё указывает на папку, из которой клиент загрузки получил команду импортировать. Так же настроен и список, который zurg сбрасывает из кэша монтирования, когда релиз появляется или удаляется.

## Список просмотра теперь может принимать торренты из индексаторов Torznab {#the-watchlist-can-take-torrents-now-from-torznab-indexers}

До сих пор список просмотра или запрос в Seerr можно было выполнить только через Usenet. Добавьте `type: torznab` к индексатору, и zurg будет искать и там. Торрент-результат передаётся аккаунту debrid, а не записывается в `nzbs/`.

**Он передаётся только тому аккаунту, который уже закэшировал этот релиз.** Хэш предлагается каждому аккаунту, который принимает добавления, потому что кэши независимы. Первый аккаунт, у которого релиз уже есть, его и забирает. Если ни у одного аккаунта его нет, это просто кандидат, который не подошёл, и zurg переходит к следующему релизу, которым может быть другой торрент или NZB. Ничего не скачивается на ваш аккаунт, лимит на добавление некэшированных файлов не расходуется, и ничего не остаётся запущенным для того, что никто не ждёт.

Если отвечают оба типа индексаторов, `prefer` определяет, к какому обращаться в первую очередь. По умолчанию это `usenet`, так что установка только с индексаторами Newznab работает точно так же, как раньше. `torrents` меняет порядок на обратный, а `best` берёт тот вариант, который ранжирование ставит первым, будь то торрент или нет.

Торрент-загрузка ждёт проверки, как и любая другая, но проверяется она по-другому. Аккаунт уже подтвердил, что у него есть этот контент, поэтому проверяется, что релиз попал в вашу библиотеку с файлами внутри. Если релиз оказывается пустым, его откладывают в сторону, чтобы очередь дошла до следующего релиза.

Вы также можете запускать получение контента только с индексаторами Torznab, без провайдера `nzb`.

## Агент, читающий библиотеку, больше не считает каждый релиз пустым {#an-agent-reading-the-library-no-longer-calls-every-release-empty}

Списки MCP в zurg измеряют размер релиза только тогда, когда их об этом попросили, потому что обход таблицы файлов всей библиотеки отнимает реальное время.
Для релизов, которые не измеряли, они показывали размер и количество файлов как ноль, и ничто в ответе не говорило читателю, что ноль означает «не измерено», а не «здесь ничего нет».
Агент, которого просили показать содержимое папки, мог сказать, что в фильме на 6.6 GB нет файлов, хотя инструмент для одного релиза всё это время возвращал правильный ответ.

Теперь список, который не измерял размер, не выводит оба числа вообще, вместо того чтобы показывать ноль.
Чтобы их получить, укажи `with_size`, сортируй по размеру или используй фильтр по размеру.
`zurg_library_search` тоже принимает `with_size`, чего раньше не умел, так что получить размеры больше не нужно ценой урезанного или переупорядоченного результата.

## zurg doctor сообщает, отвечает ли конечная точка MCP {#zurg-doctor-says-whether-the-mcp-endpoint-is-answering}

`zurg doctor` проверял только то, что порт дашборда отвечает, и на этом останавливался, а про `/mcp` ничего не говорил. Эндпоинт, который в конфиге включён, но который сервер потом не отдаёт (так бывает, когда `username` пустой), снаружи выглядел здоровым, а объяснение было только в одной строке стартового лога и больше нигде.

Когда задан `mcp.enabled`, `doctor` теперь обращается к `/mcp` по протоколу и сообщает, что пришло в ответ: отвечает, отклоняет настроенные учётные данные или включён, но не обслуживается. Экземпляр с выключенным эндпоинтом про него не спрашивают и строки не выводят.

## Открытие конечной точки MCP в браузере теперь сообщает, что это такое {#opening-the-mcp-endpoint-in-a-browser-now-tells-you-what-it-is}

Открываешь `/mcp` в браузере и получаешь «Bad Request: GET requires an Mcp-Session-Id header». Это формально правильный ответ на вопрос, которого никто не задавал.

Теперь эндпоинт сам описывает себя, когда его открывает браузер. Он показывает, какой протокол использует, адрес, на который нужно направить клиент, сниппет для stdio-моста, номер сборки и все инструменты, которые сейчас предлагает, сгруппированные по наборам инструментов. Инструменты, которые только описывают действие и ждут подтверждения, помечены отдельно.

Список формируется при регистрации, а не ведётся вручную отдельной копией. Поэтому инструмент, скрытый через `read_only`, наборы инструментов или переключатель жизненного цикла, не будет показан как доступный для вызова. Страница также сообщает, если эндпоинт работает без аутентификации.

Ни один клиент это не затрагивает. Страница отдаётся только на GET, который запрашивает HTML и не несёт сессии. Так что это браузер, а не MCP-клиент. GET самого клиента по-прежнему открывает поток событies, как и раньше.

## Воспроизведение Usenet расходует лимит соединений быстрее {#usenet-playback-fills-the-connection-allowance-sooner}

Чтение из Usenet теперь сначала ставит статью в позиции воспроизведения в планировщик аккаунта и только потом предлагает остальную часть запрошенного диапазона. Когда большой диапазон делится между конвейерными соединениями, последовательные статьи раскладываются по этим соединениям по очереди, а не так, что первому соединению достаются первые четыре, второму следующие четыре и так далее. Поэтому первые нужные статьи приходят в первом раунде соединений, а не ждут, пока пройдут более поздние байты.

Для архивных постов с мелкими статьями окно упреждающего чтения (read-ahead) составляет не меньше 64 MiB. Современные посты с многомегабайтными статьями сохраняют существующее окно. Большее количество статей не увеличивает расход памяти: спекулятивные тела статей ограничены двумя читателями и половиной `cache_size_mb` (256 MiB по умолчанию), а кэш статей сохраняет свой существующий жёсткий лимит.

Запросы размером с буфер воспроизведения теперь начинаются с 64 MiB вместо 128 MiB, поэтому буфер плеера в 90 MiB больше не попадает на путь seek/probe. Мелкие перемотки по-прежнему попадают на него.

Зависший конвейерный пакет может хеджировать до пяти разных статей одновременно. Существующий лимит аккаунта, двадцать вторичных запросов в минуту, не меняется. Упреждающее чтение, восстановление и любая другая работа, которую никто из клиентов не ждёт, по-прежнему никогда не хеджируются.

Открывание многотомных архивов тоже стало дешевле. Если PAR2 уже сообщил точную длину каждого тома, проверенный yEnc-заголовок одного тома может задать общий шаг статей для большого набора однотипных томов. Каждый из остальных томов проверяет этот вывод по своему собственному заголовку, прежде чем отдать первый байт. Поэтому разрешение больше не тратит по одной статье на каждый том последовательно, и при этом выведенной геометрии для данных не доверяется. Восстановление имени файла тоже берёт ответ из yEnc-заголовка, а не ждёт, пока загрузится остальная часть статьи.

## Сохранённые файлы .strm следуют за изменением Base URL {#saved-strm-files-follow-a-base-url-change}

После смены Base URL все `.strm`-файлы, которые уже лежали в `strm/`, продолжали указывать на старый адрес. Перезапуск не помогал, потому что zurg раньше записывал только те файлы, которых не было.

Теперь, если URL в `.strm` отличается от того, что zurg записал бы, файл переписывается на месте. Это происходит при каждом запуске, а также сразу, когда Base URL меняют на дашборде или там включают `save_strm_files`. Файлы, которые уже правильные, не трогаются, чтобы медиасервер не перечитывал всю папку при каждом сканировании.

Jellyfin запоминает URL, который прочитал из `.strm`, и подхватит новый при следующем сканировании библиотеки. `.strm`, в котором всё ещё лежит ссылка на аккаунт из старой сборки, тоже переписывается, в форму, которая переключается между аккаунтами и переживает ремонт. Файл `.strm`, отредактированный вручную внутри `strm/`, перезаписывается, так что лучше укажи нужный адрес в Base URL.

## Включение списка просмотра Plex больше не очищает его {#turning-the-plex-watchlist-on-no-longer-empties-it}

Включение списка просмотра раньше читало весь список как очередь и обрабатывало его, удаляя каждый тайтл после обработки. Первый запуск убрал 121 тайтл из списка на 163 позиции примерно за четыре минуты. Plex не сохраняет записи, которые удалены из списка просмотра, поэтому вернуть их можно было только из снимка, сделанного заранее. В конфиге и логах не было ничего, что предупреждало бы о таком поведении.

Теперь два параметра определяют, что приобретение делает со списком. Список принадлежит тебе, а не zurg.

**`watchlist.only_new_items`** по умолчанию включён. Когда ты включаешь список просмотра, zurg начинает за ним следить. Всё, что уже есть в списке, считается обработанным, а то, что ты добавишь потом, будет получено. Параметр применяется один раз, при первом запуске, и никогда не меняет очередь, которая уже существует. Поэтому установка, которая уже обрабатывала список просмотра, продолжит работать как раньше.

**`watchlist.remove_after_grab`** по умолчанию включён. Так эта функция работала всегда, поэтому ничего не меняется, пока ты сам не захочешь. Выключи его, если хочешь, чтобы список просмотра оставался списком просмотра. Ты будешь просматривать его, чтобы решить, что смотреть, а zurg будет выполнять свою работу в фоне и никогда не будет его редактировать. Тайтл, который остался в списке, не требует затрат на повторную проверку: квитанция уже его покрывает, и индексаторы о нём больше не спрашивают.

Оба параметра находятся на странице конфигурации и вступают в силу при следующем перезапуске. Источник получения, который ты явно указываешь в `acquisition.sources`, может задавать любой из них для себя отдельно. Для источника Seerr они не имеют смысла, потому что он не ведёт никакого списка, в который пишет zurg.

## Список просмотра и запросы Seerr ждут новостных серверов, прежде чем очиститься {#watchlist-and-seerr-requests-wait-for-the-news-servers-before-they-are-cleared}

Раньше граб считался законченным, как только его NZB попадал в watch-папку. Индексер отвечал, ответ распознавался как NZB, и файл записывался. Это три факта про индексер и ни одного про сам пост. После этого запрос закрывался на их основании, а для watchlist Plex это значит, что запись удаляется, и Plex не хранит следа об удалённой записи. Мёртвый пост, таким образом, забирал единственное свидетельство того, что тайтл вам нужен, ещё до того, как что-либо прочитало хоть один байт. Один прогон по watchlist из 163 позиций удалил 121 тайтл, а 12 релизов, стоявших за ними, не удалось прочитать.

Теперь каждый полученный релиз сначала проверяется на news-серверах, и только потом что-то подтверждается. Это та же проверка, которую эндпоинт SABnzbd делает начиная с ночной сборки 08.28. Есть три ответа, и они разделяются.

- **Статьи пропали.** Граб не засчитывается. Тайтл остаётся в вашем watchlist, запрос остаётся открытым, а релиз запоминается как мёртвый, чтобы следующая попытка брала следующего кандидата, а не останавливалась на том, что уже лежит в вашей библиотеке. Заведомо мёртвый релиз ничего не стоит: его не скачивают и он не занимает место среди трёх кандидатов, которые пробует попытка. Поэтому череда мёртвых постов в начале ранжирования просто пролистывается, а не перепроверяется бесконечно. Сезонный пак, оказавшийся мёртвым, возвращает весь сезон в статус «нужен», чтобы взялись за отдельные серии.
- **Серверы не удалось спросить.** Пул недоступен, аккаунт упёрся в ограничение скорости или библиотека просто ещё не видит новый NZB. Ничего не установлено, поэтому ничего не решается. Запрос ждёт и проверяется снова, а ожидание не тратит попытки. Релиз, который так и не удалось проверить примерно за два часа, откладывается так же, как мёртвый, и очередь переходит к следующему релизу. Тайтл никогда не закрывается по релизу, который никто не смог проверить.
- **Релиз на месте.** Всё как и раньше.

Установка без аккаунта Usenet проверять нечего, и её это не затрагивает.

## Проверка большого релиза больше не выходит за время на медленном новостном сервере {#checking-a-big-release-no-longer-runs-out-of-time-on-a-slow-news-server}

Перед тем как загрузка будет отмечена как завершённая, zurg спрашивает новостные серверы о каждом файле в ней. Раньше он спрашивал по одному файлу за раз. Некоторые аккаунты отвечают на такие запросы медленно и строго по очереди, поэтому отправка всех сразу через одно соединение ничуть не быстрее. Сервер одного провайдера тратил больше пяти секунд на файл, и из-за этого 4K-релиз из 133 томов требовал около двенадцати минут запросов, а на каждую проверку отводилось пять. Проверка никогда не могла завершиться, поэтому Sonarr и Radarr ждали три часа, а потом видели, что загрузка провалилась, а watchlist ждал навсегда.

Теперь файлы проверяются сразу по несколько штук, используя все соединения аккаунта, кроме одного, которое остаётся свободным для воспроизведения. Поэтому чем больше соединений разрешает ваш аккаунт, тем быстрее проверяется большой релиз. Для сравнения: тот же 133-томный релиз, который раньше вообще не мог быть проверен, теперь проверяется меньше чем за две минуты на двенадцати соединениях. На четырёх соединениях времени всё равно не хватает, потому что сами запросы и занимают время. Маленький релиз работает не медленнее, чем раньше.

Релиз, который проверка не может пройти вовремя, больше не блокирует заголовок. Watchlist откладывает его в сторону так же, как отбрасывает нерабочий, и пробует следующий релиз. Эндпоинт SABnzbd, как и раньше, сообщает, что релиз провалился, поэтому Sonarr и Radarr идут искать другой.

## Загрузки только из кэша на TorBox больше не скачивают релизы, которые должны были пропускать {#cached-only-grabs-on-torbox-no-longer-download-the-releases-they-were-meant-to-skip}

У TorBox есть флаг, из-за которого добавление отклоняет всё, чего у них ещё нет. Он есть в их API, но ни в одной из их документаций его нет, и zurg его не использовал: запрос только из кэша добавлял торрент, ждал, завершится ли он, и удалял его, когда оказывалось, что это настоящая загрузка. Из-за этого тратилось одно из шестидесяти часовых добавлений аккаунта, занимался слот передачи, и подтягивались байты для релиза, который *arr уже велел пропустить.

Запросы только из кэша теперь запрашивают контент и отклоняются меньше чем за секунду, если TorBox его не имеет, и на аккаунте ничего не остаётся. Промах всё равно стоит одного из этих шестидесяти часовых добавлений, поэтому zurg притормаживает их, как и раньше. А попадание всё равно проверяется, а не принимается на веру: кэш TorBox может сказать «да» контенту, который потом не отдаст, поэтому релиз должен полностью скачаться, прежде чем zurg сообщит о нём.

## Загрузки только из кэша на Debrid-Link больше не расходуют дневной лимит добавлений {#cached-only-grabs-on-debrid-link-no-longer-spend-the-daily-add-allowance}

Debrid-Link принимает и голый info hash, и magnet, но добавляет хэш только тогда, когда контент у него уже есть. zurg отправлял magnet, а это команда скачать: каждый промах по кэшу принимался, списывался с 50 незакэшированных добавлений в сутки и одного из 20 слотов для загрузок, а потом удалялся, чтобы вернуть лимит. Пятьдесят промахов, и аккаунт не мог ничего добавить до ежедневного сброса.

Теперь запросы только в кэше отправляют хэш. Промах отклоняется сразу, примерно за одну десятую секунды, и аккаунт не трогается. Так *arr может пройти длинный список релизов и ничего не потратить на те, которых ни у кого нет. Это касается и раздач, пришедших как файл .torrent: файл нужен, чтобы избавить сервис от поиска метаданных, который голый хэш заставляет делать, а вопрос про кэш в этом не нуждается.

## Блокировки Debrid-Link из-за лимита запросов теперь откладываются заново {#debrid-link-rate-limit-lockouts-are-backed-off-from-again}

Debrid-Link отвечает на блокировку, которая длится час и действует на каждый эндпоинт отдельно, кодом HTTP 503 с причиной в теле ответа. zurg считал любой 503 признаком того, что сервис ненадолго недоступен, поэтому он так и не смотрел на причину и продолжал повторять запросы к эндпоинту, который уже сказал подождать час. Теперь zurg распознаёт такую блокировку и не обращается к этому эндпоинту, пока она не снимется.

## `__magic__` теперь зеркалирует вашу библиотеку в `__magic__/__all__`, оставляя его корень за вами {#__magic__-now-mirrors-your-library-at-__magic____all__-leaving-its-root-to-you}

Раньше пространство имён повторяло `__all__` в своём корне. Из-за этого папка, из которой клиент загрузок импортировал файлы, совпадала с папкой, где уже лежал каждый релиз. Корневую папку Sonarr или Radarr приходилось вкладывать *внутрь* папки загрузок, чтобы обойти две проверки состояния, которые при такой схеме срабатывали. А ручной импорт, направленный на папку загрузок, обходил всю библиотеку в поисках одного релиза.

Зеркало теперь находится на уровень ниже. `__magic__/__all__` — это библиотека в том виде, как её перечисляет `__all__`, и именно её теперь вычисляют `sabnzbd.complete_dir` и `qbittorrent.save_path`. Корень `__magic__` остаётся за тобой: в нём лежат папки `tv`, `movies` и `anime`, на которые ты указываешь \*arr. Эти два пути — соседние, поэтому ни один не содержит другой, и клиенты не выводят предупреждений.

**Пути меняются.** Если ты задавал `sabnzbd.complete_dir` или `qbittorrent.save_path` вручную, например при маппинге контейнера, добавь к ним `/__all__`. Если ты направил библиотеку Plex или Jellyfin на сам `__magic__`, а не на папку внутри него, её пути сдвинутся на уровень. Укажи её на `__magic__/__all__` или на папку, в которую ты импортируешь. Твои корневые папки не двигаются, и ничего из таблицы не переезжает: размещения — это пути внутри папок, которые ты создал, а маркеры удаления привязаны к релизу, так что существующая раскладка не трогается. Загрузка, которая уже отправлена в клиент на момент обновления, сохраняет старый путь, её нужно отправить заново.

Ничего нельзя записать в `__magic__/__all__`: строка там стала бы вторым адресом для релиза, у которого уже есть адрес, поэтому MOVE, MKCOL или DELETE, направленные туда, отклоняются. Запись *внутрь* папки релиза не изменилась. Именно там \*arr кладёт .nfo рядом с импортированным файлом.

## Export Logs теперь сообщает, куда пошли ваши ссылки и сколько они живут {#export-logs-now-tells-you-where-your-links-went-and-how-long-they-last}

Export Logs пробует несколько сервисов для вставок и отдаёт вам ссылку с первого, который принимает файл. Какой именно сервис сработал, не сообщалось, а они не взаимозаменяемы. Предпочтительный сервис хранит вставку 180 дней и продлевает срок каждый раз, когда её кто-то открывает. Запасной удаляет её через три дня. Ссылки выглядят одинаково, а отчёт, отправленный в пятницу, к понедельнику превращался в две мёртвые ссылки, и ничто не объясняло почему. Теперь ссылки сопровождаются указанием сервиса, который их хранит, и сроком, который с ним связан.

Почему вы попадали на запасной сервис, объясняется во второй части. Предпочтительный сервис блокирует адрес, который загружает файлы несколько раз подряд, а экспорт за один клик публикует два файла. Из-за серии отчётов об ошибках адрес попадал под блокировку, и после этого все запросы с этой машины отклонялись, включая чтение уже сохранённой вставки. zurg всё равно направлял обе половины каждого последующего экспорта туда и записывал каждую из них в лог как неудачную загрузку, хотя проблема была не в файле, а в адресе. Теперь, если хост отказывает машине, его не трогают в течение суток, и в логе об этом написано.

## Выгрузка отладочной информации больше не публикует ключи ваших индексаторов и клиентов загрузки {#uploading-debug-info-no-longer-publishes-your-indexer-and-download-client-keys}

Export Logs скрывает каждый найденный учётный данные перед отправкой конфига на хост для вставки, но проверял он только верхний уровень. Ключи во вложенных блоках уходили открытым текстом: ключи API ваших Newznab-индексаторов — и из списка Stremio, и из списка watchlist, — токен аддона Stremio, ключи API SABnzbd и qBittorrent, токен аккаунта zrok и токен сканирования Plex. Самое неприятное — ключи индексаторов: это доступ к вашему аккаунту Usenet, а не к zurg.

Теперь они скрываются. Токены провайдеров и пароли news-серверов не затрагивались никогда.

## zurg можно управлять с помощью ИИ-агента {#zurg-can-be-driven-by-an-ai-agent}

Появился новый эндпоинт `/mcp`, который работает по протоколу Model Context Protocol. Благодаря этому клиент вроде Claude может искать по библиотеке, выяснять, почему релиз не воспроизводится, и чинить его через типизированные инструменты, а не читая HTML дашборда.

По умолчанию он выключен. Включите его командой `mcp: {enabled: true}` и укажите клиенту адрес `http://your-zurg:9999/mcp`, используя те же логин и пароль, что и для дашборда. Клиенты, которые работают только через stdio, используют `zurg mcp`. Эта команда подключается к уже запущенному экземпляру, а не запускает второй.

Помимо инструментов, он даёт клиенту напрямую читать документацию zurg и её текущее состояние как ресурсы, а также шесть промптов для процедур, которым стоит следовать строго по шагам: диагностика релиза, который не воспроизводится, безопасная подготовка сканирования Plex, разбор того, от чего repair отказался.

Он никогда не делает тихо то, что может что-то отнять. Любое такое действие сначала описывает, что именно оно сделает, и выполняется только после вашего подтверждения этого точного плана. `read_only: true` скрывает все инструменты, которые что-либо меняют. Инструменты, способные остановить zurg или его монтирование, находятся за отдельным переключателем. Ни один результат не содержит токена, пароля или разрешённой ссылки.

См. [MCP-сервер](mcp.md).

## zurg сообщает, когда ваша сборка устарела {#zurg-says-when-your-build-is-out-of-date}

Раньше zurg никак не показывал, насколько старая сборка, поэтому исправление дефекта из августа могло появиться в отчёте об ошибке в сентябре, когда исправление уже три недели как вышло, а никто в обсуждении не имел причин это заподозрить. Теперь раз в день zurg запрашивает у публичного репозитория самый свежий релиз и, если твоя сборка старее, выводит одну строку с названием релиза, его датой и твоей версией. В остальное время он молчит: если у тебя актуальная версия, ничего не выводится; если GitHub недоступен, ничего не выводится; а сборка, которая не знает, когда её собрали (это образ Docker), не угадывается. Спонсоры на nightly-сборках всегда опережают последний публичный релиз и вообще его не видят. Ответ кэшируется на сутки, поэтому перезапуск не стоит ни одного запроса, а если запрос был отклонён, следующая попытка будет только завтра. Всё это отключается параметром `disable_update_check: true`.

## Мёртвая ссылка внутри архивного релиза перестаёт объявляться здоровой при каждом проходе {#a-dead-link-inside-an-archived-release-stops-being-declared-healthy-every-sweep}

Когда релиз отдаётся одним архивом и repair не может сузить повторное добавление дальше, zurg проверяет, читается ли сам архив. Если читается, он снимает отметки о поломке с релиза, а не списывает его. Но сняты были все отметки, в том числе те, что стояли на файлах, которые аккаунт отдаёт по собственным ссылкам. Проверенная ссылка на архив доказывает, что архив читается, и ничего не говорит про эти файлы. Поэтому файл, ссылку на который аккаунт перестал отдавать, возвращали в healthy только из-за чужого чтения. Следующий sweep делал для него unrestrict, находил его мёртвым, релиз снова списывали, а проход, который его списал, заканчивался тем, что восстанавливал его снова. На релизе из 64 файлов, у которых 9 ссылок аккаунт перестал отдавать, это повторилось 111 раз за неделю, дважды за 40 секунд, по два добавления магнетов за проход.

Теперь отсрочка касается только файлов, которые архив реально отдаёт, то есть тех, у которых нет собственной ссылки. Файл, который адресует аккаунт, сохраняет вердикт, заработанный его собственной ссылкой, и уходит в repair. Это единственный путь, который может выдать ему рабочую ссылку.

## Загрузки, которые пришли лишь частично, больше не висят в очереди вечно {#downloads-that-only-partly-arrive-no-longer-sit-in-the-queue-for-ever}

Когда часть файлов релиза не могла быть прочитана, zurg держал его загрузку в очереди и ждал точные размеры файлов, которые так и не придут. Проверка, которая нашла бы проблему, запускалась только после того, как эти размеры приходили. Sonarr и Radarr показывали такую загрузку с 0% и без оставшегося времени, пока zurg продолжал работать. Релиз при этом никогда не попадал в чёрный список и поиск другого релиза не запускался.

Теперь zurg спрашивает новостные серверы о релизе, который ждёт уже тридцать минут. Если его статьи пропали или серверы вообще не удалось опросить, zurg сообщает, что загрузка не удалась. Релиз, у которого размеры файлов действительно ещё в пути, не затрагивается и по-прежнему ждёт, пока они придут.

## Релиз, от которого отказался один аккаунт, можно починить с другого {#a-release-one-account-gave-up-on-can-be-repaired-from-another}

Сервисы дебрида ведут независимые кэши. Релиз, который Real-Debrid удалил, или тот, который он отклоняет только по имени файла, может прямо сейчас лежать в кэше AllDebrid под тем же хэшем. До сих пор zurg не мог этим воспользоваться. Ремонт всегда заново добавлял релиз на тот аккаунт, откуда он пришёл, поэтому, как только этот аккаунт сдавался, попробовать было больше нечего, и релиз оставался мёртвым в вашей библиотеке, хотя другой аккаунт, за который вы уже платите, его держал.

Теперь релиз, который все аккаунты, где он есть, забраковали, предлагается вашим другим аккаунтам. Первый, у которого он уже есть, забирает его, и релиз возвращается с обоими аккаунтами за ним, переключаясь между ними, как и любой релиз, который есть на двух аккаунтах. Ничего включать не нужно: если у вас настроен второй аккаунт и ремонт включён, это именно то, что ремонт делает, когда у него заканчиваются другие варианты.

Аккаунту передаётся только тот контент, который у него уже есть. Если бы ему пришлось скачивать релиз, добавление отменяется и удаляется, так что ничего не загружается и квота на загрузки не тратится. Аккаунт, который ответил «нет», спрашивают снова через день, потом через два, потом через четыре, и так до примерно двух недель, так что релиз, который пропал навсегда, больше ничего не стоит.

## Загрузки только из кэша определяются по вашему аккаунту, а не по поиску в кэше {#cached-only-grabs-are-judged-by-your-account-not-by-a-cache-lookup}

В режиме cached-only zurg раньше спрашивал TorBox, Premiumize и Offcloud, есть ли релиз у них в кеше, и сразу отдавал этот ответ Sonarr. Но эти эндпоинты отвечают на другой вопрос. Они говорят, что контент лежит в кеше сервиса, а не что он попадёт на твой аккаунт. При этом zurg потом никак не проверял торрент. Если ответ «да» превращался в загрузку, Sonarr получал мгновенный grab, который ему обещали, а именно этого режим cached-only и должен не допускать.

Теперь все аккаунты проверяются одинаково. Торрент добавляется, за инстансом наблюдают, и только тот, что завершился в отведённое время, считается кешированным. Всё остальное удаляется, а grab отклоняется. Так Sonarr переходит к следующему релизу в своём списке. Цена в том, что промах на этих трёх сервисах теперь тратит слот добавления, тогда как раньше проверка по кешу слотов не тратила.

## Резервный ключ AllDebrid больше не отвечает за вашу библиотеку {#an-alldebrid-backup-key-no-longer-answers-for-your-library}

`download_tokens` в аккаунте AllDebrid — это отдельные аккаунты AllDebrid, которые держат для своего лимита загрузок. Как только собственный ключ аккаунта упирался в лимит и выходил из ротации, все остальные запросы тоже уходили на резервный ключ: список magnet, список файлов релиза, добавления, удаления, перезапуски, сохранённые ссылки за `__downloads__` и проверка на изменения. Из-за этого обновление библиотеки могло получить список magnet резервного аккаунта и записать их как твои, а удаление могло уйти на аккаунт, который никогда не держал этот magnet, и вернуться с ответом, будто он уже удалён. А когда все ключи были исчерпаны, каталог полностью пропадал из-за того, что по сути является всего лишь ограничением по байтам. Теперь ротация происходит только при разблокировке ссылки. Всё, что касается твоего аккаунта, теперь запрашивается у твоего аккаунта.

## Здоровый релиз перестаёт мигать туда-сюда в списке Broken {#a-healthy-release-stops-flapping-in-and-out-of-the-broken-list}

Релиз, у которого аккаунт продолжает отдавать одну мёртвую ссылку, мог бы каждые полчаса наполовину висеть в списке Broken на дашборде, хотя все файлы в нём играли отлично. Repair убирает ссылку, которая три цикла подряд отвечала `hoster_unavailable`, чтобы перепривязать релиз, и запоминает, что эту ссылку убрал, чтобы следующий список не отдал её обратно. Но эту память стирало не то: любой repair, который закончился успешно, её очищал, включая проходы, которые ничего не создают и только проверяют, что уже привязанная адресация всё ещё работает. «Архив, который отдаёт этот файл, всё ещё работает» — это крайний случай: он доказывает, что единственная ссылка, которая обслуживает релиз, работает, и ничего не говорит о ссылке, которую аккаунт отверг. Поэтому отказ забывался, следующее обновление снова брало ту же мёртвую ссылку, repair не мог назначить её заново и снова приговаривал запись, и так по циклу в тридцать минут, который не мог закончиться. По замерам на живой библиотеке за три дня один релиз был осуждён 129 раз, всего за неделю по библиотеке набралось 556 осуждений, а каждый цикл тратил от двух до четырёх добавлений magnet-ссылок. Теперь отказ забывается только тогда, когда repair действительно перепривязал релиз, а ручной repair по-прежнему забывает все отказы, так что оператор может вернуть ссылку вручную.

## Релиз, отданный одним архивом, больше не помечается как сломанный при каждом проходе {#a-release-served-as-one-archive-is-no-longer-marked-broken-every-sweep}

Некоторые релизы отдаются одним архивом: в `.rar` лежит единственная ссылка аккаунта, а каждая серия внутри архива значится отдельным файлом, и ссылок у таких файлов нет. Проверка битых файлов всё равно спрашивала аккаунт про эти внутренние файлы. Спросить было не с чем, поэтому аккаунт не опрашивался и ничего не измерялось, но ответ всё равно приходил «file is broken». Этот ответ проверка записывала в каждый файл и по нему браковала весь релиз.

Дальше всё шло по кругу и стоило двух magnet-добавлений. Аккаунту запрашивали только битые файлы, он отвечал той же единственной ссылкой на архив, которая у него и была. Затем запасной механизм с архивом проверял эту ссылку и восстанавливал все файлы, которые только что были забракованы. На живой библиотеке это выглядело так: 44 серии одного архива размером 4,9 ГБ проходили этот цикл каждые полчаса.

Теперь файл, для которого ни один аккаунт не держит ссылку, не трогается. Сам файл архива оценивается точно так же, как и раньше: если ссылка, по которой отдаётся релиз, перестаёт открываться, этот файл помечается как битый, а вместе с ним и релиз.

## Трафик возвращается к токену вашего собственного аккаунта, как только обновляется дневной лимит {#traffic-goes-back-to-your-own-accounts-token-once-its-allowance-resets}

Аккаунт Real-Debrid, который исчерпал суточный лимит, переносит трафик на первый токен из `download_tokens`, у которого ещё остался лимит. А наблюдатель возвращает собственный токен аккаунта в ротацию, как только тот снова может отдавать байты.

Но сам токен вернулся, а трафик назад не пошёл. Ротация продолжала с того места, где остановилась, и проверяла только, не исчерпан ли один этот токен. Поэтому резервный аккаунт забирал весь трафик до конца дня, хотя счётчик основного аккаунта уже был на нуле. Теперь порядок в `download_tokens` — это лишь предпочтение, а не позиция, с которой ротация идёт по кругу. Какой токен стоит ближе к началу и может отдавать трафик, тот и отдаёт. Поэтому основной аккаунт забирает трафик обратно в течение минуты после сброса своего счётчика.

## Клиент rclone, настроенный на неверный адрес, теперь сообщает об этом {#an-rclone-remote-pointed-at-the-wrong-address-now-says-so}

Если в URL WebDAV-remote у rclone не хватает `/dav/` в конце, каждый листинг падал с ошибкой "couldn't list files: 405 Method Not Allowed", и нигде не было написано, почему. Дашборд в браузере открывался нормально, поэтому zurg выглядел исправным, а в собственном логе zurg ничего не было о клиенте, который каждые несколько секунд падал с ошибкой. Теперь zurg на WebDAV-запрос, пришедший вне `/dav/`, отвечает адресом, который нужно использовать; rclone выводит его как часть своей ошибки. Кроме того, zurg пишет одно предупреждение с указанием клиента, который отправил такой запрос.

## Установки на Windows снова отправляют уведомления о сканировании в медиасервер {#windows-installs-now-send-media-server-scans-again}

Значение `mount_path` равное `Z:`, которое `zurg setup` записывает в Windows, заставляло
сканировать пути относительно текущей директории на диске, а не относительно его корня.
Из-за этого каждый путь мимо нужной секции библиотеки, и сканирование так и не
отправлялось. Предупреждение после этого просило проверить `mount_path`, который уже
был правильным. Существующим конфигам правка не нужна.

## Массовое сканирование читает библиотеку Plex один раз, а не по разу на каждый торрент {#bulk-scan-reads-the-plex-library-once-instead-of-once-per-torrent}

Сопоставление после массового сканирования из панели перечитывало всю библиотеку Plex для каждого торрента в пакете, поэтому при сканировании большой библиотеки на сервер Plex, который обычно и так был занят сканированием, отправлялwere сотни одинаковых запросов на получение всей библиотеки.

## Пути библиотеки в Windows совпадают независимо от регистра {#windows-library-paths-match-regardless-of-case}

Библиотека Plex, Jellyfin или Emby, записанная как `Z:\Movies`, больше не пропускает
`Z:\movies`, который zurg строит из собственного имени каталога. NTFS не учитывает регистр, поэтому оба пути указывают на один каталог. Раньше точное сравнение приводило к тому, что сканирование пропускалось и mount_path считался неверным.

## Файл, который перестал отдаваться, больше не тормозит сканирование Plex {#a-file-that-stops-serving-no-longer-stalls-a-plex-scan}

Сломанный файл сохранял место в списке каталога и отвечал на чтение ошибкой `503 File temporarily unavailable (being repaired)`, пока что-нибудь не снимало этот статус. Пока шла починка, он держался до её окончания. Plex останавливается на 503, поэтому один такой файл тормозит сканирование библиотеки, а библиотека, в которой их много, вообще никогда не досканирует. Jellyfin просто пропускает их и выглядит нормально.

Тут два отдельных решения, и теперь у каждого свой ответ. Запись по-прежнему остаётся в списке, пока файл может вернуться, потому что для медиасканера запись, пропавшая из папки, выглядит как удаление, и элемент отправляется в корзину. С этим ничего не меняется. Меняется само чтение: в течение минуты после того, как файл перестал отдаваться, оно получает 503, а потом 404. Минута нужна потому, что клиент может ею воспользоваться: rclone повторяет запрос при 503 и сдаётся примерно через это время. Короткий сбой поэтому всё так же гасится, и чтение проходит успешно. А если сбой длится дольше, 503 всё равно провалил бы чтение и тормозил бы все сканирования за ним.

Проверка на настоящем Plex: библиотека из пятнадцати фильмов, десять файлов отказали, но все они остались в списке. Чтения с ответом 404 завершили сканирование за 5 секунд. А 503, которое так и не снималось, нашло только три из пятнадцати, когда через десять минут прогон прервали.

## Новые задания SABnzbd больше не ждут, пока проверятся размеры всей библиотеки {#new-sabnzbd-jobs-no-longer-wait-behind-a-full-librarys-size-checks}

Когда zurg перезапускался с большой библиотекой Usenet, он ставил в очередь проверку размера для каждого релиза и забывал, какие неудачные проверки всё ещё ждали окончания одночасовой задержки перед повтором. Из-за этого только что добавленный релиз мог застрять за тысячами фоновых проверок, пока Sonarr или Radarr ждали точные размеры его файлов. Теперь проверки размера идут через очередь с фиксированным числом воркеров. Если для релиза есть ожидающая задача SABnzbd, он перемещается в начало очереди. Результаты завершённых проверок и задержки перед повтором сохраняются при перезапуске в `data/nzb-sizes/`. Пока в очереди есть работа, zurg раз в минуту выводит количество ожидающих задач, задач с приоритетом клиента и выполняющихся задач.

## Загрузки, которые клиент так и не очистил, больше не мешают импортировать новые {#downloads-a-client-never-clears-no-longer-stop-new-ones-from-being-imported}

zurg показывает Sonarr, Radarr и другим клиентам загрузок страницу с завершёнными загрузками и держит каждую на этой странице, пока клиент её не удалит. Клиенты удаляют только то, что уже импортировали или что завершилось с ошибкой, поэтому импорт, который они блокируют (например, название, которое не получается сопоставить), навсегда оставался на странице. Когда страница заполнялась такими записями, каждая новая завершённая загрузка ждала в очереди и так и не импортировалась. Теперь загрузка, которая провисела на странице десять минут без удаления, уступает место ожидающей загрузке, так же как SABnzbd вытесняет старые строки со своей страницы истории по мере появления новых. Пока на странице есть место, ничего не меняется, а повторный поиск релиза даёт ему отдельное место.

## Загрузка, найденная по своему id, появляется сразу после завершения {#a-download-looked-up-by-its-id-is-found-as-soon-as-it-finishes}

Инструменты, которые запрашивают у zurg один загруз по его id, например LazyLibrarian, теперь сразу получают статус «готово», как только загрузка завершилась, даже когда страница завершённых загрузок, которую читают Sonarr и Radarr, полна. Раньше такая загрузка могла выглядеть для них незавершённой, пока на этой странице не освобождалось место.

## У исправления сезона теперь есть страница в панели управления {#season-fix-has-a-page-in-the-dashboard}

Функция, которая переименовывает фансаб-файлы по всей библиотеке под имена, которые читает Plex, работает с момента релиза, но открыть её можно было только двумя HTTP-эндпоинтами: `/torrents/season-fix/plan` и `/torrents/season-fix/apply`. В панели управления для неё не было ни одного элемента, а описана она была одним абзацем в справочнике по именованию. Функция, которую никто не может найти, фактически не существует. А ведь в этом месяце её ещё просили в канале с пожеланиями, и люди даже не догадывались, что она уже есть.

Страница `/season-fix/` теперь объясняет, что делает этот проход. Она показывает каноническую форму, которую он создаёт, и сравнивает её с фансаб-именем, которое заменяет. Также она говорит, откуда берётся структура сезонов: из собственного провайдера метаданных Plex, а не из локальной библиотеки, потому что исправляем как раз ту библиотеку, где сезоны уже схлопнулись. Страница перечисляет, что маппер не трогает и почему. Если скан возвращает почти пустой результат, это значит, что консервативный подход работает как надо, а не что что-то сломалось.

Сканирование спрятано за кнопкой. Планирование проходит по каждому торренту и спрашивает Plex про каждый найденный сериал, поэтому открытие страницы его не запускает. Результаты сгруппированы по сериалам, каждое переименование показано как «было → стало», а пропущенные файлы спрятаны в раскрывающийся блок. Запись, помеченная как вероятное совпадение с не тем сериалом, попадает в список со снятой галочкой и повторно говорит об этом в окне подтверждения. Так что если применить всё сразу, ошибочно сопоставленный релиз тихо не переименуется.

## Воспроизведение сжатого релиза, разбитого на несколько томов {#play-a-compressed-release-that-is-split-across-several-volumes}

Релиз, который был упакован со сжатием, а не сохранён целиком, останавливался на конце своего первого тома. Все файлы внутри показывались с правильным именем и размером, но не проигрывались, а в логе появлялась ошибка bad header CRC. Теперь zurg переносит распаковку через каждое соединение томов, так что такие релизы проигрываются от начала до конца.

## Быстрый запуск, когда в вашем аккаунте есть неудачные торренты {#start-up-quickly-when-your-account-holds-failed-torrents}

Каждое обновление библиотеки заново проверяло каждый торрент, который ваш debrid-сервис пометил как неудачный, по одному запросу за раз, а сервис разрешает лишь несколько таких запросов в секунду. На аккаунте с несколькими сотнями таких торрентов это занимало больше минуты при каждом обновлении, и библиотека оставалась нечитаемой всё это время после каждого запуска. Этого достаточно, чтобы Plex просканировал ещё не появившуюся папку и пометил всё в ней как недоступное. Теперь zurg берёт информацию о неудачном торренте, которая у него уже есть, с диска и обращается к сервису снова только тогда, когда сервис сообщает, что торрент больше не неудачный.

## Перестаём повторно запрашивать у AllDebrid магнет-ссылки, которые он уже отказался повторять {#stop-re-asking-alldebrid-about-magnets-it-has-already-refused-to-retry}

Когда magnet не работает, zurg просит AllDebrid загрузить его заново. AllDebrid отказывает
в некоторых таких запросах, и этот отказ не засчитывался в два попытки, которые даются
торренту, поэтому один и тот же magnet запрашивался при каждом обновлении библиотеки,
пока работал zurg. Теперь ответ запоминается на час, а также для статуса, который выдал
аккаунт, поэтому если magnet меняется, он запрашивается заново. Количество попыток также
записывается на диск, а не сбрасывается при каждом перезапуске и не тратится заново.

## Ссылка остаётся стабильной для релиза, который есть в аккаунте дважды {#keep-the-link-steady-for-a-release-your-account-holds-twice}

A release added twice to one account has two of everything, including two download links per file. zurg kept one link per account, so each copy replaced the other's on every refresh and the entry never settled. Nothing was unplayable, but the log filled with re-pointing and the library was rewritten to disk every few seconds. zurg now leaves the link alone when it can only see part of what the account holds.

## Более быстрые проверки изменений на TorBox, когда в аккаунте есть неудачные торренты {#faster-change-checks-on-torbox-when-the-account-holds-failed-torrents}

TorBox не умеет сообщать, менялся ли аккаунт, поэтому zurg читает небольшую страницу самых новых торрентов и следит за теми, которые ещё не завершились. Торрент, который TorBox пометил как неудачный, никогда не завершится, и из-за одного такого старого сбоя каждая проверка читала страницу гораздо больше, и так до конца жизни аккаунта. Неудачные торренты больше не отслеживаются на предмет изменений, которых они всё равно не могут сделать.

## Релиз, который ваш *arr не смог импортировать, больше не удаляется из-за этой попытки {#a-release-your-arr-could-not-import-is-no-longer-deleted-by-the-attempt}

Когда zurg отказывается перемещать релиз из папки подготовки Usenet, потому что его нельзя прочитать с новостных серверов, Sonarr и Radarr не сдаются просто так. .NET при неудачном перемещении копирует файл, а потом удаляет оригинал. zurg выполнял это удаление, поэтому релиз пропадал, а на месте, куда его импортировали, оставался пустой файл. Теперь удаление, которое идёт после отказанного перемещения, тоже отклоняется по той же причине, и релиз остаётся на месте.

## Чтение из Usenet отличает медленную пачку от зависшей {#usenet-reads-tell-a-slow-batch-from-a-stalled-one}

zurg запрашивает второе новостное соединение для статьи, если ожидание затянулось, и берёт тот ответ, который придёт первым. Решение, что ожидание затянулось, принималось по таймеру. Из-за этого обычная партия больших статей на быстром аккаунте запрашивалась дважды, пока первая статья ещё приходила.

Теперь решение принимается по данным, которые реально идут по соединению. Новостное соединение и так обновляет свой таймаут каждый раз, когда приходят байты, и читатель видит эти же данные. Партия, которая посреди большой статьи, не трогается, сколько бы эта статья ни качалась. Запрашивается в другом месте только та партия, из которой байты перестали идти.

Если соединение взяло партию статей и не ответило ни на одну, zurg запрашивает у другого соединения всю оставшуюся часть партии сразу, а не ищет каждую недостающую статью отдельно. Молчащее соединение не обрывается, так что его статьи всё равно засчитываются, если придут. Повторно запрашиваются только те статьи, которые так и не пришли, и не более одного раза на партию. Статьи ближе всего к playhead идут первыми. Один второй запрос всегда остаётся в запасе, чтобы следующее чтение, которое встало на месте, могло запросить свою статью.

Чтение также перестаёт считать время, которое оно потратило на второй запрос, своей обычной скоростью. Оно запоминает только то время, которое zurg был готов ждать, и ни секунды больше. На аккаунте, где каждая статья законно качается секунду или дольше, порог теперь устанавливается около того, что этот аккаунт реально отдаёт, а не опускается до минимального значения и не запрашивает дважды почти каждую статью.

## Упреждающее чтение из Usenet держит окно заполненным между статьями и томами {#usenet-read-ahead-keeps-its-window-full-across-articles-and-volumes}

Раньше read-ahead переставал запрашивать новые байты, пока один из предыдущих артиклов запаздывал, и один медленный артикл съедал всё окно, которое уже было накоплено. Теперь zurg всё равно держит ограниченное окно запрошенных байтов в полёте, а один пакет артиклов может охватывать стык между двумя сохранёнными RAR-томами, а не заканчиваться на нём.

Окно занимает не больше четверти настроенного RAM-кэша и никогда не больше 128 MiB, поэтому меньший кэш даёт меньшее окно. Запросы сохраняют собственную отмену и лимиты подключений и кэша своего аккаунта.

## Воспроизведение из Usenet тратит меньше ресурсов ЦП на старых процессорах {#usenet-playback-costs-less-cpu-on-older-processors}

Кеш чтения вычисляет контрольную сумму для каждой записи, которую сохраняет. На процессорах Intel и AMD, у которых есть SSE4.1, но нет AVX, SHA-256 работает без какой-либо аппаратной помощи, и эта нагрузка заметна при воспроизведении. Теперь zurg использует более быструю 256-битную контрольную сумму на таких процессорах. Записи хранят версию, поэтому повреждения по-прежнему обнаруживаются, существующий кеш остаётся читаемым, а на всех остальных процессорах используется SHA-256.

## NZB-шары больше не ведут обратно к аккаунту, который их получил {#nzb-shares-no-longer-point-back-to-the-account-that-grabbed-them}

Некоторые индексаторы помечают каждую загрузку данными, по которым можно выйти на ваш аккаунт, и часть этих данных попадала в поля, которые сохранял общий доступ. Один прячет свежий токен в названии релиза и часто в пароле, а также меняет постер, дату и группу новостей у каждого файла. Другой ставит номер вашего аккаунта в начале темы одного из файлов. Третий добавляет метку аккаунта в каждый постер. Теперь `zurg nzb-share` убирает постеры и даты, задаёт всем файлам одну и ту же фиксированную группу новостей, вырезает метку в теме и игнорирует токен, где бы он ни находился. Если имя и заголовок не совпадают, побеждает имя. Два человека, которые скачали один и тот же релиз, теперь публикуют одинаковый файл. Кроме того, общий доступ больше не пропускает NZB, сохранённые в кодировке Latin-1, и перестал удваивать обратные слэши, которые есть в некоторых темах.

Что именно очищает эта команда, описано в [`zurg nzb-share`](cli.md#zurg-nzb-share).

## Локальные библиотеки добавляют хеш на AllDebrid, Premiumize и Offcloud {#local-libraries-add-the-hash-on-alldebrid-premiumize-and-offcloud}

Локальная библиотека, в манифесте которой нет переносимой ссылки, добавляет хеш в ваш аккаунт при первом воспроизведении. Манифест, экспортированный из TorBox, всегда выглядит именно так. То же самое и с манифестом, у которого истекла ссылка AllDebrid. На AllDebrid, Premiumize и Offcloud каждое такое воспроизведение завершалось ошибкой "provider did not report an active torrent allowance". zurg перед добавлением хотел, чтобы аккаунт сообщал свой лимит торрент-слотов. Эти три провайдера такой лимит никогда не сообщают. Теперь zurg использует объявленное количество слотов, как это делает repair. Если нет ни того, ни другого, он всё равно добавляет хеш, и уже провайдер отказывает, если аккаунт заполнен.

## Файлы на Offcloud теперь сообщают свою длительность {#offcloud-files-report-their-length}

Разрешение файла Offcloud оставляло его длину не заполненной. Локальная библиотека сверяет эту длину с манифестом. Поэтому она отказывала в каждом воспроизведении Offcloud с ошибкой "resolved file size does not match the portable manifest". Обычное воспроизведение тоже потеряло обработку диапазонов, которой нужна длина. Теперь zurg запрашивает длину у сервера доставки так же, как это уже делает список Offcloud.

## zurg работает на телефонах Android и Google TV {#zurg-runs-on-android-phones-and-google-tv}

Новое Android-приложение хранит твою библиотеку прямо на устройстве. Оно подходит для телефонов и планшетов, а также для Android TV и Google TV. Нужен Android 8.0 или новее, а для Usenet нужен 64-битный Android. Приложение проведёт тебя через настройку аккаунтов провайдеров и профиля устройства, а потом запустит библиотеку. Просматривать её можно прямо в приложении или через Files от Android. Воспроизводить можно во внешнем плеере на твой выбор, с полной перемоткой. Все экраны управляются с пульта от TV. MediaInfo работает на устройстве без дополнительных инструментов. Библиотеку также можно открыть другим устройствам в твоей локальной сети, но за паролем. Этот пароль никогда не передаётся плееру.

APK-файлы лежат в nightly-релизах для спонсоров. Само приложение zurg не содержит. После входа в GitHub оно установит движок zurg как отдельный пакет. Приложение и движок обновляются независимо друг от друга. В разделе Updates перечислены все опубликованные версии движка, так что если nightly-сборка работает на твоём устройстве плохо, можно откатиться к той, которая работала. Тем, кто установил первую Android-сборку, нужно один раз поставить движок из Updates. Провайдеры и настройки библиотеки при этом сохранятся без изменений.

Движок для 64-битных ARM-устройств теперь находит адреса провайдеров через встроенный в Android резолвер. В первой сборке движок мог вообще не подключаться ни к одному провайдеру.

Инструкции по настройке и плееру: [Android](../guides/android.md).

## Новый NZB появляется в библиотеке в течение нескольких секунд {#a-new-nzb-shows-up-in-the-library-within-seconds}

Раньше NZB, попавший в папку наблюдения, ждал следующей плановой проверки изменений. Потом обфусцированный релиз ждал ещё один интервал, пока читались его настоящие имена файлов. При интервале по умолчанию это занимало от 20 до 30 секунд, и всё это время заявка в Sonarr или Radarr висела в статусе Queued.

Теперь zurg сам проверяет папку наблюдения раз в секунду. Он не полагается на события файловой системы, поэтому работает одинаково на NAS и внутри контейнера. Релиз появляется в списке сразу, как только прочитаны его имена. Сезонный пак из двадцати релизов по-прежнему требует только одного листинга. Плановая проверка остаётся как страховка на случай, когда NZB заменён под именем, которое уже было.

## Потоки из Usenet сохраняют свою скорость {#usenet-streams-hold-their-speed}

Файл внутри RAR-набора попадает на новостной аккаунт по одному тому за раз. zurg открывает следующий том заранее, чтобы переход не начинался «с холодного старта». Раньше он прогревал только первые четыре мегабайта. На релизе, нарезанном на мелкие тома, это означало границу каждые секунду-две воспроизведения и заминку на каждой из них. Один такой релиз шёл со скоростью 14–16 МБ/с, тогда как обычный файл на том же аккаунте работал на 86–99 МБ/с. Теперь следующий том прогревается на всю глубину окна предварительного чтения, как только поток подходит к нему на расстояние 32 MiB. Том, в который поток только что вошёл, сохраняет заработанное предварительное чтение. Том, рядом с которым ничего не происходит, по-прежнему прогревается только в начале. Так сканирование библиотеки не будет тянуть данные, которые никогда не будут прочитаны.

Плавное чтение также около одной секунды из двадцати тормозило на одной медленной статье, пока все остальные соединения ждали за ней. Теперь zurg, когда ожидание затягивается, запрашивает эту статью через второе соединение и использует тот ответ, который придёт первым. Так он делает только для чтения, которого ждёт плеер. Предварительное чтение и восстановление никогда не дублируются. Лимит — двадцать дополнительных запросов в минуту на аккаунт.

Чтение, которого ждёт плеер, теперь идёт первым в большем числе мест. Предварительное чтение больше не забирает последнее свободное соединение аккаунта. Проход определения размера при запуске тоже оставляет одно свободным. Чтение использует соединения, которые аккаунт уже держит, вместо открытия своих. Оно ждёт соединения, которое уже открывается, а не платит за новое. Статья, на которой застрял плеер, может обогнать в очереди загрузки байтов, нужных позже. В одном замере первый байт чтения пришёл за 177 мс вместо 354 мс. Прогрев, keep-alive и чтения теперь тоже делят один лимит соединений. zurg никогда не открывает больше соединений, чем разрешено аккаунтом.

Сохранение декодированной статьи в дисковый кеш больше не задерживает чтение, которое её получило. Раньше запись находилась внутри блокировки, которая нужна всем остальным чтениям. Теперь она происходит после того, как байты дошли до плеера. Если всплеск больше, чем кеш может обработать, лишние записи пропускаются, а воспроизведение не замедляется. Существующий кеш переносится как есть.

## Sonarr и Radarr перестают ждать захватов, которые никогда не завершатся {#sonarr-and-radarr-stop-waiting-on-grabs-that-can-never-finish}

Эндпоинт SABnzbd раньше иногда оставлял некоторые задачи в очереди навсегда. Клиент их не блокировал и не брал другой релиз. Теперь в каждом из описанных случаев задача получает статус Failed и сообщение с причиной. Failed заставляет Sonarr и Radarr занести релиз в блоклист и начать поиск заново.

Релиз может исчезнуть из библиотеки после граба. Его могли удалить через дашборд, убрать из папки наблюдения или отключить на всех аккаунтах. Раньше задача просто висела на 0%, и ничто её уже не сдвигало. Теперь она падает, если релиз отсутствует пятнадцать минут. В первые пятнадцать минут после перезапуска ничего не падает, пока библиотека ещё загружается.

Грэб может прийтись на релиз, который уже опустошил предыдущий импорт. Так бывает, когда апгрейд удаляет импортированный файл, а поиск снова находит тот же релиз. Раньше zurg отвечал Completed и отправлял клиента в папку, где ничего не осталось. Теперь повторный граб опустошённого релиза сразу падает. Папка, которая пустует пятнадцать минут, тоже приводит к ошибке задачи. Это касается и папки, опустошённой вручную, и папки, которую освободил импорт из другой задачи. Граб, который выполняет импорт, пока завершается, по-прежнему показывает Completed.

Некоторые релизы никогда не доходят до конца проверки статей. Прежде чем отметить граб как готовый, zurg спрашивает новостные серверы, на месте ли статьи релиза. Проверка, которая не могла завершиться, раньше повторялась каждую минуту без конца. Теперь она падает после тридцати попыток подряд, которые охватывают не меньше трёх часов. Если новостной аккаунт лежит час, это не означает, что все ожидающие задачи попадут в блоклист. Проверка, которая наконец дала ответ, сбрасывает счётчик.

У некоторых релизов нет всего архива целиком. В наборе может не быть тома с началом файла. Может не хватать тома из середины. Набор может начинаться не с первого тома. Раньше Sonarr получал путь к папке, из которой не мог импортировать, и повторял попытки бесконечно. Теперь граб падает. Вердикт привязан к конкретным томам, на которых он был получен. После восстановления PAR2, повторного граба или второго аккаунта с недостающими томами релиз проверяется заново.

## Резервные токены загрузки берут работу на себя, когда заканчивается дневной лимит {#backup-download-tokens-take-over-when-the-daily-allowance-runs-out}

Real-Debrid отказывает в загрузке, как только токен исчерпал дневной лимит. zurg должен помечать такой токен как исчерпанный и переходить к следующему в `download_tokens`. Во время воспроизведения это перестало работать, когда проксируемые потоки перешли на новый HTTP-клиент. Отказ приходил как обычный ответ, и ничего не отмечало токен как исчерпанный. Все резервные токены простаивали, а каждое чтение снова тратило тот самый ограниченный токен.

Теперь отказ распознаётся везде, где с ним сталкивается zurg: и при воспроизведении, и в цикле обновления, и при repair. Оба последних проверяют ссылки независимо от того, идёт ли что-то в воспроизведении. Отказ, пришедший без привычного заголовка Real-Debrid, тоже теперь выводит токен из работы.

Исчерпанный токен проверяется раз в минуту, чтобы вернуться в работу, как только восстановится его лимит. Раньше эта проверка использовала ссылку, закэшированную под самим исчерпанным токеном. Но после того как токен перестаёт работать, этот кэш больше никто не обновляет. Поэтому проверка ничего не находила, и токен оставался вне работы до ежедневного сброса или перезапуска. Теперь проверка берёт ссылку у того токена, который ещё работает.

Ежедневный сброс опаздывал на сутки. Real-Debrid сбрасывает лимиты через несколько минут после полуночи по CET. zurg пропускал первую полночь после каждого запуска и сбрасывал на вторую. Из-за этого аккаунт, исчерпавший лимит, ещё день работал через резервный токен. Кроме того, zurg определял эту полночь по дате на самом хосте. В западной части Европы сброс приходился на тот час, когда zurg был запущен. Теперь каждый сброс планируется по дате в CET.

## Захват по магнет-ссылке сохраняет название релиза в аккаунте debrid {#a-magnet-grab-keeps-its-release-name-on-the-debrid-account}

Sonarr и Radarr передают эндпоинту qBittorrent весь magnet индексера. Раньше zurg перед добавлением обрезал его до info hash. Отображаемое имя и трекеры до аккаунта не доходили. Для magnet-only индексера отображаемое имя — единственное место, где есть название релиза. Некэшированный торрент тогда висел в списке аккаунта под 40-символьным хешем. Если торрент никто не раздаёт, это единственное имя, которое он вообще получит.

Теперь magnet доходит до аккаунта в том виде, в котором его отправил клиент. Repair, watchlist Plex и portable libraries по-прежнему добавляют голый хеш, потому что у них нет имени, которое можно передать дальше.

## Дамп .strm содержит только файлы, которые плеер может открыть {#the-strm-dump-holds-only-files-a-player-can-open}

`save_strm_files` раньше записывал .strm для каждого выбранного файла в релизе. Субтитры, постеры, NFO и тома PAR2 тоже превращались в записи в библиотеке, которые открывались в никуда. TorBox и AllDebrid помечают все файлы как выбранные. То же самое делает и Usenet-пост с файлами для восстановления рядом с видео. Теперь .strm получают только распознанные видео- и аудиофайлы, а также всё, что указано в `addl_playable_extensions`. Видео внутри набора RAR по-прежнему записывается, а тома вокруг него — нет. Записи, созданные предыдущими сборками, удаляются при следующем обходе релиза.

Несколько путей записи также сообщали медиасерверу, чтобы он начал сканирование, до того как файлы .strm были созданы. Plex, Jellyfin или Emby могли заглянуть в пустую папку и ничего не проиндексировать. Никто не просил их проверить снова, пока релиз не менялся. Теперь файлы сначала записываются на всех путях.

## Перенос папки zurg больше не оставляет кэш монтирования без привязки {#moving-the-zurg-folder-no-longer-strands-the-mount-cache}

rclone-монтирование хранит прочитанное в `data/rclone-cache`. rclone называет этот кэш по своей конфигурации. В конфигурацию входит полный путь к папке `data/local` zurg. Перенос папки zurg или изменение `union_writable` давали кэшу новое имя. Старое дерево оставалось на диске, где его не учитывал ни один лимит размера, и никто его не чистил. После нескольких переносов могли остаться терабайты.

При запуске монтирования zurg теперь спрашивает у rclone, какое дерево кэша активно, и удаляет остальные. Он записывает в лог, что освободил. Очистка пропускается, если в `rclone_extra_args` задан свой `--cache-dir`. Чтобы сохранить старые деревья, задайте `rclone_cache_reclaim: false`.

Активный кэш тоже больше, чем многие ожидают. По умолчанию он растёт до 256G и так и остаётся. Ночной проход медиасервера обращается к каждому файлу, поэтому лимит возраста в 72 часа почти никогда ничего не вытесняет. Планируйте с учётом лимита размера. Как его снизить, описано в [справочнике по конфигурации](config.md#disk-the-mount-uses).

## Постеры и файлы .nfo продолжают попадать в `__magic__` {#posters-and-nfo-files-keep-landing-in-__magic__}

Клиент, который пишет через маунт zurg, кладёт новые файлы в `data/local`. Это та папка, где `__magic__` хранит свои сайдкары. zurg учитывал каждый файл там в `sidecar_budget_mb`. Пара видео, которые какой-нибудь \*arr записал через маунт, могла забить весь бюджет. После этого каждый .nfo и постер отклонялись так, будто диск полный. Поднятие бюджета ничего не меняло.

Файл больше `sidecar_max_mb` не мог прийти через путь сайдкаров zurg. Такие файлы теперь не учитываются в бюджете. При запуске zurg один раз называет их в логе, потому что они всё равно занимают место на диске.

Удаление уже несуществующего пути `__magic__` теперь проходит без ошибок. Маунт может убрать общий сайдкар с обеих сторон и не сломать очистку после импорта.

## Воспроизведение из Stremio пробует следующий релиз, если первый устарел {#a-stremio-play-tries-the-next-release-when-the-first-has-aged-off}

Раньше один клик в Stremio означал один релиз. Если в нём не было ничего, что можно воспроизвести, воспроизведение падало с ошибкой 404. Обычно причина в том, что пост устарел и его удалили с новостного сервера. При этом в списке потоков могло быть десятка два других релизов.

Теперь, если воспроизведение отказало, zurg пробует ещё до двух строк из того же ранжированного списка. Он начинает со строки, которую вы выбрали, и идёт дальше. Значит, запасной вариант будет того же разрешения и меньшего размера или на ступень ниже. Больший релиз, мимо которого вы прошли, никогда не подставляется. Релиз, который ещё загружается, по-прежнему отвечает 503, и если нажать «играть» снова, он подхватится. Каждая попытка тратит один запрос к индексатору и оставляет этот релиз в библиотеке. Ссылки для воспроизведения, созданные до этого изменения, работают как и раньше.

## Списки Stremio показывают все разрешения и разброс размеров {#stremio-lists-show-every-resolution-and-a-spread-of-sizes}

Список потоков раньше ограничивался по всему списку. Результаты в 4K сортируются первыми, и у популярного тайтла их бывает больше лимита. Из-за этого список мог заполниться ремуксами по 20–40 ГБ и спрятать все найденные релизы 1080p и 720p. Теперь `stremio.max_results` считает отдельно для каждого разрешения и по умолчанию равен 5. Значение, которое вы задали вручную, сохраняет своё число и теперь действует на каждое разрешение.

Внутри одного разрешения раньше оставались только самые большие релизы. Из-за этого резали как раз 4 ГБ-кодек, который могут проиграть телефон или ноутбук. Теперь в каждом разрешении берутся равномерно распределённые варианты от самого большого релиза до самого маленького. Крайние всегда включаются.

Описание каждого потока теперь заканчивается тем, сколько назад был опубликован релиз. Выглядит это так: `3d`, `126d` или `2y`. Возраст — лучшая подсказка, что публикация, возможно, уже удалена с новостного сервера. Результаты, закэшированные до этого изменения, не показывают возраст, пока кэш этого тайтла не обновится.

Теперь в манифесте аддона указывается реальная версия сборки, а не `0.1.0`. Команда `zurg --version` выводит те же сведения о сборке, что и `zurg version`, и не требует конфигурационного файла.

## Здоровые релизы перестают пропадать из библиотеки {#healthy-releases-stop-disappearing-from-the-library}

Ошибка соединения или сбой DNS-запроса к API Real-Debrid теперь помечают аккаунт как временно недоступный. Раньше из-за этого рабочие файлы помечались как сломанные. Потом они ждали починки, даже когда сеть уже вернулась.

Очистка после обновления библиотеки раньше ждала, пока завершится фоновый анализ медиафайлов. К тому моменту более новое обновление могло вернуть релиз обратно, а поздняя очистка удаляла его снова. Теперь очистка завершается до того, как обновление возвращает управление. Анализ медиафайлов по-прежнему выполняется в фоне.

## Kodi может просматривать общий ресурс WebDAV {#kodi-can-browse-the-webdav-share}

WebDAV-листинги теперь выдают полный путь каждой папки и файла с префиксом `/dav/`. Раньше Kodi и другие строгие плееры теряли этот префикс и не могли открыть папки или медиафайлы. Имена с экранированными символами и пути внутри архивов сохраняют свои адреса.

## Занятый новостной сервер больше не делает пропусков в потоке {#a-busy-news-server-no-longer-puts-holes-in-a-stream}

Новостной сервер может ответить «no such article» на статью, которая у него есть, если он занят. Раньше zurg перепроверял этот ответ через несколько сотен миллисекунд на том же соединении. После этого он отдавал участок как нули и на сутки списывал статью. Один запрос на 32 MiB вернул 384,000 нулевых байт, хотя через минуту та же статья отдалась без проблем.

Теперь отказавшую статью спрашивают ещё раз, через секунду. Второй запрос идёт по другому соединению, если там есть свободное. Чтение ждёт этого ответа и не заполняет пропуск. Статья, которой действительно нет, по-прежнему отдаётся как тишина и чинится, как и раньше. Поэтому повреждённому релизу теперь нужна примерно на секунду больше, чтобы дойти до этой тишины.

Статью, с которой соединение замолчало, тоже спрашивают повторно один раз, но по другому соединению. Раньше из-за этого падал весь ответ. RAR-поток отвечал 500 на статью, которую провайдер просто медленно отдавал.

## Выберите, как zurg представляется сервисам, к которым обращается {#choose-how-zurg-identifies-itself-to-the-services-it-calls}

Запросы к debrid-сервисам и индексаторам теперь по умолчанию используют обычный User-Agent браузера. Поиск субтитров тоже его использует и больше не отправляет `zurg v0`. Эти запросы также не передают заголовки origin и referrer, как и собственные заголовки zurg. Так происходит и при редиректах. Редирект не может утечь приватный путь или API-ключ предыдущего URL.

`user_agent` задаёт другой agent, а `omit_user_agent` не отправляет его вовсе. Ключи `outbound_*` задают имена клиента и устройства, которые видят Plex, Jellyfin и Emby. Все они находятся на дашборде в разделе Network & Connectivity и вступают в силу после перезапуска. Соединения с Usenet не отправляют никакого идентификатора ПО. Это убирает собственные идентификаторы zurg. Но это не делает вас анонимными.

Подробности в [Outbound identity](outbound-identity.md).

## zurg по умолчанию очищает корзину Plex {#zurg-empties-the-plex-trash-by-default}

zurg выключает в Plex настройку "Empty trash automatically after every scan". Иначе скан, который наткнулся на ненадолго недоступное монтирование, удалит библиотеку вместо того, чтобы отложить её. То, что после этого оставалось, никто не замечал. Plex больше не собирал мёртвые записи, а собственное удаление zurg было включено по выбору. Поэтому по умолчанию их не убирало ничего. Записи, чьи файлы давно исчезли, копились. Самый заметный случай: файл перенесли между папками библиотеки, и его старая запись оставалась навсегда.

Если `plex_trash_sweep_every_mins` не задан, очистка корзины теперь запускается каждые 60 минут. Она отступает, если Plex сам ещё очищает свою корзину. Она удаляет по одной записи за раз и никогда не трогает запись, у которой ещё есть файл. Она работает только с монтированием, которое читается. Всё, что она не может оценить, сначала 14 дней остаётся видимым как сломанное. Укажите `plex_trash_sweep_every_mins: 0`, чтобы отключить удаление и очищать корзину вручную.

Эта настройка не передаёт очистку корзины обратно Plex. Для этого на странице конфигурации теперь есть переключатель Let Plex Empty Its Own Trash. Риск, который он несёт, описан рядом с ним.

Теперь работает и восстановление. Plex пропускает обычный скан папки, которую уже сканировал. Сериал в корзине, все файлы которого уже вернулись, мог оставаться в корзине скан за сканом. Теперь очистка просит Plex выполнить принудительный скан этой папки. Скан, запущенный вручную с панели управления, теперь также доходит до путей `__magic__`, из которых индексируется библиотека Usenet. Раньше он не находил раздел Plex и ничего не делал.

Как два сборщика делят эту работу, описано в [Plex](../guides/plex.md#who-empties-the-trash).

## Повреждённые архивы показывают правильные байты или ничего {#damaged-archives-list-the-right-bytes-or-nothing-at-all}

Некоторые повреждённые наборы RAR раньше показывали видео, которое проигрывало неверные байты. В наборе, где не хватало тома из середины, остаток файла отдавался со сдвигом и хвостом из нулей. Такие наборы теперь отклоняются. В наборе, где не удавалось прочитать первый заголовок, поздние байты тоже сдвигались. Теперь zurg сначала читает заголовки продолжения, так что все смещения совпадают. Файлы после фильма в последнем томе тоже сохраняются. Маркер конца RAR4 раньше ошибочно принимался за шифрование. Разделённые наборы с дополненными блоками в конце теряли свой первый том. Теперь они показывают полное видео.

NZB, в котором не хватает 10% или больше статей, отклоняется до того, как что-либо будет отдано. Контент, который PAR2 уже восстановил, по-прежнему воспроизводится.

Существующие списки архивов перестраиваются, чтобы эти исправления попали и в релизы, уже находящиеся в библиотеке.

## Большие библиотеки могут возвращать неиспользуемую память {#large-libraries-can-give-idle-memory-back}

`library_detail` определяет, остаются ли списки файлов каждого релиза в памяти. `resident` хранит их все и остаётся значением по умолчанию. `lazy` освобождает списки файлов, которые никто не читал дольше `library_detail_idle_secs`. Списки при этом остаются доступными, а когда что-то обращается к файлу, список снова загружается с диска. `auto` работает так же, но только при устойчивой нехватке памяти на хосте или в контейнере. Большие сезонные паки занимают заметно меньше памяти в обоих режимах. Сжатая резервная копия защищает список файлов, если его дисковый кэш повреждён. Несохранённые изменения никогда не освобождаются. На дашборде доступны все три режима. Чтобы изменение вступило в силу, нужен перезапуск.

Запуск также расходует меньше памяти при большой истории загрузок Real-Debrid. Сохранение и загрузка этой истории и кэшей библиотеки больше не создают лишних копий.

Компромиссы описаны в [справочнике по конфигурации](config.md#library-detail).

## Watchlist Plex и запросы Seerr используют одну очередь {#plex-watchlist-and-seerr-requests-share-one-queue}

Блок `acquisition:` объединяет в одну очередь элементы из watchlist в Plex и запросы из Seerr. Оба вида ищутся через твои Newznab-индексаторы и попадают в Usenet-бэкенд. Запросы из Seerr отслеживаются только после одобрения. Скачиваются только запрошенные сезоны. Запрос в 4K хранится отдельно от запроса в 1080p. Открытые запросы из Seerr проверяются повторно, чтобы находить новые вышедшие серии.

Теперь прогресс сохраняется после перезапуска. Это касается дедлайнов повторов, количества попыток и того, какие серии уже готовы. Прерванная загрузка продолжается с того места, где остановилась. Если загрузка уже завершилась, повторяется только удаление элемента из watchlist, и поиск заново не запускается. Сохранённое состояние входит в обычные бэкапы. Существующие настройки `watchlist:` продолжают работать без изменений.

Настройка описана в разделе [Получение контента](../guides/acquisition.md).

## Библиотеки debrid могут храниться в переносимых локальных файлах {#debrid-libraries-can-live-in-portable-local-files}

Аккаунт debrid теперь может брать свою библиотеку из папки с файлами `.zurgtorrent`, а не из собственного списка аккаунта. `zurg export-torrents` записывает существующую библиотеку в такие файлы. В них описано содержимое, но нет ни учётных данных, ни ссылок на загрузку. Поэтому библиотекой можно поделиться. Тот, кто её получил, воспроизводит через свой аккаунт, и на него по-прежнему действуют ограничения его провайдера. Импорт, просмотр списка и обновление файлов ничего не добавляют в аккаунт.

Существующие конфиги продолжают работать. Новые резервные копии используют формат 2 и для восстановления требуют эту сборку или более новую.

Экспорт и настройка описаны в [Локальные библиотеки](../guides/local-libraries.md).

## Кэш чтения переживает перезапуск {#read-caches-survive-a-restart}

zurg теперь хранит свои кэши чтения на диске между перезапусками. Это касается разобранных NZB и декодированных статей Usenet. Также сохраняются раскладки архивов, декодированные блоки архивов и ссылки на отдачу. После перезапуска zurg не нужно заново разбирать каждый NZB или читать заголовки всех архивов. Каждый байтовый кэш ограничен 512 MiB по умолчанию. `zurg backup --include-caches` добавляет их в бэкап для быстрого восстановления с прогретым кэшем.

Запросы на один и тот же файл AllDebrid или TorBox, пришедшие в один и тот же момент, теперь используют один общий поиск ссылки.

Настройки и лимиты описаны в [Persistent caches](../internals/persistent-caches.md).

## Раздачи Usenet теперь проверяются тщательнее, прежде чем получить статус Completed {#usenet-grabs-are-checked-more-closely-before-they-read-completed}

Перед тем как грэб получит статус Completed, zurg проверяет у сервера новостей первые шестнадцать статей и последнюю статью каждого файла с контентом. Раньше проверялась только первая. Из-за этого пропускались пробелы в заголовке медиа. Проверки отправляются одним пакетом на каждый файл, поэтому большие архивы больше не выходят за лимит времени.

Релиз, у которого недостающие статьи полностью восстановлены с помощью PAR2, теперь импортируется. Раньше импорт падал, потому что исходных статей на сервере всё ещё не было. Частичное восстановление по-прежнему не засчитывается.

`sabnzbd.history_limit` теперь может совпадать с большим лимитом истории в Sonarr или Radarr. Большой накопившийся бэклог завершённых задач тогда обрабатывается более крупными пакетами. Оба конца должны использовать одно и то же число. Значение по умолчанию остаётся шестьдесят.

## `enforce` не затрагивает видимые вам функции Plex {#enforce-leaves-the-plex-features-you-can-see-alone}

`plex_settings_policy: enforce` больше не отключает превью при перемотке и миниатюры глав. Также он не отключает выравнивание громкости и sonic-анализ. Каждый из них декодирует целые файлы, а на debrid-маунте это расходует трафик. При этом каждый даёт то, что можно увидеть. Теперь они, как и Skip Intro с Skip Credits, остаются на ваш вкус. zurg по-прежнему показывает, сколько стоит каждый из них. Просто он больше не делает выбор за вас. В группе bandwidth теперь остался только анализ, результат которого никто не видит.

## Просроченные ссылки debrid восстанавливаются без сбоя воспроизведения {#expired-debrid-links-recover-without-failing-playback}

Ссылка TorBox с устаревшим подписанным токеном теперь получает новую. Читатели, которые ждут один и тот же файл, используют один общий запрос. Повторные сбои приостанавливают воспроизведение, но не помечают файл как сломанный.

Когда сервер загрузки TorBox, Real-Debrid или AllDebrid просит zurg подождать, zurg теперь ждёт столько, сколько сервер указал. Он также перестаёт повторять запросы к серверу, который продолжает отказывать. Это касается воспроизведения, проверки ссылок и чтения архивов. Отозванная ссылка, открытая через `__downloads__`, тоже получает новую.

## zurg обновляется сам {#zurg-updates-itself}

`zurg update` заменяет запущенный бинарник самой свежей спонсорской ночной сборкой. Он читает ленту релизов, используя вход через GitHub CLI, если он есть, а иначе `GITHUB_TOKEN` или `GH_TOKEN`. Перед заменой команда проверяет, что загрузка работает, и сообщает ожидаемую версию. Затем бинарник подменяется через переименование, так что обновление не может упасть, пока zurg работает. Сборка, которая уже на самой новой ночной версии или новее её, не трогается. Внутри контейнера команда отказывается работать и советует вместо этого загрузить новый образ, потому что заменённый бинарник там пропадёт при следующем пересоздании; `--force` это обходит. Установщики получили совместимый режим `update` для сборок, которые слишком старые, чтобы понимать эту команду.

По платформам: [Linux](../setup/linux.md#updating-zurg), [macOS](../setup/macos.md#update-zurg), [Windows](../setup/windows.md#updating-zurg), [Docker](../setup/docker.md).

## Одну настройку Plex можно исключить из политики {#one-plex-setting-can-be-opted-out-of-the-policy}

`plex_settings_ignore` перечисляет настройки Plex, которые zurg не трогает, независимо от того, что говорит `plex_settings_policy`. Это для тех, кому одна из них действительно нужна: если библиотека, файлы которой перемещаются между папками, зависит от того, что Plex очищает собственную корзину, чтобы убрать оставшуюся запись, то политика по умолчанию это отключает. А переключение на `warn`, чтобы вернуть эту очистку, отключит и соседние защиты от событий файловой системы.

Игнорируемая настройка всё равно читается и всё равно отображается: на дашборде и как `skip` в `zurg plex-settings`. Её просто никогда не записывают, о ней не предупреждают и за ней не показывают баннер корзины. Игнорировать настройку безопасности можно на свой страх и риск, и zurg говорит об этом один раз при запуске. Если id ничего не называет, zurg сообщает об этом, а настройка остаётся под защитой. Так опечатка не сможет сойти за отказ от защиты.

Настройки и то, что делает с ними каждый уровень политики, описаны в [Plex](../guides/plex.md#recommended-plex-settings).

## Установщики в одну строку для каждой поддерживаемой платформы {#one-line-installers-for-every-supported-host}

Свежие установки теперь можно начать одной строкой для Linux, macOS, Windows и Docker на Linux. Скрипт проверяет или устанавливает нужные для платформы компоненты, использует вход через браузер GitHub для доступа спонсора, скачивает нужную архитектуру и передаёт управление командам `zurg setup` и `zurg doctor`. Существующие бинарники и конфиги сохраняются, а все ручные инструкции остаются доступны.

## Настройка спрашивает, какие провайдеры подключить {#setup-asks-which-providers-to-configure}

Свежие установки `zurg setup` больше не предполагают Real-Debrid по умолчанию. Интерактивный установщик спрашивает одного или нескольких провайдеров в порядке приоритета и запрашивает только учётные данные для выбранных. При неинтерактивной установке можно повторять `--provider` и использовать флаги с файлами токенов для конкретного провайдера или переменные окружения. Существующие конфиги по-прежнему сохраняются, а устаревшие входные данные Real-Debrid — `--token-file`, `TOKEN` и `RD_TOKEN` — остаются совместимыми, если их передать явно.

## Всплеск, превышающий окно истории Sonarr, больше не теряет импорты {#a-burst-larger-than-sonarrs-history-window-no-longer-loses-imports}

Sonarr и Radarr запрашивают у SABnzbd все задачи из очереди, но только шестьдесят самых новых записей из истории. Обычно это хорошо описывает настоящий загрузчик: завершения приходят постепенно, и клиент удаляет каждую задачу после импорта. Библиотека с кэшированными NZB устроена иначе. Массовый поиск сезона может завершить сотни отдельных задач по эпизодам до следующего опроса клиента. Раньше zurg удалял из очереди все такие задачи, а в истории возвращал только шестьдесят. Всё, что выходило за пределы этой страницы, не попадало ни в один из ответов. Поэтому клиент никогда не импортировал и не помечал их как неудачные, и их релиз навсегда оставался в корне `__magic__`.

zurg теперь оставляет завершённые задачи за пределами видимой страницы в очереди. Когда клиент импортирует и удаляет первые шестьдесят, следующие завершённые задачи переходят в историю. Поэтому сезон, добавленный по отдельным эпизодам, уходит пачками ограниченного размера, а не гонкой с окном фиксированного размера. Сезонный пак по-прежнему ведёт себя как одна задача.

## Удаление через монтирование всегда работает, а `dav_allow_delete` удалён {#a-delete-through-the-mount-always-works-and-dav_allow_delete-is-gone}

Удаление файла с медиасервера, который смотрит на маунт, раньше ничего не давало. zurg отклонял WebDAV DELETE с ошибкой 403, rclone превращал это в I/O error, а клиент показывал просто сбой без причины. Plex отвечает обычным `400 Bad Request` и ничего не пишет в лог. Кнопка просто не работала, и никто не говорил почему. Ключ, который это разрешал, `dav_allow_delete`, удалён. Теперь DELETE через маунт работает везде, без всякой настройки. Если в конфиге всё ещё стоит этот ключ, это не ошибка: неизвестные ключи игнорируются. Он просто больше ничего не делает.

Но то, что защищал этот ключ, никуда не делось, поэтому об этом стоит сказать прямо. rclone не умеет выразить «перезаписать». Когда он сохраняет изменённый файл, он делает DELETE, а потом PUT. Значит, программа, которая переписывает файл на месте (например, записчик `.nfo`, проход trickplay, переименование в \*arr или случайный `touch`), удалит релиз из вашего debrid-аккаунта, а не заменит файл. При этом маунт использует собственные учётные данные rclone, так что сверху никто не может отличить это от намеренного удаления. Половина PUT по-прежнему отклоняется, и именно это не даёт последовательности завершиться тихо. Если что-то пишет в ваш маунт, поставьте `mount_read_only: true`. Тогда запись будет отклонена ядром ещё до того, как она дойдёт до zurg.

## Watchlist Plex получает релизы через ваши индексаторы Newznab {#the-plex-watchlist-acquires-through-your-newznab-indexers}

Монитор списка просмотра теперь работает, и работает через ваши собственные индексаторы. Старая версия искала через API-ключ DMM и тихо переставала работать, когда Plex перенёс список просмотра на свой discover-хост: опрашиваемый эндпоинт начал отвечать 404. Теперь он опрашивает правильный хост, и каждый новый элемент списка ищется на Newznab-индексаторах, которые вы уже настроили. Фильм превращается в лучший подходящий релиз. Сериал получается по сезонам, и **сначала предпочитаются season packs**, а не отдельные серии. Если для сезона никто не выложил пак, используются отдельные серии, по лучшему релизу на каждую. Если выбранный релиз не скачивается по своей NZB-ссылке (например, индексатор вернул 429 из-за лимита частоты запросов), монитор переходит к следующему по рейтингу кандидату, и элемент при этом не теряется. Выбранный NZB попадает в Usenet-бэкенд по тем же правилам именования, что и эндпоинт SABnzbd и аддон Stremio, так что все три интерфейса видят загрузки друг друга и не дублируют их. Элемент удаляется из списка только после того, как что-то реально было получено. Раньше порядок был обратным: сначала удаляли, а потом разбирались, и любая ошибка молча стирала элемент из списка.

Настраивается это новым блоком `watchlist:` с ключами `enabled`, `check_every_secs` (по умолчанию 60), `indexers` (если пусто, берутся `stremio.indexers`), `max_size_gb` (по умолчанию 40, для фильмов и отдельных серий), `max_season_size_gb` (по умолчанию 100, для season packs) и `quality` (`best`, `4k`, `1080p`, `720p`, `smallest`). Старые ключи `plex_watchlist_*` работают как раньше. Для монитора достаточно `plex_token`: он обращается к облачному сервису Plex, поэтому работает и на инстансе без `plex_server_url`. Поиск сериалов сначала идёт по TVDB id, и только если ничего не найдено, повторяется один раз по IMDb id. Причина в том, что индексаторы ищут сериалы по TVDB, а их сопоставление IMDb на уровне шоу настолько неполное, что у сильно проиндексированного сериала поиск по imdbid может вернуть ноль результатов.

Все ключи есть на странице конфигурации в разделе **Plex Watchlist** и в [справочнике по конфигурации](config.md#watchlist).

## Аддон Stremio поверх ваших индексаторов Newznab {#a-stremio-addon-over-your-newznab-indexers}

zurg теперь умеет отвечать Stremio напрямую. Включи блок `stremio:`, перечисли свои индексаторы Newznab и вставь в Stremio залогированный URL `/stremio/<token>/manifest.json`. Клиент запрашивает потоки по IMDb id, а zurg ищет по индексаторам (фильмы через `t=movie`, эпизоды через `t=tvsearch` с сезоном и серией). Результаты приходят в виде готовых к воспроизведению потоков, отсортированных сначала по разрешению. Когда ты выбираешь один из них, NZB уходит в бэкенд Usenet по тем же правилам именования, что и эндпоинт SABnzbd, поэтому релиз, добавленный дважды, находится, а не дублируется. Воспроизведение идёт через подписанный эндпоинт `/strm/e/`, включая диапазоны, failover и содержимое архивов. Всё, что ты посмотрел, попадает в библиотеку и появляется в Plex как любой другой релиз.

Токен в пути и есть вся авторизация. Если в конфиге он не задан, zurg сгенерирует его и сохранит в `data/stremio-token`. Результаты поиска кешируются в `data/stremio-cache`, поэтому повторное открытие тайтла не делает запросов к индексаторам. Время жизни кеша зависит от того, сколько нашёл поиск: час на каждый результат, если их до четырёх, а с пяти и больше, `stremio.cache_hours` (по умолчанию 24). Пустой ответ не кешируется никогда. В закешированном списке потоков есть пункт обновления, который очищает кеш для этого тайтла. Релизы крупнее `stremio.max_size_gb` (по умолчанию 40) убираются из списка, чтобы полный ремукс с диска не обгонял все воспроизводимые варианты.

Всё целиком, включая то, сколько стоит первый запуск: [The Stremio addon](../guides/stremio.md).

## Одна папка — это вся установка Docker, и она монтируется при первом запуске {#one-folder-is-the-whole-docker-install-and-it-mounts-on-the-first-run}

Документированный способ запустить zurg в Docker был одной командой `docker run` с `TOKEN` внутри. Она создавала контейнер, который ничего не монтировал. Сгенерированный конфиг оставлял `rclone_enabled` выключенным, а `mount_path` не задавал, поэтому `/zurg_mnt/zurg` оставался пустым, пока кто-нибудь не находил два нужных переключателя в Dashboard. При этом конфиг записывался внутрь контейнера, так что следующий `docker pull` вместе с кешем библиотеки выбрасывал и его. Быстрому старту пришлось добавлять сноску с перечислением обоих пунктов, а это значит, что быстрый старт сам признаёт, что не работает.

Теперь `MOUNT_PATH` при первом запуске, который создаёт конфиг, записывает в него `rclone_enabled: true` и `mount_path`, рядом с тем, что уже записывал `TOKEN`. Рабочая директория образа — `/config`, и всё, что хранит zurg, разрешается относительно неё: `config.yml`, `data/`, `logs/`, `dump/`, `strm/`, `nzbs/` и кеш rclone. Поэтому одного `-v ~/zurg:/config` достаточно, чтобы держать всю установку, и обновление образа ничего из этого не трогает. Первый запуск — это одна команда, и в итоге у тебя примонтированная библиотека, а не поход в Dashboard.

Обе переменные читаются **только когда файла конфига ещё нет**, а после этого игнорируются. Это то же правило, что уже действует у `log_level` с `LOG_LEVEL`, и по той же причине: `MOUNT_PATH`, оставшийся в compose-файле, никогда не должен тихо отменить путь монтирования, изменённый позже в Dashboard. Теперь при старте zurg выводит предупреждение, если переменная задана и расходится с конфигом, так что тот, кто переразвёртывает контейнер и видит, что ничего не меняется, получает объяснение, почему.

Установки, сделанные по старой схеме, не затронуты. Docker создаёт цель каждого bind mount, поэтому наличие `/app/config.yml`, `/app/data` или `/app/logs` означает, что установка в старой схеме, и контейнер продолжает использовать `/app`, если видит любой из них. Полная инструкция по настройке и то, что ломает монтирование, видимое с хоста, описаны в [Docker](../setup/docker.md).

## TorBox и AllDebrid тоже получают `.torrent`, поэтому приватная раздача не зависает {#torbox-and-alldebrid-are-handed-the-torrent-too-so-a-private-grab-is-not-left-hanging}

Файл `.torrent`, который отправляет \*arr, начал передаваться вместе с добавлением в прошлом релизе, но принять его мог только Real-Debrid. Два других аккаунта по-прежнему получали только info hash, а для релиза с приватного трекера это единственный вариант, который они не могут использовать.

Ошибок не было, поэтому проблему было сложно заметить. Проверка на живом аккаунте TorBox показала: хеш без публичного роя принимался, ему выдавался torrent id, а потом он висел в `checking` с `size: -1`, без списка файлов и с оценкой в сто дней. Ровно то же самое описывали и в отчётах о загрузке с TorrentLeech, где «просто зависает, ничего не качается».

Файл того же релиза получал ответ сразу: с настоящим именем, реальным размером и списком файлов, и эндпоинт qBittorrent мог спокойно продолжать работу.

Теперь оба аккаунта принимают файл. И `createtorrent` у TorBox, и `magnet/upload/file` у AllDebrid принимают его вместо магнет-ссылки и отвечают в том же формате, что и при добавлении по магнету, поэтому всё, что идёт после добавления, не меняется. AllDebrid по-прежнему сообщает о самой загрузке, есть ли у него уже этот контент, и это единственный вариант ответа о кэше, который этот аккаунт вообще даёт.

Проверено на живых аккаунтах через собственный путь добавления zurg на обоих сервисах: релиз из кэша загрузился и через несколько секунд вернулся со статусом `done`, 100% и списком файлов. Релиз, которого ни у кого нет, вернулся с именем, размером и статусом stalled из-за отсутствия пиров. Это состояние, с которым эндпоинт может работать, в отличие от хеша, где торрент никогда не определяется и никогда не завершается.

Теперь стал понятен и один вид отказа. Когда TorBox отклонял запрос с кодом 4xx, вызывающая сторона получала голое сообщение общего HTTP-клиента «unexpected status code: 400», потому что тело ответа, где TorBox пишет свой код ошибки и подробности, отбрасывалось в пользу этой ошибки. Поэтому `.torrent`, который TorBox не принимал, для \*arr выглядел как просто номер статуса и ничего больше. Теперь сначала читается тело ответа, и причина от самого аккаунта передаётся вместе с отказом.

Что это значит при настройке индексаторов: [Sonarr и Radarr, торренты](../guides/sonarr-radarr-torrents.md).

## Элементы сжатых архивов передаются потоком и декодируются по требованию {#compressed-archive-entries-stream-decoded-on-demand}

Сжатая запись RAR или deflate-zip не может ответить на ranged read так же, как несжатая: её байты существуют только за декодером, который должен запускаться с начала записи. Поэтому zurg отказывал в них: релиз, где были только сжатые записи, отвечал 415, а сжатые записи рядом с несжатыми пропускались. Для стримера это был честный ответ, но он скрывал основную часть старого каталога Usenet: каждого постера, который упаковывал с компрессией, целиком.

Теперь такие записи отдаются через декодирование вперёд по требованию, в ограниченное окно в памяти. Ничего не пишется на диск, и ничего не декодируется, если чтение этого не запрашивало. Последовательное воспроизведение, которое генерирует плеер, доходит до края окна и немного сдвигает его с каждым чтением. Перемотка назад за пределы того, что окно сохранило, запускает декодирование заново с начала записи. Все байты записи совпадают с тем, что извлёк бы unrar: три jpg-записи реального сжатого тома RAR4 декодируются побайтово идентично тому же тестовому файлу, прочитанному отдельным независимым проходом декодера, md5 в md5.

Обход томов разделённого набора требовал цепочки томов из rardecode, которая открывает `.part02.rar` с файловой системы, а тома zurg живут за ranged сетевыми читателями. Поэтому декодер теперь вендорен в `internal/rardecode` (MIT, upstream v1.1.3) с одним изменением: `OpenReaderOver` принимает opener, так что каждый следующий том берётся из набора по имени, которое выводит сам архив. Листинги меняются соответственно. Релиз, где есть только сжатые записи, показывает свою полезную нагрузку (`stream_compressed_archives: false` возвращает старые отказы), а смешанный архив перечисляет сжатые записи рядом с несжатыми. Версия листинга — 15.

## Sonarr и Radarr могут забирать торренты, а Prowlarr — отправлять их {#sonarr-and-radarr-can-grab-torrents-and-prowlarr-can-push-them}

zurg может отвечать *arr-приложениям так, будто это qBittorrent. Они передают ему magnet-ссылку или `.torrent`, а он добавляет info hash в аккаунт дебрид-сервиса: Real-Debrid, TorBox или AllDebrid, в зависимости от того, что настроено. Когда релиз появляется в библиотеке, торрент получает статус finished и папку в `__magic__`, из которой можно импортировать. Импорт делается тем же переименованием, что и у SABnzbd-эндпоинта для Usenet-граббов: строка в таблице `__magic__`, никакие байты не перемещаются.

Эндпоинт регистрируется по путям `/api/v2` и `/qbittorrent/api/v2`. Он выключен, пока его не включишь, и защищён API-ключом, который клиенты передают как bearer-токен. Грабы предлагаются каждому аккаунту, который принимает торренты, в порядке, заданном в `providers:`. Если граб перестаёт двигаться (нет смены стадии и роста progress в течение `qbittorrent.download_timeout_mins` минут, по умолчанию пятнадцать), он снимается с этого аккаунта и пробуется на следующем. Значение `0` берёт только контент, который аккаунт уже держит в кэше, а остальное отклоняет прямо при добавлении. Именно этот отказ *arr-приложения и обрабатывают. То, что аккаунт делает с загрузкой, переводится в состояния, которые понимают клиенты. Скорость, пиры и оставшееся время показываются там, где их отдаёт аккаунт.

Одно честное ограничение: в API qBittorrent нет способа сообщить, что загрузка провалилась. Поэтому релиз, который ни один аккаунт не взял, попадает в клиент как предупреждение, а не как запись в блоклисте. В очереди видно причину, но без присмотра такой релиз заново не граббится. У SABnzbd-эндпоинта такой проблемы нет.

Prowlarr обращается к тому же эндпоинту как к download-клиенту, но только для того, чтобы вручную отправить релиз в аккаунт. После push из Prowlarr ничего не импортируется, этим занимаются *arr-приложения.

Полное руководство, снятое на живой установке: [Sonarr и Radarr, торренты](../guides/sonarr-radarr-torrents.md).

## `__magic__`, папка, которую можно упорядочить {#__magic__-a-directory-you-can-organise}

Каждый каталог, который отдаёт zurg, — это сохранённый фильтр. Релиз попадает в `movies`, потому что подходит под фильтр movies, и при этом он одновременно лежит в `__all__`, в `recent` и в `movies`. Поэтому в библиотеке никогда не было места, *куда* что-то можно было бы положить. Это не мешало, пока программа не захотела переместить файл. Radarr и Sonarr импортируют перемещением, а маунт, который не может принять перемещение, заставляет их копировать. Тогда каждый импорт тянет весь релиз с дебрид-хоста или из Usenet, а именно этого маунт и должен избегать.

`__magic__` — это новый каталог верхнего уровня. Сначала он является точной копией `__all__`: каждый релиз лежит в виде папки и содержит ровно то, что есть в `__all__/<release>/`, включая содержимое виртуализированного архива. Внутри него можно перемещать что угодно куда угодно. Выполните `mkdir -p /mnt/zurg/__magic__/tv/Show/Season 01` и `mv` серию в эту папку, и серия окажется там: ни байты не переносятся, ни торрент не переименовывается, ничего не скачивается заново, а `__all__` остаётся без изменений. Перемещение переписывает одну строку в небольшой таблице. Эта таблица ключуется по хешу содержимого релиза и по пути самого файла внутри него, поэтому ремонт, который заново добавляет релиз и перестраивает все id вокруг него, не теряет то, куда вы что-то положили. Переименование релиза из дашборда тоже ничего не теряет.

Перемещать можно в обе стороны. Файл можно переместить *внутрь* папки релиза, а также из неё. Папка покажет его рядом с собственными записями релиза. Это нужно программе, которая возвращает что-то в ту папку, из которой импортирует. Если одно имя приходит сразу из двух источников, побеждает осознанный выбор: то, что вы переместили, важнее того, как релиз называет это имя. А оно важнее файла, лежащего в `data/local`. Проигравший не показывается, а не выводится дважды.

Удаление — вторая половина, и по умолчанию оно скрывает, а не уничтожает. `rm` внутри `__magic__` убирает запись из `__magic__`, но оставляет её в `__all__` и во всех фильтр-каталогах. Поэтому клиент, который переорганизует библиотеку, ничего не потеряет. Папка релиза может исчезнуть так же. Именно это позволяет Sonarr удалить папку задачи после импорта, не трогая релиз, из которого он только что импортировал. `magic.allow_delete: true` включает более строгий смысл для файлов: тогда удаляется и содержимое. Папка релиза и каталог всегда только скрываются, какое бы значение ни стояло в этом параметре.

Функция выключена по умолчанию, потому что это записываемое дерево. Если *arr указать не на тот корневой каталог, он может переорганизовать библиотеку:

```yaml
magic:
  enabled: true
  allow_delete: false
  sidecar_max_mb: 32
  sidecar_budget_mb: 2048
```

Два ключа `sidecar_` нужны клиентам, которые монтируют `/dav` напрямую, а не через собственный маунт zurg. Такие клиенты присылают zurg `PUT` нового `.nfo`, постера или дорожки субтитров. Теперь zurg записывает тело в `data/local/__magic__/…`, то есть в то же дерево, куда собственный маунт zurg уже записывает такие файлы. Поэтому два представления показывают одну директорию, а не две. Файл читается с диапазонами, длиной и временем изменения, как любой другой. Ограничения не дают этому незаметно превратиться в общее файловое хранилище. Файл больше `sidecar_max_mb` отклоняется с 413, а файл, который вывел бы дерево за пределы `sidecar_budget_mb`, — с 507. Ничего из того, что отвечает библиотека, нельзя перезаписать: папку релиза, запись внутри неё или путь, на который что-то было перемещено, — всё это даёт 403. Перемещение никогда не уничтожает настоящий файл, чтобы освободить место для строки.

Перед тем как что-то на это направлять, стоит знать две вещи. Фильтр-каталоги намеренно не меняются, поэтому релиз, перемещённый внутрь `__magic__`, всё ещё находится в `recent` и `movies` под своим исходным именем. Направляйте медиасервер на `__magic__` **или** на фильтры, но не на оба сразу. Кроме того, маунт всегда работал в одном направлении записи: всё, что действительно новое и записывается в него (`.nfo`, субтитры, постер), попадает в собственный `data/local` zurg и объединяется с листингом. Поэтому сопутствующие файлы рядом с релизом просто работают, а тест записи в корневой каталог у *arr проходит.

`dav_allow_rename` и `dav_allow_delete` к этому не относятся. Они защищают путь, который переименовывает и удаляет то, что лежит на аккаунте дебрид, а запись в `__magic__` до аккаунта не доходит. `mount_read_only: true` перекрывает всё остальное.

На дашборде есть страница для этого, по адресу `/magic/`. Она показывает все строки таблицы, сгруппированные по релизу. Для каждой видно, что это такое, из какого файла какого релиза она взята и откуда этот файл отдаётся сейчас. Также страница показывает количество строк, объём журнала и снимка на диске и то, сколько из `sidecar_budget_mb` занимают настоящие файлы рядом с библиотекой. Ещё она показывает размер всего `data/local`. Это число говорит, импортирует ли что-то копированием: клиент, который копирует вместо перемещения, кладёт байты именно туда, и больше ничто на дашборде этого бы не показало.

Три состояния, которые показывает страница, нельзя получить из клиента. Размещение можно **сбросить** (reset), и файл возвращается туда, куда его ставит библиотека. Надгробие (tombstone) можно **показать** (unhide), и запись снова выводится в листинге. Строку **dangling**, то есть такую, чей релиз или чей файл внутри него библиотека больше не держит, можно удалить по одной или все сразу. Это новая возможность. Такая строка ни во что не разрешается, поэтому клиент не может ни вывести её, ни переместить, ни удалить. Её намеренно не удаляют, а оставляют, потому что ремонт, который возвращает релиз, возвращает и размещение вместе с ним. До сих пор убрать такие строки было негде. Сопутствующие файлы тоже показываются, и к ним применяется та же классификация. Настоящий файл в папке, которую ничто больше не учитывает, например `.nfo` рядом с релизом, покинувшим библиотеку, или внутри забытого размещения, помечается как **orphaned** и считается отдельно от остальных. Их тоже не подметают, по той же причине, по которой не трогают dangling-строки: файл всё ещё ваш, а ремонт, который вернёт релиз, снова привяжет папку. Удаление такого файла действительно удаляет его, так же как `DELETE` через маунт. Каждая из этих кнопок велит маунту забыть листинги, которые она изменила, потому что маунт кэширует каталог на двенадцать часов при выключенном опросе.

`magic:` и `sabnzbd:` теперь можно редактировать на странице конфигурации. Оба помечены **Restart Required**, и это не формальность: маршруты, которые обслуживают `__magic__`, и эндпоинт SABnzbd определяются один раз, при запуске, именно по этим значениям. Если включить один из них, значение записывается в `config.yml`, но текущий запуск, который уже ответил, не меняется. Страница `__magic__` прямо говорит об этом, а не показывает пустое пространство имён так, будто всё в порядке.

### Sonarr и Radarr теперь могут передать zurg NZB {#sonarr-and-radarr-can-now-hand-zurg-an-nzb}

Причина, по которой существует `__magic__`, в том, чтобы у \*arr было откуда импортировать. Теперь zurg реализует вторую половину: эндпоинт по адресу `/api` отвечает Sonarr и Radarr так, будто это SABnzbd. Укажи им хост и порт zurg, вставь API-ключ, и граб попадёт в `nzbs/` для Usenet-бэкенда. Как только релиз появится в библиотеке, задача получит статус Completed и папку внутри `__magic__`. Импорт — это переименование внутри маунта: одна строка в таблице, ни одного прочитанного байта, ничего не скачивается из Usenet, чтобы положить это в папку сериала.

```yaml
sabnzbd:
  enabled: true
  api_key: ""          # left empty, zurg generates one and logs it once
  categories: [tv, movies]
  complete_dir: ""     # defaults to <mount_path>/__magic__; set it to what a containerised *arr sees
```

Выключено по умолчанию, и для пользы нужны обе части: провайдер `nzb`, чтобы читать NZB, и `magic.enabled`, чтобы было откуда импортировать. Эндпоинт не защищён basic auth zurg, потому что ни один из \*arr никогда не отправляет его клиентам загрузки, а их HTTP-слой воспринимает 401 как «unable to connect». Единственная защита здесь — API-ключ, так что с этим портом обращайся осторожно. Корневые папки должны быть **внутри** `__magic__` (`__magic__/tv`, `__magic__/movies`), никогда не на нём и не выше, иначе у клиентов сработает проверка здоровья корневых папок.

Одну вещь стоит знать до переключения библиотеки: **сигнал о сбое неполный**. Релиз, который есть в библиотеке, но в котором нет ничего пригодного для импорта (все файлы битые, удалённые или отфильтрованные, или там только служебные файлы восстановления и сайдкары, что и выходит, если NZB содержит только recovery-тома), получает статус `Failed`. Именно он заставляет оба клиента занести релиз в чёрный список и взять альтернативу. RAR-набор считается содержимым, потому что zurg стримит видео прямо из него. Исключение: набор, который zurg вообще не может стримить, потому что внутри только сжатые записи. Такой набор получает Failed сразу, как только что-то его открыло и это выяснило. Этот вердикт сохраняется вместе с релизом, потому что его получение стоит чтения каждого тома в наборе.

А вот пост, чьи статьи уже устарели на новостном сервере, не отмечается. zurg пока этого не проверяет, так что мёртвый релиз получает Completed, как и любой другой, и падает при первом чтении. Sonarr видит ошибку импорта, а не ошибку загрузки. Этот случай пока решается вручную.

Всё остальное во flow работает, включая очистку после импорта: папка задачи, которую удаляет Sonarr, становится надгробием, а релиз остаётся в `__all__`.

Граб не ждёт следующего опроса изменений: zurg перечитывает каталог наблюдения, как только в него что-то записано. Так сделано только для Usenet-аккаунтов. Сезонный пак — это двадцать грабов за несколько секунд, а повторно листить библиотеку дебрид-сервиса из десятков тысяч торрентов ради того, чтобы заметить локальный файл, было бы в двадцать раз лишней работой. Если провайдер `nzb` вообще не настроен, zurg теперь сообщает об этом при запуске, а не принимает грабы, которые никто никогда не прочитает.

Страница `__magic__` показывает задачи в режиме только для чтения: `nzo_id`, по которому клиент знает граб, его категорию, время поступления, есть ли релиз уже в библиотеке, а когда есть, то папку, из которой импортирует \*arr.

Полная настройка, включая remote path mapping для \*arr в контейнерах и значение каждой ошибки теста подключения, описана в `docs/sabnzbd.md`.

## Монтирование использует больше доступной пропускной способности {#the-mount-reaches-more-of-the-bandwidth-it-has}

Чтение файла через монтирование rclone было медленнее, чем загрузка тех же байтов по HTTP, и причина была в том, как начинается чтение, а не как оно идёт.

Первый чанк запрашивался размером 4 MB, а дальше размер удваивался. Поэтому чтение, которое начиналось с холодного смещения, большую часть времени шло медленнее, чем соединение реально могло выдать, а каждый seek запускает новое чтение. Теперь первый чанк запрашивается размером 32 MB.

Замеряли на хосте с примерно 70 MB/s реально доступной скорости загрузки. Каждую настройку мерили по очереди, чтобы один медленный отрезок времени не пришёлся только на одну из них. Медианная скорость монтирования на Real-Debrid выросла с 49 до 57 MB/s, у TorBox картина такая же. У AllDebrid выигрыш меньше, потому что его лимит задаётся на соединение, а не на аккаунт.

Весь эффект даёт именно размер чанка. При тестировании мы также подняли FUSE read-ahead, но это ничего не изменило. Дополнительного трафика это тоже не стоит: размер чанка — это сколько *запрашивается*, а не сколько реально передаётся, и rclone перестаёт тянуть данные, как только воспроизведение останавливается. Чтение на 4 MB всё равно подтягивало 6 MB, точно так же, как и при полностью выключенном read-ahead. Поэтому библиотека, которую просматривают и выборочно открывают, а не смотрят от начала до конца, скачивает не больше, чем раньше.

Ничего менять не нужно: новое значение идёт по умолчанию, а `rclone_extra_args` по-прежнему его переопределяет.

## `zurg benchmark-my-setup` показывает, насколько быстра ваша установка на самом деле {#zurg-benchmark-my-setup-answers-how-fast-the-setup-actually-is}

До сих пор, чтобы понять, медленный поток виноват аккаунт, хост или маунт, приходилось только гадать. Новая команда читает реальные байты по тому же пути, которым пользуется плеер, и выводит распределение (min, median, average, max и time to first byte), а не одну цифру, которую мог дать любой неудачный замер.

Запуск идёт в три фазы. Сначала каждый аккаунт отдельно. Это число, которое нужно сравнивать с тем, что обещает сервис. Затем все настроенные аккаунты одновременно. Это единственная фаза, которая может отличить медленного провайдера от забитого канала: если аккаунты по отдельности выдают по 70 MiB/s, а вместе только 25 MiB/s, то это одно узкое место, а не три проблемы, и отчёт говорит, какой из двух случаев перед вами. Потом то же чтение через маунт rclone. Разница с первой фазой и показывает, во что обходятся FUSE и VFS. Фаза с маунтом пропускается, если `rclone_enabled` выключен.

Сэмплы берутся по случайным смещениям, и это важно. Каждый слой внизу что-то кэширует: VFS rclone хранит то, что уже загрузил, а edge-узел CDN дебрид-сервиса хранит то, что уже отдал. Поэтому повторное чтение того же смещения измеряет эти кэши, а не канал. На живой установке один и тот же файл показал 47 MiB/s при первом чтении и 285 MiB/s при втором чтении той же области.

Размер сэмпла меняет смысл цифры с маунта, поэтому отчёт об этом сообщает. rclone открывает файл с `vfs_read_chunk_size` и удваивает размер от этого значения, так что короткий сэмпл большую часть времени ещё разгоняется. На одной установке было 47 MiB/s при сэмпле 256 MiB и 88 MiB/s при 1 GiB, а HTTP в обоих случаях держался около 70. Значение по умолчанию 128 MiB показывает поведение при перемотке и поиске, а `--sample-mb 1024` даёт устойчивый потолок. Ни одна из цифр не ошибочна, и запуск сообщает, какую из них вы только что получили.

`-n` задаёт число итераций, `--provider` ограничивает запуск указанными аккаунтами, `--skip-mount` и `--skip-concurrent` пропускают фазу, а `--json` выводит отчёт для скриптов. Команда тратит реальную пропускную способность ваших собственных аккаунтов: число итераций × размер сэмпла на аккаунт, дважды, плюс фаза с маунтом. Запускайте её из директории zurg. Бэкенд NZB читает папку `nzbs/` относительно рабочей директории, а аккаунт, который ничего не перечисляет, отчёт покажет именно так, а не как аккаунт без больших файлов.

## Рабочие релизы Real-Debrid больше не помечаются как сломанные после проверки ссылки {#working-real-debrid-releases-are-no-longer-marked-broken-after-a-link-check}

Начиная с ночной сборки от 2026-08-20, здоровая библиотека могла заполнить лог строками `Link verification failed during refresh` и `keeping files as broken`. В каждой из них была пара `404 Not Found` и `invalid_download_code` с хоста загрузки. С самими релизами при этом ничего не было не так.

В этой ночной сборке появилась уборка для строк, которые Real-Debrid создаёт в My Downloads: каждая ссылка, которую проверяет zurg, создаёт такую строку. Если её не трогать, список растёт на строку на каждый торрент при каждой холодной сборке, и к старту приходится листать десятки тысяч записей. Уборка удаляет эти строки в фоне, исходя из того, что строка и URL, который она создала, — разные вещи.

На деле это не так. Удаление строки отзывает код загрузки, а поддерживает его только хост, который уже его получил. Замер от 2026-08-22: код, созданный на `124-4` и один раз полученный через `44-4`, на `44-4` всё ещё отвечал `200`, а на `124-4` и на нетронутом `125-4` отвечал `404 invalid_download_code`. zurg выбирает хост загрузки для каждого запроса из нескольких самых быстрых, поэтому хост, который проверил ссылку, редко оказывается тем, который запрашивает её следующей. Результат кэшировался на четыре часа, и все запросы к нему в этом окне возвращали `404`. Это читалось как сломанная ссылка, и релиз помечался как битый.

Теперь результат выпадает из кэша ссылок в тот момент, когда его строка ставится в очередь на удаление, так что ничего не воспроизводит URL, который уходит. Следующий запрос получит свежую ссылку. Строки по-прежнему убираются. Релизы, ошибочно помеченные как битые, восстановятся при следующем обновлении: ничего заново добавлять или сканировать не нужно.

## Сериалы с названием по дате выхода определяются как сериалы, а не фильмы {#shows-named-by-air-date-are-filed-as-shows-not-movies}

Передача без номеров сезона и серии называется по дате выхода в эфир, например `WWE SmackDown 2026-08-21`, и так же называются все ежедневные и ночные шоу. Тест на эпизод ничего об этом соглашении не знал. Он искал `S01E01`, сезон и серию, записанные словами, хеш аниме-релиза, а если ничего из этого не находил, то серию пронумерованных файлов, которую можно было бы принять за последовательность. Ежедневный релиз — это один файл с одной датой, поэтому ответ был «нет», и релиз уходил в первую папку, которая его принимала. В большинстве конфигураций это были фильмы.

Теперь дата выхода в эфир считается маркером. Она может быть записана как `2026-08-21`, `2026.08.21`, `2026 08 21`, `2026_08_21` или `20260821`. Подходят только настоящие даты: месяц должен быть от одного до двенадцати, день от одного до тридцати одного. Поэтому год рядом с разрешением, например `Movie.2026.05.1080p`, никогда не будет принят за дату. На библиотеке из 6755 релизов ни один фильм не поменял папку. На 4734 реальных релизах ежедневных шоу система теперь распознаёт 4633. Остальные — это старые scene-имена, где год сокращён до двух цифр или стоит в конце. Их нельзя надёжно отличить от раскладки аудиоканалов, поэтому пока с ними ничего не делаем.

Библиотека, которая уже лежит на диске, перераспределяется сама при запуске, так что достаточно следующего перезапуска. Ничего пересканировать или заново импортировать не нужно.
