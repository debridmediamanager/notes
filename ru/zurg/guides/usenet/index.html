Usenet с zurg

Стримьте Usenet с zurg: NZB-файлы превращаются в смонтированную библиотеку, которая начинает играть сразу, без предварительной загрузки. Настройка, новостные серверы, кэши и восстановление.

Бэкенд nzb в zurg превращает файлы .nzb в смонтированную библиотеку. Никакого загрузчика или папки с готовыми файлами нет.

Ничего не скачивается заранее, до воспроизведения. zurg хранит NZB-файлы, ограниченные кэши в data/bytecache и data/par2, а также записи индекса. По умолчанию nzb_article_disk_cache_mb равен 512 MiB. При перемотке zurg загружает только те статьи, которые покрывают нужные байты. Ремуксу на 60 GB не нужно 60 GB места на диске.

Usenet использует те же фильтры библиотеки, монтирование и интеграцию с медиасерверами, что и дебрид-бэкенды. Релизы Usenet могут лежать рядом с контентом Real-Debrid или TorBox. Можно использовать только Usenet.

Поддерживается несколько провайдеров Usenet. Одна запись nzb может содержать любое количество новостных аккаунтов — сколько угодно провайдеров, блочных аккаунтов, каких угодно — и zurg переключается между ними статья за статьей. Здесь это важнее, чем обычно важна избыточность: срок хранения задаётся для каждого провайдера отдельно, поэтому второй аккаунт очень часто разница между одним лишним запросом и восстановлением всего релиза из PAR2. См. Несколько провайдеров Usenet.

В этом руководстве рассказывается о новостных аккаунтах, NZB, монтировании и Plex.

Что понадобится

  • Как минимум один аккаунт Usenet-провайдера. Важнее всего retention: провайдер с 4000+ днями хранения ещё будет иметь посты, которые у провайдера на 1000 дней уже удалены. Второе число, которое нужно знать, — это лимит подключений вашего тарифа; именно его читает zurg.
  • Больше аккаунтов, если они есть. Второй безлимитный провайдер на другом backbone или дешёвый блочный аккаунт для пробелов — самое полезное, что можно добавить к настройке Usenet; см. Больше одного Usenet-провайдера.
  • Файлы NZB или что-то, что их загружает. Скачайте их у своего индексатора и положите в nzbs/. Или включите SABnzbd-совместимый эндпоинт и дайте Sonarr и Radarr передавать их самостоятельно. Он записывает в ту же директорию. zurg также может сам искать по вашим Newznab-индексаторам. Это происходит, когда вы нажимаете «воспроизвести» в Stremio. Так же и для запросов из вашего watchlist, а также из Seerr и *arr через acquisition. Для торрентов на debrid-аккаунте есть отдельный эндпоинт, который работает по протоколу qBittorrent.
  • zurg, а также rclone, если вы хотите монтирование файловой системы, а не WebDAV напрямую. zurg сам скачивает rclone при первом запуске.

1. Настройте новостные аккаунты

Каждый аккаунт в zurg — это отдельная запись под ключом providers:. Usenet-аккаунт авторизуется по логину и паролю к серверу, а не по API-токену, поэтому вместо token у него блок nntp:

zurg: v1
providers:
  - type: nzb
    nntp:
      host: news.example.com
      port: 563
      tls: true
      username: YOUR_USENET_USERNAME
      password: YOUR_USENET_PASSWORD
      connections: 30        # your plan's allowance — see below
      cache_size_mb: 512     # decoded articles held in memory, across all files

На этом всё. Если есть дебрид-аккаунты, добавь их рядом:

providers:
  - type: realdebrid
    token: YOUR_RD_API_TOKEN
  - type: nzb
    nntp:
      host: news.example.com
      ...
Ключ По умолчанию Примечания
host (обязательно) Новостной сервер. Если host пустой или его нет, zurg не запустится.
port 563 с TLS, 119 без TLS  
tls false Лучше включить. Незашифрованный NNTP отправляет твой пароль открытым текстом, а всё, что ты читаешь, видно любому, кто стоит на пути соединения.
username / password ""  
connections 8 Поставь здесь реальный лимит твоего тарифа. Это не ограничение скорости, которое можно выставлять «на всякий случай»: одно соединение даёт только часть пропускной способности провайдера, и zurg читает именно с таким количеством соединений. Слишком мало — стриминг будет медленным. Больше лимита тарифа — сервер начнёт отказывать в соединениях.
warm_connections 4 Простаивающие, уже авторизованные соединения, которые держатся открытыми, чтобы чтение никогда не ждало установки нового. Установка занимает около 0,8 с на TCP, TLS, приветствие и AUTHINFO. Без этого минимума такая задержка возникала бы при каждом запуске и после каждого простоя. Эти соединения берутся из connections, а не добавляются поверх него: тариф считает их открытыми соединениями, а zurg поддерживает их живыми с помощью периодического DATE. Поэтому минимум не может превышать лимит. -1 означает, что соединения не держатся; это подходит тарифам, где оплата идёт за время подключения. Верхний уровень warm_connections задаёт значение по умолчанию для аккаунта, где оно не указано, — см. тёплые соединения.
cache_size_mb 512 Декодированные данные статей, которые хранятся в памяти. Кэш общий для всех читаемых файлов, а не отдельный на каждый файл.
servers [] Дополнительные новостные аккаунты — см. Несколько Usenet-провайдеров.

Два правила, которые проверяет валидатор конфига:

  • Только одна включённая запись провайдера nzb. Две записи будут каждая сканировать одну и ту же папку nzbs/ и дублировать каждый релиз. Это не ограничение на количество Usenet-провайдеров: дополнительные новостные аккаунты добавляются в nntp.servers этой единственной записи, где они отдают ту же библиотеку, а не вторую её копию.
  • watchlist: true нельзя указать для неё. Usenet-бэкенд не умеет добавлять контент, поэтому он никогда не может быть аккаунтом, куда попадают добавления из watchlist Plex.

Больше одного провайдера Usenet

Надёжность хранения задаётся для каждого провайдера отдельно. Разница между одним лишним запросом и полной пересборкой релиза по PAR2 зависит от того, есть ли статья ещё у какого-нибудь другого аккаунта. Поэтому второй аккаунт здесь полезнее, чем обычно полезна избыточность.

Ключи, которые уже есть в блоке nntp, описывают первый аккаунт. Всё, что лежит под servers, это другие аккаунты. Аккаунты с одинаковым priority делят нагрузку, а более высокое число опрашивается только после низких. Аккаунт с backup опрашивается только тогда, когда все основные не смогли отдать статью. Существующий конфиг с одним аккаунтом продолжит работать без изменений:

providers:
  - type: nzb
    nntp:
      host: unlimited.example.com          # first account: the workhorse
      tls: true
      username: USERNAME
      password: PASSWORD
      connections: 30
      servers:
        - host: second-unlimited.example.com   # different backbone = different retention
          tls: true
          username: USERNAME
          password: PASSWORD
          connections: 20
          backbone: usenetexpress
        - host: block.example.com              # metered — only for what the others lack
          tls: true
          username: USERNAME
          password: PASSWORD
          connections: 10
          backup: true
          backbone: omicron

У каждого аккаунта своё количество соединений. Чтение идёт в пределах суммарного лимита не-backup аккаунтов с наименьшим живым priority. В примере выше это 30 + 20 = 50, потому что оба аккаунта имеют приоритет по умолчанию. Второй безлимитный провайдер с тем же приоритетом даёт и скорость, и страховку по хранению. Аккаунт с backup не даёт ни того, ни другого, и это сделано намеренно. Он используется только для того, что основные аккаунты не смогли отдать, а если бы его учитывали, окно упреждающего чтения расширилось бы для мощностей, которые при обычном просмотре вообще не нужны, но при этом платятся деньгами за трафик.

Три ключа определяют, кого опрашивать:

Ключ По умолчанию Эффект
name значение host Подписывает аккаунт в логах.
priority 0 Кого опрашивать первым: сначала с меньшим числом. Аккаунты с одинаковым приоритетом опрашиваются в порядке записи, но если у одного есть свободное соединение, а у другого лимит исчерпан, предпочтение отдаётся свободному. Так два одинаковых аккаунта делят нагрузку, а не стоят в очереди на одном.
backup false Помечает платный аккаунт с учётом трафика, к которому обращаются только тогда, когда все основные аккаунты сообщили, что у них нет статьи, прислали повреждённую копию, оборвали передачу на полпути или недоступны. Если основной аккаунт просто занят, этого мало: zurg подождёт его, а не потратит платный трафик на то, что отдал бы безлимитный аккаунт.
backbone "" Указывает, на какой спул статей резолвится аккаунт. Два аккаунта на одном backbone хранят одни и те же статьи, поэтому, как только один сказал, что статьи нет, остальные на этом спуле пропускаются и не тратят время на тот же самый ответ.

Каждый аккаунт также держит собственный прогретый минимум соединений, который берётся из его же лимита. Запрос при разрыве в хранении уходит сразу мимо основного аккаунта, поэтому аккаунт, к которому обращаются впервые, как раз тот, чьё соединение ещё никто не прогревал. Аккаунт с блоком на два соединения можно настроить так, чтобы прогрева не было, через warm_connections: -1.

Перепродажа доступа очень распространена, поэтому имеет смысл заполнять backbone. Два аккаунта, купленных у разных компаний, могут сидеть на одном спуле, и без этого каждый промах запрашивается дважды. Группируйте их любым именем, какое нравится. Строка сравнивается только с другими записями.

При запуске zurg называет каждый аккаунт, который будет использовать:

Usenet account nzb connected: nntps://unlimited.example.com:563 (30 connections) + nntps://second-unlimited.example.com:563 (20 connections) [usenetexpress] + nntps://block.example.com:563 (10 connections) [backup] [omicron]

Перепись, которая решает, нужно ли ремонтировать релиз, спрашивает каждый аккаунт, прежде чем признать статью отсутствующей. Каждый аккаунт спрашивается только о том, чего не хватало предыдущим. Ошибка передачи никогда не принимается за статью, которая устарела. Если аккаунт вышел по таймауту или оборвал статью на полпути, именно эта ошибка и будет показана, поэтому таймаут не приведёт к тому, что тишина будет отдана как контент и для того, что никуда не пропадало, запланируют ремонт. Аккаунт, до которого вообще не удалось достучаться, не учитывается: если другой аккаунт говорит, что статьи нет, её считают пропавшей.

Настройка провайдеров в Dashboard

http://localhost:9999/config/ → Essentials → Providers делает то же самое, но без редактирования YAML. В таблице перечислены все аккаунты в порядке из config:

#  Name        Type        Token                Flags
1  realdebrid  realdebrid  …DFFND4OA            —          [Edit] [Delete]
2  nzb         nzb         news.example.com     —          [Edit] [Delete]

Для строки nzb в столбце Token вместо подсказки токена показывается адрес news server (хост), потому что токена у него нет. Рядом написано, сколько ещё news server'ов есть у этого провайдера.

Чтобы добавить аккаунт Usenet:

  1. Нажми Add provider.
  2. Выбери Type nzb. Поля токенов пропадут, на их месте появятся поля NNTP.
  3. Оставь Name пустым, если хочешь что-то кроме nzb. Это имя папки для аккаунта, так что если указать здесь usenet, в mount появится __usenet__.
  4. Заполни NNTP host, Port, TLS (по умолчанию отмечено, лучше оставить), Username, Password, Connections (подсказка 8; впиши сюда реальный лимит своего тарифа) и Cache size MB (подсказка 512).
  5. Оставь Watchlist target снятым: бэкенд не может добавлять контент, и если отметить этот пункт, сохранение будет отклонено. Disabled оставляет запись в config.yml, но не загружает её.
  6. Нажми Save.

Форма проверяется так, будто изменение уже применено, так что ошибки появятся в виде alert, а не сломают config. Добавить второй провайдер nzb нельзя: форма выдаст ошибку, и в ней будет указано на Further news servers (или nntp.servers). Именно туда добавляются дополнительные аккаунты news.

Чтобы добавить ещё один news server, то есть второй аккаунт или блочный аккаунт на другом backbone, нажми Edit в строке nzb, а затем Add news server в разделе Further news servers. У каждого сервера есть свои Name, NNTP host, Port, TLS, Username, Password, Connections, Priority, Backbone и Backup only. Чтобы убрать сервер, нажми Remove server. Save запишет все серверы в nntp.servers.

Чтобы изменить один из них, нажми Edit в его строке. Форма загрузит все значения, кроме паролей. Пароль первого аккаунта и паролей дополнительных серверов остаётся пустым, и это значит оставить текущий. Введи новый пароль, только если хочешь его поменять. Настройки, для которых в форме нет поля, сохраняются так, как они записаны в config.yml.

Delete запросит подтверждение, а затем удалит запись провайдера из config.yml. Папку nzbs/ он не трогает: NZB-файлы остаются на месте и вернутся вместе с провайдером. Последний включённый провайдер нельзя ни удалить, ни отключить.

Каждое изменение здесь сразу записывается в config.yml и показывает:

Provider changes saved to config.yml — restart zurg to apply

Изменения провайдеров не подхватываются на лету. Перезапусти zurg, прежде чем ждать результата.

2. Запустите zurg и подтвердите аккаунты

./zurg
 
.\zurg.exe

Если zurg setup настроил zurg на автозапуск, перезапустите его командой zurg service restart (./zurg service restart, либо .\zurg.exe service restart в Windows).

zurg проверяет аккаунты новостных серверов один раз при запуске, потому что неверный пароль иначе проявится гораздо позже, когда каждый файл перестанет воспроизводиться:

Usenet account nzb connected: nntps://news.example.com:563 (30 connections)

Полный провал выглядит не менее заметно:

Cannot reach the news server for nzb: <reason>

Сначала проверьте порт и пару TLS (563+tls: true или 119+tls: false), затем учётные данные и то, действительно ли тариф активен.

Если аккаунтов несколько, читайте предупреждения, а не только строку о подключении. Для каждого недоступного аккаунта выводится отдельное предупреждение, и запуск продолжается, пока отвечает хотя бы один аккаунт. Ошибка выше появляется только тогда, когда недоступны все аккаунты. Поэтому мёртвый второй провайдер может выглядеть как нормальный запуск, если не обратить внимание:

Usenet account block.example.com is not reachable: <reason>

3. Добавьте NZB-файлы

zurg создаёт папку наблюдения nzbs/ при запуске. Она находится в папке, из которой запущен zurg. Копируйте туда NZB-файлы.

cp ~/Downloads/Some.Release.2024.2160p.nzb nzbs/
 
Copy-Item "$HOME\Downloads\Some.Release.2024.2160p.nzb" nzbs\

Через секунду-две zurg замечает файл и читает его, а библиотека показывает его сразу после окончания чтения. В логе написано, что именно было прочитано:

Loaded NZB Some.Release.2024.2160p.nzb: 94 files

Как быстро оно появляется

zurg сам следит за nzbs/: проверка идёт примерно раз в секунду и стоит одного системного вызова, сколько бы NZB ни лежало в каталоге. Поэтому файл, попавший туда, читается почти сразу, а не тогда, когда придёт очередная проверка изменений библиотеки. Обфусцированный релиз появляется чуть позже, потому что его настоящие имена файлов сначала нужно прочитать из его же статей. Обычно это занимает меньше секунды, и релиз попадает в список сразу, как только чтение закончено. Ни одна из этих задержек больше не зависит от check_for_changes_every_secs. Раньше зависела: обфусцированный релиз появлялся в списке через два полных интервала после того, как его положили в каталог. Один интервал уходил на чтение каталога, второй на то, что имена разрешались сразу после проверки, которая должна была его заметить. При интервале 10 секунд путь от добавления до появления релиза занимал 17,7 секунды, из них 0,67 секунды приходилось на саму работу.

Периодическая проверка никуда не делась и остаётся страховкой. Она ловит две вещи, которые наблюдаемый каталог сам по себе сообщить не может: NZB, заменённый на месте под уже существующим именем, и файловую систему, где временные метки каталогов слишком грубые, чтобы отличить два изменения, сделанные в одну и ту же секунду.

Что подхватывается

  • Файлы прямо внутри nzbs/, имя которых оканчивается на .nzb (без учёта регистра).
  • Подкаталоги пропускаются. nzbs/movies/foo.nzb невидим. Всё держим в одной папке, а не раскладываем по подпапкам: организация библиотеки задаётся фильтрами директорий, а не этой папкой.
  • Только обычный XML. .nzb.gz не распаковывается и не читается; сначала распакуйте его.
  • Файл, который не удаётся разобрать, пропускается с предупреждением и не останавливает сканирование.

Как называется релиз

Имя, которое показывает zurg, а значит и папка, которую видит Plex, берётся так:

  1. значение <meta type="name"> из самого NZB, если оно есть и переживает очистку, иначе
  2. имя файла без .nzb.

Так что чаще всего имя NZB-файла и есть название релиза. Называйте файл так же, как назвали бы сам релиз, потому что по этому имени ваш медиасервер будет искать совпадение:

# good
nzbs/Some.Movie.2024.2160p.UHD.BluRay.x265-GROUP.nzb

# bad — Plex has nothing to work with
nzbs/indexer_download_48213.nzb

Два разных релиза, которые получили одно и то же имя, различаются коротким хеш-тегом (Some.Release {a1b2c3}), как и везде в zurg.

Релизы с паролем

Если индексатор записал пароль от архива в блок метаданных NZB, zurg использует его при стриминге из RAR-набора:

<head>
  <meta type="password">thepassword</meta>
</head>

Больше ничего не нужно. Защищённый релиз, в NZB которого нет метаданных с паролем, открыть нельзя.

Обфусцированные релизы

Посты со случайными именами файлов тоже обрабатываются, и цена этого платится один раз, во время сканирования. zurg сначала пробует дешёвый источник: имя файла, которое статья всё ещё объявляет в собственном заголовке yEnc (одна статья на файл). Если его нет, используется PAR2-индекс релиза, где записано настоящее имя каждого файла вместе с MD5 его первых 16 KiB. И имя, и точный размер находятся в заголовке статьи, поэтому сканирование может ответить сразу, как только придёт этот заголовок, а тело статьи продолжает загружаться в кэш для последующего чтения. Поэтому обфусцированный релиз получает имя и размер из тех же самых статей. Он записывает в лог то, что восстановил:

Recovered 27 filename(s) in Some.Release

Весь проход по именованию ограничен 90 секундами на каждый NZB, так что недоступный сервер задержит сканирование, но не повесит его. Имена определяются до того, как по ним строится библиотека, потому что библиотека привязывает файлы к именам, и последующее переименование их потеряет.

Полностью обфусцированный пост не содержит настоящего имени, которое можно восстановить. Некоторые постеры обфусцируют файлы до того, как создают набор для восстановления, поэтому PAR2-индекс возвращает имена, которые сами по себе случайны (aJPSgA7eYizyzjJXT.part01.rar), а файл внутри архива тоже представляет собой хэш. Ничто в посте не говорит о том, что это за релиз, это знает только имя самого NZB. Поэтому zurg показывает содержимое под именем релиза, то же самое, что SABnzbd делает в конце распаковки:

Ugliest.House.in.America.S08E02.720p.AMZN.WEB-DL-RAWR/
└── Ugliest.House.in.America.S08E02.720p.AMZN.WEB-DL-RAWR.mkv

Переименовывается только тот файл, который явно является релизом: самая большая запись в архиве и только если она как минимум в три раза больше следующей, её расширение не относится к структуре диска (.vob, .m2ts, .mpls), а имя ничего не говорит. Субтитры и сэмплы с тем же именем следуют за ним. Архив, в котором несколько файлов примерно одинакового размера (например, сезонный пак), не трогается, потому что ни один из них не является релизом. Собственные имена архива продолжают работать как адреса, так что плеер, запущенный до пересканирования, не потеряет файл.

Замена и удаление

  • Удаление NZB из nzbs/ убирает релиз из библиотеки, сбрасывает его кэшированный reader и кэш статей и забывает все восстановленные байты, которые он держал.
  • Удаление релиза Usenet из Dashboard удаляет файл .nzb с диска. Другого места, где он может храниться, нет. Это не то же самое, что удаление торрента из аккаунта debrid, где файл остаётся у сервиса.
  • Замена NZB на месте — медленный способ. Перезапись файла не меняет директорию, поэтому наблюдатель выше этого не увидит. Это замечает периодическая проверка изменений: она читает время модификации файла и заново разбирает его — до первой проверки check_for_changes_every_secs, которая наступит более чем через 15 секунд после последнего чтения директории (около 30 секунд по умолчанию). Удаление старого файла и добавление нового замечаются в течение секунды-двух, и именно так и работает индексатор или эндпоинт SABnzbd.

4. Где релизы появляются в маунте

Релиз из Usenet — это обычная запись в библиотеке, поэтому существующие фильтры directories: применяются к нему без изменений:

directories:
  shows:
    group: media
    group_order: 20
    filters:
      - has_episodes: true
  movies:
    group: media
    group_order: 30
    only_show_the_biggest_file: true
    filters:
      - any_file_inside_not_regex: /\.(mp3|flac|m4b)$/i

Помимо них, у аккаунта появляется собственная директория: по умолчанию __nzb__, или __<name>__, если ты задал name: в записи провайдера. Эта директория — не просто представление: чтение из неё закреплено за аккаунтом Usenet без переключения на другой провайдер, поэтому именно здесь удобно проверить, что воспроизведение из Usenet работает и его не подменяет тихо дебрид-аккаунт. Если Usenet у тебя единственный аккаунт, эта папка не выводится в корневом списке монтирования, а __all__ содержит те же файлы. Тогда проверяй воспроизведение в __all__ на монтировании или открой прямой HTTP-путь http://localhost:9999/http/__nzb__/.

При написании фильтров нужно знать четыре вещи, специфичные для Usenet:

  • Фильтры по тегам работают с содержимым Usenet только после анализа. Каждый тег zurg_* (разрешение, HDR, битрейт, длительность, язык) берётся из ffprobe. zurg сам запускает ffprobe для файлов из Usenet, через свой сервер и в темпе, который выдерживает новостной сервер, так что релиз из Usenet получает теги, как и любой другой, после анализа. До этого директория, построенная на tags_match_any, его не содержит.
  • Файлы .par2 и .sfv скрыты. Это служебные файлы для восстановления; zurg читает их сам, а медиасерверу они ни к чему, особенно когда в сезонном паке их по восемь штук. .nfo оставлен, потому что Kodi, Emby и Jellyfin его читают.
  • RAR-наборы — это содержимое, а не архивы для распаковки. .rar и .rNN остаются видимыми, а набор томов появляется в монтировании как папка, внутри которой лежат файлы из архива. zurg стримит видео прямо из архива, ничего не распаковывая. Если релиз состоит только из одного набора томов, он заменяет собой своё содержимое: полезная нагрузка лежит прямо в папке релиза, без промежуточной папки архива, и именно там медиасервер её ищет. Файлы, опубликованные рядом с набором (.nfo, .txt от постера, арт, субтитры), тоже остаются в списке.
  • force_select_playable_files не применяется. Пост в Usenet цельный, выбирать там нечего. Все файлы с содержимым уже доступны.

Сначала посмотри результат, и только потом подключай медиасервер. http://localhost:9999/http/ — это простой HTML-индекс того, что покажет монтирование:

curl -s http://localhost:9999/http/__nzb__/ | head

Вводи curl.exe, а не curl: в Windows PowerShell 5.1 curl — это другое имя для Invoke-WebRequest.

curl.exe -s http://localhost:9999/http/__nzb__/ | Select-Object -First 10

5. Смонтируйте через rclone

Простой путь: пусть zurg запускает rclone

rclone_enabled: true
rclone_binary: bin/rclone      # downloaded automatically on first run
mount_path: "/mnt/zurg"        # /Volumes/Zurg on macOS, Z: on Windows

zurg запускает rclone с профилем VFS, уже настроенным под свой способ чтения (размер буфера, размер чанков, режим кэша, время кэша директорий, таймауты), поддерживает монтирование в рабочем состоянии и сбрасывает нужные записи dircache, когда библиотека меняется. mount_path также служит префиксом, по которому zurg сообщает Plex, какие пути сканировать, поэтому его нужно задать, даже если вы монтируете в другое место.

Проверьте:

ls /mnt/zurg/
ls /mnt/zurg/__all__/
 
ls /Volumes/Zurg/
ls /Volumes/Zurg/__all__/

Запускайте в окне PowerShell на рабочем столе: диск виден только в сеансе входа, в котором он был смонтирован (правила сеанса).

Get-ChildItem Z:\
Get-ChildItem Z:\__all__\

Ручной путь: свой rclone

Если ты уже работаешь с rclone, укажи WebDAV-remote на zurg:

[zurg]
type = webdav
url = http://localhost:9999/dav/
vendor = other
pacer_min_sleep = 0

rclone не создаёт точку монтирования, а /mnt принадлежит root:

sudo mkdir -p /mnt/zurg && sudo chown "$USER" /mnt/zurg
rclone mount zurg: /mnt/zurg --config rclone.conf --dir-cache-time 10s --vfs-handle-caching 0

Нужны macFUSE и rclone с rclone.org: rclone из Homebrew не умеет монтировать. rclone не создаёт точку монтирования, а /Volumes принадлежит root:

sudo mkdir -p /Volumes/Zurg && sudo chown "$USER" /Volumes/Zurg
rclone mount zurg: /Volumes/Zurg --config rclone.conf --dir-cache-time 10s --vfs-handle-caching 0

Нужен WinFsp. Буква диска не должна быть занята, и диск видят только программы в том сеансе входа в систему, где запущен rclone (правила сеанса).

rclone mount zurg: Z: --config rclone.conf --dir-cache-time 10s --vfs-handle-caching 0

--vfs-handle-caching 0 требует rclone 1.74 или новее и не даёт rclone продолжать загрузку ещё пять секунд после того, как читатель закроет файл. В README написано, чем грозит пропуск этого флага.

Всё равно укажи mount_path в config.yml там, куда смонтировал, иначе уведомления о сканировании медиасервера будут собираться с неправильным префиксом.

Docker

Рабочая директория zurg в образе — /config, и директория для наблюдения и кэш для ремонта лежат внутри неё. Одно bind mount пробрасывает всё это вместе с остальным:

services:
  zurg:
    image: ghcr.io/debridmediamanager/zurg:latest
    volumes:
      - ./:/config
    ports:
      - 9999:9999

После этого можно положить NZB в ./nzbs на хосте, и контейнер подхватит его без перезапуска.

Для этого монтирования нужен Linux-хост. Docker Desktop на macOS и Windows запускает контейнер внутри виртуальной машины, и монтирование не доходит до Finder, Explorer или Plex, установленного на хосте. Там используйте бинарник для macOS или Windows (почему).

Установки, сделанные до того, как /config стал bind-монтировать /app/config.yml, /app/nzbs и /app/data отдельно, продолжают работать точно так же, как работали. См. docker.md.

6. Подключите Plex

  1. Укажите zurg свои учётные данные Plex, чтобы он мог попросить Plex сканировать только изменившиеся пути, а не ждать периодического полного сканирования. Проще всего сделать это через авторизацию Plex в Dashboard, которая записывает значения обратно в config.yml:

    plex_server_url: "http://localhost:32400"
plex_token: YOUR_PLEX_TOKEN

  2. Добавьте библиотеки, указывающие на подкаталоги маунта, но никогда не на корень маунта:

    • Фильмы → /mnt/zurg/movies (/Volumes/Zurg/movies на macOS, Z:\movies на Windows)
    • Сериалы → /mnt/zurg/shows (/Volumes/Zurg/shows на macOS, Z:\shows на Windows)

    На Windows Plex видит Z: только тогда, когда работает в той же сессии входа, что и zurg. Этого добивается задача входа, которую создаёт zurg setup: см. правила сессии.

    Один и тот же релиз появляется в каждом каталоге, фильтр которого ему подходит, а также в __all__ и __nzb__. Если указать Plex на корень, он просканирует один и тот же файл несколько раз.

  3. Снимите две галочки в настройках библиотеки в разделе Edit → Advanced:

    • Снимите "Empty trash automatically after every scan". Это самое важное. Если маунт моргнёт во время сканирования Plex (перезапуск zurg, перемонтирование rclone), Plex решит, что все файлы удалены. Если автоочистка включена, они будут удалены навсегда и сразу. Если выключена, они останутся в корзине и вернутся, когда маунт восстановится. Однажды это стоило библиотеки на 30 000 элементов.
    • Снимите "Generate video preview thumbnails". Каждая миниатюра — это перемотка по всему файлу. Для Usenet это полное чтение релиза через ваш лимит трафика.

  4. Никогда не перезапускайте zurg во время сканирования Plex. Сначала проверьте:

    TOKEN=$(grep ^plex_token: config.yml | awk '{print $2}' | tr -d "\"'")
curl -s "http://localhost:32400/status/sessions?X-Plex-Token=$TOKEN" | grep -o 'size="[0-9]*"'
curl -s "http://localhost:32400/library/sections?X-Plex-Token=$TOKEN" | grep -o 'refreshing="1"' | wc -l

    В Windows, в PowerShell из папки zurg:

    $TOKEN = ((Select-String -Path config.yml -Pattern '^plex_token:').Line -split '\s+')[1].Trim('"', "'")
(Invoke-RestMethod "http://localhost:32400/status/sessions?X-Plex-Token=$TOKEN").MediaContainer.size
@((Invoke-RestMethod "http://localhost:32400/library/sections?X-Plex-Token=$TOKEN").MediaContainer.Directory | Where-Object refreshing -eq 1).Count

    Сессии с size="0" (0 в Windows) и обновляемый счётчик 0 означают, что перезапуск безопасен. Если строка с сессиями вообще ничего не выводит, Plex отклонил токен или не ответил, и 0 под ней ничего не значит: проверьте plex_token перед перезапуском. (PowerShell показывает отказ как ошибку 401.) (Используйте grep -o … | wc -l, а не grep -c: grep завершается с ненулевым кодом, когда ничего не находит, а это как раз хороший случай. Такой код прервёт цепочку && прямо перед перезапуском, который она должна была защитить.)

  5. Частичные сканирования. on_library_update получает каждый изменившийся путь. plex_update.sh в корне репозитория — эталонный скрипт:

    on_library_update: sh plex_update.sh "$@"

    Скрипту нужны curl, xmllint и python3, которые есть в Docker-образе, а строка zurg_mount должна указывать на ваш путь маунта. В Windows хук запускается в PowerShell, а не в sh, поэтому этот скрипт там не работает. Каждый изменившийся путь приходит как отдельный элемент $args, относительно маунта и с прямыми слешами (movies/Big Buck Bunny). Передайте их PowerShell-скрипту через @args:

    on_library_update: '& C:\zurg\my_update.ps1 @args'

    zurg уже просит Plex сканировать изменившиеся пути, как только выполнен шаг 1 и задан mount_path. Поэтому хук нужен только для всего остального.

Чего Plex не получит от контента Usenet: ничего, пока zurg его не проанализирует (см. раздел 4). Поэтому Plex может провести собственный анализ при первом воспроизведении, как и для любого локального файла. Размеры файлов устаканиваются вскоре после сканирования релиза. В первом списке может быть грубая оценка по количеству статей, а точная длина появляется следом: из индекса восстановления, если он есть, а иначе по одной статье на файл. Для большого многотомного архива, у которого индекс восстановления уже указывает точную длину каждого файла, один проверенный том может установить общий шаг статей. Каждый соседний том проверяет это предположение по собственному заголовку, прежде чем отдать первый байт. Как только длина установлена, библиотеке сообщают, что релиз изменился, и маунт, и Plex видят реальную длину. zurg обрабатывает до восьми релизов одновременно (но не больше, чем соединений у аккаунта) на аккаунте с двенадцатью соединениями или меньше, и больше на более крупном: двенадцать при 16 соединениях, шестнадцать от 20. Когда получение проверяет релиз по новостным серверам, эта проверка ставится в очередь рядом с этим расчётом и опережающим чтением. Она никогда не забирает соединение, которое держится для чтения, на которое ждёт плеер.

Jellyfin / Emby / Infuse

Jellyfin и Emby принимают jellyfin_server_url / jellyfin_token и emby_server_url / emby_token и получают одинаковые уведомления о сканировании; см. jellyfin.md. Infuse можно подключить напрямую по адресу http://<host>:9999/dav/ и вообще обойтись без rclone.

7. Когда статьи не хватает

Это та проблема, которая есть у Usenet и которой нет у debrid. Статьи устаревают и выпадают из хранилища провайдера или удаляются, и релиз может быть в списке как ни в чём не бывало, хотя несколько его статей уже пропали.

Ответ zurg, по порядку предпочтения:

  1. Спросить другой новостной сервер. Статья, которую устарел один провайдер, очень часто ещё есть у другого. Это один запрос, см. Несколько провайдеров Usenet.
  2. Восстановить её из PAR2-файлов самого релиза. Для этого PAR2-файлы и публикуются. Это требует чтения всего релиза: Reed-Solomon должен сложить каждый уцелевший слайс, чтобы вычислить недостающий. Поэтому для раздачи на 200 ГБ нужно прочитать 200 ГБ, чтобы восстановить несколько мегабайт.
  3. Отдать тишину. Только тогда, когда ни один из способов выше не может помочь.

Восстановление PAR2 работает в фоне, одновременно не больше двух релизов, и ему нужно:

enable_repair: true            # the default; set false to turn PAR2 repair off
par2_patch_cache_mb: 512       # budget for data/par2/; -1 keeps repairs in memory only

Восстановленные байты записываются в data/par2/<nzb-id>/ и подхватываются при следующем открытии файла, поэтому перезапуск не заставляет заново читать весь релиз. Сохраняются только те участки, которые действительно пропали: повреждённый релиз обычно стоит считаных мегабайт. Когда бюджет превышен, целые релизы удаляются по принципу «давно не использовался — первым на выход» (least-recently-used). Каждый участок релиза помечен временем изменения NZB, из которого он был восстановлен. Поэтому если NZB сохранили заново, участки сбрасываются и не отдаются байты по смещениям, которые могли сдвинуться.

Восстановление сообщает о себе и потом пишет, сколько оно стоило:

PAR2 repair of Some.Release: 5 slice(s) missing; reading the release to rebuild them
PAR2 repair of Some.Release rebuilt 5 slice(s) in 55s on the avx2 kernel, keeping 3.4 MiB of them (library holds 3.4 MiB in memory, 3.4 MiB on disk)

Два момента, которые стоит знать:

  • Воспроизведение всегда важнее восстановления. Соединения выдаются тем, кто ждёт: сначала запрос на чтение по требованию, затем упреждающее чтение, восстановление — последним. Но восстановлению гарантирована четверть лимита относительно упреждающего чтения, поэтому воспроизводимый файл всё равно может восстановить участок, на котором застрял.
  • Восстановление на уровне библиотеки в zurg здесь не поможет. Этот механизм заново добавляет торрент в тот аккаунт, откуда он пришёл. Бэкенд, который не может добавлять контент, может сообщить, что релиз сломан, но не починить его. Для Usenet ремонтом как раз и является PAR2.

У релиза без PAR2-файлов в NZB и без второго новостного аккаунта вообще нет пути восстановления. Это свойство самой публикации, а не zurg.

Производительность

   
Один поток, прямой файл ~100 Mbit/s
Один поток, из набора RAR 90–106 Mbit/s
Два параллельных потока, суммарно ~124 Mbit/s

Первый потолок для скорости одного потока задаёт лимит соединений аккаунта. zurg держит этот лимит загруженным, подбирая упреждающее чтение и по статьям, и по байтам: для архивных постов с маленькими статьями оно составляет не меньше 64 MiB, а для постов с крупными статьями (по несколько мегабайт) сохраняется то окно из соединений и конвейера, которое там и было. Поэтому:

  • Укажите в connections реальное число соединений вашего тарифа. Это главный регулятор. Восемь соединений не потянут remux.
  • Два основных аккаунта складываются. Чтение идёт на суммарный лимит всех аккаунтов без backup, которые делят самый низкий активный priority. Поэтому второй безлимитный провайдер с тем же приоритетом поднимает потолок и одновременно покрывает пробелы в хранении первого. Аккаунт с backup в этот лимит не входит.
  • warm_connections (по умолчанию 4) даёт задержку, а не пропускную способность. Он держит указанное число соединений открытыми, простаивающими и уже авторизованными. Поэтому первое чтение после запуска или затишья не тратит около 0.8 s на набор номера перед первым байтом: 1.5 s до первого байта на холодном старте против 0.15 s на прогретом. Когда поток уже идёт, эта настройка ничего не меняет.
  • Наборы соединений, которые всё-таки происходят, привязаны к одному бэкенду, поэтому TLS-сессии возобновляются. Один набор стоит около 0.8 s. Измерено на живом новостном сервере 2026-08-29: 106 ms TCP, 213 ms TLS-рукопожатие, 256 ms приветствие, 218 ms на два обмена AUTHINFO. Имя провайдера указывает на ротацию (это имя резолвится в 11 адресов), а TLS session ticket действует только на той машине, которая его выдала. Поэтому при повторном наборе на адрес, который первым назвал резолвер, возобновилось 0 из 3 сессий, а при повторном наборе на тот же адрес возобновилось 3 из 3. Теперь каждый аккаунт при повторном наборе подключается к адресу, с которого был его последний коннект. Это экономит 110–140 ms на каждом повторном наборе: возобновлённое рукопожатие занимает 109–141 ms против 225–261 ms у полного. У сервера с задержкой около 18 ms выигрыш меньше. Привязка снимается, и имя резолвится заново, как только этот адрес перестаёт отвечать, так что соединение не застревает на машине, которую провайдер уже вывел из работы. Отказ, дошедший до NNTP (аккаунт упёрся в лимит соединений или пароль отклонён), привязку сохраняет, потому что это ответ самого аккаунта, а не бэкенда. Каждый набор пишет свои фазы на уровне debug, включая resumed=.
  • cache_size_mb (по умолчанию 512) общий для всех читаемых файлов. Увеличьте его, если запускаете несколько параллельных потоков. На скорость одного потока он не влияет. Спекулятивные чтения могут занять не больше половины кэша и не больше чем у двух читателей, а вторая половина остаётся для статей, которые уже прочитаны или будут прочитаны прямо сейчас.
  • То, упакован ли релиз в RAR или выложен отдельными файлами, теперь почти не влияет на скорость.

Одна медленная статья больше не останавливает поток. Последовательное чтение, которое в среднем идёт на ~90 MB/s, всё равно иногда проседает до 1–5 MB/s примерно на секунду. Причина каждого такого провала одна: статья перестаёт приходить, пока остальные соединения доканчивают свои статьи и простаивают. Если чтение застряло на одной статье дольше, чем читатель привык ждать, zurg просит второе соединение отдать ту же статью и использует тот ответ, который придёт первым. Застрявший конвейер может заблокировать несколько подряд идущих статей на одном мёртвом сокете, поэтому от одного читателя может одновременно хеджироваться до пяти разных статей, а на посте, где статьи меньше 1 MiB, — одна или две. Одну и ту же статью дважды не запрашивают никогда. Аккаунт оплачивает не больше 20 вторых запросов в минуту. Дедлайн равен удвоенному недавнему ожиданию самого читателя, но не меньше 250 ms (125 ms для постов со статьями меньше 1 MiB) и не больше 2 s. Хеджируется только то чтение, которого реально ждёт клиент: упреждающее чтение, предзагрузка следующего тома и восстановление — нет. Статью, которую серверы только что отказали, тоже не хеджируют: через секунду на неё и так придёт подтверждение, а запрос внутри этого окна ничего не докажет. Каждый хедж пишет одну строку на уровне debug с временем, которое чтение заблокировало, а следующая строка говорит, выиграл ли второй запрос.

Для заявленных диапазонов статья с позицией воспроизведения попадает в планировщик приоритетов раньше, чем предлагаются более поздние байты. Конвейерные соединения получают не непрерывные куски, а последовательные раунды статей, поэтому первые полезные статьи распределяются по всему лимиту соединений. Запрос размером не меньше 64 MiB считается воспроизведением и получает полный фронт диапазона. Короткий seek остаётся пробой и открывает только узкий разгон.

Переход через границу тома

Файл внутри RAR-набора отдаётся по одному тому за раз, и каждый том — это отдельное чтение с news-аккаунта. zurg открывает следующий том, пока текущий ещё проигрывается, и читает его первые четыре мегабайта, поэтому переход не начинается с нуля. Но для релиза с мелкими томами одного этого начала мало: четыре мегабайта — это около десяти статей у релиза с частями примерно по ~395 KB, а тома по ~26 MB дают границу каждые 1.7 секунды воспроизведения. Поэтому поток съедал прогретое начало из памяти за четверть секунды, а потом ждал круговую задержку на всё, что шло дальше. Замер на Hetzner CCX23 через десять соединений 8 сентября 2026 года показал, что этот релиз стримился со скоростью 14–16 MB/s, тогда как обычный файл на том же аккаунте выдавал 86–99 MB/s. Скорость за секунду при этом прыгала от 1 до 29 MB/s, а из 60 слотов предварительного чтения аккаунта простаивали от 46 до 55.

Теперь zurg прогревает следующий том на всю глубину окна предварительного чтения, как только поток подходит к границе ближе чем на 32 MiB. А том, в который поток только что перешёл, сохраняет окно, которое уже заработал, и не начинает заново с двух статей. Том, до которого точка воспроизведения доберётся не раньше чем через несколько секунд, по-прежнему прогревается только до своего начала. Так сканирование библиотеки (по читателю на каждую запись, по нескольку мегабайт с каждой) не тянет окно из каждого следующего тома, который всё равно никто не будет читать. Ничего настраивать не нужно, и потолок памяти не меняется: у аккаунта по-прежнему два окна предварительного чтения одновременно, том, который проигрывается, и тот, который прогревается, в пределах cache_size_mb.

Починка релиза идёт медленно по своей природе, ведь она читает весь релиз целиком. Но работает она с фоновым приоритетом, и ограничивает её news-сервер, а не арифметика самого zurg.

Память: сколько стоит каталог для отслеживания

NZB — это список статей, а большая библиотека — это очень много статей. При разборе сохраняются message id и их смещения в памяти, чтобы чтение могло их найти. Предыдущие сборки держали все они в памяти на всё время работы процесса. По замеру на каталоге наблюдения из 2,636 NZB, в котором 27.6 миллиона элементов <segment>, это 1.52 GB живой кучи, примерно по 58 байт на статью, помимо кеша статей. Почти вся эта память не используется: при листинге нужны только имена, размеры и количество, а списки статей нужны только тогда, когда файл реально читают или восстанавливают.

nzb_segments решает, будет ли zurg их хранить:

nzb_segments: mmap             # mmap (default) | reparse | resident
nzb_segments_idle_secs: 120    # how long a release's articles are kept after the last read
  • mmap — списки записываются в data/nzb-index/<id>.bin, и этот файл отображается в память по требованию. Байты лежат в page cache, а не в куче zurg, и ядро освобождает их при нехватке памяти. Значение по умолчанию на Linux, macOS и BSD. Занимает примерно столько же места на диске, сколько сами списки.
  • reparse — списки освобождаются, когда релиз устаканился, а NZB заново читается с диска, когда нужны чтение или восстановление. Место на диске не занимает, поэтому этот режим и стоит выбрать: подходит для хоста, где data/ не должен расти.
  • resident — все списки статей всегда в памяти. Прежнее поведение, как в каждой предыдущей сборке. Поддерживается, но больше не является значением по умолчанию.

Какой бы режим ни был выбран, листинг никогда не загружает ничего. Имя файла, размер и количество статей отдаются без того, чтобы список статей оказывался в памяти, поэтому обновление библиотеки, проверка отпечатков и запросы *arr о том, устаканилась ли задача, остаются бесплатными. Ленивые режимы платят за первое чтение релиза, к которому никто не обращался дольше nzb_segments_idle_secs (проход выполняется каждые 30 секунд). При этом все файлы релиза загружаются разом: если пройти по rar-томам сезонного пака по порядку, платить придётся один раз.

Замеры на релизе из 60 файлов и 30 000 сегментов:

  куча на релиз первое чтение простаивающего релиза на статью на пути чтения
resident 1.74 MB — 6 ns
reparse 21.3 kB 39 ms 52 ns
mmap 16.6 kB 0.27 ms 63 ns

Пятьдесят наносекунд на статью — ничто по сравнению с миллисекундами, которые уходят на получение одной статьи, поэтому цифры пути чтения значат меньше, чем кажутся. Важнее перезагрузка. reparse заново читает и разбирает весь XML-документ, и на сезонном паке это десятки миллисекунд до того, как сдвинется первый байт. mmap — это вызов mmap, заголовок среза на каждый файл и контрольная сумма только что отображённого индекса: 0.08 ms из трёх, а остальные 0.19 ms — цена за то, что испорченный байт обнаруживается, а не отдаётся как message id.

А вот замеры на всей библиотеке, а не на одном релизе: 2,636 NZB, 27.6 миллиона статей, одна и та же сборка запущена три раза на одном корпусе, в простое после сканирования:

resident 2,921 MB 2,677 MB 23 % 806 ms —
reparse 1,188 MB 987 MB 31 % 1,018 ms —

Тёплые открытия (1 ms), пропускная способность потоковой передачи (38–39 MB/s) и время запуска у всех трёх режимов не отличались. mmap открывает холодный релиз быстрее, чем держит всё в памяти, потому что релиз, которого в этом запуске не открывали, при resident тоже нужно разобрать. А отобразить уже записанный архив — это системный вызов, тогда как разбор занимает мегабайты XML.

Индекс сам перезаписывается при каждом изменении NZB, сам чинится, если его не удаётся прочитать (тогда берётся NZB и индекс записывается заново), и удаляется, когда NZB покидает каталог наблюдения. И заголовок, и содержимое индекса защищены контрольными суммами, поэтому испорченный байт обнаруживается, а не отдаётся как message id, которого никто не публиковал. Текущий размер индекса показан на главной странице Dashboard, в разделе Article Index, и в строке, которую бэкенд пишет в лог при запуске. В Windows отображения в память нет: индекс пришлось бы читать в кучу, а это занятая память плюс перезагрузка. Поэтому по умолчанию там остаётся resident, а из ленивых стоит выбирать reparse.

Запрос по одной статье

GET /debug/nzb/probe отправляет один запрос к новостным аккаунтам через пул, который zurg уже использует, с приоритетом, который получает demand read. Он нужен потому, что альтернатива не работала: у аккаунта восемь соединений, а zurg занимает их все, поэтому проверить пост вручную можно было только через второй аккаунт или остановив сервер, а остановка сервера уничтожает состояние, которое нужно диагностировать. В Windows вводи curl.exe вместо curl в этих командах.

# Is this article still there? A STAT, so nothing is transferred.
curl -u user:pass 'http://localhost:9999/debug/nzb/probe?message_id=abc@news.example'

# The same question addressed the way you have it: a release id from the
# library, a file index counting from zero, an article number counting from one.
curl -u user:pass 'http://localhost:9999/debug/nzb/probe?release=<nzb id>&file=0&article=3'

# &body=1 fetches the one article and reports what actually arrived against what
# the article says should have. This is how a provider that strips trailing
# bytes is identified: `short: true` with `decoded_bytes` below `span_bytes`.

Он отвечает {"probes": [...]} с одним объектом для провайдера nzb: found, missing и время выполнения. Аккаунты опрашиваются по приоритету, пока один из них не найдёт статью (резервный аккаунт спрашивается, только если основные не нашли её). Не сообщается, какой новостной аккаунт держал статью. Проба только читает: всё, что она загружает, не попадает в кэш статей, а статья, которую она не нашла, не записывается как мёртвая, поэтому проба не может заглушить файл, который воспроизводится.
