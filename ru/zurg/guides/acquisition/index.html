Источники загрузки

Список «Посмотреть позже» в Plex, ваш список желаемого DMM, Seerr, Radarr и Sonarr используют один движок загрузки. Он отслеживает прогресс, повторные попытки и подтверждения. Результаты Newznab превращаются в NZB для бэкенда Usenet у zurg. Результаты Torznab превращаются в info hash для debrid-аккаунта. См. Newznab и Torznab.

Движок подтверждает загрузку только после проверки. NZB должен дойти до сервера новостей. На аккаунте torbox_nzb вместо этого файл должен загрузить TorBox. Торрент должен появиться в библиотеке с файлами. См. Проверка загрузки.

Релиз, который захватил zurg, сохраняет id тайтла, для которого его взяли, все те, по которым Plex сопоставляет тайтлы: IMDb, TMDB и, для сериала, TVDB. Его больше не определяют заново по имени. Эти id заменяют любые id, которые DMM или имя релиза ему дали, but никогда не тот, который вы задали вручную. Релиз, который уже был в вашей библиотеке, когда zurg его выбрал, мог быть добавлен для чего-то другого, поэтому он получает эти id только если у него нет id или уже такой же. Если задан rex_url, захваченный фильм отправляется в rex как этот фильм, по этим id, даже если DMM не смог его разместить; эпизоды сериала по-прежнему нумеруются по размещению DMM и получают id сериала. При запуске zurg делает то же самое для каждого релиза, который его сохранённые задачи захватили раньше, что исправляет релизы, потерявшие id до этого изменения.

Конфигурация

acquisition:
  quality: best
  prefer: usenet          # usenet (default), torrents, or best
  best_first: false       # true makes Radarr and Sonarr take the profile's best quality first
  max_size_gb: 0          # a cap on a film or episode, and each episode of a season pack; 0, the default, is none
  max_season_size_gb: 0   # a cap on each season a pack holds; 0, the default, is none
  exclude_words: [DV, HDR10+]  # never take a release whose name says these
  prefer_words: [FraMeSToR]    # take a release whose name says these first, within its resolution
  audio_languages: [original]  # take only releases with this audio (any one), read from the streams
  subtitle_languages: [en]     # and with these subtitles
  concurrency: 8          # titles worked on at once (default 8, at most 200)
  indexer_concurrency: 3  # calls to one indexer at once (default 3, at most 16)
  indexers:
    - name: my-indexer
      url: https://indexer.example
      api_key: YOUR_INDEXER_API_KEY
      # type: newznab      # default, a Usenet indexer
    - name: my-trackers
      url: https://prowlarr.example
      api_key: YOUR_PROWLARR_API_KEY
      type: torznab        # a torrent indexer, handed to a debrid account
    - name: zilean
      url: http://zilean:8181/torznab
      type: torznab        # no api_key: Zilean takes none, and is asked without one
  sources:
    - name: plex-watchlist
      type: plex_watchlist
      enabled: true
      check_every_secs: 60
      remove_after_grab: true   # default; false keeps the watchlist intact
      only_new_items: true      # default; false works through the existing list
    - name: requests
      type: seerr
      enabled: true
      url: http://seerr:5055
      api_key: YOUR_SEERR_API_KEY
      check_every_secs: 60
    - name: movies
      type: radarr
      enabled: true
      url: http://radarr:7878
      api_key: YOUR_RADARR_API_KEY
      library_path: /mnt/zurg/__magic__   # where Radarr sees __magic__; leave out if it sees zurg's own mount
      check_every_secs: 60
    - name: shows
      type: sonarr
      enabled: true
      url: http://sonarr:8989
      api_key: YOUR_SONARR_API_KEY
      library_path: /mnt/zurg/__magic__   # where Sonarr sees __magic__; leave out if it sees zurg's own mount
      check_every_secs: 60

Запускай это на экземпляре zurg с провайдером nzb или аккаунтом torbox_nzb (TorBox Pro), с дебрид-аккаунтом, который принимает торренты, или с обоими. NZB из индексаторов Newznab попадают в его директорию nzbs/. У аккаунта torbox_nzb нет новостных серверов для проверки; загрузка там проверяется по тому, получил ли её TorBox. Торренты из индексаторов Torznab отправляются на дебрид-аккаунт. Они добавляются только тогда, когда этот аккаунт уже имеет их в кэше. Если нет ни одного из этих аккаунтов, источники не запускаются. На странице acquisition написано почему. Plex нужен существующий plex_token. Seerr нужны его базовый URL и API-ключ, независимо от любых настроек Plex в zurg. Поддерживаются подпути URL и URL, оканчивающиеся на /api/v1. Radarr нужны его базовый URL (базовый путь вроде /radarr и завершающий /api/v3 тоже подходят), его API-ключ из Settings > General и library_path, если он видит монтирование zurg по другому пути: см. поведение Radarr. Sonarr использует те же три настройки: см. поведение Sonarr.

Оба значения читаются при запуске zurg, как и остальной блок. indexer_concurrency ограничивает поиски и загрузки NZB вместе, потому что индексатор считает запросы по ключу, а не по эндпоинту. Ключи индексаторов часто используются совместно, и три вызова на ключ — это значение, которое на практике оказалось безопасным для ключей, которые также обслуживают другое приложение.

Не меняй имена и URL Seerr: по ним определяются сохранённые очереди. Смена ключа Seerr сохраняет его очередь. Перезапускай после добавления источников или смены их URL или учётных данных. Существующие настройки watchlist: и plex_watchlist_enabled продолжают работать через автоматический адаптер plex-watchlist. Явно заданный источник plex_watchlist имеет приоритет над старым переключателем включения, даже если он выключен. Только один источник Plex может использовать настроенный аккаунт Plex. Общие настройки поиска берутся из watchlist: и его существующих значений по умолчанию; если индексаторы не указаны, используются индексаторы watchlist/Stremio.

Исключение релизов по имени

acquisition:
  exclude_words: [DV, HDR10+]

exclude_words перечисляет слова, которых не должно быть в названии ни одного найденного релиза. Используйте его, чтобы не пропускать Dolby Vision или HDR10+ на плеер, который их не показывает, но при этом брать 4K. Он действует на все источники одинаково: список Plex, Seerr, Radarr и Sonarr. Он действует и на результаты Usenet, и на результаты торрентов. Релиз, который он исключает, никогда не скачивается, не сохраняется, не добавляется в аккаунт debrid и не передаётся в Radarr или Sonarr. Если его не указывать, ничего не исключается. zurg читает его при запуске, как и остальные параметры из config.yml.

Предпочтение релизов по имени

acquisition:
  prefer_words: [FraMeSToR, CiNEPHiLES]

prefer_words — это список слов, например названий релиз-групп, которые ставят релиз первым среди релизов того же разрешения. Он работает так же, как exclude_words: совпадение по целым словам, без учёта регистра. Список задаёт порядок: релиз с первым словом идёт раньше релиза со вторым и так далее. Это предпочтение, а не фильтр. Если ни у одного релиза нет ни одного из слов, zurg берёт то, что взял бы без них.

Предпочитаемый релиз никогда не выходит за пределы своего разрешения. При quality: best релиз 2160p от любой группы всё равно идёт раньше предпочитаемого 1080p, а при quality: 1080p предпочитаемый 2160p не выходит вперёд релизов 1080p. Апгрейд на более высокое разрешение всё равно происходит, если у предпочитаемой группы нет релиза в этом разрешении.

Параметр работает для всех источников и для результатов Usenet и торрентов. Для источника radarr или sonarr профиль всё равно должен принимать предпочитаемый релиз. Когда Radarr или Sonarr используют zurg как клиент загрузки, они сами выбирают релиз, и prefer_words там не применяется. Если параметр не указан, ничего не предпочитается.

Релиз фильма также никогда не берётся, если в его названии указан год, который отличается от года фильма больше чем на один, независимо от источника. Индексаторы иногда относят раздачи к чужому фильму по IMDb id: DrunkenSlug записывает The Aswang Chronicles (2012) под его сиквел 2014 года. Название без года из-за этого не отклоняется. Для списка желаемого в DMM, который отправляет все известные названия фильма (оригинальное, альтернативные и переводы), тоже отклоняется релиз, в названии которого ни одно из них не встречается целиком: DrunkenSlug записывает Przesluchanie (1982) под An Affair (1982), а Rocky.2015 — это не Rocky Horror Show Live. Название может обрываться там, где начинается подзаголовок, после двоеточия или пробельного тире, поэтому Diana.2021 — это Diana: The Musical. Акценты и умлауты совпадают в любом написании, так что Les.Miserables и Verwuenscht.nochmal подходят.

Как сравнивается название:

  • Только целые слова. Название разбивается на слова из букв и цифр. Точки, пробелы, дефисы, подчёркивания, квадратные и круглые скобки — всё это разделители слов. Регистр не важен. DV исключает Avengers.Infinity.War.2018.DV.2160p.WEB.H265-RVKD и Mortal_Kombat_II_2026_COMPLETE_BLURAY_2160p_DV_HDR_TrueHD. Он не исключает DVDRip, DVD9, Come and See DvD 1 или название вроде Adventures, потому что ни в одном из них нет слова DV.
  • Фразы совпадают по порядку. Dolby Vision или DV HDR совпадают, когда эти слова стоят рядом в таком порядке, чем бы они ни были разделены.
  • Знак + в конце входит в слово. HDR10+ — отдельное слово. Исключение HDR10 не трогает релизы HDR10+, а исключение HDR10+ не трогает обычный HDR10. Чтобы исключить оба, перечислите оба. + между двумя словами их разделяет, как в DD+7.1 или DV+HDR10.

  • Два семейства написаний считаются одним словом. Любое написание из списка исключает все написания своего семейства.

    Напишите любое из Исключает названия с любым из
    DV, DoVi, Dolby Vision, DolbyVision DV, DoVi, Dolby.Vision, Dolby-Vision, Dolby Vision, DolbyVision
    HDR10+, HDR10Plus HDR10+, HDR10Plus

    Больше ничего не приравнивается. HDR исключает названия со словом HDR и не исключает HDR10, HDR10+ или HDRip. WEB-DL совпадает с WEB-DL, WEB.DL и WEB DL, но не с WEBDL.

  • Читается только название релиза. Это название, которое индексатор отдаёт до того, как что-либо скачано. Файлы внутри не читаются. Релиз Dolby Vision, в названии которого об этом не сказано, не исключается.

Исключение слова никак не влияет на разрешение. При исключённом DV релиз 2160p с обычным HDR или HDR10 всё равно берётся, а quality: 4k по-прежнему ставит 2160p первым. Исключённый релиз считается ненайденным. Поиск фильма или серии продолжает листать страницы каждого индексатора, пока не наберётся десять релизов, которые можно взять, пока у индексатора не закончатся страницы или не будут прочитаны десять страниц. Поиск сезона читает одну страницу и отдельно ищет каждую серию, которой на ней не нашлось. Название, у которого все релизы исключены, завершается с ошибкой "no eligible releases" точно так же, как название, у которого все релизы больше max_size_gb, и пробуется снова позже. Запрос 4K из Seerr берёт только релизы 2160p, поэтому он ждёт, пока все релизы 2160p не будут исключены.

Исключения и профили Radarr или Sonarr

Для источника radarr или sonarr исключение проверяется первым. Исключённый релиз никогда не передаётся парсеру Radarr или Sonarr. Никакой балл пользовательского формата его не вернёт, и отказом профиля он не считается. Все остальные релизы оцениваются профилем, как описано в разделах Radarr behavior и Sonarr behavior. Релиз должен пройти обе проверки. Пользовательский формат, который ставит Dolby Vision ниже минимума профиля, делает то же самое внутри *arr, и если его оставить, ничего плохого не будет.

Обновления работают по тому же правилу. Если единственные релизы, которые могли бы поднять файл до cutoff профиля, исключены, файл остаётся ниже cutoff, и проход обновлений zurg продолжает искать, ничего не забирая. Так бывает, когда пользовательский формат даёт Dolby Vision высокий балл, а cutoff без него не достигается. Тогда снизьте балл cutoff или уберите этот балл из пользовательского формата.

Когда Radarr или Sonarr используют zurg как клиент загрузки через блок sabnzbd: или qbittorrent:, они сами ищут по своим индексаторам и сами выбирают релиз. exclude_words там не действует. Исключите те же слова в *arr: через пользовательский формат с баллом ниже минимума профиля или через Must Not Contain в профиле релизов.

Выбор по языку аудио и субтитров

acquisition:
  audio_languages: [original]   # or [de], [de, en], ...
  subtitle_languages: [en]

audio_languages берёт только релизы с аудиодорожкой на одном из перечисленных языков, а subtitle_languages только релизы с субтитрами на одном из них. Если убрать любой из них, ничего не фильтруется. Оба работают для каждого источника.

Каждый список также задаёт порядок: торрент с более ранним языком идёт выше того, где есть только более поздний. [de, original] возьмёт немецкий дубляж, если он есть, а если его нет, оригинальный язык.

zurg определяет язык по потокам внутри релиза, а не по его названию. Большинство релизов не пишут языки в названии: у Parasite почти ни один релиз не содержит KOREAN. Пишите коды ISO 639, из двух или трёх букв: en, eng, de, deu и ger все работают. Такое название, как german, zurg отклонит при запуске.

У некоторых языков дубляжи или субтитры отличаются, и код может указать на конкретный вариант:

Пишите Для чего
es-419, es-ES Латиноамериканский (латино) или кастильский испанский
pt-BR, pt-PT Бразильский или европейский португальский
fr-CA, fr-FR Квебекский (VFQ) или французский из Франции (VFF, VFI)
nl-BE Фламандский
yue, cmn Кантонский или мандаринский
zh-Hant, zh-Hans Субтитры на традиционном или упрощённом китайском (zh-TW и zh-HK читаются как традиционный, zh-CN как упрощённый; для кантонского аудио пишите yue)
nb, nn Норвежский букмол или нюношк

Код без уточнения берёт все варианты: es подходит и латино, и кастильскому, zh кантонскому и мандаринскому, no и букмолу, и нюношку. Если после языка стоит часть, которую zurg не понимает, например es-latam, zurg отклонит её при запуске. Какой именно вариант у дорожки, zurg определяет по её названию, потому что в самих потоках это никогда не записано так, чтобы zurg мог это прочитать: "Latino", "Spanish (Latin American)", "Castellano", "French (Canada)", "VFQ", "Portuguese (Brazilian)", "Chinese (Cantonese)", "繁体中字". Дорожка, в названии которой ничего такого нет, никогда не отклоняется из-за этого. Если в названии релиза есть подсказка, она решает спор, например Dual-Lat, [Castellano], MULTi.VFQ, VF2, PT-BR или [ES-LA]. Название релиза никогда ничего не отклоняет, а название дорожки важнее его. Для [es-419, es] zurg берёт по порядку: дорожку с названием Latino, безымянную дорожку в релизе с названием Latino, безымянную дорожку, безымянную дорожку в релизе с названием Castellano и дорожку с названием Castellano. Для латиноамериканской семьи это может выглядеть так:

acquisition:
  audio_languages: [es-419, es]  # Latino first, then Castilian
  subtitle_languages: [es]
  audio_or_subtitles: true       # or any audio with Spanish subtitles

audio_or_subtitles: true берёт релиз, у которого есть либо аудио, либо субтитры, а не оба сразу. Релиз с аудио идёт выше релиза, где есть только субтитры.

original означает язык, на котором был снят фильм, как его записывает TMDB: корейский для Parasite, французский для Anatomy of a Fall. zurg запрашивает это у DMM, поэтому нужен dmm_api_key. Без ключа original ничего не фильтрует.

Как оценивается релиз

  • До добавления торрента. DMM хранит данные ffprobe по каждому релизу, который zurg уже проанализировал. Если задан dmm_api_key, zurg получает их для каждого торрент-результата одним запросом. Торрент, в потоках которого нет нужного языка, не добавляется никогда. Тот, где он есть, идёт вперёд торрентов, о которых ничего не известно. При замере пяти фильмов 2026-10-25 DMM имел эти данные примерно для трети торрентов, которые Real-Debrid закешировал.
  • После загрузки. Каждая загрузка, торрент или Usenet, проверяется через ffprobe, как только попадает в библиотеку: если у DMM есть её данные, используются они. Загрузка, в потоках которой нет нужного языка, откладывается, как мёртвый пост. Её удаляют из аккаунта дебрид-сервиса или из watch directory, и сразу пробуется следующий кандидат. В дашборде написано, почему, например: "it has no English audio, only French".
  • Обновление сохраняет языки. Когда список желаемого в DMM обновляет фильм до более высокого разрешения, новый релиз должен содержать языки, которые в твоих списках стоят не ниже, чем в копии, которую он заменяет. Копию Latino 1080p не меняют на кастильскую 2160p.
  • Неизвестное пропускается. Релиз никогда не отклоняют за то, что нельзя прочитать. Сюда входят дорожки без метки, дорожка с меткой und или mul, релиз, до которого добрались только через архивы, и случай, когда проверка не уложилась в минуту. zurg записывает в лог, что взял релиз как есть.

Дорожки с комментариями и аудиоописанием не считаются аудио фильма, а субтитры с комментариями не считаются его субтитрами. Это касается и комментария, названного только в заголовке, например "Commentary by Bong Joon Ho" у Parasite. Дорожки субтитров с заголовком forced (forzados, forcés), signs или songs не считаются субтитрами. Один только флаг forced не исключает дорожку: в ремуксах иностранных фильмов полные английские субтитры часто помечают как forced, чтобы плееры их показывали.

Судят только основные видеофайлы релиза, то есть те, что длиной не меньше пятой части самого длинного. В дополнениях часто меньше озвучек, чем у фильма. В сезонном паке нужный язык должен быть в каждой серии.

Релиз, отложенный из-за языка, остаётся отложенным на 30 дней, как и мёртвый пост, даже если ты поменял языки.

Список желаемого DMM

Спонсор DMM добавляет фильмы и сериалы в список желаемого кнопкой Want на своих страницах на debridmediamanager.com, а список выводится по адресу /wanted. zurg читает этот список, как только задан dmm_api_key, и больше ничего настраивать не нужно. Ничего не монтируется, Sonarr и Radarr не участвуют. Источник называется dmm-wanted и опрашивается каждые 60 секунд.

  • Что загружается. Фильм один раз, а потом любое его улучшение (см. ниже), либо копию в каждом из нескольких разрешений, если quality задан списком (см. ниже). Из сериала загружаются вышедшие серии в запрошенных сезонах, а если запрошен весь сериал, то во всех сезонах, плюс новые серии по мере выхода. DMM присылает для каждого тайтла его IMDb, TMDB и TVDB id, год, а для сериала вышедшие на данный момент серии с нумерацией TMDB. Спешлы никогда не загружаются. Сезон, который ещё выходит, загружается поштучными сериями, потому что паков для него пока нет.
  • Когда ищется. Фильм начинают искать, как только он выходит на домашних носителях: DMM присылает день его самого раннего цифрового, физического или ТВ-релиза, если TMDB его знает. zurg ждёт не дольше этого дня, затем ищет каждые две минуты в течение шести часов и каждые десять минут до двух дней после релиза, так же как для новой серии. Дата кинотеатрального показа никогда не используется, потому что WEB-DL появляется вместе с цифровым релизом. Самая новая серия сериала датируется так же, по часу выхода, если DMM его знает. Тайтл без даты получает обычные повторные попытки, не реже раза в неделю, и ни один элемент списка никогда не откладывается. Фильм, который ждёт следующей попытки, ищется на следующем опросе, если DMM увидит новый пост в Usenet с его названием.
  • Куда попадает. Так же, как из любого другого источника: NZB из Newznab-индексатора в Usenet-бэкенд этого экземпляра или торрент из Torznab-индексатора на дебрид-аккаунт, где он уже есть в кэше, в зависимости от того, что стоит первым в prefer. Применяются quality, max_size_gb (для сезонного пака, в пересчёте на серию), exclude_words и языки, а также max_season_size_gb, если вы его задали.
  • Индексаторы. Если в acquisition:, watchlist: или stremio: не указан ни один индексатор, ключ ищет также у DMM: его Usenet-индексатор и торренты, которые, по его данным, есть в кэше Real-Debrid или AllDebrid (/api/torznab/cached). Если указать любой индексатор, оба этих варианта заменяются.
  • Подтверждение. Как только проверка грабa пройдена, zurg сообщает DMM об этом, и фильм уходит из списка, который читает zurg, если только он не ждёт улучшения или другой своей копии (см. ниже). Когда это произошло, видно на /wanted. Сериал остаётся в списке и продолжает отслеживаться, пока вы сами его не удалите там. Удаление тайтла останавливает работу над ним.
  • Улучшения. Фильм, в названии релиза которого указано разрешение ниже того, к которому стремится quality (2160p для best и 4k, 1080p для 1080p, 720p для 720p), остаётся в списке. Когда выходит релиз с более высоким разрешением, чем у копии, которая есть у вас, zurg его загружает, пока не получит нужный. Как только лучшая копия проходит проверку, старая удаляется, если её загрузил zurg, начиная с ночного запуска 2026-10-30: торрент из аккаунта, в который zurg его добавил, или NZB из каталога наблюдения. Копия, которая уже была вашей, сохраняется, как и копия, часть которой попала в __magic__, например при импорте Radarr. Релиз, в названии которого не указано разрешение, никогда не улучшается, а при quality: smallest ничего не улучшается. Пока не появится лучший релиз, фильм ищется примерно раз в неделю и никогда не откладывается. Функция включена по умолчанию, отключить её можно через upgrades: false в блоке acquisition:.
  • Копия в каждом из нескольких разрешений. Если quality задан списком, например [1080p, 4k], для каждого фильма хранится копия в каждом указанном разрешении. См. копия в каждом из нескольких разрешений.
  • Без аккаунта для загрузки. Экземпляр без провайдера nzb, без аккаунта torbox_nzb (TorBox Pro) и без дебрид-аккаунта, который принимает торренты, список не читает.

Два zurg на одном ключе загружают каждый тайтл. Оба читают один и тот же список, поэтому включите список только на одном из них, а на остальных отключите, записав его как disabled:

acquisition:
  sources:
    - name: dmm-wanted
      type: dmm
      enabled: false

Истёкшая подписка или сброшенный ключ останавливают список. zurg пишет предупреждение о том, что DMM отклонил dmm_api_key, и повторяет запрос через час или сразу, когда вы зададите новый ключ. То, что уже было загружено, остаётся в вашей библиотеке.

Копия для каждого из нескольких разрешений

Запишите quality списком, чтобы хранить копию каждого фильма из списка желаемого в каждом перечисленном разрешении. Например, чтобы телевизор 1080p воспроизводил фильм без перекодирования файла 4K:

acquisition:
  quality: [1080p, 4k]

Каждая копия берёт лучший релиз с разрешением не выше своего и никогда не берёт релиз выше. Копия 1080p не берёт релиз 2160p и релиз, в названии которого не указано разрешение, потому что это может быть что угодно. Копия 4K берёт такой релиз, только если нельзя взять ни одного релиза с указанным разрешением, и тогда оставляет его навсегда, так как релиз без указанного разрешения никогда не улучшается. Каждая копия улучшается сама по себе, до своего разрешения. Если обе копии взяли бы один и тот же релиз, они используют одну копию, и она удаляется, только когда ни одна из них её больше не держит:

Вышедшие релизы Копия 1080p Копия 4K В вашей библиотеке
720p 720p тот же 720p 720p
+ 1080p улучшается до 1080p улучшается до 1080p 1080p
+ 2160p остаётся улучшается до 2160p 1080p и 2160p

Фильм, который вышел только в 2160p, сразу получает копию 4K, а копию 1080p — когда появляется релиз в 1080p или ниже. До этого его ищут примерно раз в неделю, и он никогда не откладывается. Фильм уходит из списка, который читает zurg, только когда каждая копия держит релиз, лучше которого она не ищет.

  • Что принимает список. Два или больше значений из 4k (или 2160p), 1080p и 720p, каждое один раз, в любом порядке и любом регистре. zurg не запускается с чем-либо другим и выдаёт acquisition.quality lists resolutions, each once: 4k, 1080p or 720p. Список из одного элемента читается как это значение, поэтому [1080p] — это quality: 1080p и хранит одну копию. Для 4K пишите 4k, так как [2160p] отклоняется.
  • Только в блоке acquisition:. quality в watchlist: — одно значение, и список там не даёт zurg запуститься. Настройка качества на странице конфигурации меняет только watchlist.quality и ничего не меняет, пока записан acquisition.quality.
  • Только фильмы из списка желаемого DMM. Сериалы из него и все остальные источники всё равно получают одну копию, выбранную так, будто quality называет только самое высокое перечисленное разрешение: [1080p, 4k] для них работает как quality: 4k, а [720p, 1080p] как quality: 1080p, который всё равно берёт релиз 2160p, если релиза 1080p ещё нет.
  • С upgrades: false каждая копия хранит первый взятый релиз. Пока вышел только 720p, обе копии навсегда остаются этим 720p.
  • Фильмы, загруженные до того, как вы записали список, загружаются снова, по копии на каждое разрешение. Копия, у которой лучший релиз уже есть в вашей библиотеке, использует его как есть. zurg никогда не удаляет копию, загруженную раньше: удалите её сами, если новые копии её заменят.
  • Возврат к одному значению оставляет копии на месте.
  • /wanted показывает фильм как загруженный, как только есть его первая копия, с первым релизом, который взял zurg. Он не показывает, какое разрешение ещё ждёт. Фильм, загруженный до того, как вы записали список, может продолжать показывать "waiting for" с тем разрешением, которое ждал тогда.

Просмотр фильма с YouTube

Many wanted films no indexer carries are on YouTube, uploaded whole by the studio that made them. With acquisition.youtube set, zurg streams such a film from that upload instead of leaving it unfetched. Nothing is downloaded.

acquisition:
  youtube:
    cookies: /home/you/zurg/youtube-cookies.txt   # required: a signed-in account's cookies (Netscape format)
    # ytdlp_binary: yt-dlp                        # default; the standalone build
    # js_runtime: node                            # default; yt-dlp needs one to read YouTube's player
    # channels: [UC1D36wr10qyCfisHulZ5G8Q]       # the channel ids uploads are taken from
    # searches_per_hour: 20                       # default; films looked for on YouTube in an hour

  • When. Only for a film on the DMM wanted list, and only when nothing the indexers return can be taken: no release passes quality, max_size_gb, exclude_words and the title and year checks, or every one was found gone, with every indexer answering. Never for a show or an upgrade, nor with audio_languages or subtitle_languages set, since an upload's languages cannot be read. Only the wanted list takes a stream: a film the Plex watchlist also wants is not settled for it by one, since Plex cannot play it, and the watchlist keeps looking for a release.

  • How often. At most searches_per_hour films are looked for in an hour (20 by default: 1,820 films take four days), one at a time. A film YouTube has nothing for is asked about again a day later, restarts included.

  • Which upload. zurg searches YouTube for the title and year, and for the original title when DMM sends one, and takes an upload only when all of these hold: it is on one of channels; it runs at least 90% of the film's runtime, or an hour when DMM does not know the runtime; its title begins with the film's title ('Separada' FULL MOVIE | ...), states no other year, and is no trailer, teaser, clip or Part N. Of those it takes the longest, then the most watched, and checks that YouTube streams it with picture and sound together.

  • Channels. The default list is the Philippine studios' own channels: ABS-CBN Star Cinema, Regal Entertainment, VIVA Films, SOLAR WATCH NOW, OctoArts Films, CineMo and Cinema One. Of 100 random unfetched films on one wanted list (2026-10-31), 65 had a full-length upload and 33 were on these channels; the rest were re-uploads (every Disney one) and, for new releases, scams titled "full movie". Writing channels replaces the list. A channel's id is the UC... part of its address, or what yt-dlp --print channel_id <a video's page> prints.

  • What you get. The film is named Title.Year.1080p.YouTube.WEB-DL and DMM is told it was fetched (youtube:<video id>). rex gets it as an HLS item in your movies library, read through zurg. Jellyfin and Kodi get __magic__/__movies__/Title (Year) {tmdb-N}/Title (Year) {tmdb-N}.strm, with __magic__ on. The address in the .strm is zurg's own, from base_url, and needs no login. Either address is the stream's playlist served by zurg, every segment in it an address on zurg too, which zurg fetches from YouTube itself. zurg resolves the stream with yt-dlp and keeps it until an hour before it expires. A segment's address is good for a day; a player that comes back later reads the playlist again.

  • Upgrades. A streamed film stays on the wanted list while upgrades is on, and any release of it that comes out replaces the stream, whatever its resolution: the stream, its .strm and its rex item go once the release has passed its check.

Limits:

  • Plex cannot play it. It is no file on the mount. Use rex, Jellyfin or Kodi.

  • Cookies are required. Without a signed-in account's cookies YouTube offers an address that fetches much only video and audio apart, or nothing, so zurg starts with the fallback off and says why. Export them from a browser signed in to YouTube, ideally on the same network. Signing out in that browser ends them.

  • Every byte passes through zurg. Nothing is redirected to YouTube: rex sends its source's login with every request its transcoder makes, redirected ones included, and YouTube ties a stream to the address that resolved it. So any player that reaches zurg plays it, and zurg carries the film's traffic.

Поведение Seerr

Адаптер следует маршрутам запросов, определениям статусов и контракту API из seerr-team/seerr.

  • Опрашивает все страницы одобренных запросов, используя X-Api-Key. Если страница не загрузилась, сохраняется предыдущая очередь, а работа с этим источником приостанавливается.
  • Перепроверяет одобрение перед загрузкой. Запросы в статусе pending, declined, failed, completed, removed и уже доступные не запускают загрузку.
  • Определяет ID через Seerr. Загрузка сериалов ограничена одобренными запрошенными сезонами и их известными вышедшими эпизодами. Неполный сезон остаётся в статусе pending.
  • Обрабатывает 4K и не-4K отдельно. Релиз 1080p не может закрыть запрос в 4K.
  • Перепроверяет открытые запросы каждые 30 минут после успешной загрузки, чтобы найти новые вышедшие эпизоды в запрошенных сезонах. Эпизоды, о выходе которых не объявлено, становятся задачей только тогда, когда появляются в метаданных Seerr.
  • Предпочитает паки, когда вышли все известные эпизоды. Сезоны, которые ещё выходят, используют отдельные эпизоды. Спецвыпуски (сезон 0) не поддерживаются. Запрос с одобренным сезоном 0 вообще не загружается и завершается с ошибкой, пока его не отложат (parked).
  • Не делает записей статуса запроса и доступности. Сканирование медиасервера в Seerr показывает реальную доступность и уведомляет тех, кто сделал запрос. Сохранение NZB не доказывает, что он проиндексирован или воспроизводим, поэтому движок проверяет его, прежде чем считать сезон загруженным.

Настройте сканирование библиотеки в Seerr так, чтобы в него входила библиотека, которую отдаёт этот экземпляр. Если Sonarr/Radarr уже загружают те же запросы, отключите этот пересекающийся процесс, прежде чем включать адаптер. Адаптер не эмулирует сервер *arr и не меняет настройку сервисов Seerr. Опрос обеспечивает восстановление после перезапуска, webhook не нужен.

Поведение Radarr

Radarr ведёт список и владеет библиотекой. zurg занимается поиском и загрузкой. Radarr никогда не ищет и ничего не забирает сам: zurg читает, чего хочет Radarr, выбирает релиз из своих индексаторов, проверяет его через новостные серверы (получение через TorBox на аккаунте torbox_nzb) или через дебрид-аккаунт, на котором он лежит, кладёт видео в папку фильма внутри __magic__ и просит Radarr пересканировать только этот фильм. Ничего не копируется: видео — это файл в библиотеке zurg, который Radarr теперь видит в своей папке.

Настройка Radarr

  1. Корневая папка внутри __magic__, на один уровень вглубь. Например /mnt/zurg/__magic__/movies (/Volumes/Zurg/__magic__/movies на macOS, Z:\__magic__\movies на Windows). Не сам __magic__ и не __magic__/__all__, где перечислены все релизы в библиотеке. Фильм, чья папка находится в другом месте, пропускается, и в логе zurg появляется одно предупреждение. В Windows Radarr видит Z: только если работает в той же сессии входа, что и zurg, то есть не как служба Windows. Подробнее см. правила сессии.

  2. Списки импорта с выключенным поиском при добавлении. Добавляй фильмы как удобно (вручную, по спискам, через Seerr, направленный на Radarr). Не включай Search for Movie при добавлении, потому что поиском занимается zurg.

  3. Индексаторы и клиент загрузки не нужны. Если они у Radarr есть, он может хватать релизы параллельно с zurg, поэтому выключи автоматический поиск на его индексаторах (или удали их) для фильмов, которыми занимается zurg.

  4. library_path — это путь, по которому Radarr видит __magic__. Если Radarr работает на той же машине, что и zurg, и видит точку монтирования там же, где её монтирует zurg, оставь параметр пустым: по умолчанию он равен mount_path из zurg плюс /__magic__. Если Radarr работает в контейнере, который монтирует zurg в другое место, укажи этот путь, например /data/zurg/__magic__. Тогда фильм по пути /data/zurg/__magic__/movies/Heat (1995) будет помещён в movies/Heat (1995) внутри __magic__ zurg. Пути Windows вроде Z:\__magic__ тоже работают. Контейнер Radarr поддерживается только на хосте Linux: Docker Desktop на macOS и Windows запускает контейнеры в виртуальной машине, и пробрасывание монтирования zurg в неё не тестировалось, поэтому там запускай Radarr нативно.

    Если Radarr также берёт релизы через endpoint SABnzbd или qBittorrent от zurg, он должен видеть их папку загрузок по пути library_path/__all__, через тот же том, что и его корневые папки. Иначе каждый импорт из неё будет копией всего файла. zurg спрашивает у Radarr, где тот видит обе папки, и сообщает об этом на странице добавления, в своём логе и в zurg doctor, если они не могут использовать один и тот же монтаж. См. Один том для папки загрузок и корневых папок.

Что zurg запрашивает у Radarr

Каждый опрос читает список фильмов Radarr и обрабатывает каждый фильм, который отслеживается (monitored), доступен по минимальной доступности фильма (minimum availability), и либо не имеет файла, либо имеет файл ниже cutoff профиля качества, при этом профиль разрешает апгрейды. Ниже cutoff означает ниже cutoff по качеству или ниже cutoff по счёту custom-format, как Radarr его считает. Фильм, который ещё не вышел, например с датой выхода через несколько месяцев, ждёт, пока Radarr не скажет, что он доступен.

Каждый релиз-кандидат, который zurg собирается проверить, отправляется в парсер Radarr (/api/v3/parse) и оценивается по профилю качества фильма. Так zurg принимает ровно то, что принял бы Radarr:

  • Это должен быть именно этот фильм. Radarr должен сопоставить название с тем же фильмом. Поиск по ID у индексатора возвращает и другие фильмы (поиск Psycho вернул Ed Gein: The Real Psycho), а название, которое Radarr ни с чем не сопоставил, отклоняется. Год в названии, который отличается от года фильма больше чем на один, тоже отклоняется.
  • Сначала применяются allow-list профиля и минимальный счёт. Распознанное качество должно быть разрешено профилем, счёт custom-format должен быть не ниже минимума профиля, а размер должен укладываться в лимиты качества из Settings > Quality для хронометража фильма.
  • Релиз должен быть на языке профиля. При Original, значении по умолчанию, Radarr должен прочитать название как язык оригинала фильма, так что релиз только с французской озвучкой английского фильма отклоняется. Название без указания языка считается оригинальным. Если язык назван, нужен именно он, а Any подходит любой. Это правило действует и для первого файла, и для апгрейда.
  • Апгрейды движутся к cutoff. Фильм без файла берёт любой релиз, который проходит проверки выше. Если же файл ниже cutoff, берётся только лучший релиз: более высокое качество по порядку профиля, пока файл ниже cutoff по качеству, либо более высокий счёт custom-format (минимум на шаг апгрейда профиля), пока файл ниже cutoff по счёту. Более низкое качество никогда не берётся. PROPER и REPACK того же качества апгрейдами не считаются.

Профиль применяется к релизу, который zurg собирается взять, как allow-list: нужный фильм, разрешённое качество, минимальный счёт, язык и лимиты размера. По умолчанию порядок предпочтений профиля при выборе между разрешёнными релизами не используется. zurg берёт первый разрешённый релиз, который дешевле всего проверить, и сначала пробует веб-релизы (WEB-DL, WEBRip), потом Blu-ray, а потом всё остальное, потому что веб-релизы чаще всего выкладывают одним видеофайлом. Если профиль предпочитает что-то лучшее, чем пришло, и разрешает апгрейды, Radarr видит файл фильма ниже cutoff, и upgrade-проход zurg ищет лучший релиз, как только у фильма появился первый. Первый файл приходит быстро, а порядок профиля обеспечивает апгрейд. Чтобы первая закачка следовала порядку профиля, поставь best_first: true. См. Выбор лучшего с первого раза по профилю.

Если поиск по IMDb или TMDB ID не вернул вообще ничего, zurg ищет ещё раз по названию и году, как это делает Radarr. Многие раздачи, особенно небольшие документалки, проиндексированы вообще без ID. Решение о том, тот ли это фильм, принимает парсер Radarr, так что фильм с таким же названием отклоняется, как любое другое неверное совпадение.

Radarr спрашивают о релизе только тогда, когда zurg собирается его проверить, по одному релизу за раз, поэтому у фильма с одним релизом в один файл выходит от одного до трёх запросов. Больше ничего не спрашивается, как только прямая раздача сохранена. Название с разрешением, для которого в профиле нет разрешённого качества (например, релиз 2160p для профиля HD-1080p), отклоняется без обращения к Radarr. Название без разрешения или с несколькими разрешениями всегда идёт в Radarr, и так же каждое название, если профиль разрешает качество, в названии которого не указано разрешение (SDTV, DVD, Unknown, Raw-HD, BR-DISK). zurg делает не более восьми одновременных запросов к одному Radarr.

Если до Radarr не удаётся достучаться, решение не принимается: фильм ждёт следующего опроса, и ни один релиз не отбрасывается только потому, что Radarr не ответил.

Размещение файла

Когда релиз проверен, zurg кладёт его видео в папку фильма так, как это сделал бы Radarr при импорте, то есть перемещает его внутрь __magic__. Ничего не копируется и не скачивается.

  • Самое большое видео и есть то, что кладётся. Это самый большой файл .mkv, .mp4, .m4v, .avi, .mov или .ts в релизе, при этом учитываются и файлы внутри архивов. Если релиз отдаётся из одного архива, то берётся содержимое этого архива. RAR-набор с отдельными файлами рядом, например scene-пост с сэмплом и .nfo, открывается как папка релиза, и видео из неё кладётся оттуда. Сэмплы, дополнительные материалы, субтитры и .nfo остаются в __magic__/__all__. Файл сохраняет имя, которое у него было в релизе, но только если это имя хоть что-то говорит о фильме (есть год или хотя бы слово из названия). Если не говорит, файл получает имя релиза, чтобы Radarr мог определить его качество.
  • Сэмпл никогда не кладётся. Видео, которое названо как сэмпл (sample-…, ….sample.mkv, папка Sample/), не попадает в папку, каким бы большим оно ни было, если только сам релиз не называется как сэмпл. Если в названии фильма есть это слово (Sample.Size.2019, Death.Proof.2007), то оно есть и в названии релиза. В таком случае видео пропускается, только если оно занимает меньше пятой части релиза. Если единственное видео в релизе это сэмпл, в том числе когда пост состоит только из сэмпла, такой релиз откладывается в сторону и пробуется следующий кандидат. Так апгрейд никогда не заменит твой файл клипом на одну минуту.
  • Перед перемещением файл проверяется, и если его нельзя прочитать, он отбрасывается. Это та же проверка, которую проходит импорт Sonarr или Radarr через маунт. Релиз, статьи которого новостные серверы уже не хранят, или архив которого не открывается вообще, откладывается как мёртвый пост, и пробуется следующий кандидат. Релиз, который сейчас не читается, например на аккаунте, который ещё «остывает», будет проверен позже.
  • Radarr хранит один файл на фильм, поэтому апгрейд заменяет старый файл. Когда новое видео уже лежит в папке, все остальные видео из библиотеки zurg скрываются из папки. Скрыть значит пометить как tombstone, точно так же, как при удалении через маунт: старый релиз остаётся в __all__ и на своём аккаунте. Настоящий файл, который ты положил в папку сам, не трогается. Старый файл удаляется только после того, как новый уже помещён, так что если перемещение не удалось, у фильма остаётся прежний файл.
  • Потом Radarr делает рескан. zurg сообщает маунту, какие папки изменились, чтобы при рескане не читалась папка, которую маунт ещё помнит как пустую, а затем просит Radarr пересканировать именно этот фильм.

Источнику Radarr нужен __magic__ (magic.enabled). Без него источник не запустится, и об этом будет написано в логе и на странице acquisition.

Что показывает Radarr

Activity остаётся пустым: ни записей в очереди, ни событий grab или import, потому что Radarr ничего не захватывал. После пересканирования, которое запрашивает zurg, у фильма просто появляется файл, а его качество и custom formats — это то, как Radarr прочитал этот файл. Лог zurg фиксирует каждый фильм, который он завершил.

only_new_items и remove_after_grab ни на что не влияют для источника Radarr. Запланированные фильмы в Radarr — это работа, как и одобренные запросы в Seerr, а решает, когда фильм перестаёт быть запланированным, сам Radarr. Не меняй name источника: по нему определяется сохранённая очередь, а URL и ключ можно менять свободно.

Поведение Sonarr

Sonarr работает так же, как Radarr. Sonarr ведёт список и владеет библиотекой. zurg занимается поиском и загрузкой. Sonarr никогда не ищет и не забирает релизы сам. zurg читает эпизоды, которых не хватает Sonarr, и выбирает релиз из своих индексаторов. Он проверяет релиз через новостные серверы (загрузка TorBox на аккаунте torbox_nzb) или через debrid-аккаунт, на котором лежит этот релиз, и кладёт видео каждого эпизода в папку сезона сериала внутри __magic__. После этого он просит Sonarr пересканировать только этот сериал. Ничего не копируется.

Настройка Sonarr

  1. Корневая папка внутри __magic__, на один уровень ниже. Например /mnt/zurg/__magic__/tv (/Volumes/Zurg/__magic__/tv на macOS, Z:\__magic__\tv на Windows). Сериал, папка которого находится в любом другом месте, пропускается, а zurg выводит одно предупреждение в свой лог. В Windows Sonarr должен работать в той же сессии входа, что и zurg, как и Radarr.

  2. Search on add выключен. Добавляйте сериалы как угодно. Оставьте Start search for missing episodes выключенной, так как поиском занимается zurg.

  3. Индексаторы и клиент загрузки не нужны. Если они есть в Sonarr, он может забирать релизы вместе с zurg, поэтому отключите автоматический поиск на их индексаторах для сериалов, которыми управляет zurg.

  4. library_path — это путь, по которому Sonarr видит __magic__. Работает так же, как и для Radarr, включая проверку того, что Sonarr получает доступ к папке загрузок zurg и его корневым папкам через один том. Не указывайте его, если Sonarr видит точку монтирования в том же месте, где её монтирует zurg.

Что zurg запрашивает у Sonarr

Каждый опрос читает список отсутствующих серий из Sonarr. Это отслеживаемые серии отслеживаемого сериала, которые уже вышли и для которых нет файла. zurg группирует их по сезонам и работает с каждым сезоном как с одним заданием.

  • Весь сезон, который уже закончил выходить, может прийти одним паком. Когда у всех серий сезона нет файла и ни одна ещё не вышла, сначала пробуется пак сезона. В остальных случаях отсутствующие серии сезона берутся по одной из результатов поиска по этому сезону. Сезон, у которого уже есть часть файлов, никогда не берётся паком. Иначе в папку попали бы вторые копии этих серий.
  • Новая серия — это новое задание. Когда на следующей неделе выходит новая серия, сезон снова попадает в список с этой серией. zurg не ищет заново серии, которые у него уже есть.
  • Новая серия ищется повторно в течение нескольких минут. Её релиз обычно появляется в течение часа после выхода, поэтому поиск сразу в момент выхода часто ничего не находит. Первые шесть часов после выхода серии zurg пробует каждые две минуты, а после этого каждые десять минут, до двух дней после выхода. Потом он отступает так же, как для всего остального (см. устойчивость и восстановление). На аккаунте debrid релиз также должен уже быть в кэше этого аккаунта, потому что zurg добавляет только то, что есть на аккаунте.
  • Удалённая серия снова считается нужной. Когда Sonarr показывает серию, которую zurg уже получил, zurg смотрит в папку сезона. Если видео для этой серии там больше нет, серия ищется снова. Если видео есть, значит Sonarr ещё не пересканировал папку, и поиск не запускается.
  • Улучшения считаются по файлам. Файл серии ниже cutoff профиля качества считается кандидатом на улучшение, если профиль разрешает улучшения. «Ниже cutoff» означает ниже cutoff по качеству или ниже cutoff по сумме баллов custom format. Список Sonarr Cutoff Unmet учитывает только качество. В Sonarr 4.0.20 файл с cutoff-качеством, который получает 0 баллов при cutoff 40, в этот список не попадает. zurg учитывает оба критерия, так же как правило улучшения самого Sonarr. Файл с двумя сериями считается одним улучшением для обеих серий.
  • Серии ежедневного шоу ищутся по дню выхода. Их релизы называются по дате (The.Daily.Show.2026.11.03.Min.Jin.Lee...), и индексаторы не находят их по номеру серии. Поэтому для каждой отсутствующей серии дополнительно делается текстовый поиск по названию сериала и дате: The Daily Show 2026.11.03. Парсер Sonarr переводит дату обратно в серию (S31E124), так же как и для названия с нумерацией по сезонам.
  • Серии аниме ищутся по номеру, который шоу использует в счёте. Фансаб-релизы нумеруются с первой серии шоу ([SubsPlease] Jujutsu Kaisen - 30 — это шестая серия второго сезона). Поэтому для каждой отсутствующей серии дополнительно делается текстовый поиск по названию сериала и этому номеру: JUJUTSU KAISEN 30. Пакет, который охватывает номера серий сезона ((25-47)), считается паком этого сезона. Парсер Sonarr сопоставляет номер с серией, используя его альтернативные названия для сезона (Jujutsu Kaisen 2nd Season, Jujutsu Kaisen S2), поэтому название с номером любого типа оценивается как та серия, которой оно и является. Релиз, который Sonarr не сопоставляет ни с одним сериалом, например релиз с альтернативным названием, которое Sonarr не знает, отклоняется так же, как любой другой.
  • Спешлы — это сезон 0. Отслеживаемые спешлы Sonarr показываются в списке так же, как любой сезон, и запрашиваются как сезон 00 (индексатор, которого попросили про сезон 0, отвечает другим сезоном). Подходит только релиз с S00Exx в названии. Спешл, который назван только своим заголовком, парсер не распознаёт, и в Sonarr тоже. Они кладутся в папку, которую задаёт Specials Folder Format в Sonarr.

Каждый кандидат-релиз проверяется собственным парсером Sonarr (/api/v3/parse) и оценивается по профилю качества сериала. zurg принимает то, что принял бы Sonarr.

  • Должен быть этот сериал и этот сезон. Sonarr должен сопоставить название с тем же сериалом. Название, которое Sonarr ни с чем не сопоставляет, отклоняется. Исключение: если сериал не использует scene-нумерацию и поиск сериалов Sonarr находит именно этот сериал первым по названию из заголовка (например, название на другом языке).
  • Пак должен быть целым сезоном. Частичный пак отклоняется. Пак, записанный диапазоном, например Season 1 E01-E07, засчитывается, если диапазон покрывает весь сезон. Пак из нескольких сезонов засчитывается для каждого сезона, который в нём назван (см. Паки из нескольких сезонов). Sonarr читает S01-S05 как один только первый сезон и никогда не указывает, где диапазон заканчивается, поэтому zurg берёт диапазон из названия. Sonarr всё равно должен сопоставить пак с сериалом и признать его полным многосезонным паком. Размер такого пака оценивается по хронометражу всех сезонов, которые он охватывает.
  • Серия должна быть ровно одной серией. Релиз с двумя сериями отклоняется для одиночной серии.
  • Профиль применяется так же, как в Radarr. Качество должно быть разрешено. Сумма баллов custom format должна достигать минимума профиля. Размер должен укладываться в ограничения качества в Settings > Quality с учётом хронометража серий, которые есть в релизе. Улучшение должно превосходить текущий файл по правилам Sonarr. В профилях Sonarr нет настройки языка, поэтому язык учитывается только через баллы custom format, как и в Sonarr.

Какой из разрешённых релизов идёт первым, решается иначе, чем в Radarr. Пак сезона пробуется раньше отдельных серий, потому что это одна загрузка вместо нескольких. Среди релизов, которые разрешил Sonarr, zurg берёт тот, который первым идёт по настройке quality. При best это сначала самое высокое разрешение, а затем самый большой размер, то есть пак оценивается по тому, сколько он содержит на одну серию. Поэтому законченный сезон с паком 1080p заполняется из этого пака, даже если тот же поиск содержит каждую серию в 2160p. Затем проход по улучшениям заменяет серии по одной. Пак, в котором на одну серию приходится больше max_size_gb, или больше max_season_size_gb, если вы задали его для сезона, никогда не становится кандидатом. best_first: true меняет оба этих правила. См. Выбор лучшего варианта по профилю.

Название с разрешением, для которого в профиле нет разрешённого качества, отклоняется без запроса к Sonarr. zurg делает не более восьми одновременных запросов к одному Sonarr. Если Sonarr недоступен, решение не принимается. Сезон ждёт следующего опроса, и ни один релиз не откладывается в сторону.

Размещение файлов

Когда релиз проверен, видео каждой серии кладётся в папку сезона. Это та папка, где уже лежат файлы сезона. Если в сезоне файлов ещё нет, используется папка по формату Season Folder Format из Sonarr, например Season 1. Если в сериале не используются папки сезонов, файлы попадают прямо в папку сериала.

  • У каждой серии своё видео. Видео находится по номеру серии в имени файла, в том числе внутри архивов релиза. В паке кладутся все серии, которые в нём были взяты. Сэмплы и .nfo файлы остаются в __magic__/__all__, а сэмпл никогда не ставится как серия.
  • Пак без одной серии отклоняется до того, как что-то будет перемещено. Он откладывается как нерабочий пост, и дальше пробуются следующий пак или отдельные серии.
  • Отдельная серия, чей файл ничего не называет, получает самое большое видео релиза. Так часто выглядят обфусцированные посты.
  • Видео аниме или ежедневного шоу кладётся в папку сериала и под номер серии. Rescan читает файл только по его имени и не знает про scene-нумерацию. Например, [Erai-raws] Jujutsu Kaisen 2nd Season - 08.mkv в папке сериала импортировалось как S01E08, а парсер Sonarr читает то же название как S02E08. Поэтому видео кладётся под именем JUJUTSU KAISEN - S02E08 - [Erai-raws] Jujutsu Kaisen 2nd Season - 08.mkv. Оно импортируется правильно, а его собственное имя остаётся после номера серии, чтобы Sonarr всё ещё читал качество и группу. Видео обычных сериалов и спешлов сохраняют свои имена, потому что в них уже есть номер серии.
  • Апгрейд заменяет только свою серию. Старое видео этой серии скрывается из папки сезона, когда новое уже на месте. Остальные серии в папке не трогаются. Скрыто значит tombstoned, так же как для Radarr.
  • Потом Sonarr делает rescan. zurg сообщает монтированию, какие папки изменились, и просит Sonarr выполнить rescan сериала.
  • Одна отсутствующая серия не задерживает остальные. Если для серии пока нет релиза, который может взять zurg, найденные серии всё равно проверяются и размещаются. Sonarr сразу просят сделать rescan для них. Недостающую серию снова ищут по обычному расписанию повторов.

Источник Sonarr требует __magic__ (magic.enabled). Без него источник не запускается, и об этом сообщается в логе и на странице acquisition.

Activity в Sonarr остаётся пустым, как и в Radarr. Серии просто получают файлы после rescan, который запрашивает zurg. only_new_items и remove_after_grab для источника Sonarr ничего не делают.

Пакеты из нескольких сезонов

Сезон можно взять из пака, в котором их несколько, например Game.of.Thrones.S01-08.BDRip.1080p или Breaking Bad Season 1-5. Индексеры записывают такой пак под каждым сезоном, который он покрывает. В ленте DMM 72 из 691 результатов для Breaking Bad season 3 были паками из нескольких сезонов. Для некоторых сезонов один из таких паков — единственная копия, которая есть на аккаунте.

  • По названию видно, какие это сезоны. Распознаются все такие варианты: S01-S05, S01-05, [S01-08], S1-9, Seasons 1-8, Season 1 to 5, Season 1 · 2 · 3, Stagioni 01-05 и Temporadas 1-4. Название без номеров сезонов, например Complete Series, не берётся. Не берётся и то, где один сезон назван только словом, например Season 3 Complete. Такие названия никогда не считались паками.
  • Раскладывается только этот сезон. Пак, взятый для сезона 4, кладёт серии сезона 4 в папку этого сезона. Файлы других сезонов остаются там, где их указывает библиотека. Пак, в файлах которого нет всех серий сезона, отклоняется до того, как что-либо будет перемещено, каким бы ни было его название.
  • Размер оценивается на серию. Размер пака делится на количество сезонов, которые он называет, а затем на количество серий в сезоне, и сравнивается с max_size_gb так же, как сравнивался бы тот же энкод, выложенный поэпизодно. Пак 346 GB из восьми сезонов по десять серий — это 4.3 GB на серию. Ремукс второго сезона I Love Lucy из 31 серии весит 106 GiB, то есть 3.4 GiB на серию, и укладывается в заданный вами лимит 40. Если источник не указал серии сезона, для паков никакого лимита на серию нет. max_season_size_gb, если вы его задали, дополнительно ограничивает каждый сезон, который назван в паке; по умолчанию его нет.
  • Качество по-прежнему важнее всего. Паки ранжируются, как и любые другие релизы: сначала разрешение, затем то, что они содержат на серию, так же, как их ранжирует страница сезона в DMM. Пак 2160p на один сезон берётся раньше, чем пак 1080p на восемь. В пределах одного разрешения ремукс самого сезона идёт раньше пака из восьми сезонов, который больше по общему размеру, но меньше на серию.
  • Остальные сезоны шоу берут тот же пак. Как только один сезон взял пак из нескольких сезонов, остальные сезоны шоу сначала пробуют этот пак, раньше любого пака того же разрешения, который нашёл их собственный поиск. Он уже на аккаунте, так что ничего не стоит. Пока сезоны шоу выбирают среди паков из нескольких сезонов, они выбирают по одному, чтобы сезоны, запрошенные вместе (сериал в Sonarr, все его сезоны за один опрос), не остановились каждый на своей копии шоу. Как только один из них выбрал без такого пака — потому что ни одного не было на аккаунте или профиль их не разрешал — остальные выбирают сразу. Сезон, запрошенный час спустя, ищет заново.

Наблюдаем за работой

Ссылка Acquisition на панели открывает /acquisition/ на собственном порту zurg.

Для каждого источника выводится строка: сколько его тайтлов готово, выполняется, ждёт, отложено и стоит в очереди, а также сколько тайтлов zurg обрабатывает одновременно, сколько запросов он делает к одному индексатору одновременно и сколько новостных соединений разрешено для его аккаунтов nzb. Ниже у каждого источника есть таблица со строкой на каждый тайтл. В строке видно состояние; что сейчас делает выполняющийся тайтл (поиск, сколько результатов уже проверено и допущено, какой кандидат сейчас проверяется, проверка на новостных серверах, размещение); его попытки; выбранный релиз с качеством и оценкой, которую дал источник; куда он размещён; и когда ждущий тайтл будет опробован в следующий раз. Если ни один из релизов тайтла больше не осталось попробовать, в таблице написано почему, а отказы источника подсчитаны по правилам: 14 refused by the source's own rules (title mismatch 7, quality 5, size 2). Релизы, отклонённые по разрешению без запроса к источнику, учитываются в quality. Страница обновляется сама каждые пять секунд. Тот же снимок доступен по адресу /acquisition/status.json, где эта причина находится в поле detail тайтла. Если ни один источник не включён или acquisition настроен, но приостановлен, страница сообщает об этом и объясняет почему.

Для каждого фильма, для которого выбран релиз, в лог записывается одна строка, чтобы замерить, куда уходит время:

Acquisition: chose <release> for <title>: results=143 local_refusals=97 radarr_refusals=1 inspected=2 radarr_calls=3 in 4.2s

results — это то, что вернул поиск; local_refusals — результаты, отклонённые без запроса к источнику; radarr_refusals — те, которые отклонили правила самого источника; inspected — прочитанные NZB; radarr_calls — вопросы, заданные источнику (прочитанные NZB плюс отказы по пути к ним, когда источник — Radarr). Время отсчитывается от начала поиска. Релизы, отклонённые без запроса, записываются в лог по одному и только на уровне debug.

Проверка *arr, который использует zurg только как клиент загрузки

A Sonarr or Radarr pointed at zurg's SABnzbd or qBittorrent endpoint does its own searching, and does not need a source here. zurg still wants its API key, because three of its settings decide whether every import is a free rename or a whole release downloaded from the debrid account and written to zurg's disk: Remove Completed on a qBittorrent client, the download folder and the root folders on one volume, and root folders inside __magic__. With the key, zurg turns Remove Completed on by itself (see qbittorrent.md) and warns about the other two. See One volume for the download folder and the root folders.

The easiest way to give zurg the key is the banner on the main dashboard, described below. Or add it as a source that is switched off:

acquisition:
  sources:
    - name: sonarr
      type: sonarr
      enabled: false
      url: http://sonarr:8989
      api_key: YOUR_SONARR_API_KEY

A Radarr or Sonarr source with enabled: false acquires nothing. zurg never reads its wanted list and never searches for it. With its url and api_key set, and one of the two endpoints on, zurg only reads the *arr's root folders, remote path mappings and download clients, at start, every ten minutes and as soon as the *arr first calls one of the endpoints. It turns Remove Completed on for the *arr's zurg qBittorrent client when it is off, the one change zurg makes, and reports a layout that makes imports copies. Every source with a URL and an API key, enabled or not, is checked and corrected the same way. It is listed on the acquisition page under Checked, never searched for, with what zurg changed, the findings go to the log, and zurg doctor shows them as imports (<name>). library_path is not judged for such a source, since nothing is placed for it. A source added to config.yml by hand is read at start, so restart zurg after adding one that way.

zurg also notices a Sonarr or Radarr it cannot check. Both send their name in every request to the endpoints (Sonarr/4.0.20.3014 (alpine 3.24.1)), so zurg records which ones call it and from which address. When one calls and no source of its kind has a URL and an API key, zurg logs one warning, zurg doctor reports it on its *arr settings line, and the main dashboard shows a banner with a form for its URL and API key. The URL is filled in with a guess: the address the *arr calls from, on its default port (8989 for Sonarr, 7878 for Radarr). That address is often a container's own, which zurg may or may not reach, so change it to whatever URL reaches the *arr from where zurg runs. The API key is in the *arr under Settings, General, Security. zurg first asks the *arr for its status with that key, and saves nothing unless it answers as the app it was named as. It then adds the source above to config.yml with enabled: false, keeping everything else in the file as it was, and checks it straight away, with no restart. The form shows what zurg found and changed. The key is written to config.yml and sent to the *arr, and nowhere else.

The banner matches by kind, not by address: an *arr calls zurg from inside its container, on an address that has nothing to do with the URL zurg reaches it on, so one Sonarr source with a key silences the banner for every Sonarr.

Поиск дублирующихся релизов

После обновления в библиотеке остаётся релиз, который был заменён. Если magic.allow_delete выключен, удаление старого файла в Radarr или Sonarr лишь прячет его в __magic__, поэтому старый релиз остаётся в __all__ и на вашем аккаунте. Захваты с нескольких индексаторов или сезонный пак рядом с отдельными сериями тоже оставляют несколько релизов одного и того же. Manage > Duplicates (/manage/duplicates/) показывает их, сообщает, какой из них использует Radarr или Sonarr, и позволяет удалить остальные. Само по себе он ничего не удаляет.

Используемый релиз определяется по путям, а не по именам. Каждый файл, который держат Radarr и Sonarr, назван путём внутри __magic__, и zurg знает, из какого релиза взят каждый путь, потому что при перемещении файла туда он это записал. Представление читает каждый файл, который *arr импортировал, отслеживал или нет, достиг он порога качества или нет, и связывает каждый файл с его релизом. Файл Sonarr связывается поэпизодно, так что сезонный пак, из которого Sonarr берёт три серии, показывается как используемый для этих трёх.

Какие релизы могут быть копиями, это догадка, и так и написано. Релизы группируются с фильмом или с сезоном, когда:

  • в них есть файл *arr,
  • в истории *arr сказано, что файл импортирован из них или что удалён файл, пришедший из них (обновлением, вручную или из-за отсутствия на диске),
  • zurg определил их как IMDb id фильма или сериала, или
  • их имя читается как название и год (год, отличающийся на единицу, или второй год Radarr для фильма, тоже засчитывается) или как название сериала и сезон.

Каждый релиз показывает, какие из этих признаков поместили его в группу. Сезон образует группу только там, где релизы содержат одни и те же серии: шестьдесят односерийных релизов одного сезона — это шестьдесят разных серий. В группе сезона перечисляются серии, которые есть более чем в одном релизе, какой релиз содержит каждую из них, в каком из них лежит файл Sonarr, и сколько серий содержит каждый релиз, которых нет ни в одном другом релизе группы. Победитель не выбирается. Релизы, которые не совпали ни с одним элементом Radarr или Sonarr, находятся в разделе Name matches only и сгруппированы по своим именам и IMDb id.

Каждый релиз имеет статус In use, No reference found или Unknown.

State Значение
In use Файл, который Radarr или Sonarr держат прямо сейчас, находится в этом релизе. Его нельзя выбрать.
No reference found Все настроенные Radarr и Sonarr были прочитаны полностью, и ни один их файл не находится в этом релизе. Plex, Jellyfin и другие клиенты, читающие монтирование, здесь не видны, поэтому это не доказательство того, что его никто не проигрывает.
Unknown zurg не может определить. Все релизы имеют Unknown, пока *arr нельзя прочитать, пока библиотека ещё загружается или при выключенном __magic__. Релиз также Unknown, если файл *arr для того же фильма или серии не удаётся связать ни с одним релизом, или если в истории *arr видно, что файл из этого релиза пропал с диска, а у фильма или серии с тех пор не было файла.

Качество показывается в терминах профиля. Для релиза, который использует *arr, это собственная оценка файла от *arr. Для релиза, который *arr импортировал раньше, это оценка, которую он дал тогда. В остальных случаях оно читается из имени релиза, и это так и указывается. Каждое значение помещается в профиль качества элемента, например "rank 15 of 17 in 4K or best available (cutoff at 17)".

Перед удалением zurg перечитывает данные. Выберите релизы и нажмите Check again and delete. zurg заново читает текущие файлы каждого *arr и только после этого предлагает удаление. Релиз, который начал использоваться после загрузки страницы, пропускается, а релиз со статусом Unknown удаляется, только если вы снова отметите его в этом диалоге. Само удаление — это массовое удаление со страницы управления, которое убирает все копии релиза со всех аккаунтов, где он есть.

Когда читается. При первом открытии страницы читаются все Radarr и Sonarr из acquisition.sources, включая историю импорта и удаления. Чтение истории большой библиотеки может занять минуту. Потом страница показывает, что и когда читалось в последний раз, пока вы не нажмёте Read Radarr and Sonarr again. Источник с enabled: false всё равно читается: выключение acquisition не меняет того, что держит этот *arr. Страница показывает счётчики каждого источника: сколько файлов прочитано, сколько связано с релизом, сколько лежит по пути вне его library_path и сколько внутри __magic__, но никуда не ведут. Если ни один файл источника не связан с релизом, проверьте его library_path.

Тот же отчёт доступен по адресу /manage/duplicates/report.json, а POST /manage/duplicates/check с {"hashes": [...]} заново читает *arr и возвращает состояние каждого релиза.

Newznab и Torznab

Индексатор указывает свой тип в поле type. Если поля нет, считается, что это newznab. Так было со всеми записями, созданными до появления этого поля. Запрос к обоим типам одинаковый, а ответ разный. Результат Newznab — это NZB: он скачивается и сохраняется в nzbs/ для Usenet-бэкенда. Результат Torznab — это info hash, который передаётся аккаунту debrid. Результат Torznab без magnet-ссылки или атрибута infohash пропускается: zurg никогда не скачивает .torrent, поэтому результат, до которого можно добраться только так, для него недоступен.

Торрент всегда добавляется только в тот аккаунт, который уже его хранит. Хэш предлагается каждому аккаунту, который принимает добавления, за одним исключением: аккаунт Real-Debrid пропускается для имени релиза, который он прямо отказывается принимать, потому что кэши независимы, и то, что один аккаунт удалил релиз, ничего не говорит о следующем. Первый аккаунт, который уже его имеет, и забирает торрент. Промах везде — это обычный неудачный кандидат, поэтому обход спускается по рейтингу к следующему релизу, которым может быть другой торрент или NZB.

На TorBox и Debrid-Link промах ничего не добавляет, а на AllDebrid и Offcloud такой торрент сразу удаляется. Real-Debrid и Premiumize добавляют торрент и следят за ним до 20 секунд. Кэшированный контент готов за секунду-две. Всё, что продолжает загружаться после этого, удаляется, так что на аккаунте никогда не остаётся запущенной загрузки. Однако промах всё же не совсем бесплатен: он может засчитаться в лимит добавлений аккаунта. На TorBox он расходует один из 60 добавлений без кэша, доступных в час.

Аккаунт с watchlist: true получает торрент первым. Остальные идут в порядке твоего списка providers:. Аккаунт с add_torrents: false никогда не получает торрент.

prefer определяет, какой тип проверяется первым, если оба могут подойти под цель с одинаковым разрешением. Сначала идёт разрешение: торрент 2160p, который уже есть на аккаунте, берётся раньше NZB 1080p, что бы ни стояло в prefer. usenet — значение по умолчанию, потому что загрузка из Usenet стоит одной загрузки, а торрент тратит один из слотов добавления аккаунта. torrents меняет порядок на обратный, а best убирает различие и берёт то, что стоит первым в рейтинге, то есть больший релиз внутри одного разрешения.

Для фильма за одну попытку пробуется до трёх торрентов. Каждый стоит одного добавления. До 24 его NZB проверяются по отдельности, как описано в разделе choosing a movie's release. При usenet NZB одного разрешения пробуются раньше его торрентов. При torrents вперёд идут торренты. При best каждый торрент ждёт своей очереди в рейтинге. NZB одного разрешения пробуются вместе на месте лучшего из них. Если источник Radarr, NZB всех разрешений пробуются вместе на месте лучшего из них, начиная с самых дешёвых, как описано в этом разделе. Для сезонного пака за попытку пробуется три релиза любого типа. То же относится и к каждому отдельному эпизоду.

Проверка, которой ждёт загрузка, зависит от источника. Релиз Usenet проверяется на новостных серверах: это единственный способ узнать, существует ли пост до сих пор. У аккаунта torbox_nzb новостных серверов нет, поэтому загрузка там проверяется по тому, скачал ли её TorBox. Торрент добавляется только потому, что аккаунт сообщил, что уже хранит контент, поэтому остаётся убедиться лишь в том, что релиз попал в библиотеку с файлами. Именно это и проверяется. Релиз, который аккаунт показывает пустым, отбрасывается так же, как мёртвый пост.

Установка без NZB-аккаунта (nzb или torbox_nzb) всё равно может запускать получение контента только из индексаторов Torznab. Её индексаторы Newznab там не ищутся, потому что на такой установке нечем воспроизвести NZB. Для каждого из них лог сообщает об этом один раз. Установка без аккаунта, который принимает торренты, так же не ищет свои индексаторы Torznab. В обоих случаях релиз того типа, который установке некуда поместить, никогда не становится кандидатом. Поэтому он не расходует ни одного из релизов, которые пробует попытка, и источник вроде Radarr о нём никогда не спрашивают.

Лимиты индексаторов и отклонённые ключи

zurg не упирается в лимит DMM, а держится в его рамках. DMM разрешает ключу спонсора 20 поисков в минуту по всем его торрент-лентам, поэтому zurg отправляет в DMM не больше одного поиска каждые три секунды. Поиск сверх этого ждёт своей очереди, и ожидание не считается неудачным поиском. Поиск, чья очередь наступит после окончания попытки для его тайтла или через более чем две минуты, не выполняется: тайтл продолжает работу с тем, что нашли другие индексаторы.

Индексатор, который отвечает 429 или 503, не трогаем всё время, которое он просит. Каждый поиск, загрузка NZB и проверка возможностей ждут, пока истечёт их Retry-After, но не дольше двух минут, включая запросы, которые уже стоят в очереди. Индексатор, который просит больше, не опрашивают до истечения этого времени.

Несколько zurg на одном ключе DMM делят его 20 поисков. Каждый из них держится в рамках всего лимита, поэтому два или три zurg на одном ключе всё равно упираются в лимит DMM, и каждый отказ приостанавливает поиски этого zurg в DMM на минуту. Из-за этого тайтл может дольше ждать своего поиска и загрузки.

Отвергнутый ключ не трогаем в течение часа. Индексатор, который отвечает ошибкой 100 (неверный ключ) или 101 (аккаунт приостановлен, так DMM отвечает на истёкшее спонсорство), не опрашивают снова в течение часа ни для поисков, ни для загрузок NZB. В логе это пишется один раз, например DMM torrents refused the API key: check dmm_api_key, а на странице получения контента это отображается в списке Indexers not asked now. Ключ, который вы поменяли в config.yml, проверяется сразу. Любая другая ошибка касается только этого одного поиска.

Выбор релиза для фильма

Кандидаты фильма из Usenet пробуются в порядке того, во что обходится их проверка, а не только в порядке их качества. Пост с одним именованным видео стоит zurg два чтения статей и обычно полный. Набор из сорока томов архива требует прохода по размеру и чтения в начале и в конце каждого тома, а около двух третей наборов remux из нескольких томов на индексаторах уже пропали. Поле files у индексатора показывает, какой будет структура, поэтому кандидаты сортируются по нему: сначала до десяти файлов, затем до тридцати, потом больше, потом неизвестное количество, а внутри каждой группы по самому числу файлов. Среди постов с одинаковой ценой, если такой источник, как Radarr, оценивает релизы по своему профилю, название с WEB-DL или WEBRip идёт первым, потом Blu-ray, потом остальные, а внутри каждой группы сначала больший пост. Рейтинг самого источника здесь не используется, потому что его можно узнать только спросив сам источник, а zurg спрашивает о релизе только тогда, когда собирается его проверять. Без источника решают рейтинг качества, а потом размер. Если ни один источник не оценивает кандидатов, разрешение из настройки quality стоит впереди цены, так что список с best всё равно получит лучшее доступное разрешение, а внутри него самый дешёвый пост первым. Результаты, названные по одной части разбитого поста ([1/9] "Movie.part1.rar"), никогда не становятся кандидатами, а из двух постов с одним именем остаётся только тот, у которого меньше файлов, потому что библиотека может хранить только один из них.

Затем проверяются до 24 кандидатов: каждый NZB скачивается и разбирается собственным парсером zurg. Пост с не более чем двумя содержательными файлами, один из которых именованное видео .mkv, .mp4, .m4v, .avi, .mov или .ts размером не менее 500 МБ, считается прямым постом. Тома PAR2 и сопутствующие файлы, такие как .nfo, .sfv, .srr, .nzb, изображения, .txt, .url и .exe, содержательными файлами не считаются. Первый прямой пост сохраняется сразу. Архивные посты придерживаются, пока прямые из текущей выборки не закончатся, затем пробуются от наименьшего числа томов к большему, через шлюз, который не даёт более чем шести архивным релизам одновременно ждать на новостных серверах. Пост, в котором есть только данные для восстановления и сопутствующие файлы, никогда не сохраняется. Проверенные NZB запоминаются в памяти, поэтому, когда сохранённый релиз оказывается мёртвым и название пробуется снова, следующий кандидат берётся без повторной загрузки уже проверенных. Поиск и загрузка NZB делят один лимит одновременных запросов на каждый индексатор, а если индексатор отвечает 429 или 503, запрос повторяется после паузы, с учётом заголовка Retry-After. Дашборд показывает каждый шаг: поиск, какой кандидат сейчас проверяется и что было сохранено. Для сериалов используется более ранний проход: три лучших по рейтингу релиза, которые не отложены в сторону. Когда источник сам оценивает релизы, как это делает Sonarr, каждый из них сначала передаётся ему, и релиз, который он отклонит, в число трёх не попадает. best_first меняет порядок обоих проходов, как описано в следующем разделе.

Сначала лучшее из профиля

acquisition:
  best_first: true

По умолчанию выключено. Если включить, то первый захват из источника Radarr или Sonarr будет следовать порядку предпочтений профиля качества, а не тому, сколько стоит проверка релиза. Список просмотра Plex и Seerr не имеют профиля, поэтому на них это не влияет. На странице получения написано, когда опция включена.

  • Лучшее разрешение из профиля идёт первым. Каждый релиз ставится по разрешению, которое указано в его названии. Его место определяется лучшим качеством, которое профиль допускает в этом разрешении. zurg берёт это из профиля, который у него уже есть, и больше ни о чём не спрашивает Radarr и Sonarr. WEB-DL, Blu-ray и remux одного разрешения занимают одно место. Внутри одного места фильм всё равно берёт релиз, который дешевле всего проверить. Сериал берёт тот, который quality ставит выше всех. Название без разрешения идёт в самом конце.
  • Порог обновления считается верхом. Пока профиль разрешает обновления, каждое качество на уровне порога или выше считается таким же, как сам порог. Проход обновлений никогда не заменит ни одно из них. Профиль, который обновляется до WEB 1080p, ничего не выигрывает от режима «лучшее first», даже если он допускает и 2160p. Профиль без обновлений сохраняет весь свой порядок. Его первый файл — тот, который он оставляет.
  • Откат вниз по профилю. Релиз, чей NZB нельзя получить или прочитать, пропускается. Релиз, который отклонили новостные серверы, откладывается в сторону, как и раньше. Затем пробуется следующий релиз в порядке профиля. Одна попытка всё равно читает не больше 24 NZB, независимо от их места.
  • Он идёт раньше предпочтения Usenet или торрента. Торрент, который уже есть на аккаунте, берётся раньше NZB, который профиль ставит ниже. prefer по-прежнему решает между NZB и торрентом одного места.
  • Пакет сезона должен быть не хуже отдельных серий. Пакет, который по рейтингу ниже отдельной серии из того же поиска, пропускается. Тогда серии берутся по одной. Sonarr делает такой же выбор. Сравнивается только этот один поиск. Серия не ищется отдельно ещё раз на случай, если существует её более удачный релиз.

У этого есть цена. Верх профиля 2160p в основном состоит из remux и наборов Blu-ray по сорок томов и больше, а не из отдельных видеофайлов. Такой набор дольше проверяется. Его чаще нет на новостных серверах. Кроме того, он ждёт очереди на шлюз архивов. Поэтому первый файл обычно приходит позже. Если все лучшие релизы тайтла отсутствуют, каждый из них сначала захватывается, проверяется и откладывается в сторону, и только потом zurg переходит ниже по профилю. Сезон, взятый отдельными сериями, даёт несколько захватов там, где пакет понадобился бы один. Выигрыш в том, что не нужен второй захват. Первый файл на уровне порога никогда не обновляется.

Что делает получение с собственным списком источника

Список желаемого в Plex — это список, который кто-то составил сам, и это единственная запись о том, что человек хотел посмотреть этот тайтл. Plex не хранит историю удалённых записей. Два параметра определяют, что zurg может делать с этим списком. Оба применяются к источникам plex_watchlist. У источников Seerr и Radarr нет списка, в который zurg что-то записывает, поэтому там оба параметра не работают.

remove_after_grab (по умолчанию true) убирает полученный тайтл из списка желаемого, как только проверен релиз, который за ним стоит. Так эта функция работала всегда: список желаемого читается как очередь того, что нужно получить, и тайтл, который zurg уже получил, считается выполненным. Если установить false, список останется списком желаемого, то есть постоянным списком для просмотра, который zurg отрабатывает в фоне, ничего в нём не меняя. Оставить тайтл в списке ничего не стоит при повторной проверке: квитанция его уже покрывает, поэтому индексаторы о нём снова не спрашивают.

Тайтл, по которому zurg ничего не получил, остаётся в списке independently от этого параметра. Когда все релизы, которые закрывают тайтл, уже были в библиотеке (ваша собственная копия или та, которую добавил другой запрос), ничего не было загружено или добавлено, и удаление только изменило бы ваш список. Эти релизы всё равно проверяются, и тайтл всё равно считается выполненным, поэтому пока он в списке, его повторно не ищут. Если его удалить и добавить снова, он снова останется в списке. Сериал, из которого zurg загрузил хотя бы один сезон или эпизод, считается полученным и удаляется, как и раньше.

only_new_items (по умолчанию true) при первом запуске источника принимает всё, что уже есть в списке, и действует только на то, что добавлено позже. Включение функции должно начинать отслеживание списка, а не забирать целый вечер на обработку всего, что в нём есть. Если установить false, существующий список будет считаться очередью, которую нужно обработать.

Параметр применяется один раз, при первом запуске источника. Источник, у которого уже есть очередь, работает, и именно эта очередь, а не этот переключатель, фиксирует, что уже сделано, а что нет. Поэтому включение параметра позже никогда не сбросит очередь, которая уже в работе. Принятый тайтл остаётся принятым, пока он в списке. Если его удалить и добавить снова, это обычный новый запрос.

Проверка захвата

Сохранённый NZB ещё не является релизом. То, что индексатор ответил, ответ разобрался как NZB и файл попал в nzbs/, говорит только об индексаторе, а не о самой публикации. Поэтому каждый полученный NZB проверяется на настроенных новостных аккаунтах до того, как движок подтвердит запрос. Первые шестнадцать статей и последняя статья каждого файла проверяются командой STAT. Первая статья каждого файла, а также несколько дополнительных статей релиза с небольшим количеством файлов, загружаются целиком (не больше sixty-four). Так сделано потому, что новостной сервер может отвечать на STAT для статьи, которую уже удалил. Статья, на которую STAT отвечает отказом, тоже загружается целиком, прежде чем её сочтут пропавшей. Причина в том, что новостной сервер может отказывать в STAT для статьи, которую он всё ещё отдаёт (NewsDemon так делал 2026-10-21). Таких статей на релиз не больше шестнадцати. Тот же проход делает /api?mode=addfile для Sonarr и Radarr. Есть три варианта ответа, и важно не путать их:

  • Статьи пропали. Граб не засчитывается. Квитанция переоткрывается, поэтому цель снова считается нужной. Релиз записывается как мёртвый на 30 дней, чтобы при следующей попытке выбрать следующего кандидата, а не тот, что уже стоит в библиотеке. Релиз из этого списка не считается кандидатом: его не загружают, и он не тратит один из кандидатов, которые пробует попытка. Так серия мёртвых публикаций вверху рейтинга просто пролистывается, а не закрывает доступ ко всему, что ниже. Если мёртвый пак сезона, весь сезон снова становится нужным, а отдельные серии берутся вместо него. NZB, который был получен самим сервисом, затем удаляется из каталога наблюдения, чтобы после перезапуска его не загружали и не проверяли заново до открытия библиотеки. NZB, который уже был в каталоге наблюдения или в библиотеке, а также тот, из которого импортировали Sonarr или Radarr, остаётся на месте.
  • Аккаунты не удалось опросить. Пул недоступен, аккаунт ограничивает скорость или библиотека ещё не видит новый NZB, что здесь самое обычное дело. Ничего не установлено, поэтому ничего не решается. Запрос снова проверяется через двадцать секунд, потом через 40 и 80 секунд, затем каждые две минуты. Ожидание не тратит попытку повтора. Проверка, которая просто не уложилась по времени, относится к другому случаю: она сразу запускается заново с полным временем, но не больше трёх раз, и только потом начинается ожидание. Это время составляет пять минут, а для релиза с большим количеством файлов на аккаунте с малым числом соединений оно больше. zurg вычисляет его из двух величин: количества соединений и самой медленной скорости, которую проверка показала, а также из шести проверок, которые идут одновременно, и затем удваивает. Релиз из 90 томов на четырёх соединениях получает около 53 минут. Раньше пять минут заканчивались при каждой попытке, и релиз в итоге откладывали без проверки. Двадцать проверок за два часа, которые ничего не установили, откладывают релиз так же, как мёртвый. Следующая попытка пробует другой релиз. Запрос никогда не подтверждается по релизу, который никто не смог проверить.
  • Релиз на месте. Квитанция отпускает то, что держала, и подтверждение проходит.

Проверка ждёт, пока zurg закончит определять точные размеры файлов релиза или откажется от этого. Это та же точка, на которой проверяет endpoint SABnzbd. Определение размеров читает первую статью каждого файла, и проверка делает то же самое, поэтому запуск обоих одновременно только замедлял оба. В списке из 99 фильмов проверка каждого релиза сразу после появления в списке отодвинула загрузку последнего файла в папку Radarr почти на девять минут. Проверка, которая всё ещё ждёт размеров, когда у неё кончается время, сразу запускается заново, как и проверка, которая не уложилась по времени. Релиз, размер которого всё ещё определяется через 30 минут, всё равно проверяется. Одновременно проверяется не больше шести релизов, остальные ждут своей очереди.

Проверка только читает. Она не переносит тела статей в кэш и не записывает мёртвые статьи, поэтому не может заглушить файл, который воспроизводится. Когда проход определения размеров только что загрузил первую статью файла, проверка читает эту копию и не загружает её второй раз.

Установка без аккаунта NZB (nzb или torbox_nzb) не может проверить граб NZB. Получение при этом всё равно работает, если дебрид-аккаунт принимает торренты. Каждый торрент проверяется по тому, попадает ли он в библиотеку с файлами внутри, как описано в разделе Newznab and Torznab. Ему также нужно содержать то, что можно воспроизвести: видео, аудио или архив, который zurg отдаёт потоком (RAR, 7z, zip или пронумерованные части). Торрент, который содержит только программу, образ диска или текст, является подделкой. Такие подделки часто появляются в первые часы после выхода новых серий. Его откладывают как мёртвую публикацию, и следующий релиз пробуется сразу. Если zurg добавил торрент на аккаунт ради этого запроса, его удаляют с аккаунта. Торрент, который уже был на аккаунте, остаётся на месте. Граб NZB никогда не подтверждается без аккаунта NZB, потому что проверить или воспроизвести его будет нечем. Запрос, который остался в ожидании ещё с тех пор, как удалили последний аккаунт NZB, откладывается как мёртвая публикация, и пробуется следующий релиз.

Сохранение и восстановление

data/acquisition.json хранит ID источников и запросов, попытки, сроки повторов, работу в процессе и квитанции по отдельным загрузкам, включая эпизоды. Там же для каждого источника записано, что первый снимок был принят, поэтому only_new_items решается один раз, а не при каждом перезапуске. Подходящие медиацели и издания используют квитанции совместно между источниками. Имена файлов релизов тоже дедуплицируются относительно библиотеки и сохранённых NZB. Квитанция также содержит захваты, по которым ещё ждётся ответ от новостных серверов, а реестр хранит релизы, уже признанные нерабочими. Поэтому перезапуск в середине ожидания не подтверждает непроверенный захват и не возвращает нерабочий релиз в ранжирование. Квитанциям нельзя доверять вечно. Прежде чем считать тайтл имеющимся, zurg проверяет, что то, что его закрыло, всё ещё на месте: загруженное видео в папке Radarr или Sonarr, а для тайтла из списка желаемого DMM, списка просмотра Plex или Seerr сам релиз в библиотеке. Если его удалили, тайтл ищется снова, даже если он всё ещё числится в списке и задача завершена. Релиз, удалённый со страницы manage, снова не берётся.

Каждый сохранённый релиз сразу записывается на диск. Счётчики попыток и времена повторов записываются в течение минуты, поэтому при сбое можно потерять до минуты этих данных, но никогда не захват. При записи сначала сохраняется временный файл, затем реестр заменяется, и родительский каталог сбрасывается на диск, там где это поддерживается. NZB, записанные до сбоя, переиспользуются, даже если последняя запись реестра не завершилась. Как только загрузка записана, повторные попытки удаления из Plex не запрашивают тайтл снова.

Неудачи повторяются через 5, 10 и 15 минут, затем через час и через шесть часов. Дальше тайтл ждёт вдвое дольше, чем уже падает, поэтому ожидания растут: примерно полдня после суток неудач, два дня после четырёх, около недели максимум, с погрешностью в четверть. Так тайтлы, которые упали вместе, не повторяются вместе. Попытка, которая исчерпала свои пять минут и ничего не нашла, тоже считается неудачей. Но если ничего не найдено, пока один из ваших индексеров не мог быть опрошен, потому что он попросил оставить его в покое до времени не дальше чем через сутки (Retry-After), это неудачей не считается. Тайтл пробуют снова после этого времени, но не более чем через такой же промежуток после него, чтобы очередь тайтлов не запрашивала индексер сразу. Если индексер отдыхает десять минут, следующая попытка будет в пределах двадцати. Так происходит не больше трёх раз подряд, после чего попытка считается как обычно. Индексер, который не называет времени, например отвечающий 410 Gone или отказывающий в ключе, не ждут. Тайтл, который падает две недели и при этом сделал не меньше восьми попыток, становится parked (припаркован): zurg перестаёт спрашивать о нём индексеры. Он остаётся на странице acquisition как parked, с указанием, как долго и почему он падал, а в логе это пишется один раз. Resume на этой странице, для одного тайтла или для всех припаркованных тайтлов источника, запускает его снова с первого короткого повтора. Если источник перестаёт перечислять тайтл, а затем снова его перечисляет, это значит, что он запросил тайтл заново, и это тоже его возобновляет. Захват, подтверждённый новостными серверами, начинает две недели тайтла заново, поэтому сезон, который ещё находит эпизоды, никогда не паркуется. Не паркуется и апгрейд из любого источника: его лучший релиз может выйти через месяцы, а тайтл остаётся в списке. Поэтому повторы для него идут не реже чем раз в неделю. Не паркуется и ничто из списка желаемого DMM, по той же причине: фильм, который ещё не вышел, или старый, который никто не выложил, остаётся желаемым, пока его не получат или вы его не удалите. Счётчики и сроки переживают перезагрузки, включая долгие выключения.

Очередь, которая падает вечно, обходится дорого так, как не показывает список тайтлов. На одной установке тысячи тайтлов Radarr и Sonarr, для которых ничего не нашли и которые повторялись каждые шесть часов навсегда, подняли нагрузку на индексер с нескольких сотен запросов в день до десятков тысяч, и индексер приостановил аккаунт. Большинство из них были фильмами без релиза Usenet, а также апгрейдами, для которых каждый релиз, разрешённый профилем, уже был отклонён. Открытые запросы Seerr остаются под наблюдением. Элементы Plex покидают список просмотра только после того, как все запланированные сезоны получены и проверены (NZB по новостным серверам или, на аккаунте torbox_nzb, по тому, забрал ли TorBox файл; торрент по тому, что библиотека получила что-то для воспроизведения). Это происходит только тогда, когда remove_after_grab это разрешает, и только если zurg что-то для них получил. Его резервный механизм для отдельных эпизодов по-прежнему ограничен эпизодами, найденными в результатах индексеров.

Недоступный источник приостанавливает только свою работу. Неудачная запись состояния приостанавливает дальнейший захват, пока сохранение не пройдёт успешно. Нечитаемый или неподдерживаемый реестр приостанавливает захват и сохраняется как есть: почините или восстановите его и перезапустите zurg. Другие службы zurg продолжают работать.

Предыдущий data/plex-watchlist.json импортируется один раз вместе с историей, повторами и попытками, которые ждут только удаления из Plex. Исходный файл сохраняется. Оба реестра включаются в обычные бэкапы без --include-caches. Сохраняйте data/ и nzbs/ при замене контейнеров.

Добавление другого адаптера

Реализуй acquisition.Source в отдельном пакете:

  1. ID() определяет инстанс, чтобы он оставался тем же после перезапусков.
  2. List(ctx) возвращает полный снимок ссылок на Item. Если пагинация выдаёт ошибку, снимок целиком считается неудачным. Сохраняй только метаданные, никогда не сохраняй учётные данные или полные объекты пользователя из API.
  3. Resolve(ctx, item) заново проверяет элемент и возвращает нормализованные цели: фильм, сезон или эпизод. Gone отменяет ненужную работу. Follow оставляет открытый запрос под наблюдением, когда текущие цели уже получены.
  4. Complete(ctx, item) подтверждает разовую загрузку. Метод должен спокойно переносить повторные вызовы после сбоя. Для списка только для чтения можно сделать пустую реализацию (no-op). Движок вызывает его только тогда, когда все граб-запросы по элементу ответили, поэтому адаптеру никогда не нужно самому проверять релиз. При этом сам факт вызова не должен восприниматься как доказательство чего-либо, кроме этого.

Источник с собственным профилем качества может также реализовать acquisition.Assessor, оценивая каждый кандидат-релиз по его собственным правилам. Адаптеры Radarr и Sonarr так и делают, через свои парсеры.

Зарегистрируй тип конфигурации и фабрику в сервисе acquisition. Очередь, персистентность, повторные попытки и исполнитель не должны содержать веток, специфичных для источника. Trakt, MDBList и Simkl подходят под этот контракт, но пока не реализованы.
