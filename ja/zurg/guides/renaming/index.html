リリースとファイルの名前変更

zurg のマウントで書き込みできるのは 1 つだけです。リリースのフォルダーや、その中のファイルの 名前を変更する ことができます。ライブラリのどこでも可能です。これはデフォルトでオンになっています。何もコピーされず、何もダウンロードされず、debrid アカウントにも触れません。新しい名前はリリースの横に保存され、zurg が本来計算する名前より優先されます。

できないのは、何かを 移動する ことです。ファイルマネージャーでは名前の変更と場所の移動が同じ操作に見えますが、zurg はこの 2 つを正反対のものとして扱います。その理由は 最後のセクション で説明しています。

名前ではなく レイアウト（フォルダーの配置など）を保存したい場合、たとえば *arr が移動でインポートする場合は、__magic__ を見てください。このページでは名前だけを扱います。

マウント経由での名前変更

A rename in the mount is a WebDAV MOVE whose destination differs from the source in the last path segment alone. rclone turns a rename on the mount (a FUSE rename(2), or its WinFsp counterpart on Windows) into exactly that, so mv or Rename-Item in the mount, renaming in Finder, Explorer or another file manager, and a WebDAV client all arrive at the same handler.

mv "/mnt/zurg/shows/Show.S01.1080p.WEB-DL/Show.S01E01.mkv" \
   "/mnt/zurg/shows/Show.S01.1080p.WEB-DL/Show - s01e01.mkv"

mount_path を変更していなければ、macOS でのマウント先は /Volumes/Zurg です。

 
Rename-Item -LiteralPath "Z:\shows\Show.S01.1080p.WEB-DL\Show.S01E01.mkv" -NewName "Show - s01e01.mkv"

どちらのレベルでも動作します。

名前の変更 保存先の形式
リリースフォルダー Torrent.Rename
リリース内のファイル File.Rename

/dav/ と /infuse/ のエンドポイントは MOVE に対応しています。/http/ は対応していません。読み取り専用のブラウザで、__magic__ の外では 405 を返します。

名前が満たすべき条件

新しい名前は、前後の空白を削除した後に、空でなく、/ や \ を含まず、自分自身の filepath.Clean と一致する場合に受け付けられます（これにより . と .. も拒否されます）。さらにリリースフォルダーの場合は、別のハッシュのアクセスキーと衝突しないことも必要です。ファイル名は、そのリリース内で一意である必要があります。

結果 ステータス
名前を変更できた 201
名前が空、区切り文字を含む、またはディレクトリ名だけを指す宛先 400
その名前はすでに使われている 412
ソースが見つからない 404
アーカイブの内部、または下記の理由で拒否された 403

アーカイブの内部にあるファイルの名前を変更することはできません。アーカイブの中身はアーカイブから生成されるため、名前を書き込める場所がないからです。zurg は、アーカイブ内のファイルは名前を変更できないというメッセージとともに 403 を返して、この操作を拒否します。

ダッシュボードと API からの名前変更

同じ2つの名前変更は POST エンドポイントです。それぞれに対応するリセットがあり、保存された名前を削除して、リリースを計算された名前に戻します。

POST /manage/{torrentHash}/rename
POST /manage/{torrentHash}/clear-rename
POST /manage/{torrentHash}/files/{fileid}/rename
POST /manage/{torrentHash}/files/{fileid}/clear-rename

マウント経由で clear-rename に相当するものはありません。元の名前に戻す名前変更は、その名前を保存するだけで、上書きを削除するわけではありません。

シーズンの修正

GET /torrents/season-fix/plan と POST /torrents/season-fix/apply は、Plex 自身のエピソードマッチングを使ってファイル名を一括で変更する機能です。ファイルの番号の付け方が解析できないリリース向けに用意されています。plan は読み取り専用で、ファイルごとにスキップされた理由を表示します。apply では「すべて適用」フラグではなく、ハッシュの明示的なリストを渡します。確認したものだけを適用できるようにするためです。

名前変更で残るもの

保存された名前はリリース自体に紐づいていて、その .zurgtorrent にシリアライズされるため、次の場合も保持されます:

  • ライブラリの更新。プロバイダーのリストからリリースのファイルエントリを作り直す更新も含みます。
  • 再起動。
  • 修復。ハッシュを使ってリリースを新しいIDで再追加する操作です。
  • プロバイダーが裏側でトレント名を変更した場合。Real-Debrid はこれを行います。

名前は持ち運びもできます。エクスポートした .zurgtorrent にはリネームも含まれるため、ローカルライブラリ は付けた名前のまま届きます。

保存された名前が残らないのは ignore_renames: true を設定したときだけです。これはこのキーの目的そのものです。zurg は保存済みの名前をすべて無視して計算された名前を表示し、マウント経由での新しいリネームも受け付けなくなります。リネームは削除されるのではなく無視されるだけなので、この設定を元に戻すとリネームも戻ります。

名前変更の前後で変わるもの

リネームは「ビュー」の変更にすぎませんが、その上にいくつかのものが作られていて、それらもリネームに合わせて更新されます。

  • マウント。 rclone のディレクトリキャッシュを古いパスと新しいパスの両方で無効化するので、キャッシュの期限切れを待たなくても変更が反映されます。
  • .strm ファイル（save_strm_files が有効な場合）。古いファイルは削除され、新しい名前で書き直されます。
  • Plex と Jellyfinには、そのリリースを改めて確認するよう依頼されます。
  • ディスク上のキャッシュ記録。 .zurgtorrent は新しい名前で書き込まれ、古いファイルは削除されます。この削除は重要です。古いファイルを残したままにすると、再起動時に両方が読み込まれ、ハッシュの衝突によってもう一方のコピーに解決されてしまい、リネームが黙って元に戻ります。これは 2026-08-17 に実際に見つかったバグです。
  • SABnzbd と qBittorrent のエンドポイント。 ポーリングのたびに Sonarr と Radarr に報告するフォルダを計算し直すので、インポートの途中でリネームしても、インポート元のパスが新しい場所に移され、取り残されることがありません。

3 つの落とし穴

リネームすると、次のリフレッシュでリリースが別のディレクトリに移ることがあります。 ディレクトリへの振り分けは、directories: のフィルターをリリース名に対して実行して決まります。そしてフィルターが見るのはリネーム後の名前です。リネーム自体はフィルターを再評価しないので、リリースは元のディレクトリに残ります。ただ、次のリフレッシュでは再評価されます。名前の一部でマッチしていたフィルターに、新しい名前が合わなくなっていると、リネームした時点では何も気づけないまま、あとでリリースが別のディレクトリに移ります。名前で振り分けているフィルターがある場合は、慎重にリネームしてください。

拡張子を変えると、ファイルの扱いも変わります。 episode.mkv を episode.txt に変えることは止められません。拒否されるのは区切り文字だけです。ただ、ファイルが見えるかどうかはクライアントが見る名前で判定されるため、リネーム後のファイルは only_show_the_biggest_file の対象から外れたり、再生可能ファイルの判定から外れたり、メディアサーバーのスキャンに引っかからなくなったりします。

すでに別の場所に渡した .strm の URL は壊れます。 署名付きトークンにはアクセスキーとファイル名が含まれているため、リネーム前に取得した URL はリネーム後には解決できず、404 が返ります。zurg が作る .strm のツリーは書き換えられますが、そこから URL をコピーして別の場所で使っているものは書き換えられません。

無効にする方法

キー デフォルト 効果
dav_allow_rename true false にすると、マウントからの MOVE を 403 で拒否します。本文にはキー名が表示されます。
ignore_renames false true にすると、保存されたリネームをすべて無視して計算された名前を返します。また、マウント経由の新しいリネームは 403 で拒否されます。
mount_read_only false true にすると、rclone が --read-only 付きで起動します。そのため、zurg に届く前にカーネルが書き込みを拒否します。

dav_allow_rename はマウントを対象とします。ダッシュボードのエンドポイントは対象外で、デブリッドアカウントに接続されない __magic__ 配下への書き込みも対象外です。 ミラーだけは例外ですが、これはこのキーが理由ではありません。__magic__/__all__ と、その直下にあるリリースフォルダーは、ライブラリ自体のレイアウトです。そのため、この設定に関係なく、いずれへの書き込みも拒否されます。リリースフォルダーの中は通常どおり扱われます。

mount_read_only はすべてを上書きし、カーネルレベルで効きます。マウントの DELETE を止められる唯一の方法でもあります。リネームより重要な理由は config.md を参照してください。

名前変更は拒否されず、移動が拒否される理由

試すこと ステータス
リリースフォルダを別のディレクトリに移動 403
ファイルを別のリリースに移動 403
ファイルを、同じリリース内のサブフォルダに移動 400
トップレベルのディレクトリの名前変更や移動 405
__magic__ の外へ移動 403
__magic__/__all__ への書き込み、またはその直下の名前への書き込み 403

どの場合も根っこにあるルールは同じです。名前の変更は保存先がありますが、移動にはありません。

リリースの名前はリリース自身が持つ1つの文字列なので、新しい名前を書き込むのはフィールドへの代入になります。以降のすべての検索はその値を読み返します。

でもトップレベルのディレクトリはフォルダではなく、保存されたフィルターです。その所属は、更新のたびに directories: の設定から計算し直されます。リリースを movies に「入れる」移動をしても何も書き込まれません。その問いへの保存済みの答えを読む者がいないからです。次の更新でフィルターから所属が計算し直され、移動は取り消されてしまいます。拒否するのが正直な答えです。

リリース内のサブフォルダも同じです。その形はアカウント自身のファイル一覧から決まります。

__magic__ が存在するのは、保存されたレイアウトが本当に役立つからです。また、保存先がないふりをせず、その問題を解決しています。この中での移動は、コンテンツハッシュをキーにした小さなテーブルに1行書き込みます。だから、リリースが新しいIDで再登録される修復を経ても残ります。そのテーブルは、意図的に1つの名前空間に限定されています。

拒否の範囲を気軽に広げない理由が、もう1つあります。rclone の移動拒否に関するドキュメントでは、移動を予期していないクライアントに対して、拒否された MOVE が何をするかを説明しています。rclone 1.72.0 では、VFSエントリが試みた移動先を指したままになります。さらに、copy-then-delete にフォールバックする呼び出し元は EOF を読んで成功と報告し、本人は書いたつもりの0バイトのファイルができあがります。上のすべての拒否は、何かが耐えなければならない拒否なのです。
