# `__magic__`、整理できるディレクトリ {#__magic__-a-directory-you-can-organise}

他の zurg のディレクトリはすべて計算によって生成されます。`movies` はムービーフィルターを適用し、`__all__` にはすべてが含まれます。

リリースフォルダには、アカウントが報告する内容がそのまま入ります。レイアウトは更新のたびに組み直されます。

`__magic__` は**保存された**パスを持つ唯一のディレクトリです。移動すると、テーブルの1行だけが書き換えられます。ファイルの実体は動かず、debrid アカウントも変わりません。手で整理するか、Sonarr と Radarr に使わせてもかまいません。

ここには3種類のものがあります。`__magic__/__all__` には、まだ何も配置されていないリリースがすべて入ります。これはダウンロードクライアントがインポート元にするフォルダです。計算によって生成されるため、トップレベルには何も作成できず、リリースフォルダがすでに持っている名前にファイルの実体を書き込むこともできません（リリースフォルダは、使われていない名前でサイドカーを受け入れます）。DMM のスポンサーキーがあれば、zurg は DMM が識別したものすべてをタイトルごとに `__movies__` と `__shows__` に振り分けます（[下記](#__movies__-and-__shows__-sorted-by-title)を参照）。`__magic__` の直下にあるその他のものは、すべてあなたのものです:

```
/mnt/zurg/__magic__
├── __all__     <- what nothing has placed yet, where a grab lands
├── __movies__  <- films zurg filed by title
├── __shows__   <- shows zurg filed by title
├── __anime__   <- anime shows, with magic.anime: true
├── anime
├── movies
└── tv          <- your *arr root folders
```

このページのパスは Linux のマウント `/mnt/zurg` を使っています。macOS では `/Volumes/Zurg`、Windows では `Z:\` です。つまり `/mnt/zurg/__magic__/tv` は `/Volumes/Zurg/__magic__/tv` または `Z:\__magic__\tv` になります。

その分離がこの仕組みのポイントです。クライアントが*インポートする元の*フォルダと*インポート先の*フォルダは兄弟の関係にあり、どちらも相手を含みません。そのため、ダウンロードフォルダを指定した手動インポートがライブラリツリーをたどることはなく、Sonarr も Radarr もこの配置について警告しません。

この機能はデフォルトではオフです。次のように設定してオンにします:

```yaml
magic:
  enabled: true
```

そのあと再起動してください。ルートはスタートアップ時に決まるため、ダッシュボードから切り替えただけでは、再起動するまで名前空間が応答しません。

## 何のための機能か {#what-it-is-for}

\*arr は、ファイルをダウンロードフォルダーからライブラリーへ**移動**することでインポートします。zurg にはその移動を受け取る先がなかったため、\*arr はコピーにフォールバックしていました。debrid マウントからのコピーは、リリース全体をネットワーク越しに丸ごとダウンロードすることを意味します。マウントがそもそも避けるためにあるのは、まさにそれです。

`__magic__` を使うと、インポートは一つの名前空間の中での名前変更になります。行が書き込まれ、ファイルは \*arr が置いた場所に現れ、何もダウンロードされません。これがあるからこそ、[SABnzbd エンドポイント](sonarr-radarr.md) に価値があるのです。SABnzbd エンドポイントはこの仕組みの上に載った薄い層で、これがなければインポートのたびに全ダウンロードが発生してしまいます。

これが機能するには、\*arr の **ルートフォルダーも `__magic__` の内側になければなりません**。例えば `/mnt/zurg/__magic__/tv` であり、マシン上の別の場所にあるディレクトリではいけません。移動先が名前空間の外にあると、二つのファイルシステムの間の移動になり、それは再びコピーになってしまいます。そのため zurg はこれを `403` で明確に拒否し、黙って実行させることはありません。名前空間内で唯一拒否される場所は `__magic__/__all__` の最上位です。これはライブラリー自体のレイアウトであり、ファイルを置く場所ではないからです。正確な設定は [sabnzbd.md](sonarr-radarr.md) にあります。

`__all__` の外に配置されたファイルは、そこにも表示され続けます。また `__all__` での削除はアカウントからの削除になります。そのため zurg は、ここでの配置が `__all__` などのライブラリーフォルダーからストリーミングしている間は、そのライブラリーフォルダー経由でのファイル削除を拒否します。代わりに `__magic__` 配下で削除してください。これにより、`__all__` からインポートした後にダウンロードフォルダーをクリーンアップする \*arr（DMM の SABnzbd プロキシに接続されたものなど）が、インポートしたばかりのリリースを削除してしまうことを防ぎます。

また \*arr は、ダウンロードフォルダーとルートフォルダーに**一つのマウントを通じて**到達できなければなりません。`__magic__/__all__` と `__magic__/tv` を別々のボリュームとして与えられたコンテナは、両方とも zurg のものであっても二つのファイルシステムとして見えます。そのためカーネルは、zurg がそれを知る前にコンテナ内でのリネームを拒否し、\*arr はファイル全体をコピーしてしまいます。zurg は、着地したそのようなコピーを後から配置に変換し `A client copied …` とログに記録しますが、その時点でダウンロードはすでに完了しています。zurg のマウント全体を含む一つのディレクトリをコンテナにバインドしてください。[ダウンロードフォルダーとルートフォルダーに一つのボリューム](sonarr-radarr.md#one-volume-for-the-download-folder-and-the-root-folders) を参照してください。

zurg 自身の取得処理もここにファイルを配置します。Radarr のソースは、確認した各リリースを、インポートと同じ移動でムービーのフォルダーに置き、その後 Radarr に再スキャンを依頼します。[acquisition.md](acquisition.md#placing-the-file) を参照してください。

zurg はまた、`__movies__` と `__shows__` に自分でファイルを配置します。[下記](#__movies__-and-__shows__-sorted-by-title) を参照してください。

ライブラリーを手作業で整理することがもう一つの方法で、\*arr が関与しなくても機能します。

## 何も保存されていない場合、`__all__`のリリースが実際のフォルダとして表示される {#with-nothing-stored-it-is-__all__s-releases-as-real-folders}

`__magic__/__all__` を新規インストール直後に開くと、`__all__` にあるリリースがすべて、それぞれフォルダとして表示されます。テーブルは空の状態から始まり、デフォルトからの**差分**だけを保存します。そのため、何も変更していないライブラリは何も保存せず、`__magic__` のルートにはミラーだけがあります。新しいリリースは、他の場所に現れた瞬間にここにも現れます。何かがリリースを配置すると（\*arr のインポートや zurg 自身による `__movies__` と `__shows__` への振り分け）、そのリリースは `__magic__/__all__` から外れます。ミラーは、まだ何にも配置されていないものが置かれる場所です。

ここにはディレクトリ設定はありません。`only_show_the_biggest_file` もサイズフィルターもありません。リリースが持っているものがそのまま見えます。

`__all__` との唯一の違いは、**リリースフォルダの中身の形**です。それ以外の場所では、zurg はリリースを1つのディレクトリにフラット化し、ファイル名で並べます。2つのファイルが衝突する場合は、サフィックスを付けます：

```
__all__/Show.S01/Show.S01E01.mkv
__all__/Show.S01/Gag Reel (Extras).mkv
```

`__magic__/__all__` では、リリースが実際に持っているツリーをそのまま表示します：

```
__magic__/__all__/Show.S01/Show.S01E01.mkv
__magic__/__all__/Show.S01/Extras/Gag Reel.mkv
```

これは見た目だけの話ではありません。Sonarr と Radarr はダウンロードフォルダを、フォルダとしてスキャンします。`extras`、`samples`、`featurettes`、`trailers`、`deleted scenes` という名前の**サブフォルダ**の中にあるファイルはスキップされ、トップレベルにあるファイルは対象になります。そのため、フラット化された `Gag Reel (Extras).mkv` はインポート候補として提示されますが、実際のツリーでは対象外になるはずです。また、\*arr のインポートは、フォルダに動画が1本しかない場合にだけ、ダウンロードの元のタイトルを解析に使うフォールバックを行います。特典映像と並んでフラット化された映画は、このフォールバックが効かなくなります。[SABnzbd エンドポイント](sonarr-radarr.md) は \*arr に `__magic__/__all__` 配下のフォルダを渡すので、これらのルールが適用されるのはこの部分です。

この形には、次の2つの詳細があります：

- **1階層のラッパーフォルダは取り除かれます。** ほとんどのリリースは、すべてを入れた1つのフォルダになっています。そのフォルダ名は、リリースがすでに**そう呼ばれている**名前です。デブリッドバックエンドはこの名前を、そのフォルダから導出しています。そのため、`/Show.S01/Season 01/ep1.mkv` は `Show.S01/Season 01/ep1.mkv` と表示され、`Show.S01/Show.S01/Season 01/ep1.mkv` にはなりません。取り除くのは1階層だけで、その隣に何もない場合だけです。トップにファイルがあり、その横にフォルダがある場合は、両方とも残ります。
- **重複名のサフィックスは付けません。** サフィックスは、フラット化された一覧を曖昧にしないためのものです。ツリーにはそのためのディレクトリがあります。

リリースフォルダのそれ以外の部分は変わりません。アーカイブも同じです。RAR セットは引き続きディレクトリとして閲覧でき、ボリュームがツリー内にある場所に表示されます。1つのアーカイブとしてフラット化されて提供されているリリースは、そのアーカイブの中身を引き続き一覧表示します。

`__all__` と `directories:` フィルターは、フラットのままです。これらはメディアサーバーを向けるべき場所であり、これらについては何も変わりません。

## 整理する {#organising-it}

マウント経由で、普通のコマンドを使います:

+++ Linux
```bash
mkdir -p /mnt/zurg/__magic__/tv/The\ Show/Season\ 01
mv /mnt/zurg/__magic__/__all__/Some.Release.S01E01.1080p/ep1.mkv \
   /mnt/zurg/__magic__/tv/The\ Show/Season\ 01/S01E01.mkv
```
+++ macOS
```bash
mkdir -p /Volumes/Zurg/__magic__/tv/The\ Show/Season\ 01
mv /Volumes/Zurg/__magic__/__all__/Some.Release.S01E01.1080p/ep1.mkv \
   /Volumes/Zurg/__magic__/tv/The\ Show/Season\ 01/S01E01.mkv
```
+++ Windows
```powershell
New-Item -ItemType Directory -Force "Z:\__magic__\tv\The Show\Season 01"
Move-Item -LiteralPath "Z:\__magic__\__all__\Some.Release.S01E01.1080p\ep1.mkv" `
  -Destination "Z:\__magic__\tv\The Show\Season 01\S01E01.mkv"
```
`-LiteralPath` を付けると、多くのリリース名に含まれる角括弧がワイルドカードとして解釈されるのを防げます。
+++

ファイルは新しいパスに移動し、古いパスからは消えます。ストリーミングは、これまでと同じアカウントから続きます。

リリースフォルダ全体も、1 行で移動できます:

+++ Linux
```bash
mv /mnt/zurg/__magic__/__all__/Some.Movie.2024.2160p /mnt/zurg/__magic__/movies/Some\ Movie\ \(2024\)
```
+++ macOS
```bash
mv /Volumes/Zurg/__magic__/__all__/Some.Movie.2024.2160p /Volumes/Zurg/__magic__/movies/Some\ Movie\ \(2024\)
```
+++ Windows
```powershell
Move-Item -LiteralPath "Z:\__magic__\__all__\Some.Movie.2024.2160p" -Destination "Z:\__magic__\movies\Some Movie (2024)"
```
+++

ディレクトリは、中身もまとめて 1 つのバッチとして移動します。移動は双方向に使えます。ファイルはリリースフォルダの外から中へも、中から外へも移動でき、フォルダには、そのリリース自身のエントリと並んで表示されます。取り込み元のフォルダに何かを戻すプログラムには、この動作が必要です。同じ名前が 2 つの場所から同時に来る場合は、あなたが意図的に行った方が勝ちます。移動したものはリリースの名前より優先され、リリースの名前は `data/local` の実ファイルより優先されます。負けた方は二重に表示されず、一覧から外されます。

組み込みマウントでは、1 つの操作だけ失敗します。それは既定の `union_writable: local` の場合に限ります。マウント経由で作成したディレクトリの名前を変更する操作、つまり `mkdir` の後に、そのディレクトリに対して `mv` を実行するケースです。既定の順序では、`mkdir` が rclone 自身のローカル upstream にディレクトリを作ります。一方で、その下の行がサーバー側にも同じディレクトリを存在させます。そのため rclone はローカル側のコピーの名前を変更し、行を 1 ファイルずつ移動します。zurg はそれぞれの操作に正しく応答します。しかし、その後で、すでに名前を変えてしまった移動元を削除しようとして失敗します:

```
ERROR : __magic__/tv/Saul: Dir.Rename error: RenameDir rmdir: object not found
```

行は指定した場所に正しく配置されます。zurg は新しいパスを返し、古いパスには 404 を返します。ただし `mv` は終了コード 1 で終わります。また、ディレクトリの一覧を再読み込みするまで、マウントには空になった移動元が表示されたままで、移動先は表示されません。この削除のリクエストは zurg に届かないため、zurg 側では防げません。ファイルの移動やリリースフォルダ全体の移動は、どちらの順序でも動作します。マウント経由でディレクトリを整理する場合は、[`union_writable: server`](../reference/config.md#rclone-settings) を設定してください。この設定では、ディレクトリは名前空間にだけ存在し、名前変更はサーバー側の 1 回の操作になります。

測定: rclone 1.71.2 で確認しています。

`rm` は中身を隠すだけです。詳しくは [削除は隠すだけで、破棄はしない](#deleting-hides-it-does-not-destroy) を参照してください。

## `__movies__`と`__shows__`をタイトル順に並べる {#__movies__-and-__shows__-sorted-by-title}

KodiとPlexは、ファイルが何かをフォルダー名とファイル名から判断します。`Succession.S01.MULTi.1080p.BluRay.REMUX.AVC-DEMS`のようなリリース名は、多くの場合、読み取るには複雑すぎます。リリース名のままだと、テストではKodiが56作品中8作品しか認識できませんでした。

DMMのスポンサーキーがあれば、zurgはDMMが識別したすべてのリリースを、プレイヤーがすぐに照合できる名前の2つのフォルダーに振り分けます：

```
__magic__/__movies__/Casper (1995) {tmdb-8839}/Casper (1995) {tmdb-8839}.mkv
__magic__/__movies__/Casper (1995) {tmdb-8839}/Casper (1995) {tmdb-8839}.nfo
__magic__/__shows__/Detective Conan (1996) {tmdb-30983}/tvshow.nfo
__magic__/__shows__/Detective Conan (1996) {tmdb-30983}/Season 01/Detective Conan (1996) - S01E1194 [tmdbid-30983].mkv
```

同じライブラリをこの方法で振り分けると、Kodiと Plexは70本の映画、44作品のシリーズ、554話すべてを照合できました。

### 有効にする {#turning-it-on}

zurg のナイトリービルド（2026-10-26 以降のもの）、`__magic__` を有効にした状態、そして [gatekeeper](https://gatekeeper.debridmediamanager.com/) にスポンサー登録すると一度だけ表示される DMM API キーが必要です:

```yaml
magic:
  enabled: true
dmm_api_key: YOUR_DMM_API_KEY
```

zurg を再起動してください。ライブラリの読み込みと DMM による識別が終わると、2つのフォルダにファイルが入ってきます。大きなライブラリだと、初回は数分かかることがあります。その後は、DMM が新しいリリースを識別してから1分以内にファイルが振り分けられます。次に、**Movies** ライブラリを `/mnt/zurg/__magic__/__movies__` に、**TV** ライブラリを `/mnt/zurg/__magic__/__shows__` に向けて追加し、スキャンしてください（macOS の場合は `/Volumes/Zurg/__magic__/...`、Windows の場合は `Z:\__magic__\__movies__` と `Z:\__magic__\__shows__`）。Kodi では、TV ソースのスクレイパーをデフォルトのまま **The Movie Database** に設定し、最新の状態に保ってください。`tvshow.nfo` ファイルには Kodi の TMDb TV スクレイパーのバージョン 1.7 以降が必要です。

各ライブラリは必ずそれぞれのフォルダに向けてください。`__magic__` 自体を指定すると `__all__` や他のフォルダまでスキャンされ、同じものが二重に見つかってしまいます。

### 何をするか {#what-it-does}

- **映画かシリーズかは、DMM が判定したとおり**に決まります。フォルダのルールでは決めません。シリーズのパックに入っていた映画は、その映画として分類されます。
- **同じシリーズのリリースはすべて 1 つのフォルダに入ります**。シーズンとエピソードの番号は TMDB の番号付けに従い、Plex がデフォルトで使う順番になります。話数で番号が付いたアニメは、そのシーズンに配置されます。`Detective Conan - 1194` は S01E1194 になります。
- **TMDB ID はフォルダ、すべてのファイル名、`.nfo` に入ります**。こうしておけば、各プレーヤーが探す場所で見つかります。Plex はフォルダ、Kodi は `.nfo`、ファイル名しか読まないプレーヤーはファイル名から見つけられます。
- **1 タイトルにつきコピーは 1 つだけ**。同じエピソードや映画の別リリースが複数ある場合は、解像度、次にサイズで良いほうを分類します。残りは `__all__` に残ります。
- **エクストラとサンプルは `__all__` に残したまま**にします。DMM が特定できなかったものも同じです。リリースは、DMM が特定した時点で分類されます。

### アニメを専用のフォルダに入れる {#anime-in-a-folder-of-its-own}

アニメ番組は、3つ目のフォルダ `__anime__` に分けて置けます。そうすると、Kodi と Plex で専用の Anime ライブラリが使えます。アニメ用に2つ目の Sonarr を置いていた場合と似た仕組みです。必要なのは 2026-11-10 以降の zurg nightly で、さらに次の1行を追加します:

```yaml
magic:
  enabled: true
  placement: true
  anime: true
dmm_api_key: YOUR_DMM_API_KEY
```

zurg を再起動してから、`/mnt/zurg/__magic__/__anime__` を指す **TV** ライブラリを追加して、スキャンしてください。何をアニメとみなすかは DMM が TMDB の情報をもとに判断します。TMDB でアニメーション（animation）に分類され、言語が日本語で国が日本の番組、この3つすべてに当てはまる番組、または TMDB で *anime* キーワードが付いている番組が対象です。Detective Conan、Ace of the Diamond、Cyberpunk: Edgerunners は `__anime__` に入ります。Hazbin Hotel（米国のアニメーション）、Alice in Borderland（日本の実写）、LINK CLICK（中国のアニメーション）は `__shows__` に残ります。映画は、アニメ映画を含めて `__movies__` に残ります。Movies ライブラリは1種類のタイプしか扱えず、このフォルダも同じだからです。

この設定をオンにすると、数分以内にすべてのアニメ番組が `__shows__` から移動します。プレイヤー側では、番組がひとつのライブラリから消えて、別のライブラリに現れるように見えます:

- **Plex** は、番組を TV ライブラリから外します（「missing」として残るか、スキャン後にゴミ箱を空にする設定なら完全に削除されます）。そして次のスキャンで Anime ライブラリに取り込みます。視聴状況も引き継がれます。Plex は視聴状況をライブラリではなく番組に紐づけるため、TV ライブラリで視聴したエピソードは Anime ライブラリでも視聴済みと表示されます（2026-11-09 に確認）。
- **Kodi** は視聴状況をファイルのパスに紐づけます。そのため、この設定をオンにする前に動画ライブラリをエクスポートしてください（Settings → Media → Library → Export）。Anime ソースをスキャンした後に、インポートし直します。

オフにすると、同じ仕組みで番組は元の場所に戻ります。

### DMMのウィッシュリストを使う {#with-the-dmm-wanted-list}

DMMで**Want**を押すと、zurgがそのタイトルを取得します（[DMMのwanted list](dmm-wanted.md)）。取得したものはほかのものと同じようにここに整理されるので、映画やドラマは Kodi や Plex に自分の名前で表示されます。Sonarr や Radarr は使いません。トレントで取得したものが整理されるまでには最大1時間かかることがあります。NZBの場合は、DMMがそれを識別するとすぐに整理されます。

### SonarrとRadarrを使う {#with-sonarr-and-radarr}

Sonarr と Radarr は自分のライブラリを保持します。zurg 経由で取得したリリースは、取得した時点から `__all__` に残るので、彼らがインポートできます。zurg が彼らの配置したファイルを移動させることはありません。彼らが、zurg がすでに整理したタイトルを自分のルートフォルダへ移動してインポートした場合、そのタイトルは以後彼らのものになり、zurg はそのまま残します。

Kodi と Plex でも同じようにライブラリを合わせるには、次のようにします。

- 各アプリで **Settings → Metadata → Kodi (XBMC) / Emby** を有効にします。これで映画や番組ごとに、タイトルの ID を含む `.nfo` が作られます。zurg はそれを残します。
- フォルダ名に ID を入れます。**Settings → Media Management** で設定します。

  | | フォルダ形式 |
  |---|---|
  | Radarr | `{Movie CleanTitle} ({Release Year}) {tmdb-{TmdbId}}` |
  | Sonarr | `{Series TitleYear} {tvdb-{TvdbId}}` |

### 知っておくと良いこと {#good-to-know}

- **プレーヤーで削除すると、ファイルは非表示になります**。`__magic__` で行った削除はすべて同じ扱いです。ファイルはデブリッドアカウントに残り、zurg が再度ファイルすることはありません。
- **`__movies__`、`__shows__`、`__anime__` には何も移動できません**。これらは zurg が管理するフォルダーです。\*arr のインポートのように、そこから別の場所へ移動するのは問題なく行えます。
- **DMM がリリースの識別情報を変更した場合**、zurg はファイルを新しい名前へ移動します。
- **壊れたファイルは、修復中もその場所に残ります**。そのため、メディアサーバーからファイルが消えることはありません。
- **DMM のスポンサーキーがないと、何もファイルされません**。キーを削除しても、`__magic__` をオフにしても、すでにファイルされたものはそのままの場所に残ります。

## 移動は修復、名前変更、再リストでも維持される {#a-move-survives-repair-rename-and-re-listing}

zurgは壊れたリリースを、アカウントに再度追加することで修復します。このとき、トレントID、アクセスキー、ファイルIDがすべて変わります。そのため、これらのどれかをキーにしたテーブルでは、リンクが腐るたびにすべての配置を失ってしまいます。代わりに、各行は**コンテンツハッシュ**とリリース内でのファイルの**パス**をキーにしています。どちらも修復では変わりません。

これは意図した動作で、結果は次のとおりです。

- **修復してもレイアウトは保たれます。** リリースは新しいIDで戻ってきますが、ファイルは配置した場所にそのまま残ります。
- **リリース名を変えても何も移動しません。** 名前の変更と、同じフォルダー名になる2つの別リリースに対してzurgが付けるサフィックスは、どちらもリリースの既定フォルダー名を変えます。配置には影響しません。
- **見つからなくなったファイルも忘れられません。** 修復でファイルセットが変わった場合（Real-Debridがrarのリリースを再パックするのが典型的な原因です）、対応するファイルが存在しなくなった行は**残りますが、一覧には表示されません**。ファイルが戻ってくれば、その位置も戻ります。この状態の行はダッシュボードに**dangling**と表示され、そこで削除できます。
- **リリースを削除して再度追加しても、レイアウトは保たれます。** DMMの再追加や、同じリリースを削除してから新たに追加した場合でも、同じハッシュが戻ってきます。ファイルは配置した場所に戻ります。また、\*arrがインポート後に削除するジョブフォルダーなど、削除したフォルダーは非表示のままです。リリースを`__magic__/__all__`に再度表示するには、ダッシュボードの`__magic__`ページでリリースを検索し、そのリリースの release tombstone にある **Unhide** を押してください。

Usenetのバックエンドでは、正確なパス一致だけでは不十分です。Usenetの投稿のファイル名は与えられるものではなく**解決**されるもので、読み込みのたびに再計算され、保存はされません。ニュースサーバーに接続できないときに読み込まれた投稿は、後で再読み込みして本当の名前を取得できるまで、難読化された名前のままになります。その間、行はまずNZB内のファイルのインデックスで照合し、それでも決まらない場合は、ちょうど1つのファイルだけが一致するときに限り、ベースネーム＋サイズで照合します。

## 削除は非表示にするだけで、完全には消えない {#deleting-hides-it-does-not-destroy}

`rm` を `__magic__` の下で実行すると、**トゥームストーン**が作られます。エントリは `__magic__` から消えますが、`__all__`、すべてのフィルターディレクトリ、そしてデブリッドアカウント上では元の場所に残ります。何も削除されません。

これは臆病だからではありません。*arr を安全に向けられるようにするための仕組みです。品質アップグレードの際、*arr は古いファイルを削除し、インポートの際にはジョブフォルダ全体を削除します。これらの削除でコンテンツが消えてしまうと、アップグレードでリリースそのものが壊れてしまいます。また、削除が*行*だけを消すだけだと、ファイルは既定の場所に戻ってしまい、*arr がインポート元にしているフォルダにそのまま戻ってきてしまいます。

削除を本当に削除として動かしたい場合は、次を設定してください:

```yaml
magic:
  allow_delete: true
```

この設定を有効にすると、**ファイル**の削除はアカウントからもコンテンツを削除します。リリースフォルダとディレクトリは、この設定が何であっても決して削除されません。リリースフォルダは Sonarr がインポートのたびに削除するものだからです。

アーカイブ内のエントリは、ほとんどの Usenet リリースにおけるエピソードや映画にあたります。エントリ自体のファイルはありません。アーカイブにはリリース内の他のすべても入っています。そのため、`__magic__` の下のどこも残りの部分を使っていない場合にのみ、そのエントリを削除するとリリース全体が削除されます。そのアーカイブのどのファイルも、どこかに配置されたままであってはいけません。そのエントリのフォルダも削除されているか、インポートするものが何も残っていない必要があります。これは、アップグレードによって置き換えられた Usenet エピソードが置かれる状態です。この処理が入るまでは、置き換えられたリリースはライブラリに残り続け、その NZB も `nzbs/` に残り続けていました。

単独の動画ファイルは、それ単体で削除されます。`__magic__` の下のどこもそのリリースのものを使っていなければ、リリースも削除されます。判断に使われるルールは同じ2つです。

リリースは動画以外も投稿されることが多いです。`.nfo`、字幕、ポスターが動画の横に置かれていますが、それらを誰もインポートしません。この処理が入るまでは、唯一の動画が削除された後もリリースがライブラリに残っていました。その NZB は `nzbs/` に残り、デブリッドのリリースもアカウントに残っていました。

同じパックの別のエピソードが配置されているか、まだリリースフォルダにある場合は、リリースは残ります。移動されたリリースフォルダがある場合も同様に残ります。読み取りが停止していても、修復される可能性があるエピソードも残ります。投稿された場所にあるサイドカーを削除しても、リリースは削除されません。Sonarr や Radarr が動画の横にインポートした最後の字幕を削除した場合にのみ、リリースが削除されます。

`dav_allow_rename` と、マウント自体がゲートなしで行う削除パスは、この件とは一切関係ありません。これらは、デブリッドアカウントが保持しているものの名前変更や破棄を行う経路を扱います。`__magic__` の下への書き込みはどのアカウントにも届きません。`mount_read_only: true` は、カーネルレベルで依然としてすべてを上書きします。

トゥームストーンを元に戻すには、ダッシュボードでクリックするだけです。

そのため、アップグレードによって置き換えられたリリースは、ライブラリに残ります。**Manage > Duplicates** には、*arr が今使っているリリースと並んでそれらの残存物が一覧表示され、選んだものを削除できます。詳しくは [重複リリースの見つけ方](acquisition.md#finding-duplicate-releases) を参照してください。

## フィルターと`__all__`には影響しない {#filters-and-__all__-are-untouched}

移動したリリースは、元の名前のまま `movies` にも `recent` にも `__all__` にも残ったままです。`__magic__` は同じライブラリを別の角度から見たビューで、場所を移すものではありません。

これに驚く人は多いので、はっきり書いておきます。**`__magic__` で何かを移動しても変わるのは `__magic__` だけです。** フィルターのディレクトリはリリースの情報から計算されていて、そのリリース自体は変わっていないからです。

メディアサーバーで使うなら、どちらか**一方だけ**を指定してください。`shows/` と `__magic__/tv` の両方をスキャンする Plex ライブラリだと、すべてのエピソードが二重に見つかってしまいます。`__movies__`、`__shows__`、`__anime__` も同じです。ライブラリを向けるのは、そのどれか一つにしてください。`__magic__` 自体は指定しないでください。

## サイドカー: `.nfo`、ポスター、字幕 {#sidecars-nfo-posters-subtitles}

\*arr は動画のすぐ横にメタデータを書き込み、Bazarr は字幕を書き込みます。これらは実際のファイルですが、zurg にはデブリッドのライブラリ内に置く場所がないため、`data/local/__magic__/` 以下のローカルディスクに保存されます。

Bazarr の設定と、字幕が rex にどう届くかについては、[Bazarr での字幕](subtitles.md) を参照してください。

zurg の組み込みマウントを使っている場合、これはすでに自動で行われるので、あなたが何かをする必要はありません。マウントは `data/local` と zurg の WebDAV を合わせたユニオンで、rclone は新しく作られたファイルをすべてローカル側に送ります。zurg はその書き込みにすら気づきません。これが Sonarr の "is this folder writable?" テストが通る理由でもあります。

`/dav` を自分でマウントする場合（自分の rclone、Infuse、Windows の WebDAV ドライブなど）、zurg は `PUT` を受け付けて、同じツリーに書き込みます。そのため、両方の見え方は一致します。上限は 2 つあります:

```yaml
magic:
  sidecar_max_mb: 32       # per file
  sidecar_budget_mb: 2048  # the whole tree
```

1つ目の上限を超えると `413`、2つ目の上限を超えると `507` が返されます。これらは *zurg* が書き込む量を制限するものです。デフォルトの `union_writable: local` の場合、rclone 自身のローカル側への書き込みはここから拒否することはできません。ただし、拒否する前にツリーのサイズは再計測されます。そのため、rclone が置いたファイルは、zurg が次にファイルを書き込もうとしたときに上限の計算に含まれます。ただし `sidecar_max_mb` より大きいファイルは除外されます。

`union_writable: server` にすると、この扱いが逆になります。ファイルの作成そのものが zurg に届くため、マウント経由のすべての書き込みも上限で判断されます。また `__magic__` の外への書き込みは、すべて即座に拒否されます。

サイドカーはリリースフォルダの中に置くこともできます。\*arr は、取り込んだファイルの `.nfo` をここに書き込みます。zurg は、そのリリースがまだ使っていない名前であれば、どの名前でもサイドカーを書き込み、名前変更できます。リリース自身のファイルと同じ名前になるものは拒否します。サイドカーに対する `DELETE` は本当に削除されます。これは `__magic__` の中で、削除がトゥームストーンにならない唯一の場所です。トゥームストーンは、ライブラリが別の場所に持っているエントリを隠すだけですが、サイドカーのデータは `data/local` にしか存在しないためです。

## ダッシュボード {#the-dashboard}

ライブラリの読み込みが終わると、zurg はテーブルに何行あるか、そのうち何行が dangling（参照切れ）かを 1 行でログに出力します。そのため、コンテンツを失ったライブラリに、どれにも言及されない行が増え続けることはありません。

zurg の通常のポートにある `/magic/` では、テーブルの中身が分かります。保存されているすべての行がリリースごとにまとめられ、それぞれが何で、どこから来たのかが表示されます。dangling の行は専用のセクションに並びます。さらに、サイドカーのツリーとそのサイズを予算と比べて表示します。ジャーナルとスナップショットのサイズや、`data/local` 全体のサイズも報告されます。後者の数値は、何かがコピーによってインポートされているかどうかを示すものです。デフォルトの `union_writable: local` では、移動ではなくコピーを行うクライアントがそのバイトをそこに書き込み、ほかの場所には何も表示されないからです。

`union_writable: server` の場合、この数値はゼロのままで、代わりにログがその状況を伝えます。コピーを行うクライアントの `PUT` は拒否されるため、本来そのクライアントが埋めるはずだったツリーには何も書き込まれません。拒否されてもバイトは保存されません。rclone のキャッシュがそれを保持して再試行しますが、もはや zurg が数えられる名前でこのディスク上に存在するわけではありません。[qBittorrent ガイド](sonarr-radarr-torrents.md)に原因が書かれています。原因は、どの場合もクライアント側の設定です。\*arr は、ダウンロードを後で削除してもよい場合にだけ、インポートを移動で行うからです。

そこから、配置をリセットする（ファイルがデフォルトの場所に戻る）、削除マーカー（tombstone）を消す（エントリが戻る）、dangling の行を削除する、それらすべてを一括削除する、サイドカーを削除する、といった操作ができます。どの操作も、実行前に確認が求められます。

保存された行の一覧には最初の 1000 行だけが表示されます。\*arr が整理しているライブラリでは、これはテーブルのごく一部にすぎません。インポートのたびに削除マーカーが残るからです。特定のリリースに到達するには、検索してください。リリース名、マウント上のパス、またはハッシュを入力すると、テーブルの大きさに関係なく、そのリリースに関するすべての行が、それぞれのボタン付きで一覧表示されます。dangling の一覧も同じ検索を使えます。ライブラリにもう存在しないリリースは、テーブルに名前がなく、ハッシュと、その行が指しているパスだけが残ります。

もはや**どの行とも対応しない**サイドカーは、ほかとは別に一覧され、件数も数えられます。たとえば、ライブラリから消えたリリースの隣にある `.nfo` や、忘れられた配置の中にある `.nfo` です。それでもこれらは配信され続けます。実ファイルは、パスが最後に解決される先だからです。その上にそれを主張する上位のものもありません。失われたのは、それが置かれた理由のほうです。zurg がこれを自動で掃除することはありません。zurg ではなくマウント経由で、サイドカー用に自分で作ったディレクトリも同じように表示されます。そのようなディレクトリにも行が残らないからです。

SABnzbd エンドポイントが有効な場合、このページには SABnzbd のジョブも表示されます。ID、名前、カテゴリ、状態、そして \*arr に渡されたフォルダです。「なぜ Sonarr がまだダウンロード中と表示しているのか」を調べる最も早い方法です。

## 耐久性 {#durability}

`data/magic.journal` に変更がすべて追記され、リクエストに応答する**前**にディスクへ書き出されます。そのため、\*arr が移動できたと認識したものは、クラッシュしても残ります。ジャーナルは、起動時、一定サイズを超えたとき、シャットダウン時に `data/magic.json` のスナップショットへまとめられます。

どちらのファイルも、テーブルを変更するための場所ではありません。zurg はテーブルをメモリ上で保持し、そこから `magic.json` を書き出します。そのため、zurg の実行中にファイルから手で削除した行は、次の再起動後に元に戻ります。変更にはダッシュボードのボタンを使ってください。

電源が切れたときに途中まで書かれた最後の行は破棄されますが、それより前のデータはすべて残ります。別のスキーマバージョンで書かれたスナップショットは、推測で読み込まず破棄されます。また、別バージョンのジャーナル行に当たると、そこでリプレイを止めます。スナップショットやジャーナルが読み込めない場合は、起動を失敗させず、警告を出して空のテーブルとして扱います。テーブルのファイルを*開けない*場合、`__magic__` は `__all__` と同じく読み取り専用で提供され続け、すべての書き込みは拒否されます。シャットダウン中に届いた書き込みは、確認応答をしてから失われるのを防ぐため、`503` で拒否されます。

## ステータスコード {#status-codes}

WebDAV で名前空間を直接操作する場合に役立ちます。マウントを使えば、これらはすべて自動で処理されます。

| Code | Meaning |
|---|---|
| `201` | MOVE、MKCOL、PUT で何かが作成された |
| `204` | DELETE、または sidecar を置き換えた PUT |
| `400` | この名前空間に保存できないパス、または読めない、もしくは存在しない `Destination` ヘッダー |
| `403` | `__magic__` の外、または `__movies__`、`__shows__`、`__anime__` の中への宛先、ライブラリが応答するパス、ファイルの中を通るパス、`__magic__` 自体、または読み取り専用のテーブル |
| `404` | そこに何もない（何もないものを DELETE しても `204` が返ります）、またはエントリがもう存在しないアーカイブからの MOVE |
| `405` | 既に何かが存在する場所への MKCOL、またはディレクトリへの PUT |
| `409` | 親がない、ディレクトリが空でない、`Overwrite: T` の場合に占有されている宛先、または開けないアーカイブからの MOVE |
| `412` | `Overwrite: F` の場合に占有されている宛先 |
| `413` / `507` | `sidecar_max_mb` または `sidecar_budget_mb` を超えた場合 |
| `503` | シャットダウン中、または今は元のソースを提供できない MOVE。`Retry-After` 付き |

`MOVE` は `__magic__` の外への宛先を拒否します。フィルターディレクトリは読み取り専用のままです。

**アーカイブから**の `MOVE` は、何かが書き込まれる前にアーカイブ自体もチェックされます。インポートは `MOVE` で行われ、成功した `MOVE` の後は誰も再チェックしてくれません。また、クライアントがたどったリストは根拠になりません。解析済みのアーカイブ内容はメモ化されるため、バイトが消えたリリースでもエピソードの一覧が表示され続けることがあります。そのため、まずボリュームの健全性、リリースの記事の損傷、そしてそれらで判断できない場合はアーカイブ自体が確認されます。これは同じパスに対する `HEAD` が確認するのとまったく同じです。健全なリリースは、一覧表示のときに作られたのと同じメモから応答します。二度と読めないソースは `409`、今は読めないソースは `Retry-After` 付きの `503`、アーカイブに存在しない名前は `404` のままです。拒否された場合、何も記録されません。

## 知っておきたい制限 {#limits-worth-knowing}

- **`magic.enabled` は再起動が必要です。** ルートは起動時に登録されるからです。
- **1ファイルにつき配置は1つだけです。** ファイルをもう一度移動すると再配置されます。同じファイルを2つのパスに置くことはできません。
- **rarセット内のファイルも**、他のファイルと同じように配置できます。行にはボリュームと内部のパスが記録されるので、再パックしても通常のファイルと同じように残ります。ただし、配置済みファイルの*下*には何も作成できません。配置済みファイルを経由するパスは拒否されます。
- **`__magic__` の一覧では `serve_strm_files` は無視されます。** この名前空間の目的は、\*arrが実ファイルをここから移動することです。`.strm` は、どのインポート処理でも取り込めるファイルではないからです。ただし、名前を指定して要求したクライアントには引き続き応答します。
- **パスは届いたとおりに正確に比較されます。** Unicodeの正規化も大文字小文字の変換も行わないため、クライアントが名前の綴りを違えて要求すると見つかりません。
