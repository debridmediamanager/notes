TorBoxの制限と、zurgがそれにどう対応するか

zurg のライブラリ動作は Real-Debrid の制約に合わせて育ってきました。TorBox の制約は規模が違うだけでなく、性質そのものが違います。Real-Debrid と同じように扱うと、最初のライブラリスキャンから数秒でアカウントがレート制限を受けてしまいます。ここでは、その制限が何か、数値がどこから来ているか、そして zurg が各制限にどう対処するかを説明します。

プロバイダーの制限はコード内で debrid.Capabilities として宣言されており、汎用のライブラリコードはそれを直接読み取ります。そのため、ほかのバックエンドを追加するときは、この構造体を埋めるだけで済みます。torrent マネージャーを編集する必要はありません。

レート制限

上限 値 出典
全エンドポイント合計、APIトークンごと 300/min 公式
POST /torrents/createtorrent（キャッシュにないものだけ） 60/hour 公式に記載
POST /webdl/createwebdownload、POST /usenet/createusenetdownload 60/hour 公式に記載
GET /torrents/requestdl 約100回の呼び出しの後に429 — レートではなく予算 実測、2026-08-30
1つのCDNホストへの同時接続数 ちょうど20、それを超えると429 実測、2026-08-23
全体のバースト上限 約40の同時接続で発動し、全エンドポイントを絞る 実測
429からの回復 Retry-After: 300、二択の切り替え 実測

上限はAPIトークンごとで、TorBoxのサーバー間で同期されています。IPごとではないので、他のマシンからの追加クライアントも同じ予算を共有します。TorBoxも明言していて、上限はトークンで管理されているため、IPホワイトリストの申請受付を停止しました。

見出しの300/minの数字より厳しくなる理由が3つあります:

  • 300/minはエンドポイントごとではありません。 キー全体で使う1つの予算なので、各エンドポイントを個別にペース調整すると、どれも単独では超えない上限を合計が超えてしまうことがあります。

  • requestdlはドキュメントより遥かに厳しく、しかもレートではありません。 ダウンロードURLを発行するエンドポイントで、同じ同時実行数でuser/me、mylist、checkcachedが500回以上を処理できたのに、約100回で打ち切られました。

    ペースを落としても増えません。2026-08-30にメインアカウントで実測しました。各回ロックアウトをリセットした状態から3回ずつ実行:

    ペース 429が発生した時点 経過時間
    できるだけ速く、60→240/minに段階的に上げる 呼び出し 100 回目 56s
    1秒に1回（60/min） 呼び出し 94 回目 108s
    2秒に1回（30/min） 呼び出し 101 回目 198s
    3秒に1回（20/min） 発生せず — 241回 721s、問題なし

    レートを半分にすると90秒多く使えただけで呼び出し数は増えず、さらに半分にすると429は一切発生しませんでした。このアカウントが持っているのは 5分間のローリングウィンドウで100回、つまり20/min で、4回の実行すべてに合うのはこの解釈だけです。最初の3回ではt≈100s、t≈200s、そして即時に発生すると予測し、4回目はちょうど境界線上で耐えると予測します。

    このファイルの残りを読むうえで一番大事な訂正です。分単位のリミッターではzurgを予算内に収められないので、以下のペース設定の数値は余裕を作るためではなく滑らかさのためのものです。リミッターを速くしてもライブラリスキャンが早く終わるわけではなく、同じロックアウトに早く到達して、発生すると5分間マウントが何にも応答しなくなるだけです。スキャンがどこまで進むかを決めるのは 呼び出しを減らすこと だけです。だからここでは先読みを見送り、解決済みファイルの名前付けでリクエストを1回も使ってはいけないのです。

  • 429は坂ではなく崖です。 一度発動すると、約5分間すべてのリクエストが失敗します。耐えられる部分的なスループット低下はありません。

CDNのダウンロードは別で計測され、APIの予算は共有 しません。ファイルのストリーミングがリンク解決の枠を消費することはありません。これは両方向で確認しました。CDNダウンロードを429まで飽和させてもrequestdlは正常に応答し続け、逆も同様でした。

どちらも20という数字の、2つの異なる制限

上の表には 20 が2回出てきますが、この2つは無関係です。混同しやすく、間違ったものを制限してしまう原因になります。

  • requestdl の同時実行 ~20 は API の上限です。この同時実行数だと、429 が返されるまでに約100回の呼び出しができ、アカウントのリクエスト枠を消費します。
  • CDN ホストあたり 20 接続 は バイト転送経路 の上限です。2026-08-23 に、段階的に増やしながら計測しました。requestdl の呼び出しは一切不要で、一度取得済みの URL を再利用するだけで到達します。

バイト転送経路の上限は ちょうど 20 です。なだらかに頭打ちになるのではなく、厳密な上限として動作します。24、32、40、48 接続を要求しても、常に 20 接続で安定し、上限を超える分は接続拒否（refusals）として返されます。

これは CDN ホスト単位であり、オブジェクト単位でも IP 単位でもありません。以前の「Cloudflare 層での IP 単位」という理解を訂正するものです。

  • 1つの nexus-NNN ホストから配信される 異なる2つのファイル は、20 の上限を1つの枠として共有し、超過分は同じように拒否されます。
  • 同じ負荷を2つのホストに分けると、問題なく動作します。
  • 同じ IP から、16 ホストに分散した 32 の同時ストリームは問題ありません。

同じ方法で計測した他のプロバイダーとの比較です。Real-Debrid はホストあたり 32 が上限で、TCP 層で HTTP ステータスなしに拒否します。AllDebrid は 32 で、HTTP 429 を返します。Premiumize は 64 まで上限が見られませんでした。TorBox の 20 は、4社の中で最も低い数値です。

TorBox のグローバルエッジには、この上限はありません。 20 は、requestdl が発行するノードごとの nexus-NNN.<region>.tb-cdn.st ホストの特性です。2つのグローバルエッジ（nexus.erth.tb-cdn.earth と nexus.hare.tb-cdn.earth）は、アカウント内の任意のファイルを配信でき、どちらも 64 同時接続まで段階的に増やしても拒否はゼロでした。異なるのはホストだけで、パスとトークンは今もリクエストの認証に使われます。zurg は現時点ではそちらへ書き換えません（兄弟サービスの debrid は TORBOX_CDN_EDGE 経由で書き換えます）。そのため、ここでは下記の上限が適用されます。

zurgがやること

  • GetTorrentInfo は torrent 一覧から返されます。 TorBox の mylist にはすべての torrent のファイル一覧がすでに含まれているため、ライブラリの更新は torrent ごとに 1 回ずつではなく、リクエスト 1 回で済みます。これは Capabilities.ListIncludesFiles として宣言されています。このフラグを設定したプロバイダーでは、更新処理が torrent ごとの呼び出しとディスク上の情報キャッシュの両方をスキップします。torrent が 213 件あるアカウントでは、リクエスト数が 213 回から 1 回になります。

  • 1 つのリミッターですべてのエンドポイントを制御します。 上限は文書化された 300/分に対して 240/分に設定しています。同じキーを使う他のもの（TorBox のダッシュボード、別のクライアント、2 つ目の zurg など）のために余裕を残しています。

  • requestdl には、さらに別のリミッターがあります。 上限は 15/分です。解決処理は両方のリミッターから枠を使います。この数値は実測の 20/分ちょうどではなく、少し下に設定しています。理由は、全体のリミッターを 300 ではなく 240 にしているのと同じです。枠はそのキーを持つすべてのものが使うため、20/分は他に何も使っていない状態で測定された値だからです。TestTheRequestdlBudgetCannotBeSpentInsideItsWindow が本当に守りたい条件を検証しています。つまり、枠を全部使い切ると、それを補充するウィンドウの中で使えてしまう、という状態を防ぎます。そのため、この定数がこっそり上限を超える値に戻ることはありません。

  • ダウンロードクライアントは、CDN ホストごとに 20 接続までに制限しています。 （internal/torbox/client.go の maxConnsPerCDNHost。rdclient.HTTPClientOptions.MaxConnsPerHost 経由で渡しています。）Go の MaxConnsPerHost は、21 個目のリクエストを失敗させるのではなく、空きの接続ができるまで待たせます。そのため、この上限によって、プロバイダーによる拒否が手元でのキューイングに変わります。この設定がないと、ダウンロードクライアントは汎用トランスポートの無制限設定を引き継いでしまい、すべての API リミッターを守っていても、バイト転送の段階で 429 を受ける可能性がありました。

  • 429 応答が出ると、すべての呼び出し元を Retry-After の時間だけ待機させます。 各呼び出しが個別にリクエストを消費してロックアウトを確かめ直す、という無駄を防ぎます。このロックアウトはアカウント単位なので、どれかのエンドポイントで 429 を受けると、他のすべてのエンドポイントも待機します。

  • 同時実行は、処理中のリクエストを 16 件までに制限しています。 これは全体のバースト上限（約 40）より低く、ダウンロードクライアント用の余裕を残すためです。

  • 先読みはしないことにしました。 zurg は、コールドリードの際に、そのリリースの次のファイルを先に温めます。分あたりの枠に実際の上限があるバックエンドなら、これを吸収できます。問題になるのはライブラリのスキャンです。スキャンは各ファイルを 1 回ずつ開くため、開くたびにコールドになります。そのため、ウォームリードの拒否判定が一度も働かず、ファイル 1 つにつき 2 回の解決がアカウントに要求されてしまいます。2026-08-30 の計測では、40 ファイルのスキャンで、読み込み 40 回と並行して投機的な解決が 40 回発生しました。誰も求めていないファイルのために、枠の半分を使っていたことになります。TorBox は Capabilities.SpeculativeResolutionsAffordable を false として宣言しており、投機的な解決は一切要求されません。

  • 解決済みファイルの名前取得では、リクエストを消費しません。 解決のたびに、ダウンロード記録用にそのファイルの名前とサイズを調べます。以前はこの調べ物をリストのスナップショット経由で行っていたため、30 秒の鮮度ウィンドウが切れると、次の読み込みでは答える前に torrent 一覧全体を取得する必要がありました。スキャン中は 30 秒ごとに、スキャンが続く限りこれが繰り返され、3,700 件のライブラリでは一覧取得が 4 ページ分に及びました。今は、そのリストがどれだけ古くても、手元にある一覧をそのまま読みます。完了した torrent のファイル名とサイズは変わらないため、これで問題ありません。

  • リンクキャッシュは 1 日保持し、明示的な拒否があった場合は回復します。 2026-08-30 の検証では、requestdl を繰り返し呼ぶと、1 時間後であっても同じ URL が返されました。また、3 時間 25 分経過した URL でもまだ 206 が返されました。これは再利用されることを示していますが、無期限に有効だという意味ではありません。2026-09-04 には、正しく認証された、キャッシュ済みの URL が 400 と「Invalid Presigned Token」を返しました。一方で、同じ torrent とファイルに対する新しい解決では、別のホストとパスが返され、206 が配信されました。クエリは変わっていませんでした。古い URL のパスとクエリだけを新しいホストに移しても、やはり 400 が返されました。

    24 時間のキャッシュは、枠の使い方を考えた結果です。スキャンは 20/分で解決を進めるため、数時間かかることがあります。明示的な無効トークンの拒否があった場合、その URL を無効にして、新しく解決し直します。同時に読み込む処理は解決の作業を共有します。また、遅れて届いた拒否が、より新しいキャッシュ済み URL を追い出すことはありません。新しく解決した URL も拒否された場合、そのファイルに問題があると判断せず、再生をローカルで 1 分間一時停止します。曖昧な 400 は、URL が古いという証拠にはならないため、短いクールダウンを発生させるだけです。CDN からの 429 では Retry-After を保持し、ファイルをまたいで、また検証の呼び出しも含めて、そのホストへの読み込みを待機させます。API の枠は別管理のままです。

  • すべての一覧呼び出しで bypass_cache=true を指定します。 TorBox 側の mylist キャッシュの TTL は約 5 分です。そのキャッシュから返すと、WebDAV マウントが実際の状態より 5〜15 分遅れる原因になります。このパラメーターはレート制限の枠を消費せず、反映までの時間を 1 秒未満に短縮します。

  • ポーリング 1 回につき、一覧取得も 1 回だけです。 ライブラリの変更ポーリングだけが強制的に取得を行います。変更を検知することがその役割だからです。同じティックで行うアクティブ数の取得と、変更後に続く完全な更新は、直前に埋められたスナップショットを読みます。ここでも強制取得すると、ポーリング 1 回につきライブラリ全体を 2〜3 回読み直すことになります。デフォルトの 10 秒間隔では、1 日に数千回もの無駄なライブラリ全体の読み込みが発生します。しかも、zurg がすでにバイパスしている、TorBox 側の一覧キャッシュに対してです。

  • 一覧は 1000 件ずつのページに分けて取得します。 mylist は 1 回の応答を 1000 件までに制限します。これは limit の文書化されたデフォルト値で、それ以上を指定しても上限は上がりません。一方で、総数も「まだ続きがある」という情報も返しません。そのため、1 回のリクエストでは、件数の多いアカウントに対して最新の 1000 件だけが返り、完全なライブラリとまったく同じに見えてしまいます。zurg は、ページが不足するまで offset でページングを続け、途中で ID の重複を除去します。一覧は ID の降順で並んでいるため、取得の途中で新しい torrent が追加されると、ウィンドウが 1 つずれ、境界で同じ項目が重複して現れることがあるためです。

出典: アカウント制限。

/user/me はプランを数字で返しますが、その数字は価格順ではありません: 0 Free, 1 Essential, 2 Pro, 3 Standard。Standard は Pro の後に追加されました。2026-10-03 まで zurg はプラン 2 を Standard として読んでいたため、Pro アカウントは 5 スロットと Standard の利用下限を与えられていました。

アクティブスロットは TorBox を特徴づける制限で、Real-Debrid では帯域幅がそれにあたります。 トレントはダウンロード中も シーディング中も スロットを占有するため、有料プランでは完了したトレントが最長 30 日間スロットを使い続けることがあります。

zurgがやること

  • GetActiveTorrentCount は、プランの実際の上限を報告します。 user レコードの plan から読み取るため、repair は上限に達するとブロックして待機し、アカウントに拒否される追加を queue に入れなくなります。プロバイダーが上限を報告しない場合は、永遠にブロックするのではなく、無制限として扱います。

  • 追加したトレントは、デフォルトで seed しない設定になります。 Seeding は数週間もスロットを占有し、送信トラフィックも課金されるため、ストリーミング用のマウントには何の役にも立ちません。プライベートトラッカーで ratio を気にするオペレーターの場合は、tb_seed_torrents で変更できます。never は seed=3（デフォルト）を送信し、always は seed=2 を送信し、auto はこのフィールドを省きます。TorBox 自身によるこのフィールドの説明は "1 is auto. 2 is seed. 3 is don't seed. Optional. Default is 1, or whatever the user has in their settings. Overwrites option in settings" です。つまり、1 を含め送信した値はどれもアカウントの Seeding 設定を上書きし、フィールドを省いた場合だけ設定が適用されます。同じモードは 3 つの追加パスすべて（magnet 追加、キャッシュのみの追加、.torrent のアップロード）に適用されます。Seeding を有効にすると、完了したトレントがスロットを保持し続けるため、seed 中のトレントがすべてのスロットを占有すると、repair と download-client エンドポイントが上限に当たって止まります。

  • 追加する前にキャッシュを確認することは一切ありません。 checkcached は呼び出し箇所が一つもありません。キャッシュのみモード（qbittorrent.download_timeout_mins: 0）だけが例外でしたが、現在はこのモードでも他のバックエンドと同じように、トレントを追加してインスタンスを監視する方式に変わりました。理由は、このエンドポイントが報告するのは、コンテンツが TorBox のキャッシュにあるかどうかであって、このアカウントが実際にそれを保持できるかどうかではないからです。キャッシュにない場合は実際にコストがかかります。キャッシュにない追加は、確認だけなら消費しなかった 60 回/時の枠を消費します。キャッシュにある追加は、引き続き 300 回/分の枠の対象です。

コンテンツの有効期限

Pro のコンテンツは30日で期限切れになります。期限切れのトレントは、API からは expired または reported missing として返ってきます。それでも download_finished: true と download_present: false は報告されたままです。

download_finished だけを見ると、どのリンクも 404 になるトレント全体をマウントしてしまいます。zurg は両方の表現を error ステータスにマップし、Capabilities.ContentExpires でそれをバックエンドの通常の状態として扱い、障害とはみなしません。

この2つのブール値だけでは、データが消えたとは判断できません。 正常なキャッシュなしダウンロードも、processing、downloading、uploading を経る間の最後の 9.6 秒間は download_finished: true と download_present: false を報告します。これは 2026-08-30 に 0.5 秒間隔のポーリングで測定し、docs/torrent-lifecycle.md にまとめてあります。以前の zurg は、state の文字列に関係なくこの組み合わせを死とみなしていたため、delete_error_torrents: true で動いているインスタンスでは、ダウンロードの途中でこうしたトレントが削除されてしまいました。当日だけで5つのプローブ用トレントがこの形で消えています。現在は、download_state がまったくないペイロードに対してのみ構造ルールで判断します。コードがまだ見たことのない表現は、代わりに作業中として扱われます。processing も測定されるまではそうした表現の一つだったからです。

それでもそうしたファイルに読み取りが届いた場合、呼び出し回数は1回では済まなくなりました。配信パスは、発行済みの配信 URL に対する 404 を、ファイルがないのではなく失効したリンクとして扱います。これは Real-Debrid での挙動と同じで、Real-Debrid ではダウンロードの行が削除されるとコードが無効になります。そのため、諦める前に再解決を行います。その結果、期限切れの TorBox ファイルは、1回の読み取りあたり requestdl を最大4回呼び出すようになりました（以前は1回）。呼び出し回数は読み取りごとに上限があり、一覧ではすでにそのトレントが error とマークされているので、この速度で期限切れのライブラリ全体を走査することはありません。ただし、同じ期限切れパスを連続で叩くクライアントは、以前の4倍のコストを払うことになります。

zurgがやること

期限切れになるバックエンドのトレントは、何があっても自動で再追加されません。 修復では、壊れたトレントのマグネットをもう一度追加します。これは、コンテンツを保持するバックエンドでは修復になりますが、期限切れにするバックエンドでは再ダウンロードになります。ライブラリ全体にこれをタイマーで繰り返すのは、TorBoxがアカウント停止の理由として最初に挙げている行為です。「excessive transfer retention (using tools to artificially keep transfers active)」（転送を人為的に維持するツールを使った過剰な転送保持）がそれにあたります。さらに、キャッシュされていない再追加はどれも、プランの枠に数えられる受信転送になります。

そのため、定期スキャンは、修復可能なコピーがContentExpiresを宣言しているプロバイダーにあるトレントをスキップします。これらは壊れたまま表示され続けます。ダッシュボードの修復ボタンは引き続き動作しますし、Real-Debridにも同じリリースがあれば、そのコピーからいつも通り修復されます。違いは何が壊れたかではなく、誰が要求したかです。

利用状況と不正利用対策システム

TorBox は、リクエストを細かく取り締まったりはしません。代わりに、15日間のローリングウィンドウで転送されたバイト数を測ります。その上限は、各プランの99パーセンタイルから導き出された値です。警告は3回出て、警告のたびに API キーがローテーションされます。4回目でBANです。公表されている下限（動的しきい値がこれ以下にはならない値）は次のとおりです。

Plan Floor
Free 5 TB/month
Essential 10 TB/month
Standard 20 TB/month
Pro 30 TB/month

カウントは両方向です。キャッシュされていない追加の受信と、デバイスやスウォームへ送り出すすべての送信が対象になります。キャッシュ済みの追加は対象外です。計測はバイト単位で正確なので、一部だけ読んだファイルは読んだ分だけのコストになります。

/user/me の cooldown_until は、これらの警告のどれでもありません。 これを警告だと読むと、丸1日を無駄にします。2026-08-12 に plan-2 のアカウントで検証しました。クールダウンが有効で、たった今設定されたばかり（24時間後まで、updated_at は1分前）の状態です。このとき /user/me、checkcached、mylist はすべて 200 success:true を返し、WebDAV の PROPFIND は 207 を返しました。さらに bytes=0-0 の範囲読み取りは、正しい Content-Range 付きで 206 を2.8秒で返しました。どの層でもサービスが拒否されることはありませんでした。このアカウントの累計転送量は14.1 GBで、月30 TB の下限には遠く及ばないので、これは帯域制限ではなく API レート制限のクールダウンでした。見分けるポイントはキーです。本物の警告ではキーがローテーションされ、その後すべてのエンドポイントが AUTH_ERROR を返します。一方、キーがそのままのクールダウンでは、目に見える影響はありません。そして checkcached は、TorBox が実際には配信しないリリースをキャッシュ済みと報告することがあるため、範囲読み取りだけがサービス可能かどうかを確かめられるプローブです。TorBox が使えないと結論づける前に、必ずバイトの経路を確認してください。

出典: The TorBox Abuse System。

zurgがやること

  • 追加したtorrentはデフォルトでは決してseedされないため、zurgが読むだけのコンテンツについて外向きの課金は発生しません。tb_seed_torrents: always（またはseedする設定のアカウントでのauto）だけがこの動作を変える設定で、そのときのアップロードも通常どおり課金されます。
  • 使用量はサンプリングして差分を取ります。 APIは直近の値を公開しておらず、/user/meで生涯カウンターだけを取得できます。そのため、アカウントのリフレッシャーが30分ごとにこのカウンターをdata/torbox_usage.jsonに記録し、サンプル同士の差分を計算します。直近30日の使用量がプランの下限の80%を超えると、警告ログが出ます。この警告こそがサンプリングの目的です。ダッシュボードに表示されるのはzurg自身がプロキシした分だけで、この差分は表示されません。新規インストールには履歴がないため、安心できる0を表示するのではなく、その旨を表示します。
  • 拒否されたキーは、設定ミスやコンテンツの不具合ではなく、悪用の可能性があるという警告として報告されます。 キーのローテーションこそがTorBoxがこの種の警告を伝える方法だからです。これを不具合として扱うと、ライブラリ全体を修復対象にしてしまいます。

意図的に対応付けていない項目

エラーが起きていないことを示すため、ここでは単にunrecognised→「認識されない」と訳します。

認識されない download_state は、error ではなく downloading として報告されます。 delete_error_torrents が有効になっている場合、エラー状態になると zurg はそのトレントをアカウントから削除します。そのため、このコードを書いた後に TorBox が新しく導入した状態が、削除を引き起こすことがあってはなりません。
