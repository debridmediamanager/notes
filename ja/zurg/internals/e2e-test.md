# E2E テスト {#e2e-testing}

ザーグ（zurg）がデプロイ後に正しく動作しているかを確認するためのエンドツーエンドテスト。

## Plex 再生テスト {#plex-playback-test}

ランダムに映画を1本選び、再生パイプライン全体をテストして、Plexで実際に再生できるかを確認します。

### テストを実行する {#run-the-test}

```bash
./scripts/plex-e2e-test.sh
```

このスクリプトは、`config.yml` から `plex_server_url` と `plex_token` を自動的に読み込みます。

カスタム設定で上書きするには:
```bash
PLEX_URL="http://your-plex:32400" PLEX_TOKEN="your-token" ./scripts/plex-e2e-test.sh
```

### テストの内容 {#what-it-tests}

| Step | Description |
|------|-------------|
| 1 | Plex API で Movies ライブラリを探す |
| 2 | 映画の総数を取得する |
| 3 | ランダムに映画を1本選ぶ |
| 4 | その映画のストリーム URL を取得する |
| 5 | ストリームにアクセスできるか確認する (HTTP 200) |
| 6 | ffmpeg で動画を3秒分デコードする |
| 7 | Plex のセッション追跡を作成して確認する |

### 期待される出力 {#expected-output}

```

[2/7] Getting movie count...
  Total movies: 1234

Movie '2 Fast 2 Furious (2003)' is playable via Plex
```

### 前提条件 {#prerequisites}

- Plex サーバーが起動していて、アクセスできること
- `config.yml` に `plex_server_url` と `plex_token` が設定されていること
- `curl`、`jq`、`ffmpeg` がインストールされていること

### トラブルシューティング {#troubleshooting}

| エラー | 原因 | 対処法 |
|-------|-------|-----|
| No movie library found | ライブラリの種類が違うか、空になっている | Plex に "Movies" ライブラリがあるか確認 |
| Stream not accessible (HTTP 4xx) | 認証またはパスの問題 | トークンを確認し、ファイルが存在するか確認 |
| Failed to decode video frames | ファイルの破損またはネットワークの問題 | zurg のログを確認し、別の映画を試す |
| Session not detected | Plex のセッションがタイムアウトした | Plex のログを確認 |

## 統合テストスイート {#integration-suite}

```bash
ssh zen
cd /path/to/isolated/zurg/source
make integration-test
```

**`zen` 上の隔離されたターゲットで実行してください。** そこに Go ツールチェーン、shellcheck、rclone、.NET の move probe を用意します。テストスイートは独自の zurg プロセスとマウントを作成するので、zen で普段使っている zurg サービスやマウントを置き換える必要はありません。別のソースディレクトリ、`TMPDIR`、設定、ポート、`MOUNT_PATH` を使ってください。実行前に scratch 設定を確認し、`TMPDIR` を分けている場合でも、ホスト全体で共有する `INTEGRATION_LOCK_FILE=/tmp/zurg-integration-rd.lock` はそのまま残してください。こうしておくと、他のセッションとも順番待ちになり、テストが重ならずに済みます。

前提条件が揃っていないテストは、成功終了でスキップされます。出力を読んで、FUSE、rclone、Plex、NNTP が本当に実行されたかを確認してください。

| テスト | FUSE が必要 | Plex が必要 | Usenet アカウントが必要 |
|------|:----------:|:----------:|:----------------------:|
| `refresh_repair_integration.sh` | | | |
| `network_test_cache_integration.sh` | | | |
| `rclone_mount_integration.sh` | はい | | |
| `magic_mount_integration.sh` | はい | | |
| `magic_move_refusal.sh` | はい | | |
| `magic_library_move_integration.sh` | はい | | |
| `plex_integration.sh` | はい | はい | |
| `nzb_bench_integration.sh` | | | はい |

`force_location_integration.sh` はスイートに**含まれていません**。このテストは zurg ではなく、このホストから Real-Debrid の CDN までのネットワーク経路について確認するものです。そのため、変更内容に関係なく、経路が応答しない環境では失敗します。実行するなら、強制するリージョンへ IPv4 で接続できるホストで、`make force-location-test` を使って意図的に実行してください。詳しくは [Force Location 統合テスト](#force-location-integration-test) を参照してください。

Real-Debrid を使う 5 つのテストは、同じアカウントを使います。詳しくは [テスト用 Real-Debrid アカウントは共有されています](#the-real-debrid-test-account-is-shared) を見てください。ベンチマークはニュースアカウントを使い、Real-Debrid にはまったくアクセスしません。ただし、他のテストと同じホスト全体のロックを取ります。他のスイートが読み込みをしている最中に計測すると、計測しているのは別のスイートの負荷になってしまうので注意してください。

Mac でも、macFUSE が入っていればマウントテストを実行できます。動作確認は macFUSE と Linux の `fusermount` の両方で行っています。Plex テストには、scratch 設定に `plex_server_url` と `plex_token` が必要です。また、Plex はマウント先までの親ディレクトリをすべて辿れる必要があります。プライベートなホームディレクトリの下にマウントすると、テストユーザーからは見えても Plex からは見えない、ということが起きます。

`make integration-test` は、zurg をビルドし、スクリプトに対して shellcheck を実行し、`lib.sh` のセルフテストと `integration/nzbbench` のユニットテストを走らせたあと、7 つすべてを軽いものから順に実行します。順番は、network test cache、rclone マウント、Plex、`__magic__` マウント、.NET の move 拒否、refresh/repair、最後に Usenet ベンチマークです。最後の 2 つは重いテストです。refresh/repair はライブラリの全体スキャンが終わるまで待ち、ベンチマークはニュースサーバーから数ギガバイトを 2 回読み込みます。そのため、他のテストで問題があれば、その待ち時間を払う前に気づけるようにしてあります。`make integration-test-media` は rclone、Plex、`__magic__` マウントのテストを、`make nzb-bench-test` はベンチマークだけを実行します。

各スクリプトは `$TMPDIR` 配下に作業ディレクトリを持ち、独自のポートを使い、zurg のログをそこへ書き出します。スイートは `STREAM_LOGS=false` で実行されるため、ターミナルに出るのはテスト自身のアサーションだけです。デバッグ中に zurg のログを stderr で追いたいときは、`STREAM_LOGS=true` を設定してください。

共通のヘルパーは `integration/lib.sh`（プロセス制御、Real-Debrid API、ディスク上のライブラリ照会）と `integration/lib_media.sh`（FUSE と Plex）にあります。新しいテストを追加するときは、これらを source して使ってください。他のスクリプトをコピーしてはいけません。`integration/lib_test.sh` はヘルパー自体をテストします。アカウントもネットワークも不要で、約 1 秒で終わります。`integration/nzb_bench_timing_gate_test.sh` は、ベンチマークのラッパーがツールの終了コードをスイートの判定にどう変換するかを確認します。このテストは `integration/testdata/` にある実際のレポートを一部切り出したものを使います。どちらも `make test-integration-lib` で実行されます。

### Real-Debrid のテストアカウントは共有されています {#the-real-debrid-test-account-is-shared}

このスイートは Real-Debrid のテスト用アカウントを 1 つ使いますが、そのアカウントは非公開ではありません。`zen` の本番用 zurg も同じライブラリを監視しているため、テストが追加したばかりのトレントを一覧表示して更新してしまいます。このアカウント上で **修復を有効にした** インスタンスは、それらを検証、修復、整理もします。

以下の 2 つの失敗は 2026-08-23 に診断したものです。そのとき `macmini` の zurg が、このアカウントで 10 分ごとの修復を有効にして動いていました。そのインスタンスは 2026-08-29 に停止されており、監視している人もいません。また、zen の実行は `enable_repair: false` で動いています。そのため 2026-09-01 時点では、どちらの失敗も発生源が残っていません。このアカウントのどこかで修復を再び有効にすると、すぐに再発します。だからこそ、以下の直列化ルールは今も有効です。

それによって実行が受ける影響は次のとおりです。テスト対象のビルドとそのベースラインの両方で、6 本中 4 本のスクリプトが失敗したあとに、これが起きています。

- **いつまでも現れないフィクスチャ。** Real-Debrid はダウンロード ID をリンクごとに重複排除しており、downloads の行を削除すると、そのコードを持つ全員に対してコードが無効になります。別のインスタンスのクリーンアップが、今回の実行が解決したばかりのコードを無効にすると、今回の検証は `404 invalid_download_code` を返します。すると zurg はそのファイルを壊れたものとして扱います。壊れたトレントはすべての一覧から隠されます。その結果、テストは `zurg serves the fixture over HTTP but it never appeared under .../mnt/movies within 180s` と表示しますが、これはマウントや dircache のバグのように見えるだけで、実際にはどちらでもありません。
- **削除したのに元に戻るケース。** 修復を行うインスタンスが、今回の実行が削除したばかりのトレントを再追加します。その結果、`refresh never dropped <hash> after it was deleted from the account` が失敗します。しかし、ライブラリは現実を正しく報告しています。

影響を受けやすいのは、削除と修復に関するアサーションです。変更のせいにする前に、以下で説明する失敗のコンテキストを確認してください。実行を確実にクリーンにしたいなら、他のインスタンスの修復を先に止めてください。

**同時に動かしてはいけないスクリプトがあります。** このホスト上でも、同じホストの別セッションからでも、2 つ以上を同時に実行しないでください。これらはアカウントの 1 分あたりの API 上限を共有しています。そのため 2 本が並ぶと `API rate limit (code=34)` が発生し、アサーションは動作ではなくトラフィックによって失敗し始めます（`fun` での 2 並列実行で計測）。また、各スクリプトはトレントをハッシュで削除するため、ある実行のクリーンアップが、別の実行のフィクスチャをためらいなく削除してしまいます。そこで各スクリプトは、`main` の先頭で、最初の API 呼び出しより前にホスト全体のロックを取得し、終了するまで保持します。

| 変数 | デフォルト | 説明 |
|----------|---------|-------------|
| `INTEGRATION_LOCK_FILE` | `$TMPDIR/zurg-integration-rd.lock` | ロックファイル。`flock` が使える環境では `flock` を使い、ない環境（macOS には `flock` がありません）では pid を書き込んだ `.d` ディレクトリを使います |
| `INTEGRATION_LOCK_WAIT` | `0` | 実行中のジョブの後ろで待つ秒数。`0` は即座に拒否します。これが望ましい設定です。待つ代わりに、コールドスキャンの後ろで 1 時間待たされることになるからです |

強制終了された実行が残したロックは自動的に回収されます。ディレクトリにはロック保持者の pid が入っており、`flock` はカーネルが解放します。もちろん、このロックは zen や macmini には何も伝えません。あくまでこのホストの実行同士を分けておくためのものです。

**失敗の読み方。** 今では、すべての `fail` が、その実行の zurg ログから次の情報を表示します。共有アカウントに起因する各症状の件数、つまり `invalid_download_code`、`hoster_unavailable`、レート制限の行、`code=34`、`Link verification failed`、`keeping files as broken`、`broken_file]`、`Deleted downloads entry` です。続いて、それぞれの最後 10 行、そしてテスト対象のフィクスチャ名を含む最後の数行を表示します。`none present, so this failure is probably zurg's own and not the account's` と表示された場合は、アカウントではなく、コードの方を調べてください、という意味です。

`docs/realdebrid-behavior.txt` には、これらすべての基礎となるリンクの仕様が書かれています。どのアカウントからどのリンクが引き換えられるか、そして `unavailable_file` と `hoster_unavailable` がなぜ別の意味を持つのか、といった内容です。

### 実行時間 {#runtime}

指定した作業ディレクトリで最初に実行すると、ライブラリのコールドスキャンが発生します。トレントごとに info 呼び出しを 1 回と、リンク検証を 1 回行い、その速度はアカウントの API 上限に合わせて制限されます。数千件のトレントがあるアカウントでは数十分かかります。このアカウントは 2026-08-29 時点で 3,361 件のトレントを持っていて、`code=34` が継続的に返され、1 スクリプトあたり約 20 分かかりました。作業ディレクトリは実行をまたいで 3 つのキャッシュを保持するので、以降の実行ではこれらをスキップできます。その 3 つは `info/`、`linkcache/`、ネットワークテストの結果です。コールドな経路を強制的に使うには、作業ディレクトリを削除してください。

`linkcache/` は `internal/debrid.LinkCache` が保存するもので、プロバイダーのインスタンスごとに 1 ファイルです。20 分を削っているのはこちらの半分です。トレントを初めて見たとき、そのリンクの一つを解決して検証します。キャッシュが空なら、トレントごとに `unrestrict/link` 呼び出しが 1 回発生し、キャッシュが温まっていればこの呼び出しは不要です。効果はキャッシュの 4 時間の TTL で頭打ちになります。翌日にスイートを再実行すると、またコールドな状態に戻ります。つまり、これは反復作業を速くするもので、初回実行を速くするものではありません。

`info/` も `linkcache/` もリンクを含まないわけではありません。どちらも、共有アカウント上の別のインスタンスが取り消せるコードを保持しています。`.zurginfo` は `TorrentInfo` をそのまま保存したものなので、トレントの Real-Debrid `/d/` コードが入っています。`linkcache/` には、それらのコードが解決された先の情報が入っています。それでも両方とも保持されます。再構築にこそ数十分かかるからです。取り消されたエントリは誤った答えではありません。検証は `404 invalid_download_code` を受け取り、zurg がそのエントリを無効化して再発行するので、呼び出しが必要になるのは取り消されたエントリだけです。毎回いくつかは発生すると考えてください。また、その数によって高速化の度合いは変わります。

フィクスチャの範囲はさらに狭くなります。`clean_state_for_hash` は、ハッシュが一致する `info/` のエントリを削除するので、そのリンク一覧は必ずアカウントから再取得されます。`linkcache/` はハッシュではなくリンクをキーにしていて、フィクスチャごとに掃除されません。そのため、リンクの*解決結果*は前回の実行のものが残っている場合があります。ただ、ここでのどのアサーションもそれに依存していません。フィクスチャが検証するのは、リフレッシュ、ルーティング、マウント、修復です。古くなった解決結果は検証に失敗し、どのテストも見る前に再発行されます。

### Refresh/Repair 統合テスト {#refreshrepair-integration-test}

```bash
./integration/refresh_repair_integration.sh
```

scratch 設定では自動修復が無効のままです。明示的な `/manage/{hash}/repair` リクエストは2つあり、この設定を無視してフィクスチャを修復します。無人修復を有効にすると、共有アカウント内の無関係なエントリもスキャン・変更してしまい、アサーションに必要な API の枠を使い切ってしまいます。
`refresh_repair_config_test.sh` は、2026-09-10 の失敗時に取得したマスク済みの scratch 入力を使い、プロバイダーへの通信なしで生成された設定を確認します。

| シナリオ | 説明 |
|----------|-------------|
| 1. 自動リフレッシュ（追加） | RD API 経由でトレントを追加し、リフレッシュループがそれを検知するまで待ちます。再起動はしません。さもないとコールドロードのパスをテストしてしまうためです |
| 2. ディレクトリの割り当てとルーティング | ファイルが HTTP/DAV の仮想ディレクトリに表示されることを確認します |
| 3. 永続化（再起動） | zurg を再起動し、キャッシュ済みの状態が残っていることを確認します |
| 4. 自動リフレッシュ（削除） | トレントを削除し、obsolete-key sweep がそれを除外するまで待ちます |
| 5. 修復のトリガー | Manage API で修復をトリガーし、zurg が要求を受け付けたことをログで確認して、0 個の壊れたファイルで `ok_torrent` になるまで待ちます |
| 6. 修復の検証 | 2つ目のトレントを修復し、そこから動画ファイルを範囲指定で取得します |

### Force Location 統合テスト {#force-location-integration-test}

```bash
make force-location-test
```

`make integration-test` の一部ではなく、必要なときに個別に実行するテストです。`fun` で 2026-08-29 に測定したところ、強制指定した `nyk` のホストが、ダウンロードクライアントが `tcp4` で接続する AAAA レコードに解決されていました。そのため HEAD リクエストはすべて `no suitable address found` で失敗しました。このテストが待つライブラリスキャンは、再試行が各 3 回だと、ほとんどの場合 1 時間近く待たされてから失敗します。しかも失敗の原因は zurg ではなく、ホストのネットワークです。このテストには、リージョンが正常でないときにスキップする処理がすでにあります（下記参照）。ただ、その処理では、ホストが*正常な*リージョンに IPv4 で到達できない場合はカバーできません。

`LOCATION`（デフォルトは `nyk`）に固定したネットワークテスト用キャッシュを用意し、zurg の `/strm/` エンドポイント経由で解決したリンクが、そのロケーションのダウンロードホストへリダイレクトされることを確認します。`MAX_GEO_PROBES`（デフォルトは `4`）は、シード処理が調べる geo サーバーの数の上限です。

`cdn_host_preference` を設定すると、zurg が検証するリンクはすべて強制指定したリージョンを通ります。そのリージョンが正常でないと、一覧が空になり、失敗が zurg のバグのように見えてしまいます。そのため、このテストはまずリージョンを確認します。Real-Debrid がそのリージョン向けのリンクを発行しない場合、または返されたホストがバイトを配信しない場合は、失敗ではなくスキップします。

### Network Test Cache 統合テスト {#network-test-cache-integration-test}

```bash
./integration/network_test_cache_integration.sh
```

zurg を 2 回起動します。最初の起動でレイテンシ測定 (latency sweep) を実行し、`data/network_test_results.json` を書き出す必要があります。2 回目の起動ではそのファイルを読み込むだけで、新しい測定は実行されないはずです。

### Rclone Mount 統合テスト {#rclone-mount-integration-test}

```bash
./integration/rclone_mount_integration.sh
```

プレーヤーが実際にたどる経路を順に見ていきます — FUSE → zurg HTTP → Real-Debrid:

| ステップ | 検証内容 |
|------|-----------|
| 2 | zurg が自身のマウントを立ち上げ、`Mount verification successful` とログに出力します |
| 3 | 設定したディレクトリがマウントのルートに表示されます |
| 4a–4c | フィクスチャがライブラリに入り、HTTP 経由で配信され、マウントに届くまでを段階的に確認します。失敗時には「マウントに無い」だけでなく、どの区間で壊れたかがわかるようになっています |
| 5 | FUSE 経由でファイルを読むと、実データが返ってきます |
| 6 | zurg を終了するとマウントが解放されます |

ステップ 4c は VFS の dircache に関する検証です。フィクスチャがマウントに現れるのは、ディレクトリ一覧が無効化された場合だけです。トレントが届く前にキャッシュされた一覧をそのまま返していたら、ここで失敗します。

フィクスチャ自身の名前から作られた正規表現でライブラリを絞り込むので、マウントにはアカウント全体ではなく 1 つのリリースだけが入ります。`MOUNT_PATH` のデフォルトは `$WORK_DIR/mnt` で、本番の `/mnt/zurg` は使いません。`RCLONE_BIN` のデフォルトは `$(pwd)/bin/rclone` です。

### Plex 統合テスト {#plex-integration-test}

```bash
./integration/plex_integration.sh
```

| Step | Assertion |
|------|-----------|
| 2 | zurg のログに `Successfully connected to Plex server` と出力される |
| 3 | フィクスチャがライブラリに届くこと。マウントにも現れた場合は読み取り可能であること（Plex は自分のユーザーとして読み取ります） |
| 4 | 新しい使い捨てのセクションを `$MOUNT_PATH/movies` 上に作成する |
| 5 | zurg がそのライブラリパスをセクションに解決し、**フィクスチャのパス**に対して更新をキューに入れる |
| 6 | Plex がアイテムをインデックス済みにする |

ここでは、フィクスチャがマウントに表示されることは検証項目ではなく、前提条件です。Plex が設定されていると、zurg は Plex ライブラリ全体に対してもマッチャーを実行するため、更新処理と競合し、VFS の一覧表示が大幅に遅れることがあります。テストはその旨を表示し、`MOUNT_VISIBLE_TIMEOUT`（デフォルトは `420`）を過ぎても続行します。ステップ 5 と 6 は、Plex がファイルを見られない場合にすでに失敗するので、無効化が機能することの確認はマウントテストの役目です。`PLEX_URL` と `PLEX_TOKEN` は、設定の `plex_server_url`/`plex_token` を上書きします。

Plex は新しいセクションを自動的にスキャンするため、作成が返される前に完了している場合があります。テストは最初の件数を報告します。ステップ 5 は、明示的な manage リクエストの後に zurg が正しいパスをキューに入れるかどうかを、独立して確認します。

セクションは `agent=tv.plex.agents.none` と `Plex Video
Files` スキャナーで作成されるため、Plex はオンラインのメタデータエージェントを参照せずにローカルでインデックスを作成します。終了時には、失敗時も含めて EXIT トラップから削除されます。ただし SIGKILL の場合は何も実行されないので、強制終了後は自分のセクションだけを確認して削除してください。既存のセクションは別のセッションに属している可能性があるため、ハーネスは触りません。既存のライブラリは決して変更されません。

ステップ 5 では、次の完全なパスを待つのではなく、zurg に `POST /manage/{hash}/scan` で副作用を実行するよう依頼します。ディレクトリ割り当てのトリガーは、トレントが検出された時点で一度だけ発火します。これはセクションが作成される前に必ず起きます。次の完全なパスを待つと、数千本のトレントを持つアカウントでは数十分かかります。テストされているマッピングは変わりません。zurg は、自分のライブラリパスを正しいセクションに自力で解決する必要があります。

### Usenet ベンチマークの回帰 {#usenet-benchmark-regression}

```bash
./integration/nzb_bench_integration.sh
make nzb-bench-test
```

ほかのテストでは、NNTP 経由で 1 バイトも読みません。記事の取得、yEnc のデコード、PAR2 の修復、アーカイブの読み取りのどれかを変えると、スループットが半分になったり、メモリが 2 倍になったり、記事が欠けている場所で無音を返すようになったりします。それでも他のテストは全部通ります。このテストでは、用意した 4 つのリリースを使い捨ての zurg 経由で読み、数値とバイト列の両方を確認します。

**なぜ保存した数値ではなく A/B にするのか。** ライブのニュースサーバーのスループットは、夕方の間に 10〜20% ぶれます。同じリリースを 6 回読んだだけでも、1 回のセッションで 34〜50 MB/s の幅が出ました。先週記録した数値に対して狭い許容幅を設けると、コードではなく回線の状態で失敗してしまいます。そこでこのテストは、同じホストで同じ時間帯に 2 つのバイナリを計測します。回ごとに実行順を入れ替えて、プロバイダー側のウォームアップが両方に均等に当たるようにし、それぞれの中央値を比べます。

A はベースラインです。デフォルトでは、`HEAD` から到達できる最新の `*-nightly` タグを使います。`git archive` で展開して一度ビルドし、その結果を作業ディレクトリにキャッシュします。次回以降の実行ではキャッシュを再利用します。B は候補で、このリポジトリで今ビルドした `zurg` です。**B が A より 5% を超えて悪い場合、その指標は失敗になります**（`BENCH_TOLERANCE`）。良くなっている場合は改善として報告します。片方だけに指標がある場合は、回帰ではなく `n/a` として扱います。

1 回の実行では、コールドオープン、最初のバイトまでの時間、64 MiB の読み取り、同じ 64 MiB のウォームな再読み取り、8 地点のスクラブ、256 MiB の読み取りを計測します。256 MiB の読み取りでは、ギガバイトあたりの CPU 秒数とピーク RSS も併せて記録します（Linux のみ。どちらも `/proc` から取得します）。さらに、`ffprobe` が読んだコンテナの再生時間も計測します。

正しさの確認は候補のバイナリだけに対して行い、時間では判断しません。すべての読み取りで md5 を記録し、それが記録済みの定数と一致し、2 つのバイナリ間でも一致している必要があります。破損したリリースは、元のバイト列か無音のどちらかを返さなければなりません。それ以外は許されません。修復後は元のデータに戻っている必要があり、さらに再起動後も正しいままであることを確認します。

テストコーパスは `integration/nzbbench/corpus/` にチェックインされています。6 つの NZB があり、それぞれ 6 つの問いに対応しています。

| NZB | 中身 | 役割 |
|-----|------|------|
| `ToyStory5.nzb` | 6.61 GB の WEB-DL、4 MiB の記事 1,576 本 | すべてのスループットとレイテンシの数値、および ffprobe の検証 |
| `ToyStory5Damaged.nzb` | 同じリリースで、記事 21 の message-id を壊してあり、どのサーバーでも `430` が返る | 穴の部分は元のバイト列か無音で読めなければなりません。それ以外は正しさのバグです。その後 PAR2 で修復でき、修復結果は再起動後も残っている必要があります |
| `Obfuscated.nzb` | 同じ映画を、`<hex> [n/7] yEnc` という形式の 7 ファイルとして投稿したもの。本当の名前は PAR2 のインデックスからしか分からない | 名前の処理を確認します。正しい `.mkv` 名で、正しいサイズで一覧に出る必要があり、`.par2` は見えてはいけません |
| `FatherBrown.nzb` | 1 話分を入れた 11 ボリュームの RAR、`Sample/` ディレクトリ、nfo | アーカイブリーダーの確認です。フォルダ構造が残っている必要があります。アーカイブ内の読み取りには専用のスループット値（`rar_read_MBps`、1 回のリードを毎回実行）があります |
| `WrongTurn3.nzb.gz` | 無圧縮 (stored) の 7z を 1 GiB のボリューム 54 本に分けたもの（最後の 1 本は短い）と PAR2 ファイル 7 本を含む、58 GB の UHD BluRay の一式。NZB が平文で 7 MB あるので gzip 圧縮してあります | 分割 7z のリーダーの確認です。ボリュームを結合し、最後のボリュームの末尾にあるヘッダーを読んでから、何かを一覧表示する必要があります。計測するのはその一覧表示の時間です（`sevenzip_list_s`、クリアしたレイアウトから毎回 1 回）。その後、57.6 GB の本編ストリームで、8 GiB の位置から 16 MiB を読み、記録済みの md5 と一致する必要があります。これはタイミングではなく正しさの確認です。このリリースではスループットの数値は出しません。このプロバイダーでは、どのボリュームも記事の約 5 分の 1 が欠けているため、時間を計ると穴の検出を計ることになってしまうからです |
| `NestedRar.nzb` | 2 枚組の XviD リポスト。外側に RAR5 のボリュームセットが 1 つあり、そのメンバーはさらに 2 つの RAR セットのボリュームです。内側のセットは `CD1/` と `CD2/` にあります。加えて `Sample/` のクリップと nfo もあります | ネストしたアーカイブのリーダーの確認です。内側の 2 つのセットの両方を開く必要があります。フラットなテストでは、比較可能な 2 つのセットは拒否されます。セットをまとめているのは投稿者のディレクトリ構成です。両方の映画が正しいサイズで一覧に出る必要があり、それぞれに専用のスループット値（`nested_read_MBps`、毎回 1 回のリード）があります |

**アカウントは 1 つ、インスタンスも 1 つ。** 同じニュースアカウントで 2 つ目の zurg を動かすと、1 つ目と接続の上限を奪い合います。その場合、サーバーは*古い方*の接続を拒否します。`fun` では、本番の `zurg-usenet` がアカウントのプランで許される接続をすべて保持しているので、ベンチマークは 10 接続（`BENCH_NNTP_CONNECTIONS`）で動きます。`Too many connections` の拒否が出た場合は、**失敗ではなくスキップ**として報告します。サーバーに接続できない場合や `AUTHINFO` が拒否された場合も同じです。環境がこの問いに答えられなかったことになるので、テストはビルドのせいにせず、そのことを伝えます。

デフォルトの 4 回でおよそ 15〜20 分かかります。ベースラインを初めてビルドする場合は、それに加えて数分かかります。

| 変数 | デフォルト | 説明 |
|----------|---------|-------------|
| `PORT` | `12358` | ベンチマーク用 zurg インスタンスのポート（一度に 1 つ） |
| `WORK_DIR` | `$TMPDIR/zurg-nzb-bench` | 生成された設定、両方のバイナリの実行ディレクトリとログ、`report.json`、キャッシュされたベースラインのバイナリを保存します。実行間で保持されます。永続化された `data/` があるおかげで、後続の回は冷えた学習ではなく再起動を計測できます |
| `BENCH_ENV_FILE` | `~/.config/zurg/bench-account.env` | アカウントファイル。存在する場合に読み込まれます。`BENCH_NNTP_*` 変数を `KEY=value` の行で書きます。**ベンチマーク専用のアカウントを渡すための推奨方法**で、認証情報をリポジトリやシェルの履歴に残さないためのものです |
| `CONFIG_PATH` | `config.yml` | 環境変数もアカウントファイルも指定していない場合に、ニュースアカウントを借りる設定ファイル。最初の `type: nzb` プロバイダーの `nntp:` ブロックを使います。そのアカウントにここからの接続がすでに開いている場合は、借用を拒否します。詳しくは下を参照してください |
| `BENCH_NNTP_HOST` / `_PORT` / `_TLS` / `_USER` / `_PASS` | *（まず `BENCH_ENV_FILE`、次に `CONFIG_PATH` から）* | ニュースアカウント。エクスポートされた値はアカウントファイルより優先されます。どこにも値がなければスキップします |
| `BENCH_NNTP_CONNECTIONS` | `10` | ベンチマークが開く接続数。上限です。それより少ない接続数で設定されたアカウントは、その数をそのまま使います |
| `BENCH_ALLOW_SHARED_ACCOUNT` | *（未設定）* | `1` にすると、すでに接続が開いている借用アカウントでベンチマークします。アカウントに余裕があると確認できた場合だけ使ってください |
| `BASELINE_REF` | `HEAD` から到達できる最新の `*-nightly` | 比較対象。ベストエフォートで `git fetch --tags` を実行したあとに解決されます |
| `BASELINE_BIN` | *（`BASELINE_REF` からビルド）* | 事前にビルド済みのベースラインを、そのまま使います。ここではもうビルドできないものと比較する方法です |
| `BENCH_REPS` | `4` | バイナリごとの回数。中央値はこの回数から求めます |
| `BENCH_TOLERANCE` | `0.05` | B がどこまで悪くなっても回帰とみなさないかの許容値 |
| `BENCH_SKIP` | *（なし）* | 除外するフェーズのカンマ区切りリスト: `repair`, `obfuscated`, `rar`, `ffprobe`。`PATH` にも `bin/` にも ffprobe がない場合は、自動的に `ffprobe` が追加されます |
| `REPORT_JSON` | `$WORK_DIR/report.json` | レポートの出力先 |
| `STREAM_LOGS` | `true` | 候補の `zurg.log` を stderr に流します。ツール自身の進捗表示は、この設定に関係なく出力されます |

`report.json` には、両方のバイナリについての回ごとの全データ、中央値、指標ごとの判定、両方のバイナリの `version` 出力、ホストと OS が入ります。そのため、どの数値も、それを生み出したコードと照らし合わせて読めます。何も比較せずに数値だけを記録したい場合は、単一の `--bin` を指定してツールを直接呼び出してください。計測して JSON を書き出し、終了コード 0 で終わります。

```bash
cd integration/nzbbench && go build -o /tmp/nzbbench . && cd -
/tmp/nzbbench --config /path/to/a-config-with-an-nzb-provider.yml --port 12358 \
  --corpus integration/nzbbench/corpus --work /tmp/nzbbench-record \
  --bin candidate=./zurg --out /tmp/record.json
```

設定ファイルは必ず自分用のものを使ってください。ラッパーが生成する設定ファイルには、ニュースアカウントのパスワードが平文で入っていて、実行が終わると削除されます。

`integration/nzbbench/README.md` に、ツール自体のフラグと終了コードがまとめられています。

**`nzb_bench_integration.sh` の終了コード。** `0` は比較が行われて合格した場合、またはホストがベンチマークを全く実行できずに実行がスキップされた場合です。`1` は機能アサーションの失敗またはメトリクスの回帰です。`4` は、すべての機能アサーションは合格したものの、タイミングゲートが**判定されなかった**場合です。実行中にニュースサーバーがツールの安定性の上限を超えたため、スループットとレイテンシの比較は破棄されました。4 は、壊れたビルドの 1 とも、スキップの 0 とも、意図的に区別されています。パフォーマンスについては何も判断されていないので、答えは、より静かな時間帯での再実行です。実行時には、ゲートとそれを破った spread を示すバナーが表示されます。`make integration-test` は失敗したレシピ行を make 自身の終了コード 2 に変換するため、スイートの実行では、ターゲットの「All integration tests passed.」の行ではなく、非ゼロの make 終了とこのバナーが表示されます。4 そのものによって処理を分岐させる必要がある場合は、スクリプトを直接呼び出してください。

### 前提条件 {#prerequisites-1}

- Real-Debrid のトークン（`config.yml` 内の `realdebrid` プロバイダーとして）または `RD_TOKEN`
- `curl`、`python3`、そしてビルド済みの zurg バイナリ
- `make lint-integration` 用の `shellcheck`（ない場合は通知が出て、スキップされます）
- マウントと Plex のテスト用: `fusermount`/macFUSE、rclone バイナリ、そして Plex がマウントを読めるように `/etc/fuse.conf` の `user_allow_other`
- MOVE の拒否チェック用: `scripts/build-rclone-move-fix.sh` で作成した修正版 rclone を、`RCLONE_BIN` と `RCLONE_TEST_BIN` の両方に設定してください。新しい未修正の upstream rclone では不十分です。詳しくは [MOVE の回帰問題](rclone-move-refusal.md) を見てください。ビルド済みのヘルパーは `DOTNET_MOVE_PROBE_BIN` で指定するか、ビルド用の Docker を用意してください。特権のないコンテナユーザーでビルドする場合は、.NET に CLI と NuGet キャッシュのディレクトリに加えて、書き込み可能な `XDG_DATA_HOME` も渡してください。
- Usenet ベンチマーク用: ニュースサーバーのアカウントと、Go、`git`、`tar`、`make`。ベースラインは nightly タグの `git archive` から作られます。

### ベンチマーク用に専用のニュースアカウントを用意する {#give-the-benchmark-its-own-news-account}

接続の上限は**アカウント**に紐づくもので、プロセスごとではありません。ベンチマークを本番インスタンスがすでに使っているアカウントに向けると、両方が同じプランの枠を一緒に使うことになります。そうなると、サーバーは*古い*接続の持ち主を拒否します。それは、原因となったベンチマークのことを何も知らない本番環境です。

そのため、ベンチマークは `CONFIG_PATH` からはフォールバックとしてのみ借ります。また、**このホストですでに接続が開いているアカウントは借りないようになっています**。専用のアカウントを `~/.config/zurg/bench-account.env` に設定してください:

```
BENCH_NNTP_HOST=news.example.net
BENCH_NNTP_PORT=563
BENCH_NNTP_TLS=true
BENCH_NNTP_USER=...
BENCH_NNTP_PASS=...
BENCH_NNTP_CONNECTIONS=25
```

どこにも使われていない余裕のあるアカウントを選んでください。測定された上限が、どのインスタンスの設定値よりもはるかに高いサーバーであれば、ベンチマークが読み取り側の処理を圧迫することはありません。

コマンドラインで export した値は、ファイルの設定より優先されます。空きがあることを確認済みであれば、`BENCH_ALLOW_SHARED_ACCOUNT=1` を設定して拒否を無効にできます。

### スイートには含まれていない {#not-in-the-suite}

`rename_integration.sh`、`tag_stats_integration.sh`、`test_repair_verification.sh` は `make integration-test` では実行されません。今もそれぞれ `lib.sh` 導入前のヘルパーのコピーを持っています。これらを `lib.sh` を使うように移植し、組み込む前にポート番号が衝突しないように割り当ててください。
