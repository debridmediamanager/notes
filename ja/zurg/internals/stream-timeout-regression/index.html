プロキシ経由ストリームのタイムアウト回帰

概要

zurg は download_timeout_secs を、プロキシ経由の HTTP ダウンロードの壁時計ベースの期限（wall-clock deadline）として使っていました。デフォルトは 15 秒なので、ボディの受信に 15 秒以上かかる上流のレスポンスは、データが普通に届いている最中でも途中で打ち切られていました。

この不具合は 2026-08-21 に Discord で報告されました。対象は 2026.08.21.0151-nightly（fc2a21f）です。zurg 経由で 2 GB の範囲リクエスト（ranged request）を繰り返したところ、約 1.26 GB を 84 MB/s で届けたあと、15.001 秒で終了していました。同じ範囲は Real-Debrid から直接なら完了しており、download_timeout_secs を 3600 に上げると、zurg 経由でも 25.8 秒でリクエストが完了しました。

これは zurg 側の回帰（regression）です。コンテンツのフィルタリングや CDN の障害、fc2a21f の回帰ではありません。原因はコミット 6edeaa8c（Optimize client、2024-11-17）です。通常のプロキシ配信の経路は 41db7245 で修正され、その後 eff972b8 により、プロバイダー API の境界で同じミスが再び入りにくくなりました。

ユーザーへの影響

影響を受けていたのは、zurg が HTTP ベースのデバッドプロバイダーから中継するレスポンスボディのうち、download_timeout_secs を超えて接続が開いたままになるものです。Real-Debrid は 2024 年 11 月から影響を受けていました。TorBox と AllDebrid も、これらのプロバイダーを追加したときに同じ動作を引き継いでいました。ローカルで提供される NZB の読み込みは HTTP ダウンロードクライアントを通らないため、影響はありませんでした。

ユーザーが目にする症状は次のとおりです。

  • 再生中に Infuse や、その他の WebDAV クライアントが固まる。
  • シークによって新しい範囲リクエストが開かれた後、再生が失敗する。
  • HTTP の 206 Partial Content を受け取っているのに、ダウンロードが途中で終わる。
  • 直接リクエストは正常に完了しているのに、メディアファイルや CDN が原因に見えるクライアントエラーが出る。

再生が開始されてから必ず 15 秒後に失敗するわけではありません。報告された 84 MB/s の速度では、期限までに zurg が転送するのはおよそ 1.26 GB です。プレイヤーはこのバッファを数分かけて使い切るため、正確に 15 秒で切れるネットワークの制限が、不規則に起きる再生の停止のように見えていました。

根本原因

Go の http.Client.Timeout は、リクエスト全体のライフサイクルに対する期限です。アイドル時間や停止を検知するタイムアウトではありません。タイマーはリクエストの開始時に動き出し、データが流れているかどうかに関係なく、レスポンスボディを読み続けている間も動き続けます。

6edeaa8c より前は、ダウンロード用クライアント自体にリクエスト全体のタイムアウトがありませんでした:

client: &http.Client{}

download_timeout_secs は、トランスポートのダイアラーと ResponseHeaderTimeout を通じて、接続フェーズとレスポンスヘッダーフェーズだけを制限していました。レスポンスボディが届いたあとは、下流のクライアントが必要とする限り、配信処理が読み続けられました。

6edeaa8c で HTTP トランスポートが再構成され、設定されたタイムアウトがクライアント自体に追加されました。同時に ResponseHeaderTimeout は削除されています:

client.client = &http.Client{
    Transport: transport,
    Timeout:   time.Duration(timeoutSecs) * time.Second,
}

これにより、既存の 15 秒という値の意味が変わりました。接続フェーズは引き続き保護されますが、レスポンスボディに対しても絶対的な期限が課されるようになったのです。配信処理はすでにこのクライアント経由でメディアを取得していたため、この変更が入った時点で回帰がすぐに表面化しました。

障害は静かに起きました。zurg は、ボディをプレーヤーにコピーする前に、成功したアップストリームのステータスとヘッダーを送信していました。クライアントの期限がボディを中断すると、コピー処理はエラーを返しましたが、配信処理はそのエラーを捨てていました:

n, _ = copyBuffered(resp, body)

その時点ですでに 206 レスポンスは確定しており、エラーステータスに置き換えることはできません。リクエストログが無効になっていると、ボディが途中で切れた理由は何も報告されません。その結果、下流のクライアントには、告知された長さに届く前にボディが終わっている、成功扱いの部分コンテンツレスポンスが届いてしまいました。

回帰の経緯

関連するコミットは、問題が報告されたナイトリービルドよりも長い連鎖になっています:

日付 コミット 影響
2024-06-28 c3aea427 既存のサービング読み取りを DownloadFile 経由に変更。ダウンロードクライアントにまだリクエスト全体のタイムアウトがなかったため、動作は変わりませんでした。
2024-11-17 6edeaa8c ダウンロードクライアントに http.Client.Timeout を追加。これが、通常のプロキシ経由のボディが途中で切れ始めたリグレッションです。
2026-02-26 dea98d34 RAR アーカイブ読み取りで同じ15秒のカットオフを正しく特定し、タイムアウトなしのストリーミングクライアントを追加して、RAR のパスだけをそちらに移しました。通常のファイル配信は DownloadFile のままでした。
2026-08-02 e9318e66 ダウンロードを複数プロバイダー対応の debrid.Provider インターフェースの背後に移し、通常のサービング呼び出しはそのまま引き継ぎました。Real-Debrid のバグを生んだわけではありませんが、新しい HTTP ベースのプロバイダーがこの危険なメソッドを引き継ぎました。
2026-08-21 fc2a21f 報告で使われたナイトリービルド。バグを含んでいましたが、バグを導入したわけではありません。
2026-08-21 41db7245 通常のプロキシ再生が DownloadFileStreaming を使うように変更し、最初のエンドツーエンドのタイムアウトリグレッションテストを追加しました。
2026-08-21 eff972b8 すべての HTTP プロバイダーの DownloadFile をタイムアウトなしにし、構造的なガードとしました。カバレッジも Real-Debrid、AllDebrid、TorBox、そして比較用の NZB まで広げました。

2月のRAR修正は、重要なニアミスです。そのコミットメッセージには、http.Client.Timeout がボディにも効くこと、そして15秒のデフォルト値がRARストリームを切っていたことが明記されていました。診断は正しかったのですが、修正はRARリーダーだけに限定されていました。DownloadFile と DownloadFileStreaming を別々のメソッドとして残したため、通常の配信パスは危険な選択をそのまま保ち、さらに6か月間残ってしまいました。

発見が遅れた理由

以下のいくつかの要因が重なって、約21か月もこの回帰に気づけませんでした。

  1. ほとんどのメディアサーバー環境では、zurg に直接 WebDAV でアクセスするのではなく、rclone 経由で接続しています。rclone は範囲を限定したリクエスト (ranged request) を使います。現在の managed mount の既定値は 4 MB から始まり、上限は 512 MB まで増えます。そのため回線が速いと、個々の上流リクエストの多くは 15 秒以内に完了します。これによって問題が表に出にくくなりましたが、経路が安全になったわけではありません。特に回線が遅い場合は危険なままです。
  2. Infuse などの WebDAV クライアントは、大きい範囲や終端を指定しない範囲をリクエストすることがあります。こうしたリクエストでは、1 本の上流レスポンスが期限まで維持されるため、タイムアウトに確実に達します。Discord で再現できたのが 3 つの異なるオフセットすべてだったのも、これが理由です。
  3. 再生時のバッファリングが、原因と症状を分かりにくくしていました。上流リクエストは 15 秒で止まっていましたが、再生が止まるのは、プレイヤーが既に届いていたバイト列を消費しきった後です。目に見える遅延は、ビットレート、バッファリング、シークによって変わりました。
  4. レスポンス自体は正常に見えていました。CDN は有効な 206 を返し、zurg はそれを転送していました。ヘッダーを送った後のボディコピーのエラーは無視されていました。CDN への直接テストは正常で、通常のログにもタイムアウトのエラーは残っていませんでした。
  5. 設定値を上げると問題が解決したように見えました。そのため、この不具合は、誤ったものに紐づいたタイムアウトではなく、単に調整値が小さすぎるだけのように見えてしまいました。
  6. 既存のテストでは、設定されたタイムアウト内に完了するボディやレンジしか使っていませんでした。期限を超えてもレスポンスのボディを流し続け、その後に配信経路を通して全体の長さとチェックサムを検証する、というテストは一つもありませんでした。
  7. RAR の狭い修正によって、以前の最も分かりやすい症状は消えました。しかし、通常のダウンロードで危険な既定値が残ったままになっていました。

タイムアウトを延ばすと直ったように見えた理由

設定を3600秒に変えても、タイムアウトが対象とする範囲は変わりませんでした。変わったのは、報告された25.8秒の転送が完了できるように、実時間ベースの期限を十分先まで延ばしたことだけです:

15 seconds   < 25.8-second transfer < 3600 seconds

これは回避策であって、安全な修正ではありません。どんな有限のリクエスト全体のタイムアウトでも、十分に長いボディは、遅いクライアントや一時停止した接続などによって途中で切断される可能性があります。また、この設定はダウンロードクライアントのダイヤルタイムアウトや、上限付きの検証リクエストにも使われるため、1時間に増やすと、到達できないホストが失敗するまでにかなり長い時間がかかることがあります。修正版のビルドでは、通常の設定値を使うべきです。この値はもう、プロキシされたメディアボディに上限をかけません。

修正とガードレール

41db7245 の応急処置では、streamFileToResponse が Provider.DownloadFileStreaming 経由で取得するように変更しました。このクライアントは同じトランスポートを使いますが、http.Client.Timeout がないため、ボディの寿命は download_timeout_secs に縛られなくなりました。リクエストは下流のリクエストコンテキストを引き続き使うので、プレーヤーを切断すると上流の読み取りもキャンセルされます。接続の確立と TLS ハンドシェイクは、引き続きトランスポート側で制限されます。

eff972b8 では、呼び出し側がメソッド名に "Streaming" を含むものを選ぶことに頼らないようにしました:

  • Real-Debrid の DownloadFile は、今では DoStreaming を使います。
  • 共有ヘルパー debrid.DownloadRanged は StreamingDoer を受け取ります。これは DoStreaming だけを公開しています。AllDebrid と TorBox はこのヘルパーを使っています。
  • そのため、両プロバイダーのダウンロードメソッドは、長いレスポンスボディでも安全に使えるようになりました。
  • 再生以外の上限付き読み取り（OpenSubtitles のハッシュ用の 64 KiB 読み取り 2 回など）には、安全でないクライアント全体のボディタイムアウトに頼らず、専用の明示的なコンテキスト期限が設定されるようになりました。

回帰テストは internal/universal/stream_timeout_test.go にあります。このテストでは、設定されたタイムアウトが 1 秒なのに対し、約 1.6 秒かけて 16 個のチャンクで 1.6 MB のボディを送るローカルサーバーを使います。サイズとチェックサムの両方を検証します:

  • Real-Debrid、AllDebrid、TorBox の両プロバイダーのダウンロードメソッドを直接呼び出す場合;
  • HTTP ベースの 3 プロバイダーすべてについて、streamFileToResponse を通したエンドツーエンドの場合; そして
  • 影響を受けない対照として、NZB 形式のローカルプロバイダーを通した場合。

不変条件は今や明示的になりました。ダウンロードボディを返すメソッドは、リクエスト全体のタイムアウトを決して使ってはなりません。短いプローブやメタデータ読み取りは、自身のコンテキストに期限を持たせるべきです。ストリーミングのボディは、完了、下流のキャンセル、または実際のトランスポートエラーまで生きたままにするべきです。

時間ではなく進捗で制限する

生きたまま完了まで待つと、読み込みが永遠に終わらないパターンが一つあります。配信ノードが接続を開いたままデータを送るのをやめるか、まったく応答しないケースです。2026年9月、Plexのスキャンが、読み込みが一度も失敗しなかったReal-Debridのファイル一つで11時間止まりました。このクライアントには諦める上限がなく、rcloneの --timeout はアイドル時間の上限です。zurgは本体を256 KiBずつ書き込むため、ノードが5分ごとに256 KiBを送る（1 KB/s未満の）場合、タイマーは毎回リセットされて永遠に切れません。もっと遅いノードならタイマーは発動しますが、rcloneは同じノードへ同じリクエストを送り直し、3回のタイムアウトごとにエラーを1件ログに出すだけです。2026年10月3日にzen上でrclone 1.75とマウントの独自フラグを使って計測したところ、そのようなノードで読み込んでいたリーダーは30分たってもまだブロックされたままでした。

internal/universal/starved_read.go では、ノードが30秒間で1 MiB未満しか配信しなかった時点で、プロキシした読み込みを打ち切るようになりました。計測対象はzurgがそのノードの応答を待っていた時間だけです。具体的には、リクエストに接続ができてからヘッダーが届くまでの時間と、本体の各読み取りの中で待った時間です。クライアントへの書き込みにかかる時間は含みません。そのため上記の性質は変わらず、一時停止中や遅いクライアントは好きなだけストリームを開いたままにできます。打ち切られたファイルには2分間 503 を返すので、rcloneのリトライは次の待機時間を待たずにすぐ終わります。ローカルで配信しているNZBの読み込みは監視しません。

アーカイブ内のファイルの読み込みは、以前は streamFileToResponse を通らなかったため、カード204まではこの上限の対象外でした。そのバイトはアーカイブの各ボリュームの範囲から取得され、同じクライアントを通して providerDoer.Do で取得し、RARパーサーが読み取ります。そのため、ノードは接続を保っている限りそれを保持し続けられました。今では、各ボリュームの取得も同じ下限で監視されます。打ち切られた場合はそのエントリーを2分間拒否し、アーカイブの一覧化中に打ち切られたら、パーサーがそのボリュームを壊れたものとして除外するのではなく、一覧化そのものを失敗させます。実際の5ボリュームのセットでは、そうでなければ2つ目のボリュームの後でエントリーのフルの長さを、間違ったバイトで返していました。

カード222では、ノードがボリュームの読み込みを失敗させる他のすべてのパターンでも同じ問題が見つかりました。5xx、429、ヘッダーの途中で切断された接続などです。パーサーはこれらを壊れたボリュームとみなし、そのボリュームを外した状態でアーカイブを一覧化していました。そしてその一覧はキャッシュされていたため、同じセットでボリューム3が503を返すと、オフセット16,057から間違ったバイトを返し続け、ノードが復旧した後も返し続けていました。今ではパーサーが、バイトが解析できなかったボリュームと、バイトがそもそも届かなかったボリュームを区別します（rarstream.ErrVolumeUnavailable）。前者は HTTPSrc が見たステータスごとにマークされ、後者は providerDoer がリモート読み込みで失敗したすべてのケースと、NZBのボディがトランスポートとして分類したものに対してマークされます。後者の場合は一覧化が失敗します。ネストされたセットやボリュームヘッダーのグルーピングも含みます。この失敗には Retry-After 付きの 503 を返し、アーカイブの失敗としてキャッシュすることも、判定として記録することもありません。また、アーカイブの中身の代わりに生のボリュームを返す形で、ブラウズに応答することもありません。壊れているか存在しないボリュームは、これまでどおり除外して一覧化します。

上で触れた256 KiBの書き込みは、カード204でも変更しました。コピーは、ノードが速い間は今までどおりバッファをいっぱいにします。そのため速いボディは、今までどおり丸ごとバッファ単位で送られます。ただし最初のバイトが届いた瞬間に送り出し、どのバイトも250 ms（internal/universal/downloader.go の defaultCopyFlushAfter）を超えて保持しないようにし、そのバイトをフラッシュしてレスポンスを返します。遅いノードがクライアントにヘッダーを返さないようにすることもなくなりました。以前は、zen上でrcloneとマウントの独自フラグを使ったとき、64 KiBを送った後で4分ごとに16 KiBを送るノードのアーカイブエントリーでは、rcloneがちょうど5分で諦めるまでに、3回とも何も届いていませんでした。ノードが送ったものはすべてバッファに残ったままだったのです。
