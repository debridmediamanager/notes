# 永続的な読み取りキャッシュ {#persistent-read-caches}

Imported NZBs、Real-Debrid、AllDebrid、TorBox のエントリはすべて、ライブラリの状態を `data/*.zurgtorrent` に保持します。これらのファイルがライブラリを表しています。読み取り用の準備データやバイトキャッシュはその横に置かれるので、派生キャッシュを変更したり削除したりしても、ライブラリが書き換わることはなく、タグ、名前、アカウントの紐付けが失われることもありません。

## 再起動後に残るもの {#what-survives-a-restart}

| キャッシュ | 場所 | 避けられる作業 |
| --- | --- | --- |
| NZB ドキュメントマニフェスト | `data/nzb-manifests/` | 変更のない XML を解析して、名前、サイズ、リカバリー分類、パスワード、セグメント数を取り出す作業 |
| NZB 記事インデックス | `data/nzb-index/` | 記事の参照を作り直す作業。`mmap` と `resident` の両方のモードで使われます |
| デコード済み Usenet 記事 | `data/bytecache/articles/` | 一度読み込んだ記事を取得して yEnc デコードし直す作業 |
| アーカイブレイアウト | `data/archive-layouts/` | アーカイブヘッダーを読み直して、ボリュームの範囲、ネストされたエントリ、学習済みの ZIP オフセットを作り直す作業 |
| 展開済みアーカイブブロック | `data/bytecache/decoded/` | 再起動後やバックシークの後に、保持しているバイト範囲まで再度デコードする作業 |
| プロバイダーの状態 | `data/provider-cache/` | 変更のない RD のダウンロードウィンドウを作り直す作業や、新しい TorBox の領域テーブルを取得し直す作業 |
| 配信リンク | `data/linkcache/` | まだ有効な URL をもう一度解決する作業 |

アーカイブレイアウトは、保存された (stored) RAR/ZIP エントリと圧縮された RAR/ZIP エントリ、ネストされたソース、暗号化されたスパン、対応している分割アーカイブに対応しています。
保持しているのはソースへの参照とオフセットで、生きている HTTP リーダーは持ちません。
復元時に、現在のプロバイダーの URL が付けられます。
ボリュームが欠けている不完全なレイアウトは、ソースから作り直されます。
学習した ZIP のペイロードオフセットは、最初の読み込みの後に保存されます。ディレクトリの一覧表示中に、すべてのエントリのヘッダーを先に取得することはありません。

NZB マニフェストは、ソースファイルのサイズ、ナノ秒単位の更新時刻、パーサーのバージョンと照合されます。
`mmap` は、メタデータをすぐに復元し、必要になったときに記事インデックスをマップします。
`resident` は、そのインデックスをヒープメモリに読み込みます。
`reparse` は、メタデータをすぐに復元しますが、記事の参照が必要になったときには XML をまた解析します。
既存のライブラリは、このバージョンでの最初のスキャン中にマニフェストを作成します。起動時の保存は、その後のスキャンと再起動から適用されます。

AllDebrid と TorBox では、同じ未キャッシュのアカウント/ファイルに対する同時リクエストが、1 回の解決にまとめられるようになりました。
ある呼び出し元をキャンセルしても、別の呼び出し元の解決はキャンセルされません。
RD は、もともとあった結合の仕組みをそのまま残しています。
TorBox は、ファイルを解決するときに、そのファイルの詳細をもう一度取得する代わりに、既知のカタログの名前とサイズを使います。

`data/info/` にあるプロバイダーの詳細レコードは、プロセスごとに最初の JSON デコードの後にメモ化されます。
再利用のたびにファイルの同一性、サイズ、更新時刻を確認し、独立したコピーを返します。
ライブラリと詳細のファイルは、アトミックに置き換えられます。

## ストレージの予算 {#storage-budgets}

これらの任意のトップレベル設定は MiB 単位で、再起動後に反映されます:

```yaml
nzb_article_disk_cache_mb: 512
archive_decoded_disk_cache_mb: 512
```

各キャッシュの既定値は、インスタンス全体で 512 MiB です。0 にするとそのキャッシュは無効になります。負の値は 0 として扱われます。この予算は、ファイルシステムの割り当てオーバーヘッドではなく、チェックサムを含むレコードのバイト数を対象にします。新しいレコードが届くと、最も古く使われていないレコードから削除されます。予算を減らすと、初期化時に既存のキャッシュが切り詰められます。キャッシュを無効にしても既存のファイルは残るので、手動で削除できます。

記事キャッシュは、既存の RAM キャッシュを補完します。アーカイブキャッシュは 64 KiB のデコード済みブロックを保持し、各デコーダーの 64 MiB のローリング RAM ウィンドウを補完します。どちらのキャッシュもライブラリを事前にダウンロードするわけではありません。保持されているデコード済みブロックの外側を読む場合は、圧縮エントリの先頭からデコードする必要があります。Rclone の VFS キャッシュは別物で、完全にキャッシュされた範囲の配信を引き続き行い、これらのパスは通りません。これらのキャッシュは、直接の HTTP/WebDAV 読み取りにも効果があります。

圧縮エントリは先頭からしかデコードできないため、奥の方を読むと、まずアーカイブ全体を取得することになります。zurg はこのような読み取りを 20 秒間保留し、その後はクライアントが応答を待ちぼうけにならないように `503` を返します。デコードがどこまで進んだかは保持されるので、プレイヤーが前方シークを再試行するたびに、少しずつ先まで進みます。エントリの終わり近くで拒否された読み取りは、そのエントリのバックグラウンドデコードも 1 つ開始します（一度に 1 エントリ）。これにより、エントリの最後の 8 MiB が `data/bytecache/decoded-tails/` に保持されます。その後はファイルの末尾が即座に読めるようになります。メディアサーバーがファイルを解析するときに、まさにこの読み取りを要求します。このストアは `archive_decoded_disk_cache_mb` と同じ予算をもう一度使い、同じ設定で無効にできます。

派生メタデータはライブラリの規模に応じて増えるもので、これらのバイト予算とは別に扱われます。NZB スキャンでは、削除されたドキュメントのマニフェストと記事インデックスが削除されます。古いアーカイブレイアウトのリビジョンは、インスタンスを停止した状態で削除できます。これらは使い捨てのデータで、必要になれば再構築されます。

## 検証と復旧 {#validation-and-recovery}

新しいメタデータレコードとバイト列のブロブには、チェックサムが付いています。壊れたレコードやキャッシュへの書き込みに失敗した場合は、ソースから取得し直します。記事レコードは、取得が完全に成功した後にのみディスクキャッシュに入ります。また、記事は取得した読み取り処理に渡されたあとで書き込まれるので、読み取りがキャッシュを待つことはありません。同時に実行できる数を超える記事の書き込みが一度に来た場合、余分なレコードは読み取りを待たせる代わりに破棄されます。破棄されたレコードは、次に必要になったときに再度取得されます。記事の識別情報には、NZB のリビジョン、サーバー設定、ファイル、セグメントが含まれます。アーカイブの識別情報には、現在のソース参照、サイズ、アカウント設定、パスワード、フォーマットのバージョンが含まれます。NZB ソースを置き換えると、アーカイブのレイアウトとデコード済みのバイト列も無効になります。

ローカルソースのフィンガープリントは、ファイルが置き換えられるとサイズか更新日時が変わることを前提としています。起動のたびに XML 全体をハッシュ化しないよう、あえてそうしています。サイズと更新日時の両方が変わらないまま置き換えた場合は、関連する派生キャッシュを削除する必要があります。

RD のスナップショットは、同じトークンと設定済みのダウンロード上限に対してのみ、かつ 1 時間以内で、ライブプローブが最新のエントリと総数で一致した場合にのみ受け入れられます。リストが変わった場合は、完全な照合が実行されます。TorBox のリージョンテーブルは、既存の 6 時間の有効期限をそのまま維持します。配信 URL の有効期限とプロバイダーの障害処理は変更ありません。ウォームなレイアウトは、HTTP の成功を確定する前にペイロードを開くので、無効化された URL は通常の解決・再試行の流れに進めます。

配信リンクの変更があると、約 1 秒後にまとめてディスクへ書き出されます。5 分ごとの再試行と、シャットダウン時のフラッシュは残ります。アトミックな置き換えにより、読み取り側が書き込み途中のレコードを見ることはなくなります。ただし、停電に対する fsync の保証ではありません。Unix では、新しいキャッシュファイルは `0600` のモードで作成されます。リンクや暗号化されたアーカイブのレイアウトには、認証情報や派生キーが含まれる可能性があるためです。Windows では、Unix のパーミッションビットの代わりに、含まれるディレクトリの ACL を使います。

## ウォームキャッシュ付きのバックアップ {#backups-with-warm-caches}

デフォルトのバックアップには、正式な状態が保存されます。派生キャッシュとインスタンス固有の rclone VFS キャッシュも含めるには、次のコマンドを使います。

```sh
./zurg backup --include-caches --out warm.zurgbackup
```

これは標準のバックアップよりかなり大きくなることがあります。上記で挙げたルートに加えて、NZB の命名・サイズ・PAR2 キャッシュとネットワークテストの状態も含まれます。ログと Plex データベースのスナップショットは引き続き除外されます。`data/rclone-cache/` の外にある rclone キャッシュは含まれません。アクティブなキャッシュの整合性のとれたスナップショットが必要な場合は、インスタンスを停止してください。

復元するには、インスタンスを停止した状態で `./zurg restore-backup warm.zurgbackup` を実行します。
バックアップはナノ秒単位の元のタイムスタンプを保持するため、変更のない NZB は、インデックスとマニフェストをそのまま維持できます。復元されたキャッシュも、通常の検証と有効期限チェックを受けます。バックアップには、設定ファイルのトークンとキャッシュされた認証情報が含まれるので注意してください。

## 再現可能なチェック {#reproducible-checks}

`BenchmarkParsedDocumentStartup` は、60 ファイルと 30,000 セグメントを使って、XML パースと各 manifest restore mode を比較します。`BenchmarkDetailJSONRefresh` は、1,000 ファイルのレコードに対して、JSON の読み取りパスとメモ化されたアクセスを比較します。どちらもローカルのウォームなファイルシステム上のベンチマークで、本番環境でのエンドツーエンドの起動時間を測ったものではありません。

2026-09-05 に Apple M3 Pro で、500 ms の実行を 3 回ずつ行って計測しました（操作ごとの中央値）。

| 操作 | 時間 | 割り当てバイト数 |
| --- | ---: | ---: |
| NZB XML をパース | 43.49 ms | 20.27 MB |
| `mmap` モードでメタデータを復元 | 0.224 ms | 59 KB |
| メタデータと常駐記事インデックスを復元 | 0.577 ms | 1.79 MB |
| `reparse` モードでメタデータを復元 | 0.199 ms | 59 KB |
| プロバイダーの詳細レコードを読み取り/デコード | 0.538 ms | 784 KB |
| stat チェックとコピーで詳細レコードを再利用 | 0.0084 ms | 59 KB |

詳細デコードのケースでは、呼び出しごとに新しいメモをクリアしてから実行するため、メモを埋めるコストも含まれます。この数値は現在の 2 つのアクセス経路を比較したものです。ネットワーク遅延を見積もったり、ライブラリ全体の起動時間を予測したりするものではありません。

回帰テストでは、再起動後の再利用、破損、ソースの変更、アカウントの分離、並行解決、先頭/中間/末尾でのバイト同一性、RAM ウィンドウを超えた後方シーク、レイアウト復元後の URL 失効をテストしています。

```sh
go test ./...
go test -race ./internal/debrid ./internal/nzb ./internal/rarstream ./internal/universal ./pkg/cachefile ./pkg/diskcache
go test ./internal/nzb ./internal/torrent -run '^$' -bench 'Benchmark(ParsedDocumentStartup|DetailJSONRefresh)$' -benchmem
make integration-test
```

統合テスト対象には、ドキュメントに記載された実際のテスト用アカウントとホストの依存関係が必要です。統合スクリプトをスキップした場合、キャッシュの変更は検証されたことになりません。
