# デブリッドの基準値 {#the-debrid-baseline}

zurg のコストと、**debrid** 経路（Real-Debrid、AllDebrid、TorBox）での速さについて。競合はいません。挑戦者は後のバージョンの zurg で、このファイルが、それが超えるべき基準です。

- **テスト対象のビルド:** `23869fa4`（`2026.08.18.0140-nightly-48-g23869fa4`）
- **計測日:** 2026-08-19、`zen` 上（2コア、7.6 GB、Ubuntu 22.04）
- **検証環境:** `scripts/dbench/`、zen 上の `~/dbench` にデプロイ

## 読み方 {#how-to-read-it}

3つのプロバイダーも、互いに競合する関係ではありません。
ライブラリの規模は2桁も違います。Real-Debrid には 3416 本、TorBox には 479 本、AllDebrid には 14 本です。そのため、絶対的なコールドビルド時間を見ても、zurg の性能より、アカウントの状態について分かることの方が多いんです。
だから、サイズに依存する数値は、トレント1本あたりの値も必ず併記します。そして意味のある比較は、常に **同じアカウントで、今回のビルドと次のビルドを比べること** です。

プロバイダー間で本当に比較できるのは、コストの *形* です。バックエンドがトレント1本あたりに何回 API を呼ぶ必要があるか、リンク検証を行うかどうか、変更ポーリングがページ単位かトークン単位か、といった点ですね。

## 設定 {#configuration}

各インスタンスは、プロバイダーを1つだけ、独自のポートと独自のデータディレクトリで動かします。出荷時のデフォルトから変えているのは、分離のために必要な次の設定だけです。

| 設定 | ベンチ | 理由 |
|---|---|---|
| `host` / `port` | `127.0.0.1`, 9991-9994 | 1つのホストで4つのインスタンスを動かすため |
| `providers` | インスタンスごとに1つ | コストをバックエンドごとに分けて把握するため |
| `rclone_enabled` | `false` | 計測はHTTP経由で行い、FUSEは使わないため |
| `directories` | `all` を1つだけ、フィルターなし | 一覧取得のコストがライブラリのサイズに比例するようにするため |
| `enable_repair` | `false` | 同じTorBoxアカウントに別の zurg が読み込まれていて、1つのアカウントを修復できるのは1インスタンスだけだから |

それ以外の設定は、あえて出荷時のデフォルトのままにしています。そのうち2つは結果に大きく影響するので、それ自体が検証結果のひとつです。

- `log_level: DEBUG` — 出荷時のデフォルト (`pkg/logutil/factory.go`)。
- `torrents_rate_limit_per_minute: 75` — 出荷時のデフォルトで、コールドな Real-Debrid ビルドでボトルネックになる制約です。

## コーパス {#corpus}

12本のリリースは、**3つのアカウントすべてで同じinfohash**なので、プロバイダーごとの差はファイルではなくプロバイダー側の違いです。サイズは1.5 GBのエピソードから334 GBのremuxパックまであり、形式は単一ファイルの映画、シーズンパック、349ファイルのシリーズパックです。エントリ0の`The Shawshank Redemption (1994) DS4K`（7.31 GB、1ファイル）は、レイテンシとスループットのフェーズで使うストリーミング対象です。

コーパスを組み立てるのが一番厄介だったので、記録しておきます。TorBoxのキャッシュはReal-Debridのライブラリと約2%しか重なりませんでした（136回のprobeで3ヒット）。そのため、Real-Debrid側ではなくTorBox側からコーパスを作る必要がありました。AllDebridはキャッシュが何もなく、16件中14件のmagnetを即座に受け付けてくれました。Real-Debridは、451のthrottleに引っかからないよう追加のたびに20〜45秒の間隔が必要で、2件は拒否されました。1件は文書化されている決定的な名前ブロックによるもので（`Supergirl…WEB-DL…`）、3分間放置した後の最初の試行できれいに拒否されました。もう1件はthrottleされたままでした。

## API コストの測定 {#measuring-api-cost}

zurg は送信リクエストのカウンターを持っていません。さらに `log_requests` は意図的に Real-Debrid の 2 つのエンドポイント `torrents/activeCount` と `torrents?limit=1&…` を除外しています。この 2 つが変更検出のポーリングの全体です。そのため、ログから数えると Real-Debrid のアイドル時のコストがゼロと報告されてしまいます。

そこでカウントはプロセスの外で行います。mitmproxy が TLS を終端し、アドオンがリクエストごとに JSONL を 1 行ずつ書き出します。インスタンスは、`HTTPS_PROXY` と `SSL_CERT_FILE` を傍受用の CA に向けた状態で起動します。Go の x509 ローダーは `SSL_CERT_FILE` を参照するので、信頼設定はそのプロセスだけに限定され、ホスト上のものは何も変更されません。リクエストは `api`、`nettest`、`content`、`other` のいずれかに分類されます。

プロキシはリクエストの経路上に入るため、API コストを測るフェーズでだけ使い、タイミングのフェーズは直接接続で実行します。TorBox はビルド全体の呼び出しが 4 回だけです。プロキシ経由の実行と直接の実行では、それぞれ 3.0 秒と 4.0 秒でした。この規模ではプロキシの影響は誤差の範囲内です。

## 結果 {#results}

すべての数値は、2026-08-19 に zen 上でビルド `23869fa4` を使って取得したものです。レイテンシーとスループットは、同じ 7.31 GB のファイルに対する 1 回の交互（interleaved）実行から得ています。3 つのアカウントすべてで同じインフォハッシュを使っており、`ffprobe` では各アカウントから同じ 8552.574 s という再生時間が報告されています。つまり、コンテンツは実際にバイト単位で同一です。

#### 失敗の内容 {#what-the-failures-are}

2回目の実行でフローログが残っていたので、699件の内訳が分かりました。

| Status | Count | Endpoint |
|---|---|---|
| 429 | 589 | `unrestrict/link` |
| 503 | 85 | `unrestrict/link` |
| 404 | **22** | `downloads/delete/{id}` |
| 451 | 3 | `unrestrict/link` |

問題は2つあって、どちらも「プロバイダーが不安定だった」が原因ではありません。

- **589件のレート制限による拒否**。すべて `unrestrict/link` で起きています。`api_rate_limit_per_minute` のデフォルトは 250 ですが、これでは unrestrict を Real-Debrid が実際に許す上限の内側に収められません。そのため、キャッシュなしの初回ビルドの約 8% が拒否とリトライになっています。
- **23件の `downloads/delete` 呼び出しのうち22件が 404 を返しました**。3,992件の unrestrict とバランスを取るはずのクリーンアップが、稀に失敗するのではなく、実行されるたびに失敗しています。存在しない ID を削除しようとしているのです。unrestrict のたびにアカウントの downloads リストに永続的なエントリが作られ、今回のスキャン後にテスト用アカウントには **12,469** 件ありました。

1回目と2回目で動いた数値が1つあり、まだ説明がついていません。`*.download.real-debrid.com` への HEAD プローブ数は、1回目のビルドが 88 件、2回目が **3,426** 件でした（ほぼトレントごとに1件）。downloads リストが増えたことと相関していて、2回目は `/downloads` の取得回数も1回目の1回に対して8回でした。ただ、これは相関であって原因ではありません。最適化する前に、ここをはっきりさせておく価値があります。

### アイドル時の定常状態 {#idle-steady-state}

10分間、読み込み済みのライブラリが何もしていない状態です。
順位は、各バックエンドにどれだけ安く問い合わせられるかで決まっています。これは `LibraryFingerprinter` が存在する理由を最もよく示す例です。

| | API呼び出し/分 | APIバイト/分 | CPU秒 / 10分 | ピークRSS | 送信内容 |
|---|---|---|---|---|---|
| AllDebrid | **4.0** | **867** | 0.20 | 28 MB | ポーリングごとに Live Mode の差分を1回。変化がなければ空 |
| TorBox | 7.9 | 43.6 KB | 0.33 | 53 MB | `mylist` をページ単位で取得。差分フィードもキャッシュ検証子もなし |
| Real-Debrid | 11.4 | 59.8 KB | 0.43 | 85 MB | `torrents?limit=1` と `activeCount`、さらに `/downloads` |

Real-Debridは114回の呼び出しのうち32回を、`/downloads` の一覧を再取得するために使っています。これは初回ビルドで12,469件まで増えたのと同じ一覧です。

この表は、件数を `log_requests` からではなくプロキシ経由で数えている理由でもあります。Real-Debridのアイドル時の114回の呼び出しのうち80回は、`ShouldSkipLogging` が抑制する2つのエンドポイントへのものです。そのため、ログではアイドル時のコストがほぼゼロと報告されてしまうはずでした。

### コールドオープンの実際の内訳 {#where-cold-open-actually-goes}

`apiref.py` は、プロバイダー側の処理時間を測定します。具体的には、保存済みのファイルを取得可能な URL に変換する呼び出しと、その URL から最初のバイトが届くまでの時間です。zurg は計測から外しています。テストは 2 回実行しました。1 回目は AllDebrid の修正より前に行ったため、その行は 1 サンプルしかありません。

| | resolve | CDN TTFB | provider total | zurg cold open | zurg's share |
|---|---|---|---|---|---|
| Real-Debrid, run 1 | 0.133 s | 0.267 s | 0.400 s | 1.294 s | **0.89 s** |
| Real-Debrid, run 2 | 0.157 s | 0.383 s | 0.540 s | 1.294 s | **0.75 s** |
| AllDebrid | 0.139 s | 0.333 s | 0.472 s | 0.476 s | 0.00 s |
| TorBox, run 1 | 0.260 s | 0.277 s | 0.537 s | 0.565 s | 0.03 s |
| TorBox, run 2 | 0.270 s | 0.381 s | 0.651 s | 0.565 s | ~0 |

プロバイダーの数値と zurg の数値は計測したタイミングが違うため、差し引いた値はあくまで目安です。正確な値ではありません。ただ、2 回のテストで同じ傾向が出ています。AllDebrid と TorBox は、プロバイダー自体のコストに対してほぼ上乗せがありません。一方 Real-Debrid は 0.75～0.89 秒上乗せされています。まず狙うべきは、この差がいちばんはっきりした点です。

### 1 つのインスタンスで 3 プロバイダーすべて {#all-three-providers-in-one-instance}

統合されたインスタンスには、すべてのアカウントが一度に含まれています。コーパスは意図的に3つすべてに配置してあるので、1つのリリースが複数のアカウントに保持されているケースもテストできます。

| | Real-Debrid 単独 | 3 アカウント統合 |
|---|---|---|
| 確認された torrent 数 | 3,316 | 3,781 |
| ユニークなリリース数 | 3,318 | 3,778 |
| compiled までの時間 | 1,774 s | 1,775 s |
| API リクエスト数 | 7,442 | 7,491 |
| ピーク RSS | 77 MB | 82 MB |
| ライブラリ全体の PROPFIND | 26 ms / 1.17 MB | 23 ms / 1.34 MB |

Real-Debrid のインスタンスに TorBox と AllDebrid を追加しても、ほぼコストはかかりません。torrent が 465 件増えるのに、API 呼び出しは 49 回、RSS は 5 MB 増えるだけで、計測できるほどの時間は増えません。統合は本物です。3 つのアカウントをそれぞれ数えると合計 3,809 件の torrent がありますが、ここでは 3,781 件になります。つまりコーパスが 3 つのコピーから 1 つにまとまっているということです。

### 追加と削除の検出 {#add-and-delete-detection}

プロバイダー側で変更してから、マウント側の内容が一致するまでどれくらいかかるか。

| | Delete detected | Add detected |
|---|---|---|
| Real-Debrid | 18.7 s | 12.7 s |
| AllDebrid | 16.5 s | 14.4 s |

どちらも `check_for_changes_every_secs` の 1 回分と refresh の時間に収まっています。そのため `library_resync_every_mins` の待ち時間はかかっていません。TorBox はテストしていません。テスト用のリリースがそのアカウントに常に残っていて、削除すると、再追加してもキャッシュされていないかもしれず、元に戻せないからです。

### プロバイダー障害、CDN は稼働中 {#provider-outage-cdn-up}

`ca/outage.py` は、コンテンツへのリクエストはそのまま通しつつ、すべてのプロバイダー API 呼び出しに 503 を返すようにします。そのうえで zurg をこの状態に向けて起動します。

| | 障害前に読み込み | 障害中のライブラリ構築 | 障害中の読み込み |
|---|---|---|---|
| Real-Debrid | 206, 1.60 s | never (180 s) | 120 s でタイムアウト |
| AllDebrid | 206, 0.44 s | never (180 s) | 120 s でタイムアウト |
| TorBox | 206, 1.53 s | never (180 s) | 400, 0.035 s |

**プロバイダーがダウンしている間に zurg を起動すると、空のマウントができてしまいます。** 運用上いちばん重要なのがこのシナリオです。Real-Debrid の 503 が続いている最中にホストが再起動する、というケースがこれにあたります。8 月に `fun` で数万件もの Plex アイテムを消してしまったのも、まさにこの状態でした。スキャン中に一時的にマウントが空になると、「ファイルがすべて削除された」と見えてしまったのです。これを防ぐ仕組みは zurg ではなく Plex 側にあります（`autoEmptyTrash 0`）。

Real-Debrid と AllDebrid は、失敗を即座に返すのではなく、リーダー自身のタイムアウトが切れるまで待たされます。TorBox は 35 ms で応答を返します。

### 一時的な 503 でリリースが空のフォルダーとして残る {#a-transient-503-leaves-releases-as-empty-folders}

これは、実行結果で最も明確な欠陥です。しかも偶然見つかりました。

Real-Debrid のコールドビルドで扱った 3,316 件の torrent のうち、**85 件のレスポンスが 503** になり、**84 件が `broken_torrent`** で終わりました。この状態のリリースはマウントには表示されたままですが、ディレクトリは**空**です。2 件を PROPFIND で確認したところ、保存されたレコードには 10 件と 3 件の選択済みファイルがあるのに、どちらも何も返しませんでした。

これは自然には解消しません。ベンチマークは `enable_repair: false` で動かしていて、そのリリースは 1 時間以上、再起動を何回か挟んでも壊れたままでした。

修復（repair）をオンにすると、shipped のデフォルトでもあり、壊れたものを処理はしてくれます。ただし遅いです。手動で修復パスを起動したときの推移は次のとおりです。

| Elapsed | Broken | Under repair |
|---|---|---|
| 0 min | 85 | 0 |
| ~2 min | 77 | 2 |
| ~15 min | 73 | 4 |

15 分で 12 件のリリースしか直らず、しかも最初の数分を過ぎると処理速度が落ちます。この調子だと、コールドビルド 1 回分の壊れたリリースを片付けるのに 1 時間以上かかります。そして修復が回ってこないリリースは、その間ずっと空のフォルダのままです。

つまり影響の大きさは設定によって変わります。

- 修復がオン（デフォルト）の場合、スキャン中の 503 は、修復パスがそのリリースに届くまでファイルを失わせます。ライブラリ全体で 1 時間ほどです。
- 修復がオフの場合、リリースは無期限に空のフォルダのままになります。

TorBox ではさらに厄介です。`StoredLinksCanRot: false` を報告するため、refresh がリンクを再検証することはありません。修復を使う以外に、壊れた状態を解消する経路がないのです。障害テストで壊れ扱いになった TorBox のリリースは 1 件でしたが、68 分と何度かの再起動を経ても壊れたままでした。その間、プロバイダ側では `cached`、`download_present`、ファイル 1 個、7.31 GB と報告されていました。

### 読み取りの整合性 {#read-integrity}

ファーストスループットの実行で、AllDebrid の読み取りが1回、268,435,456 バイトの範囲に対して 263,798,425 バイトしか返しませんでした。ステータスは 206 で、エラーはありませんでした。**再現はしませんでした**。Real-Debrid と AllDebrid のそれぞれで8回ずつ繰り返しましたが、毎回、範囲全体が返ってきました。これは一度きりの現象として記録し、不具合とは見なしていません。ただ、今後も注意して見ておく価値はあります。

## Plex の負荷時 {#under-plexs-load}

ここまでの測定は、一度に1つだけ読み込む前提でした。でも実際のメディアサーバーは、そういう動き方をしません。
Plex はスキャンを行い、数千ものファイルをそれぞれ少しずつ読みます。同時に Plex はストリーミングも行い、この2つは重なります。これらのフェーズでは、両方が同時に動いている状態でマウントを測定しています。

**全体の数値は zurg ではなく zen の特性として読んでください。** どのターゲットも、プロバイダーやモードに関係なく 73〜78 MB/s で頭打ちになります。これはホストの回線速度です。一般化できるのは *完了率* と、プロバイダーごとの失敗パターンのほうです。速度の上限はローカル環境によるものです。

### 複数の読み取り、異なるファイル、1 つのプロバイダー {#multiple-readers-different-files-one-provider}

ストリームあたり 96 MB、すべて別ファイルです。

| ストリーム数 | Real-Debrid | AllDebrid | TorBox | 統合 |
|---|---|---|---|---|
| 1 | 44.8 | 52.1 | 45.6 | 51.8 |
| 2 | 72.3 | 63.5 | 71.4 | 69.8 |
| 4 | 73.7 | 64.2 | 74.6 | 70.2 |
| 8 | 73.6 | 73.4 | 65.5 | 75.1 |
| 12 | 77.1 | 73.8 | 76.3 | 77.1 |

合計 MB/s です。2 ストリームで帯域はいっぱいになります。それ以上は、読み手が増えるほど同じ帯域を分け合うことになります。ストリームごとの中央値は、1 本で約 45 MB/s、12 本で約 8 MB/s まで下がります。

注目すべきは完了数の列です：

| ストリーム数 | Real-Debrid | AllDebrid | TorBox | 統合 |
|---|---|---|---|---|
| 4 | 4/4 | **2/4** | 4/4 | 4/4 |
| 8 | 8/8 | **3/8** | 8/8 | 8/8 |
| 12 | 10/12 | **4/12** | 9/12 | 10/12 |

**AllDebrid は、4 つの別ファイルを同時に読むと読み込みを完了できなくなります。** データ自体は流れていて、合計速度は提供元の上限のままです。ただし個々のストリームは終わらず、8 と 12 では中央値が 0 になり、TTFB の中央値は 3 秒を超えます。他のプロバイダーは 12 まで問題ありませんが、12 では 4 つすべてで 1〜2 本ずつ失敗します。

> **2026-08-23 に撤回。これはプロバイダーの同時接続数の上限ではありません。**
> zurg 経由で全速力で試すのではなく、再生ビットレートを制限して API に直接テストし直したところ、AllDebrid は **4/8/12/16/24 の同時別リンクを 100%** 解決でき、**24/24** のライブストリームを維持できました。上記の失敗は、**経路が null に向けられていた AllDebrid CDN ホスト 3 つ**が原因でした。
> `l4m5n6.debrid.it`、`o7p8q9.debrid.it`、`c1uw74.debrid.it` はいずれも `0.0.0.0` に解決され、**解決されたリンクの 15.6%** を占めていました。最初のホストは、この文書の後ろで一度きりのデッドリンクとして記録されているものと同じです。一度きりではありません。
>
> 死んだホストは、そのファイルがバッチに含まれているときだけ失敗します。そのため失敗数は N とともに増え、同時接続数の上限とまったく同じ形になります。**段階を上げるごとに別ファイルを増やすテストは、どれもこの誤った結果を再現してしまいます。**
>
> 同じ理由で、この完了数の列全体もテスト方法の制約を受けています。これらの試行は、飽和した 73〜78 MB/s の回線で全速力で引っ張ったものなので、測っているのは **帯域の取り合いであり、プロバイダーの上限ではありません**。
> 実際のホストごとの上限は、いずれも公式には記載されていません。Real-Debrid は **32**（TCP 層で切断）、AllDebrid は **32**（HTTP 429）、TorBox は `nexus-NNN` ホストごとに **20**（HTTP 429、IP ごとではなくホストごと）です。Premiumize は 64 でも上限は見つかりませんでした。
>
> 撤回の内容を読みすぎないための注意点が 1 つあります。null に向けられたホストは約 0.1 秒で失敗しますが、上記の TTFB 中央値は 3 秒を超えています。これは別の特徴を持つ、遅い失敗です。そのため、帯域の不足も起きていた可能性が高いです。どちらの要因も、プロバイダー側の上限ではないことを示しています。
>
> **そこから導ける対策:** AllDebrid の CDN ホストで接続レベルの失敗が起きたら、同時接続数を減らすのではなく、**リンクを再度 unlock して** 再試行できるものとして扱います。新しい `/link/unlock` は別のホストを返します。`0.0.0.0` を拒否する DNS 照会は、ここで確認されたケースをすべて捕まえ、コストもかかりません。

### 複数の読み取り、同じファイル {#multiple-readers-one-file}

同じ負荷レベル、同じファイル、異なるオフセット。先読みとシークの組み合わせです。

| streams | Real-Debrid | AllDebrid | TorBox |
|---|---|---|---|
| 4 | 4/4 | 4/4 | 4/4 |
| 8 | 8/8 | 8/8 | 8/8 |
| 12 | 10/12 | 9/12 | 10/12 |

AllDebrid は、ここでは **問題ありません**。4/4 と 8/8 です。一方、別々のファイルでは 2/4 と 3/8 でした。
この逆転が原因の手がかりです。上限は帯域幅でもtorrentごとの上限でもなく、同時の**リンク解決**にあります。別々のファイルなら、それぞれ個別にアンロックが必要になります。同じファイルなら一度解決すれば、あとはストリーミングするだけです。

> **2026-08-23 に撤回** — この逆転には、もっと単純な説明がありました。別々のファイルは別々の CDN ホストに割り当てられ、そのうち3つが AllDebrid 側で null ルーティングされていました。同じファイルは1つのホストに解決されるので、動くか動かないかのどちらかです。リンク解決そのものは、同時24件でも問題ないことを測定で確認しています。上の注記を参照してください。

### 複数の読み取り、異なるプロバイダーをまたぐ {#multiple-readers-across-different-providers}

これはマルチプロバイダー構成のケースで、マッチ版のコーパスでは試せないデータが必要です。統合インスタンスは複数アカウントのリリースを`Sources[0]`から配信するので、マッチ版コーパスの読み取りはすべて Real-Debrid に当たります。そこで、ここではプロバイダーごとに排他的なプールを使います。Real-Debrid だけが持つファイルが 8 件、AllDebrid だけが持つファイルが 7 件、TorBox だけが持つファイルが 8 件です。

| ストリーム数（プロバイダーごと） | 合計 MB/s | 完了 | RD | AD | TB |
|---|---|---|---|---|---|
| 3（各 1） | 55.3 | 2/3 | 28.8 | — | 27.9 |
| 6（各 2） | 66.9 | 5/6 | 16.1 | 13.3 | 21.5 |
| 12（各 4） | 75.9 | 11/12 | 7.4 | 8.4 | 9.0 |

プロバイダーごとの列は、ストリームごとの中央値（MB/s）です。

異なるアカウントへの読み取りは、確かに並列で動きます。ただ、それぞれが同じ 76 MB/s のホスト上限に達します。これは、1 つのプロバイダーだけでも到達できる上限です。**このホストでは、バックエンドを混ぜても帯域幅は増えません。** 他の環境で増えるかどうかは、1 つのプロバイダーが埋めきれないほど太い回線があるかどうかにかかっています。zen にはそこまでの回線はありません。混ぜることで得られるのは可用性です。ただし、その効果も一部だけです。詳しくは下のフェイルオーバーの節を見てください。

繰り返し起きている失敗は 1 つだけです。AllDebrid の 1 ファイルで、CDN のホスト名 `l4m5n6.debrid.it` が **0.0.0.0** に解決されます。これは zurg の問題ではなく、AllDebrid が無効なリンクを返しているためです。ただ、zurg は 3 回リトライするのに約 4 秒かけてから 500 を返します。しかもこのファイルは他のアカウントにはないので、切り替え先がありません。

### フェイルオーバー: 一方向のみ {#failover-only-from-one-direction}

統合インスタンスは負荷を分散できないので、そこで期待できるのは、1つのアカウントが不調になったときの生存性だけです。`ca/cdnfail.py` は、あるアカウントの CDN だけを止めて、他のすべての API と他のアカウントはそのまま残します。そのためライブラリの読み込みは成功し、影響を受けるのはファイルの中身だけです。読み取りに使ったリリースは対象のコーパスで、3つのアカウントすべてがそれを持っています。

| CDNダウン | 配信できた読み取り | 読み取りの動き |
|---|---|---|
| Real-Debrid | 2/2 | AllDebridにフォールバック、0.6秒 |
| AllDebrid | **0/3** | AllDebridに1回試行、503、その後0.1秒で**クライアントへ500** |

**フォールバックが起きるのは、失敗したアカウントが Real-Debrid のときだけです。** その理由は、他のバックエンドが設定していない機能にあります。Refresh がリンクを先回りで検証するのは `StoredLinksCanRot` が true のときだけで、これは Real-Debrid だけに当てはまります。

```
Link verification failed during refresh for /A.Business.Proposal…: (code: 503)
```

この処理によってソースが降格され、その後は読み取りが別のアカウントにきれいに移ります。AllDebrid と TorBox は一度も確認されないため、どちらかの CDN が落ちていても気づかれず、ソースも降格されません。その結果、状態が続く限り、そのリリースの読み取りはずっと500を返します。

これにはさらに2つの問題があります。

- **読み取りパスには、その場でのフォールバックがまったくありません。** 選ばれたアカウントの CDN から503が返ると、0.1秒でクライアント向けの500に変換されてしまい、同じファイルを持つ他のアカウントは試されません。回復はすべてバックグラウンドの Refresh が担っているため、Real-Debrid の場合でも読み取りが失敗する時間帯が生じます。
- 同じ仕組みの欠落が、68分間 `broken_torrent` のままだった TorBox のリリースの原因にもなっています。TorBox や AllDebrid のリンクを再検証する仕組みがないため、不良状態を解除することも、回復したことに気づくこともできません。

### プロバイダーからの無効なリンク {#a-dead-link-from-the-provider}

AllDebrid の exclusive プールにある 1 つのファイルは、触るたびに、スキャンの実行でも mixed-reader の実行でも毎回失敗しました。その CDN ホスト名は、ヌルルートに解決されています。

```
$ getent hosts l4m5n6.debrid.it
::              l4m5n6.debrid.it
0.0.0.0
```

AllDebrid は `0.0.0.0` を指すリンクを返していました。ここはプロバイダー側の問題で、zurg のせいではありません。zurg がその後どう振る舞ったかが問題です。約 4 秒の間に 3 回試行し、そのあと 500 を返しました。このファイルは他のアカウントにはないので、代わりにできることはありませんでした。ただ、上のフェイルオーバーの結果を見ると、そもそもフォールバックしなかっただろうということもわかります。

> **2026-08-23: 1 つのホストだけの話ではなく、1 つのファイルだけの話でもありません。** AllDebrid の CDN ホスト名 3 つが同時にヌルルートされていました。`l4m5n6.debrid.it`、`o7p8q9.debrid.it`、`c1uw74.debrid.it` です。1 回目のサンプルでは 32 リンク中 5 件、別のサンプルでは 32 リンク中 4 件で、内容はまったく関係のないコンテンツでした。AllDebrid は同じ死んだホストを別のファイルにも払い出しており、この実行から数日たっても続いていました。これは同社のサーバー群にある継続的な穴であり、上で撤回された並行性に関する調査結果の原因にもなっていました。
>
> 3 回の試行と 500 は適切な応答ではありません。代わりに**リンクを再度 unlock してください**。`/link/unlock` は別のホストを返します。そして、`0.0.0.0` を拒否する DNS ルックアップで事前チェックを行ってください。これなら、観測されたケースはすべて、追加コストなしで捕まえられます。

### スキャン {#scanning}

`ffprobe` を23ファイルの混在プール全体に対して実行したものです。これは Plex の解析パスと同じ形です。

| 同時実行数 | files/min | ファイルごとの中央値 | ファイルごとの最大値 | CPU 秒 |
|---|---|---|---|---|
| 1 | 43.7 | 1.16 s | 3.11 s | 2.22 |
| 4 | 112.0 | 1.67 s | 4.19 s | 1.29 |
| 8 | 142.3 | 1.87 s | 6.67 s | 1.16 |

スキャンは並列化がよく効きます。スレッドを1本から8本にすると3.3x速くなり、ファイルごとの遅延は60%しか増えません。3,316リリースの Real-Debrid ライブラリだと、Plex 自身の処理を除いて、
スレッド1本で約**76分**、8本で約**23分**かかる計算です。

### スキャン中のストリーミング {#streaming-while-scanning}

天罰のように恐れるべきケースは、一時的に不調なマウントに対してスキャンを走らせたときです。実際、それで `fun` の Plex アイテムが数万件も失われました。

| スキャンの同時実行数 | ストリームのみ | スキャン中のストリーム | 維持率 | スキャン所要時間 |
|---|---|---|---|---|
| 4 | 57.7 MB/s | 66.5 MB/s | 115% | 11.8 s |
| 8 | 67.8 MB/s | 66.8 MB/s | 98.5% | 9.7 s |

**スキャンがストリームの帯域を奪うことはありません。** 視聴側はほぼすべてのスループットを維持し、最初のバイトまでの時間もむしろ改善します（1.18 s から 0.15 s へ）。その時点ではすでに接続が温まっているためです。デブリッド経由の経路が、心配していたよりも良く動く数少ない箇所です。

## 今回の実行で見つかった不具合 {#defects-this-run-surfaced}

1. **一時的な 503 が、リリースを空のフォルダとして残してしまう。** 1 回のコールドビルド中の 85 x 503 により、84 件のリリースが `broken_torrent` に入りました。壊れたリリースは、中身のファイルが何も無い状態で一覧に出ます。repair がオフの場合は解消されることがなく、オンの場合も、パスがそのリリースに到達したときにしか解消されません。TorBox には再検証の仕組みが一切なく (`StoredLinksCanRot: false`)、そこで壊れていた 1 件のリリースは、プロバイダーがキャッシュ済みで存在すると報告しているにもかかわらず、68 分後もまだ壊れたままでした。
2. **ダウンロードエントリのクリーンアップが壊れており、そのコストは積み重なっていく。** `unrestrict/link` が 3,992 回なのに対し `downloads/delete` は 23 回で、そのうち **23 件中 22 件が 404 を返しました**。クリーンアップは存在しない id を削除しようとしています。アカウントのエントリ数は、さらに 2 回のコールドビルドの間に 12,469 件から **18,768 件** に増えました。zurg は起動時に全リストを 5,000 件ずつページ分割して読むため、このリークは起動コストとして表れ、エントリが増えるほどそのコストも増えていきます。
3. **1 回のコールドビルドで 589 件のレート制限拒否。** すべて `unrestrict/link` で発生し、パス全体の約 8% にあたります。デフォルトの `api_rate_limit_per_minute: 250` では、unrestrict を Real-Debrid の実際の上限内に収められません。これらと 503 は、欠陥 1 を引き起こすのと同じ出来事です。
4. **プロバイダーの障害中に起動すると、空のマウントになる。** その状態で Real-Debrid や AllDebrid への読み取りを行うと、すぐに失敗せず、クライアント自身のタイムアウトまでハングします。TorBox は 35 ms で 400 を返します。
5. ~~**AllDebrid は、異なるファイルへの同時読み取りを完了しなくなる。**~~ **2026-08-23 に撤回 — 上の「Multiple readers, different files」の注記を参照してください。** 原因は同時実行数の上限ではなく、リンクの 15.6% を運ぶ 3 つの null-routed AllDebrid CDN ホストでした。直接再テストすると、AD は同時に 24 個の異なるリンクを 100% 解決し、24/24 のストリームを維持しました。元の文章は記録のため以下に残しています。

   2 of 4, 3 of 8, 4 of 12. 同じ水準を *単一* のファイルに対して行うと問題ありません (4/4, 8/8)。つまり制限は帯域や torrent ごとの上限ではなく、同時リンク解決にあります。4 つのファイルを同時に再生するのは、家庭では普通の夜の過ごし方です。
6. **複数アカウントのリリースは、常に同じアカウントから配信される。** `File.PrimarySource` は `Sources[0]` を返すため、最初に見つかったアカウントが選ばれます。コーパスの 7 件すべてのリリースが Real-Debrid から配信されていたことを確認しました。一方、AllDebrid と TorBox には同一のコピーがありました。より速い、あるいは負荷の低いアカウントを選ぶことはありません。
7. **フェイルオーバーは一方向にしか動かず、その場では決して起きない。** Real-Debrid の CDN が拒否している間、読み取りは AllDebrid へ移りました。AllDebrid の CDN が拒否している場合、3 件中 0 件の読み取りしか配信されず、それぞれ 0.1 秒で 500 を返し、同じファイルを持つ 2 つのアカウントを試すことはありませんでした。`StoredLinksCanRot` を設定しているのは Real-Debrid だけなので、リフレッシュ時に再検証されるのもそのリンクだけで、ソースを降格させるのも Real-Debrid の失敗だけです。読み取りパスでは、エラーが起きても 2 つ目のアカウントを試す処理がありません。
8. **起動時のネットワークテストが、すべてのバックエンドで実行される。** TorBox のみ、および AllDebrid のみのインスタンスで、Real-Debrid のダウンロードホストに対して 88 回の HEAD リクエストが送られていましたが、どちらもその結果を必要としていません。
9. **コレクション自身の PROPFIND href が 404 になる。** zurg は `<d:href>/all/…</d:href>` を出力し、`/dav` プレフィックスが抜けています。そのパスを取得すると 404 が返ります。子要素は相対 href で出力されるため、誤っているのは自分自身のエントリだけです。RFC 4918 は、クライアントが解決できる href を求めています。rclone と Plex は、この href を使っていないおかげで動いているだけです。
10. **`user`/`user/me` が、起動のたびに 3 回呼ばれる。** コールドでもウォームでも、TorBox と AllDebrid の両方で発生します。

## 不具合ではないが知っておくとよいこと {#not-defects-but-worth-knowing}

- **Real-Debrid は infohash で重複を排除しません。** アカウントに既にあるマグネットを追加すると、*2つ目*のエントリが作られます。そのため 3,416 件のトレントが 3,318 件のユニークなリリースにまとまります。これにより最初の削除検出プローブが無効になりました。プローブは直前に作成した重複を削除してしまい、何も検出されなかったという結論になっていました。
- **`torrents_rate_limit_per_minute` のデフォルトは 75** で、これが初回の Real-Debrid ビルドの速度を制限しています。意図したデフォルトであり、バグではありません。ただし、29分という数字を決めているのはこの値です。
