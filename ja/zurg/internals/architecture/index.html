アーキテクチャ

zurgとは何か、各パーツがどう組み合わさっているか、そして各パッケージがなぜ存在するのかを示す地図です。これからコードを変更しようとしている人向けで、設計上の重要な判断と、気づかないうちに壊れやすい不変条件を挙げています。

パッケージごとの詳細は、各パッケージのdoc.goにあります。このドキュメントはその一段上の内容で、全体の形と、その形がどんな理由から来ているのかを扱います。

zurg とは

debrid アカウントのトレントライブラリを仮想ファイルシステムとして見せる Go 製のデーモンです。メディアは一切保存しません。読み取りのたびに、リクエストの時点でプロバイダの CDN に対してレンジ指定の HTTP GET に変換されます。

独自のコンテンツは持たず、PUT は拒否します。そのため、バイトデータに関して言えば読み取り専用です。受け付ける書き込みは2種類あります。1つは名前の変更で、名前を保存するだけでアカウントには触れません（renaming.mdを参照）。もう1つは DELETE で、そのリリースを保持しているすべてのアカウントから削除します。__magic__ は、ある名前空間の中に3つ目の書き込みを加えます。保存されるレイアウトです（magic.mdを参照）。その中のどこでも書き込めますが、__magic__/__all__ とその直下にあるリリースフォルダは除きます。これらは、ダウンロードクライアントがインポートする、計算で生成されたミラーです。

同じライブラリを見るためのビューは4つあります。

Endpoint 用途
/dav/ WebDAV。rclone がマウントするもの
/http/ HTML のディレクトリブラウザ
/infuse/ Infuse 特有の挙動に対応した WebDAV バリアント
/strm/ .strm ファイル内の署名付き URL。マウントではなく URL を求めるプレーヤー向け

rclone は /dav/ を FUSE でマウントするので、Plex、Jellyfin、Emby、Infuse は普通のディレクトリツリーとして見えます。

設計上の課題は一貫して、ファイルシステムが約束するもの（安定したパス、即座の stat、必要なときにバイトを返すこと）と、debrid API が提供するもの（レート制限のかかった JSON、腐ってしまうリンク、ファイルシステムのセマンティクスが一切ないこと）との間のギャップです。ほぼすべてのパッケージは、そのギャップの一部を埋めるために存在しています。

起動シーケンス

cmd/zurg は薄い Cobra CLI です（serve、version、network-test、clear downloads/torrents、mount の操作、download requirements）。実際の処理はすべて internal/app.go で行われ、その MainApp は意図的にひと目で読める 1 つの関数になっています。

  1. ランタイム用のディレクトリ（logs、data、data/info、dump、 strm、nzbs）とロガーを作成します。

  2. ensureConfigAndRequirements — 設定を読み込み、ffprobe と rclone がなければダウンロードします（internal/requirements）。設定ファイルがない初回起動では、デフォルトの設定ファイルを書き出して停止します。ただしトークンが環境変数から渡されている場合は停止しません。

  3. strmlink を早めに初期化します。こうするとデータディレクトリに書き込めない場合でも、次回の再起動後に .strm ファイルが解決できなくなってから気づく、ということがなくなり、今の時点で報告されます。

  4. Real-Debrid のダウンロードホスト（internal/rdclient）に対して ネットワークのレイテンシーテスト を実行します。新しければ、ディスクにキャッシュされた結果を読み込むだけです。このテストで CDN ホストの順位が決まり、後のホストのローテーションがこれを利用します。

  5. レジストリから設定されたすべてのプロバイダーを作成し、debrid.Set にまとめます。最初の Real-Debrid のプロバイダーには型付きのハンドルを保持しておきます。ダッシュボード、ホストページ、ネットワークテストは今も RD 専用として扱っているためです。

  6. TorrentManager を作成します。作成直後からバックグラウンドでディスク上のキャッシュ済みライブラリの読み込みを始め、その後は更新を続けます。

  7. chi ルーターを取り付けて HTTP サーバーを起動し、サーバーが接続を受け付けられるようになってから rclone を起動します。

  8. SIGINT/SIGTERM/SIGQUIT を待ちます。シグナルを受け取ったら、HTTP サーバーを終了させ、Plex サービスを停止し、rclone をアンマウントします。それぞれに 20 秒の制限時間があります。

ZURG_PPROF=1 を設定すると、127.0.0.1:6060 で pprof が有効になります。ループバックだけで待ち受けるのは意図的です。スキャンが大量に走る場面で CPU の消費元を特定するには、稼働中のインスタンスをプロファイルするのが唯一の方法ですが、このエンドポイントはネットワーク上から絶対に到達できてはいけないからです。

レイヤー 1 — 設定

internal/config が唯一の信頼できる情報源（single source of truth）で、ほぼすべての他のパッケージが ZurgConfigV1 を読み込みます。型付きゲッターはフィールドがゼロのときにデフォルト値を適用するので、呼び出し側は値が存在しないかをチェックする必要がありません。

一番ボリュームのある部分は filters.go です。これは入れ子にできる AND/OR のフィルター言語で、各 torrent を 1 つ以上の 仮想ディレクトリ に振り分けます。これがフラットな torrent 一覧を movies/、shows/、anime/、recent/ に変えるしくみです。

条件では、torrent の名前（regex、contains、not_regex）、サイズ、中のファイル（any_file_inside_regex、any_file_inside_size_gte）、タグ（tags_match_any、tags_missing_all）、経過時間（added_within_hours、added_after）、派生プロパティ（has_episodes、is_music）、そしてどのアカウントから来たか（provider、not_provider）を指定できます。

ディレクトリごとの表示ルールも一緒に使えます: only_show_the_biggest_file、サイズの下限と上限です。

割り当て処理の 1 回ごとに torrent 単位で使われる正規表現は、パッケージレベルで一度だけコンパイルされます。呼び出しごとに MustCompile を走らせていたら、起動時間の大部分を占めていることが計測でわかったためです。

設定はダッシュボードからライブで編集できます。UpdateConfigFileAtomic はファイル全体を書き出し直すのではなく、キー単位で編集を行うので、コメントや未知のキーはそのまま残ります。

レイヤー 2 — バックエンド抽象化

internal/debrid は中核です。ほかのすべてのパッケージが使うドメイン型（Torrent、TorrentInfo、File、Download、User）と、各バックエンドが実装する Provider インターフェースを持っています。

プロバイダーと機能

Provider は小さく保ちます。リストの取得、詳細の取得、削除、リンクの解決、リンクの検証、バイト列の取得、アカウント状態の報告だけを行います。サービスによっては欠けていてもおかしくない機能は、オプションの capability インターフェースにします。呼び出し側はそれを型アサーションで確認し、使えなければ機能を落として動作します。

インターフェース 追加される機能 必要とするもの
MagnetAdder ハッシュで追加、ファイル選択、同時実行スロット数の確認 修復 (repair)
TorrentRestarter 失敗したトレントをその場で再試行 修復 (repair)、最も安上がりな方法
HostRotator CDN ホストプールの入れ替え ネットワークテスト、/hosts ページ
DownloadLister ホスターのダウンロードを別リストとして取得 __downloads__ ディレクトリ
ArchivePasswordKeeper リリースのアーカイブ用パスワードの保持 Usenet のみ
PremiumMonitor プランの残り期間 起動時の警告

それとは別に、Capabilities はプロバイダーの自己申告です。何ができるかではなく、どの範囲の制限内で動かさなければならないかを示します。これがあるのは、zurg のライブラリの動作が Real-Debrid の仕組みを前提に育ってきたためです。その仕組みをハードコードしたままだと、他のバックエンドは壊れるか無駄が多くなってしまいます。

すでに実際の動作を決めている flag が 2 つあります。

  • ListIncludesFiles: トレントのリストにすでにファイルごとの詳細が含まれている場合に true になります。コールドのライブラリスキャンが、トレントごとに 1 回の API 呼び出しから、全体で 1 回の呼び出しに減ります。バックエンドによる違いの中で最も大きなコストの差です。
  • StoredLinksCanRot: トレントは正常に見えていても、保存済みのリンクが無効になることがあります。そのためリンクは確認（プローブ）が必要です。これは Real-Debrid の性質で、確認に多くのコストがかかります。リクエストに応じて URL を発行するバックエンドでは確認するものがないため、この確認をスキップします。スキップするかどうかで、スキャンが無料で済むか、アカウント全体のロックアウトを引き起こすかが分かれます。

ServesLinksLocally、MaxActiveSlots、MaxConcurrentRequests、AddsPerHour、ContentExpires、SupportsFileSelection などの残りの項目は、すべてのバックエンドが宣言し、汎用的なコードが読み取ります。ゼロ値は意図的に最も保守的な解釈にしてあります。そのため、ある項目を設定し忘れたプロバイダーは、大量のリクエストを送るのではなく慎重な動作になります。zurg で解決できないプロバイダーは internal/torrent/providers.go の unknownProviderCaps にフォールバックします。このファイルで慎重な値を一度だけ定義しておき、各呼び出し箇所で繰り返さないようにしています。

3 つ目のパターンがあります。これは上の 2 つの flag のどちらでも表せません。AllDebrid のリストにはファイルが含まれませんが、トレントごとのエンドポイントは ID のバッチを受け取れます。これは capability ではなく、プロバイダーの内部で処理しています。変わるのはプロバイダー自身がリクエストをどう使うかだけだからです。汎用のリフレッシュ処理はこれまで通りトレントを 1 つずつ問い合わせるので、その仕組みを知る必要はありません。

Set

Set は設定されたすべてのプロバイダーを設定ファイルの順番どおりに持つもので、torrent マネージャー、ハンドラー、ダッシュボードは具体的なクライアントではなくこれに依存しています。重要なアクセスパターンは2つです。fan-out は、ライブラリの更新のように、すべてのアカウントに対して操作を実行する場合です。dispatch は、削除、解決、修復のように、torrent を所有しているアカウントだけに操作を届ける必要がある場合です。また、アカウントの正常性や利用可能かどうかの状態も持っています。

リンクキャッシュ

LinkCache は解決済みの URL を、リンクだけでなく トークンごと に保存します。あるトークンで発行された URL は、そのトークンのクォータに対してだけ有効です。そのため、トークンが帯域幅の上限に達したときは、ローテーションで次のトークンに回してそのまま再利用するのではなく、そのトークンのエントリを全部破棄しなければなりません。エントリの期限は挿入時刻ではなく Generated タイムスタンプを基準に切れます。そのため、プロバイダー自身のダウンロードリストから事前に取り込んだリンクは、プロバイダーのスケジュールに従って期限切れになります。

internal/nzb は、この抽象化が成り立っていることの証拠です。同じインターフェースを、ローカルディレクトリとニュースサーバーの両方で実装しています。これがうまくいくのは、インターフェースの本当の契約が "CDNをプロキシすること" ではなく "範囲指定のGETにバイトで答えること" だからです。

バックエンドの追加

新しいパッケージを作成し、debrid.Provider を実装して、init で debrid.Register を呼び出します。そのうえで internal/app.go に空のインポートを追加します。internal/debrid は一切変更しません。

レイヤー 3 — ライブラリ

internal/torrent は zurg のコアで、最大のパッケージです。TorrentManager はライブラリ全体を cmap の並行マップに保持し、ロックなしで読み取れるようにしています。設定のフィルターを評価して torrent をディレクトリに振り分け、リンクを解決してキャッシュし、バックグラウンドジョブを実行します。

永続化

各エントリは JSON として data/<name>.zurgtorrent に書き込まれ、トレントごとの情報は data/info/ にキャッシュされます。再起動するとディスクから読み込まれ、すぐに使える状態になります。その後、更新が行われます。これは重要で、コールドスキャンは CPU ではなくレート制限に縛られるためです。アカウントから削除されたトレントは dump/ にアーカイブし、__dump__ ディレクトリとして表示できます（load_dumped_torrents）。

他では再構築できない状態（設定、すべての zurgtorrent、data/local/ 配下の __magic__ ストア、nzbs/ 配下の元の NZB）は、ストリーミング形式の単一の .zurgbackup にまとめられます。zurg backup で作成でき、ダッシュボードの Backup & Restore ページでも作成できます。zurg restore-backup <file> で作業ディレクトリに展開されます。internal/backup がフォーマットを管理しています。マニフェストが最初のエントリになっているため、復元時は書き込みの前に中身を検証します。

予約済みのディレクトリ名: __all__、__unplayable__、__dump__、__downloads__、そして各アカウント用の __<provider-name>__。

Torrent と TorrentCopy

リリースは複数のアカウントにまたがって存在することがあります。zurg はそれを1回だけ表示します。内訳はこうです。

  • コンテンツの情報はエントリ (Torrent) に属します。名前、ハッシュ、どのファイルが存在するか、タグ、IMDB ID、rename がこれにあたります。
  • アカウントの情報はコピー (TorrentCopy) に属します。そのアカウントが発行した torrent ID、発行されたリンク、そのコピー独自の壊れ状態、リトライのカウンターがこれにあたります。

特にファイル ID はアカウントごとに違います。Real-Debrid はtorrent 内のファイルに番号を振り、そのうち選択されたものだけをマークします。TorBox はダウンロードしたものだけを一覧にし、独自の番号を振ります。そのため FileSource は、プロバイダーごとに FileID を保持します。repair は、修復対象のコピーの ID を使って選択内容を組み立てます。別のアカウントの ID を読んでしまうと、違うファイルを再追加してしまいます。

コピーは config に書かれた順に保存されていて、その順番が優先順位になります。読み取りでは、最初の正常なコピーを優先し、ダメならフェイルオーバーします。エントリを削除すると、すべてのコピーも削除されます。コピーが1つもないエントリは存在しないものとして扱われます。

GetKey は純粋に保つこと

GetKey は、仮想ライブラリにおけるトレントの名前です。ディレクトリのエントリ、.zurgtorrent のファイル名、そしてすべての検索が通るハンドルでもあります。検索のたびに再計算され、保存されることはありません。 そのため、使用中の名前を確認して名前の衝突を解決する方法は使えません。答えはライブラリの状態によって変わってしまい、トレントが登録された名前で見つからなくなってしまうからです。

唯一のサフィックスは、同じ名前を持つ別々のリリースが衝突する、まれなケースのためのものです。これはコンテンツ自身のハッシュのタグで、名前そのものと同じくらい純粋なものです。これを有効にするフラグは、ライブラリ全体を見られる更新パスによって決まり、トレントに保存されます。

修復

このパッケージで二番目に大きな関心事です。ファイルは FSM の状態を持ちます（pkg/fsm 経由の ok_file / broken_file）。トレントとコピーもそれぞれ独自の状態を持ちます。リンクがバイト列を返さなくなると、修復は次の戦略へと段階的にエスカレートします。

  1. その場での再起動 (TorrentRestarter) — 最も安上がりです。新しいアップロードも追加スロットも使わず、トレントの ID も維持されるため、ライブラリのエントリは削除されて再検出されることなく残ります。リフレッシュ処理は、アカウント上で見つけた失敗トレントに対してこれを実行します。ただし、失敗トレントへの対応自体が許可されているインスタンスに限ります（enable_repair または delete_error_torrents）。両方オフの場合、アカウントには何もせず、そのままにしておきます（mayRestartFailedTorrents）。
  2. 壊れたファイルの再ダウンロード — 壊れているものだけを選び直します。
  3. 再挿入 — マグネットを再度追加し、新しいリンクを取得します。
  4. アーカイブ — 復旧できないリリース向けの最後の手段です。
  5. そのリリースを持っていないアカウントに提示する (repair_across_accounts.go) — サービスはそれぞれ独立したキャッシュを持っているため、あるアカウントがパージした、またはファイル名を理由に拒否したリリースが、別のアカウントにキャッシュされている可能性があります。このリリースを保持しているアカウントがすべて修復できなくなると、設定されている、そのハッシュを持たないアカウントに順番に問い合わせます。最初に既にそのハッシュを持っているアカウントがそれを引き受けます。その後の一覧取得で、通常の absorbCopy の経路を通じて、2 つ目のコピーとしてエントリに結び付けられ、その際エントリの判定は自動的にクリアされます。対象は常にキャッシュ済みのものだけで、AddIfCached 経由で行い、restrict_repair_to_cached は使いません。アカウントが取得を必要とする追加は取り下げられて再度削除されるため、これは再ダウンロードではなく修復として扱われます。応答しないアカウントは、1 日から約 2 週間までバックオフします。また、1 回のスイープで行える提示は最大 10 件に限られるため、判定済みのリリースが多数あるライブラリに対しても、指示がなくて自動で実行しても、コストが見合うようになっています。

その周りには、次のような仕組みがあります。指数バックオフ、コピーごとのリトライ上限（RepairCycles、AssignRetries。上限は再起動後も残るよう永続化されます）、Capabilities.AddsPerHour による 1 時間あたりの追加予算ゲート、アクティブスロットのチェック、セット型キューによる重複排除。さらに、スイープ全体でのヒューリスティックもあり、ホスター側の利用不可エラーが短時間に集中した場合は、N 件の壊れたトレントではなく、1 件のプロバイダー障害として扱います。修復不能の判定はコピーごとに記録され、すべてのコピーが判定を持っている場合にのみエントリへ反映されます。Real-Debrid の恒久的なエラーは、TorBox のコピーについては何も示しません。

運用者は手動で修復を強制できます。強制の状態は、コンテキストではなくトレントに保持されます。スイープの途中で届いたリクエストはキューに入れられ、後でスイープ自身のコンテキストで取り出されるためです。ボタンは 5 番目の手順にも到達しますが、順序は次のとおりです。まず、そのリリースに対するすべての判定をクリアするので、リリースを保持しているアカウントは従来どおり再試行されます。提示は、その試行が失敗した場合にのみ行われます。判定をクリアするため、名指しされたトレントは、スイープが修復不能と判定されたエントリを収集する際に対象になりますが、判定されるのは直前に実行された修復によってだけです。そのため、ループの中ではなく、その修復の後に収集されます。そうしないと、誰かが待っている唯一の経路が、提示されることのない唯一の経路になってしまうからです。

パッケージ内のその他

mediainfo.go（ffprobe による解析で、duration や codec のタグに反映）、tags.go、rename.go（refresh 後も残す必要があるリネーム）、delete.go、strm.go（ライブラリ全体の .strm ファイルを生成）、hooks.go（ライフサイクルイベントでユーザースクリプトを実行）、assign_links.go、unrestrict.go、opensubtitles.go、provider_directories.go、reset_all.go.

レイヤー 4 — 配信

ルーター

internal/handlers が chi のルーターを組み立てて、すべてを配線します。WebDAV の非標準メソッド（PROPFIND、MKCOL、MOVE）は、init の時点で chi に登録されます。

Basic 認証はすべてに適用されますが、除外されるものが 2 つあります。version.txt と /ready はヘルスチェックが動くように除外されています。.strm のエンドポイントも除外されています。.strm を開くメディアプレーヤーは認証情報を送れないため、代わりにパスに含まれる署名付きトークンで認可します。

ルーティングで学んだ教訓が 2 つあり、コメントにも書いてあります。同じ落とし穴は繰り返さないようにしましょう。1 つ目は、chi は正規表現のパスパラメータを 1 つのセグメント内 でしか適用しないことです。そのため、アーカイブ経由でアドレスされるファイル（<archive>.rar/<inner>.mkv）や、その中のネストされたディレクトリは、どのルートにもマッチしませんでした。どちらも末尾のワイルドカードが必要でした。2 つ目は、ルートがパスの深さを気にしなくなったあとは、torrent 内のパスが末尾のスラッシュで一覧表示とダウンロードに振り分けられることです。

一覧表示

internal/dav は PROPFIND の XML を生成し、DELETE と MOVE(リネーム。ディレクトリをまたぐ移動や別のトレントへの移動も含めて検証します)、さらに Infuse 向けのバリアントを処理します。pkg/dav は XML マーシャリングを使わず、最適化した文字列組み立てで XML を自前で作ります。WebDAV クライアントが必要とする RFC 3339 から RFC 1123 への変換も行い、パスは URL 用と XML 用の両方でエスケープします。

internal/htmlindex は同じツリーを /http/ 用の HTML として描画します。

どちらも同じ表示ルールを適用します。最大サイズのファイルだけを表示すること、サイズのしきい値、壊れている/削除済みの状態などです。また、どちらも複数ボリュームの RAR アーカイブをまとめて、最初のボリュームだけが見えるようにします。

バイトパス

internal/universal は、リクエストが実際のバイト列になる場所です。

  • singleflight でリンク解決を重複排除しているので、同じファイルへの100件の同時読み取りでも、リンク解決は1回だけです。
  • disable_stream_proxy の設定に従ってプロキシかリダイレクトかを決めます。ただし、ServesLinksLocally のリンクにはリダイレクトしません。クライアントがそのリンクを開く手段を持っていないからです。
  • 壊れたリンクに当たったら、少ない回数の上限内で再度 unrestrict します。
  • ファイルごとのネットワーク障害クールダウンがあります。3回連続でエラーになると、そのファイルを5分間停止します。これによって、到達できない CDN ホストで無限リトライループになるのを防ぎます。
  • レート制限の期間中は、すぐにエラーを返す代わりに、読み取りを短時間保留します。短いクールダウン中に読み取りをエラーにすると、1つのスロットリングされたアカウントが rclone の VFS を通じてエラーの嵐になります。待機が詰まり、D 状態のリーダーが生まれ、メディアサーバーが固まってしまいます。そのため、保留するほうが安上がりな対応です。より長いクールダウンのクラスは、引き続きすぐに失敗させます。
  • トークンごとの帯域幅を計測します。カウンターは CET の午前0時にリセットして、Real-Debrid の1日のトラフィックリセットに合わせています。

アーカイブ

internal/rarstream は、バイト範囲リクエスト（HTTP 206）越しに RAR4、RAR5、ZIP のヘッダーを解析し、ボリューム全体のチャンクマップを作って、単一ファイルの内容をその場で再構築します。展開（デコンプレッション）は行いません。対応しているのは格納（stored）されたデータだけで、これはシーンリリースで使われている形式です。VolumeKey と IsVolume は、dav と htmlindex が複数ボリュームを1つのエントリにまとめるために使う、さまざまな分割ファイルの命名規則（.part001.rar、.r00、.rar）を正規化します。リスティングはトレントにキャッシュされ、パーサーの ListingVersion が刻印されます。そのため、別のパーサーで作られたリスティングは配信されず、破棄されます。

STRM

internal/strmlink が、.strm に入る URL のエンコードと署名を担当します。置き換え前の Real-Debrid 専用の方式は、たまたま安全だっただけでした。URL に RD の 13 文字のダウンロードコードが含まれていたので、その URL を持っていること自体が認可の証明になっていたからです。

ほかのバックエンドは、推測しやすい ID（torbox://17/3 など）でファイルを指定します。同じ形式を使うと、ポットに到達できる人なら誰でもアカウントに対する CDN URL を作ったり、ニュースサーバーの接続を消費したりできてしまいます。data/strm_secret の秘密鍵を使った HMAC でこれを防ぎます。zurg が発行していないトークンは解決されません。

秘密鍵はプロセスが終了しても残っている必要があります。すでに書き出されている .strm はすべて、その署名鍵が有効な間だけ動作し続けます。

ダッシュボードと管理

internal/handlers/dashboard は、埋め込みテンプレートから Web UI を描画します。テンプレートは起動時に事前にパースされるので、構文エラーはリクエスト時ではなく起動時にすぐ失敗します。 ページは、ライブの torrent ステータス、インタラクティブな YAML 設定エディタ、ホストのレイテンシ、ディレクトリ管理、プロバイダー管理、メディアサーバーの接続状態、アカウント/プレミアム情報、帯域幅、rclone ステータス、Plex の "Wrapped" 統計です。 各メディアサーバーのステータス取得は並行して動くので、ページの読み込みが重くなりにくいです。

internal/handlers/manage は、torrent ごとの操作用 UI です。タグ、状態の詳細付きのファイル一覧、Plex のマッチング、リネーム、ファイルごとの削除/復元/force-show、一括削除とスキャンができます。

重複表示は internal/duplicates にあります。internal/arrinventory と、Radarr および Sonarr アダプターの横にある Inventory リーダーは、*arr が持つすべてのファイルを読み取ります。読み取り専用で、取得処理には関わりません。magic.Resolver.HolderOf は各ファイルのパスを、その元になったリリースまで辿ります。このパッケージは、同じ映画やエピソードを含んでいる可能性のあるリリースをグループ化します。グループ化には、名前、IMDb ID、*arr の履歴を使います。リリースが使用中かどうかは、辿ったパスだけで判断されます。

internal/static は、CSS、favicon、ロゴ、robots.txt を go:embed で埋め込みます。そのため、バイナリ単体で動作します。

レイヤー 5 — マウント

internal/rclone は rclone をサブプロセスとして管理します。マウントコマンドを組み立てます（zurg 自身の /dav/ を指す WebDAV リモート）。起動と停止を行い、30 s ごとにヘルスチェックをします。失敗したら再起動し、再起動の間隔は指数バックオフ（1 s → 60 s）で長くなっていきます。

起動時に、49152–65535 の範囲からエフェメラル RC ポートを 1 つ選びます。このポートは VFS キャッシュの無効化とステータス確認に使われます。この無効化が重要になるタイミングは 2 つあります。キャッシュされたライブラリの読み込みが終わったときと、最初の完全リフレッシュが終わった後です。ここで無効化しないと、マウントが読み込み途中で取得した不完全な一覧が、--dir-cache-time の間ずっと残ってしまいます。

認証情報は環境変数で渡します。コマンドラインには載せません。Controller はハンドラーとダッシュボードが使うインターフェースです。Runner と Command はプロセス管理を抽象化していて、テストで使います。

レイヤー 6 — メディアサーバー

2つの異なるものが「Plex」という言葉を共有しています:

  • pkg/plex、pkg/jellyfin、pkg/emby は、メディアサーバーのクライアントです。それぞれ common.MediaServerWorker を満たします。pkg/common は共通のジョブのライフサイクルを提供します。具体的には、上限のない動的キュー、ジョブごとのリトライ管理、ジッター付きの指数バックオフ、連続失敗後のサーキットブレーカー、そして止まってしまったジョブの検出です。macOS の大文字小文字を区別しない APFS を扱うパスヘルパーもここにあります。pkg/scan はその上に載る統合された MediaScanner です。パスの更新ジョブを、そのパスを管理しているサーバーに振り分け、サーバーごとのキューの深さを報告します。
  • internal/plex は zurg 専用の動作です。Matcher は、ファイルパス、IMDB ID、TVDb/TMDb ID を使って torrent と Plex のライブラリ項目を組み合わせます。キャッシュされたメタデータを使い、ワーカープールで定期的に実行されます。また、見つかった IMDB ID を torrent に後から書き込みます。
  • internal/acquisition は、永続化される取得キューと共通の executor を管理します。executor は、Newznab インデクサーから NZB を、Torznab インデクサーからキャッシュ済みの torrent を取得します。Plex のウォッチリスト、Seerr、Radarr、Sonarr はソースアダプターで、リクエストを movie、season、episode のターゲットに変換します。data/acquisition.json には、再起動をまたいでリトライの期限と各ターゲットの進捗が保存されます。設定とアダプターの仕様については 取得ソース を参照してください。

pkg/mediabrowser には、Emby と Jellyfin が共有する型があります。

レイヤー 7 — サポート

パッケージ 用途
pkg/fsm 小さなステートマシンが2種類あります。FSMWithExternalMutex は、既にロックされた何かに組み込まれている場合に使います。FSMWithTime は、独自のロックと遷移のタイムスタンプが必要な場合に使います（そのため SinceWhen で「どれくらい壊れた状態が続いているか」を確認できます）。
pkg/logutil Zap を使い、出力は2つです。色付きのコンソールと、ローテーションするファイル（lumberjack 経由で 10 MB × 20）です。ログの詳細度は config.yml の log_level から取得し、なければ環境変数 LOG_LEVEL、それもなければ DEBUG になります。レベルは共有の zap.AtomicLevel で管理されているので、ダッシュボードから再起動なしですべてのロガーのレベルを一度に変更できます。ダッシュボードのビューワーや Export Logs 用にログを読み戻す機能も含みます。
pkg/utils ブロックしたホストの保存、ファイルの表示ルール、トークンの伏せ字化、動画/音声の検出、.strm の命名、そして GetZurgBaseURL（リバースプロキシの背後では X-Forwarded-* を尊重します）です。
pkg/script ユーザーが設定するライフサイクルイベントのスクリプトを実行します。Windows では PowerShell、それ以外では /bin/sh を使います。
pkg/dmm debridmediamanager.com の検索 API 用クライアントです。サーバー側の制限（2秒に1回）に合わせてリクエストを抑えています。ウォッチリストモニターで使われます。
internal/version ldflags で埋め込まれるビルド情報です。/http/version.txt にある ASCII バナーもここにあります。
internal/requirements 初回起動時に、お使いのプラットフォームに合った ffprobe と rclone を GitHub のリリースからダウンロードし、config.yml に 相対パス を書き込みます。そのため設定ファイルは持ち運びできます。非対応のプラットフォームでは、失敗ではなく警告を出します。
internal/clear 認証 Cookie を使って Web インターフェースを操作し、RD のダウンロードとトレントをまとめて削除します。空になるまで繰り返します。
internal/handlers/tmplcache ダッシュボード用のテンプレートキャッシュです。

横断的な設計判断

if provider == "realdebrid" よりケイパビリティを優先。 Real-Debrid の仕組みを前提にするものは、型チェックではなく機能フラグ（capability flag）の後ろに置いてください。これが torrent マネージャーをバックエンド非依存に保つためのルールです。

インターフェースの契約はプロキシではなくバイト列です。 Provider が保証するのはリモートの CDN ではなく、範囲指定の GET に応答できることだけです。だから Usenet バックエンドも組み込めます。CDN 前提が漏れていた箇所は2つ（リダイレクトと、外部バイナリが開ける必要があるURLを ffprobe に渡す処理）でしたが、どちらも今は ServesLinksLocally でガードされています。

位置ベースのリンク対応付けは必須です。 TorrentInfo.Links[i] は TorrentInfo.Files 内の i 番目の選択済みファイルと対応します。リンクを作れないファイルは、省略するのではなく未選択として報告しなければなりません。さもないと後続のファイルがすべて黙って別のリンクに解決されてしまいます。すべてのバックエンドがこれを守る必要があります。

1つの torrent は必ず1つのアカウントに属します。 サービスに届く呼び出しはすべて、プライマリプロバイダーではなく、その torrent のプロバイダー経由（ProviderFor、resolveLink、verifyLink、DeleteByID）でディスパッチしてください。ここを間違えると、別のアカウントからファイルを削除してしまいます。

ディスクも実質的な層です。 .zurgtorrent エントリ、data/info/ の torrent ごとの詳細、ネットワークテストの結果とタイムスタンプ、ジョブのタイムスタンプ、STRM の署名用シークレット、RAR の一覧キャッシュ、ブロックされたホスト。再起動時はスキャンし直すのではなく、途中から再開します。

すべてにペース制御があります。 プロバイダーごとのトークンバケット、同時実行数の上限、1時間ごとの追加制限、リンクの TTL、ファイルごとのクールダウン、レート制限の保留。特に TorBox では、リンク解決が貴重なリソースです。その前段にあるリンクキャッシュがあるからこそ、ライブラリのスキャンが現実的なコストで済みます。

読み取りはロックフリー、書き込みは最小限に。 並行マップがディレクトリ／torrent／ファイルのツリーを支えています。変更はグローバルなロックではなく、torrent ごとのロック（copiesMu、tagsMutex、operationsMutex、archiveCacheMutex）で守られています。

rdclient は共有されていますが、そのポリシーは Real-Debrid のものです。 エラーの分類とリトライのルールは RD 由来です。2xx 以外をエラーとして報告しつつレスポンスも返すので、ステータスが必要なプロバイダー（Retry-After 付きの 429 など）は、err より先に resp を確認しなければなりません。

ビルド、テスト、デプロイ

  • Build: make build。バージョン、コミット、ビルド時刻は ldflags 経由で internal/version に埋め込まれます。
  • Unit tests: go test ./...。pre-commit では gofmt、golangci-lint、go test -short、そしてフルの品質チェック一式が実行されます。
  • Integration tests: make integration-test。軽いものから順に実行され、refresh_repair は最後です。ライブラリの全体スキャンが終わるまで待つためです。Go、rclone、FUSE、Plex がそろったホストで実行してください。それ以外の環境では、マウントや Plex のテストが大きく警告を出してスキップされますが、終了コードは 0 のままです。ですので、終了コードではなく出力をよく確認してください。詳しくは e2e-test.md を参照してください。
  • Docker: 2段階の Alpine ビルドです。ランタイムイメージには ffmpeg、rclone、fuse3、ヘルスチェックが追加されます。
  • Deploy: make deploy USER=… HOST=… DIR=…。Plex と zurg のサービスを停止し、バイナリを入れ替えて、version.txt が 200 を返すまで待ち、最後に Plex を再起動します。
