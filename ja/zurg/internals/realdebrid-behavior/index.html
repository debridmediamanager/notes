トレント

Real-Debridは、無制限の数のtorrentファイルとmagnetリンクのダウンロードに対応しています。さらに、その中からダウンロードしたいファイルを選ぶこともできます。 別のユーザーがすでにそのtorrentファイルまたはmagnetリンクをダウンロード済みの場合、それは「キャッシュ済み」とみなされ、Real-Debridがそのキャッシュ済みのリンクをすぐに提供します。 キャッシュ済みでない場合は、公開トラッカーまたはDHT/PEXからmagnetリンクのダウンロードを試みます。 トラッカー情報を含むtorrentファイルの場合は、そのトラッカー情報を使います。これはプライベートトラッカーで役立ちますが、残念ながら多くのプライベートトラッカーはReal-Debridのダウンロードサーバーをブロックしています。 torrentにシーダーもリーチャーもいなくなり、torrentのすべてのピースをダウンロードできなくなった場合は、エラーになります。 ダウンロードが完了すると、次のような形式のキャッシュ済みリンクも得られます: https://real-debrid.com/d/DOWNLOADCODE DOWNLOADCODEは、特定のファイルを一意に識別する13文字のIDです（13文字目より後ろの部分は無視されます）。

ファイルの選択

ご存じのとおり、トレント内で必要なファイルだけを選んでダウンロードすることができます。 トレントにファイル A、B、C が入っていて、A と B を選んだ場合、ダウンロードされるのは A と B だけです。 トレントのキャッシュ状態は、この一意のファイル選択によって実際に変わります。 ファイル A、B、C を含むトレントに戻ると、A、B、B（単体）、A+B、B+C、A+C（ペア）、A+B+C（すべてのファイル）ごとに異なるキャッシュ状態があります。 選択の組み合わせごとに、トレントはトラッカーから再びダウンロードされ、同じファイルでも異なるキャッシュ済みリンクが返されます。

キャッシュ済みリンク

キャッシュリンクはダウンロードできるリンクではなく、実際には Real-Debrid 内の DOWNLOAD CODES を入れておくコンテナにすぎません。

ダウンロードやストリーミングをするには、「unrestrict」して、実際に使えるリンクに変換する必要があります。このリンクは7日で期限切れになります。

キャッシュリンク自体は7日以上持ちます。トレントに動作するキャッシュリンクがある場合（つまり unrestrict に成功する場合）、そのトレントはまだ Real-Debrid にキャッシュされています。

確実にはわかっていませんが、その可能性は非常に高いです。より多くのユーザーがキャッシュリンクを unrestrict すれば、トレントのキャッシュ状態が延長される可能性があります。

覚えておいてください。キャッシュリンクが動作するかを確認する唯一の方法は、それを unrestrict して、HTTP Range ヘッダーを使って unrestrict されたリンクの最初のバイトを確認することです。

zurg は use_range_verification 設定オプションで、HEAD（デフォルト、高速）と Range ベース（GET bytes=0-0、より詳細）の両方の確認方法に対応しています。

アカウント間でのキャッシュ済みリンクの共有（2026-08-19 時点で計測）

RDは、リンクIDを2種類の長さで返します。13文字（約70%）と16文字（約30%）です。余分な3文字によって、そのリンクを誰がunrestrictできるかが変わります。

  • 最初の13文字に切り詰めた/d/リンクは、生成したアカウントだけでなく、どのプレミアムアカウントからでもunrestrictできます。呼び出し側の torrent ライブラリには何も影響せず、唯一の副作用は呼び出し側の downloads 履歴に項目が追加されることだけです。
  • 16文字の完全なIDのまま送ると、同じリンクは生成したアカウントからだけunrestrictできます。ほかのアカウントはどれも、生成元の torrent がまだ生きていても、呼び出し側が同じ infohash を自分のライブラリに持っていても、ip パラメータの値に関係なく "unavailable_file" を受け取ります。

そのため、保存しておいたリンクをunrestrictする前には、必ず13文字に切り詰めてください。切り詰めていないIDでテストすると、リンク共有は不可能だという誤った結論になります。

キャッシュされたリンクは、生成元のアカウントがtorrentを削除しても生き残ります。ただし、時間が経つと失効します。大規模にサンプリングしたところ、1〜2か月前に発行されたリンクはすべてアカウントをまたいでも今もunrestrictできました。一方、約3か月より古いリンクはすべて "hoster_unavailable" を返しました。別の問題として、RDはコンテンツそのものをキャッシュから取り除くことがあります。1か月前にキャッシュ済みと確認されたハッシュが、翌月にはシーダー0の状態でダウンロード中になることもあります。その場合、リンクは生成元のアカウントも含めて全員に対して "unavailable_file" を返します。

保存済みのキャッシュリンクでunrestrictエラーが出たときの読み解き方は次のとおりです。

  • 13文字のリンク + hoster_unavailable → リンクが期限切れになっています。同じ選択内容でtorrentを追加し直せば新しいリンクが発行されます（下の修復の項を参照）。
  • 13文字のリンク + unavailable_file → RDがコンテンツを完全に削除しています。新しいリンクを得るには、シーダーから本当に再ダウンロードする必要があります。
  • 16文字のリンク + unavailable_file → 可用性については何もわかりません。単に生成元のアカウントではないだけです。13文字に切り詰めて再試行してください。

unrestrict済みのリンク（*.download ホストのURL）は、拒否によってではなく、サーバー側の追跡によってIPに紐づけられています。 CDNは、別のIPからの206レスポンスも問題なく配信します。ただし、RDはダウンロードしたIPを記録しており、1つのアカウントのリンクを複数のIPで使うと、アカウント共有の警告を受けることがあります。そのため、unrestrict/link にはダウンローダーのIPを渡してください（ip パラメータ）。そうすると、実際にバイトを取得するIPに対してリンクが発行されます。

壊れたキャッシュ済みリンクの修復

キャッシュされたリンクや、トレント内のファイルの unrestricted リンクでさえ、動かなくなることがあります。

これは unrestrict API のエラーが原因のこともあれば、unrestricted リンクが HTTP エラー応答を返しているのが原因のこともあります。

直すには、トレントをもう一度ダウンロードして、新しいキャッシュリンクを生成し直す必要があります。

まずは、同じファイル選択のままトレントを再ダウンロードしてみてください。新しいキャッシュリンクが生成されるか確認しましょう。

それでもダメなら、そのトレントのファイル選択を変えてみる必要があります。

たとえば、複数ファイルのトレントで壊れているのが 1 つだけなら、その壊れたファイルだけを選び直してください。

それでも壊れたキャッシュリンクが返ってくるなら、選択にもう 1 つファイルを追加してみてください。

動作する新しいキャッシュリンクが手に入るまで、この手順を繰り返します。

RAR の動作

Real-Debrid には、ストリーミングできないサポート外のファイル形式を選ぶと、トレントを RAR ファイル（無圧縮）にまとめて保存してしまう動きがあります。

確認済みの動画ファイル形式: .avi .flv .m2ts .m4v .mkv .mov .mp4 .mpg .mpeg .ts .webm .wmv 確認済みの音声ファイル形式: .mp3 .flac .m4a

これらの形式を選ぶと、Real-Debrid では各ファイルが個別にストリーミングできるリンクになります。 それ以外を選ぶと、Real-Debrid は確実に RAR アーカイブに入れます。 たとえば .mkv の動画と .sub の字幕を選ぶと RAR 化されます。 .jpg のポスターだけを選んでも同じく RAR 化されます。

複数ファイルのトレントでも、RAR 化されると、RAR ファイルを指すキャッシュ済みリンクが 1 つだけ返ってきます。 確認済みの動画/音声形式だけを選べば RAR 化されないので、選んだファイルごとにキャッシュ済みリンクが得られます。

ダウンロード一覧の行を削除すると、その行で発行された URL も無効になります

2026-08-22にテストアカウントで計測しました（ケースごとにunrestrictを1回ずつ）。

unrestrictを実行すると、/downloads に行が1つ作られ、番号付きのホスト1つ上にURLが発行されます。例: https://124-4.download.real-debrid.com/d/<13-char code>/. このコードはホストに紐づいていません。行を削除する前であれば、同じコードは 44-4、125-4、そして元の 124-4 のどれに対しても200を返します。末尾のファイル名部分は省略可能で、zurgはそれを取り除くため、どちらの形式でも同じ応答になります。

DELETE /downloads/delete/ はそのコードを無効にします。何が残るかは、どのホストがすでにそのコードで配信したかによって決まります。

  • URLが一度も取得されないまま行を削除した場合: すべてのホストが X-Error: invalid_download_code 付きの404を返します。30秒後も404のままで、この状態は落ち着きません。
  • 44-4で1回取得した後に行を削除した場合: 44-4 は引き続き200を返しますが、発行元の 124-4 と、触れていない 125-4 はどちらも invalid_download_code の404を返します。

つまり、取得によってそのコードは配信したホストで有効化され、行があることで他のホストも配信を続けられる、ということです。これは、ダウンロード一覧のクリーンアップが前提にしていた想定とは逆です。zurgはリクエストごとにダウンロードホストを選ぶ（ensureReachableDownloadServer が最速のN台のいずれかに書き換える）ため、これは重要です。検証用のHEADが届いたホストと、次のリクエストが選ぶホストは同じとは限りません。そのため、行を削除した後もリンクキャッシュに残った解決結果は、以降のほぼすべてのリクエストで 404 invalid_download_code を返すことになります。これは「リンクが壊れた」と読まれ、正常なリリースが壊れたものとしてマークされてしまいます。

削除後に同じリンクを再度unrestrictすると、最終的には別のホスト上で新しいidが発行され、正常に動作します。idは再利用されません。

ただし、すぐにではありません。最初の計測では「影響なし」と出ましたが、それは数分後に測ったためでした。2026-08-23にテストアカウントで再計測したところ、DELETE /downloads/delete/ の後、unrestrict/link は75秒間ずっと同じ無効なidを返し続け、新しいidが発行されたのは t+81s でした。

ここから2つのことが言えて、どちらもコードに表れています。まず、downloadsCleanupMinAge は行を消す前に2分間保持するため、その間に同じリンクを解決した別のインスタンスは有効なコードを受け取ります。次に、配信パスの再unrestrictチェーン（約6秒以内に4回の試行）はこの猶予期間にすべて収まります。そのため、このチェーンを使い切っても、ファイルの状態については何もわかりません。すべての解決結果が、たった今404を返したURLと同じだった場合、zurgは正常なリリースを壊れたとマークする代わりに、Retry-After 付きで読み取りを拒否します。
