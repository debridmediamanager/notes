# zurg のネーミング {#zurg-naming}

zurgが表示する名前は、ほぼすべて保存されず、計算で求められます。リリースのフォルダ名、その中にあるファイル名、キャッシュレコードのディスク上のファイル名は、検索のたびにtorrentから導出されます。これらを書き出して後で読み戻す処理はありません。保存された名前は、ライブラリと足並みをそろえて保つべきもう一つの情報になりますし、その足並みを崩すのがまさに修復やNZBの再解決だからです。

例外は、運用者が指定したリネームです。こちらは保存されます。リリース自体に保存され、以下のどの導出よりも優先されます。ルールは第9節にあり、ユーザー向けの版はリネームガイドです。このページのそれ以外の内容は、リネームが設定されていないときのリリースの名前について説明しています。

最初に書いておく価値のある結果が一つあります。zurgと連携するものにとって、これがほとんどの驚きの原因になるからです。フォルダの名前は、何かが「リネーム」しなくても変わることがあります。入力が変わったので、出力も変わったのです。

このファイルに書かれているのはルールであり、しきい値ではありません。ルールがヒューリスティックによって決まる場合は、それを決める関数の名前を挙げて、そこで止めています。これらは実際のリリースに合わせて調整されており、変わることもあります。ここにコピーすると、足並みをそろえるべきものがまた一つ増えてしまうからです。コード参照はパッケージ相対です。

## 1. リリースフォルダー名 {#1-the-release-folder-name}

`internal/torrent/key.go`, GetKey / GetKey_Original

`__all__/` 配下のフォルダー名、`.zurgtorrent` のファイル名、すべての検索が使うキー、そして zurg が「access key」と呼ぶものは、すべて同じ1つの文字列です。以下の順番で決まり、最初に一致したものが採用されます:

| 条件                                        | フォルダー名              |
|---------------------------------------------|---------------------------|
| `ignore_renames: false`、Torrent.Rename が設定されている | Torrent.Rename            |
| `retain_rd_torrent_name: true`              | Name、変更なし            |
| `retain_folder_name_extension: true` かつ   | Name、変更なし            |
|   Name に OriginalName が含まれる           |                           |
| それ以外（両方のフラグがデフォルトの場合）  | OriginalName、`.mp4` と `.mkv` を順に削除 |
|                                             |   したもの                |

`retain_rd_torrent_name` が先にチェックされ、`retain_folder_name_extension` は完全に無効化されます。2つ目は、Name に OriginalName が部分文字列として含まれる場合にのみ適用されます。含まれない場合でも、トリムは行われます。

トリムは `strings.TrimSuffix` を2回実行するもので、実質的に3つのルールがひとまとめになっています。取り除かれるのは `.mp4` と `.mkv` だけなので、`.avi`、`.ts`、`.iso` などはフォルダー名に残ります。大文字と小文字を区別するため、`Movie.2019.MKV` は `.MKV` が残ります。また、2つは代替ではなく順番に実行されるので、`Movie.2019.mkv.mp4` は `Movie.2019` になります。この後、サフィックスが追加される場合があります（4節を参照）。結果は1つのパス要素で、`/` で分割されることはありません。

非推奨です。`retain_folder_name_extension` と `retain_rd_torrent_name` は非推奨で、将来削除される予定です。今のところ動作は変わりませんが、どちらかを設定すると起動時に警告がログに出ます。どちらも、アカウントが zurg の下で書き換える Name（2節）でライブラリのキーを決めます。デフォルトでは、トレント自身が宣言した値でキーを決めます。こちらはアカウント側で変更されません。Sonarr や Radarr の前段に置いている場合（`sabnzbd:` または `qbittorrent:` ブロックがあるインスタンス）は、デフォルトの値だけが正しい設定です。インポート後にアクセスキーが変わると、リリースを見失ってしまうからです。`ignore_renames` は非推奨ではありません。

## 2. Name と OriginalName の取得元 {#2-where-name-and-originalname-come-from}

  Real-Debrid   `internal/realdebrid/types.go`
                Name = `filename`, OriginalName = `original_filename`

  TorBox        `internal/torbox/types.go`, wireTorrent.originalName
                Name = `name`。OriginalName は、すべてのファイルが置かれている
                単一のディレクトリです（ちょうど1つある場合）。ツリーのルートにある
                ファイルは `name` にフォールバックします。ただし、ルートに置かれた
                単独のファイルだけは、そのファイル自身の名前が使われます。

  AllDebrid     `internal/alldebrid/types.go`, originalName
                同じルールを、平坦化されたファイル一覧に対して TorBox と同様に
                適用します。フォールバック先は magnet の `filename` です。

  NZB           `internal/nzb/provider.go`
                Name と OriginalName はどちらも releaseName で、torrent の
                Hash はリリース ID です。3 節を参照。

debrid バックエンドは OriginalName を torrent 自身のルートフォルダから導出するため、同じコンテンツを持つ2つのアカウントは同じフォルダ名を生成します。

Real-Debrid の2つのフィールドの意味は、2026-08-27 に約8.4万件の torrent を持つテストアカウントに対して測定したものです。そのうち252件を `GET /torrents/info` 経由で読み取り専用にサンプリングしました:

`original_filename` は、すべてのケースで torrent が宣言した名前（パックまたはフォルダ名）でした。個々のファイル名になることは一度もありませんでした。

`filename` は違います。複数ファイルからなる torrent で1つのファイルだけが選択されている場合に限り、そのファイル自身のベース名に縮退します。該当する形の112件中90件でそうなり、複数選択だが全部ではない34件中0件、全選択の24件中0件でした。221ファイルのパックで1エピソードだけを選択した場合、`original_filename` は `Marvel Cinematic Universe MCU Collection 2008-2023 1080p jZQ` を、`filename` は `Spider-Man.No.Way.Home.2021.1080p.BluRay.x264...-NOGRP.mkv` を返しました。

つまり、デフォルトではパック名になり、`retain_rd_torrent_name: true` を指定すると個々のファイル名になります。このフラグが非推奨になったのもそのためです。`filename` はアカウントの状態に従って変わってしまいますが、アクセスキーはそうであってはいけません。

## 3. NZB リリースのネーミング {#3-nzb-release-naming}

`internal/nzb/provider.go`、releaseName; `internal/nzb/parse.go`

リリースID（Hashでもあります）は `hex(sha1(lowercase(nzb filename)))` です。
中身ではなくファイル名から計算するので、NZBを保存し直しても、そこから作ったtorrentが親を失うことはありません。
フォルダー名は、そのファイル名から拡張子を除いたものです。ただし、stemがハッシュっぽく見える場合や、サニタイズすると何も残らない場合は、代わりにNZB自身の `<head>` メタデータにある名前を使います。
ファイル名を優先するのは、それがインデクサーの付けた名前で、ダウンローダーが保存した名前で、自動化ツールがリリースを探すときに使う名前だからです。インデクサーは、メタデータブロックに件名（subject）を入れたまま再投稿することがよくあるためです。

`stemLooksJunk`、`looksLikeHash`、`sanitizeReleaseName` は `internal/nzb/parse.go` にあり、この3つの疑問はすべてこれで決まります。中身は気にせず、ブラックボックスとして扱ってください。

## 4. 3 つの名前サフィックス {#4-the-three-name-suffixes}

  ` {xxxxxx}`   リリースのフォルダーで、2つの**異なる**リリースが同じ名前を持つときに付きます:
                そのリリース自身のinfohashの16進数6文字です。同じグループ内では、
                **最後に追加された**リリースだけが名前をそのまま使い、
                それ以外のリリースにはタグが付きます。これは更新のたびに、ライブラリ全体を見渡せるパスによって一度だけ決められ、
                KeySuffixedとして保存されます。そのため、GetKeyはtorrentだけで決まる純粋な関数のままです
                （`internal/torrent/key.go`、disambiguateNames）。RDのtorrentと
                同じリリースのNZBは、ここでは別々のリリースとして扱われます。
                NZBのハッシュはファイル名のsha1だからです。

  ` (tag).ext`  1つのリリース内でベース名が重複しているファイルに付きます。zurgはtorrentのツリーを1つのディレクトリに平坦化するためです。
                タグは、衝突しているファイル同士を区別できるディレクトリそのもので、
                グループ全体で異なっている中で最も浅いパスの要素です。それがなければ
                ファイルパスのsha1の16進数6文字になります。どの深さが使われるか、また
                パスの要素がファイル名に何を含めてよいかは、
                `internal/torrent/dupenames.go`内の`dupeTags`と`sanitizeTag`で決まります。
                これら2つは中身を気にせず、ブラックボックスとして扱ってください。
                グループには一覧内のすべてのファイルが含まれます（選択されているかどうかは問いません）。
                選択されなくなったファイルも、登録されていたキーで解決されます。
                `__magic__`だけは例外です。ここではリリース本来のツリーがタグなしで表示されます。ディレクトリ自体でファイルを区別できるからです（セクション8）。

  `_xxxxxxxx`   ディスク上（ON-DISK）のファイル名で、元の入力に非ASCII文字が1つでも含まれていた場合に付きます:
                その入力のsha256の16進数8文字です。
                セクション6を参照。マウント上には決して表示されません。

## 5. リリース内のファイル名 {#5-file-names-inside-a-release}

`internal/torrent/manager.go`。VisibleName(key, file) は、マウントに表示される名前と、ルックアップが一致させるべき名前を決める唯一の基準です。File.Rename があり、
かつ `ignore_renames` が false の場合はそれを使います。それ以外の場合は SelectedFiles のキーを使い、
このキーにはすでにセクション 4 のタグが含まれています。GetFilename は代わりに `filepath.Base(file.Path)` を返すので、
そのタグが失われます。表示もルックアップも、両方とも VisibleName を通す必要があります。
そうしないと、タグ付きの名前へのリクエストが何も見つからず、
N 個のファイルが同じ素の名前を共有してしまいます。

（前回の翻訳は却下されました：コードスパンが一致していませんでした。構造をそのまま維持してください。）

## 6. ディスク上のファイル名 {#6-on-disk-filenames}

`internal/torrent/utils.go`、sanitizeFilename は中身が見えにくい関数です。適用されるのは zurg がホスト上に書き出すファイル（`data/<name>.zurgtorrent` と STRM ツリー）だけで、マウントが配信する内容には一切適用されません。上で説明したものよりずっと攻めた処理をします。マウント上のフォルダ名が `Три богатыря` のリリースでは、キャッシュファイルの名前がアンダースコアの連続と `_xxxxxxxx` のサフィックスになります。このサフィックスのおかげで、次のキリル文字タイトルと区別できます。これは別の名前空間の話で、一致させることは想定されていません。

## 7. アーカイブ内部 {#7-archive-interiors}

RAR、ZIP、7z から配信されたリリースでは、ボリュームではなくアーカイブの中身が一覧に出ます。そのため、名前の扱いを決めるルールが2つあります。

`stripRedundantRoot`(`internal/universal/rar_streamer.go`)は、アーカイブ全体を包んでいる先頭のディレクトリを取り除きます。`payloadRenames`(`internal/universal/deobfuscate.go`)は、難読化された単一のペイロードを、リリース本来の名前で見せます。同じステムを持つエントリもすべて一緒に移動します。何を難読化とみなすかは、同じファイル内の `looksObfuscated` で決まります。これは zurg が SABnzbd のテストを移植したもので、そのまわりのガード処理と合わせて、判定の中身は少しわかりにくくなっています。ディスク上のファイルは一切書き換えません。また、`archiveName` はアーカイブ自身の表記も解決します。

## 8. ディレクトリー名 {#8-directory-names}

`internal/torrent/manager.go`, `internal/torrent/provider_directories.go`

組み込みで、予約済みのもの:

    __all__          すべてのリリース
    __unplayable__   再生可能なものがないリリース
    __dump__         ダンプされたトレント
    __downloads__    ダウンロード表示
    __magic__        書き込み可能なオーバーレイ。レイアウトを計算ではなく保存している、唯一のディレクトリ。
                     その中の `__all__` はライブラリをミラーしたものです。`__all__` に含まれるすべてのリリースを、
                     平坦化せず、ファイルの `File.Path` 値が示すディレクトリツリーとして表示します
                     (`internal/magic/tree.go`)。このミラーの隣にあるものはすべて、ユーザーが保存したものです。
                     ミラーは計算によって生成されるため、そこに何も書き込むことはできません。
                     `internal/magic/resolve.go` の `MirrorDirectory` がこれを指定しています
    int__all__       内部ハッシュインデックス

`__downloads__` と `__magic__` はフィルターではないので、ルートの一覧に手動で追加されます。
`__magic__` は magic が有効な場合にのみ表示されます。`int__` で始まる名前は、ルートの一覧から完全にスキップされます。

アカウントごとに、もう一つ追加されます: `"__" + account name + "__"`。
たとえば `__realdebrid__`、`__torbox__`、`__nzb__` です。providers ブロックから作られます。
また、読み取りの送り先も決めます。`__torbox__` の下で開かれたファイルは、別のアカウントが同じリリースを持っていて設定の順番で勝つ場合でも、TorBox から配信されます。
予約名と衝突するアカウント名のアカウントには追加されず、zurg が警告します。
ルートにあるそれ以外のものはすべて、`directories:` ブロックのキーがそのまま使われます。

## 9. ユーザーによる名前変更 {#9-user-renames}

`internal/torrent/rename.go`, `internal/torrent/rename_bulk.go`

リネームはただの表示上の設定で、デブリッドアカウント上のものは何も変わりません。Torrent.Rename または File.Rename として保存され、上で説明したすべての導出より優先されます。`ignore_renames: true` にすると、zurg はリネームを完全に無視します。

torrent のリネームは、次の条件をすべて満たすときだけ受け付けられます。トリム後の名前が空でないこと。`/` や `\` を含まないこと。`filepath.Clean` の結果と同じであること（これで `.` と `..` も弾かれます）。そして、別のハッシュが持っている既存のアクセスキーと衝突しないこと。適用すると、ディレクトリマップのキーを付け替え、新しい名前で `.zurgtorrent` を書き出し、古い名前のファイルは削除します。古いファイルを残しておくと、再起動時に両方が読み込まれ、リネームが知らないうちに元に戻ってしまいます。

シーズン修正（`/torrents/season-fix/plan` と `/apply`）は、Plex 自身のエピソードマッチングを使ったファイルの一括リネームです。plan は読み取り専用で、ファイルごとにスキップ理由を返します。apply はすべて適用フラグではなく、ハッシュのリストを明示的に受け取ります。ダッシュボードは `/season-fix/` からこの両方を操作します。このページには、マッピングのルールとスキップ理由も管理者向けに書かれています。

## 10. zurg と連携するものへの影響 {#10-consequences-for-anything-integrating-with-zurg}

トレントの名前からパスを組み立てる場合（symlink の集まり、リモートのパスマッピング、スクリプトなど）、次のような点で間違えやすいです:

  a. 拡張子。`.mkv` と `.mp4` だけが、大文字と小文字を区別して取り除かれます。
     それ以外のコンテナは、拡張子がフォルダ名に残ります。

  b. リネーム。`Torrent.Rename` は派生した名前より優先されます。また、RD 側で
     トレントをリネームすると、`Name` が知らないうちに変わります。

  c. ハッシュのサフィックス。同じ名前を共有する2つの異なるリリースがあると、
     そのうちの1つには ` {a1b2c3}` が付きます。どちらに付くかは、コンテンツが
     追加されると変わります。

  d. 重複ファイルのタグ。リリース内でベース名が重複するファイルは、`name (tag).ext`
     として配信されます。tag はディレクトリの要素かパスのハッシュです。
     `filepath.Base(file.Path)` ではこれを再現できません。

  e. アーカイブのリネーム。アーカイブ内の難読化されたペイロードは、自身の名前ではなく
     リリース名で表示されます。

  f. NZB の名前は `.nzb` の FILENAME から取られ、中身からは取られません。ただし、
     ファイル名がハッシュの場合は別です。ファイルに名前を付けたら、フォルダにも
     名前を付けましょう。

  g. サニタイズされたオンディスクのファイル名は、マウント名とは別の名前空間にあります。
     非ASCIIのリリースでは、意図的に一致しません。

確実な方法は、まずハッシュでリリースを特定し、それから zurg にその名前を尋ねることです。
名前を自分で再構築するのは推測にすぎず、上のどのルールも、その推測が外れる原因になります。
