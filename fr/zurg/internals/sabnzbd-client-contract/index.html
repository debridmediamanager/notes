Contrat de l'API SABnzbd tel qu'utilisé par Sonarr et Radarr (develop)

Source de référence : fichiers récupérés depuis raw.githubusercontent.com/{Sonarr/Sonarr,Radarr/Radarr}/develop/... le 2026-08-22. Chaque numéro de ligne indiqué ci-dessous a été relevé dans ces fichiers.

Gardé ici pour expliquer pourquoi internal/sabnzbd répond sous la forme qu'il a. Rien dans ce package ne doit être modifié sans le paragraphe ici qui explique ce que le client fait du champ : une mauvaise balise de structure ne fait pas échouer, elle laisse le client lire un zéro, et une mauvaise valeur d'énumération lève une erreur dans son désérialiseur et fait tomber toute l'interrogation. Pour savoir comment pointer Sonarr ou Radarr vers zurg, voir sabnzbd.md.

Sauf indication contraire dans une section, les fichiers SAB des deux dépôts sont identiques octet pour octet, à part un BOM UTF-8 et le renommage TvCategory → MovieCategory / RemoteEpisode → RemoteMovie, et les numéros de ligne correspondent un à un. Chaque citation Sabnzbd* s'applique donc aux deux dépôts, à la même ligne. Les chemins sont src/NzbDrone.Core/Download/Clients/Sabnzbd/... dans les deux cas. Les différences vérifiées sont consignées au §6.

Rien ici n'est une supposition sur SAB lui-même : chaque affirmation décrit ce que fait le client. Lorsque j'énonce la sémantique de Newtonsoft.Json ou du runtime .NET (et non du code de Sonarr), je le dis explicitement.

0. Règles au niveau du transport (elles piègent en premier)

0.1 Forme de l'URL

SabnzbdProxy.BuildRequest (SabnzbdProxy.cs:162-185) :

private HttpRequestBuilder BuildRequest(string mode, SabnzbdSettings settings)
{
    var baseUrl = GetBaseUrl(settings, "api");                      // :164
    var requestBuilder = new HttpRequestBuilder(baseUrl)
        .Accept(HttpAccept.Json)                                    // :167  -> Accept: application/json
        .AddQueryParam("mode", mode);                               // :168
    requestBuilder.LogResponseContent = true;                       // :170
    if (settings.ApiKey.IsNotNullOrWhiteSpace())
        requestBuilder.AddSuffixQueryParam("apikey", settings.ApiKey);        // :174
    else
    {
        requestBuilder.AddSuffixQueryParam("ma_username", settings.Username); // :178
        requestBuilder.AddSuffixQueryParam("ma_password", settings.Password); // :179
    }
    requestBuilder.AddSuffixQueryParam("output", "json");           // :182

  • URL de base : HttpRequestBuilder.BuildBaseUrl (src/NzbDrone.Common/Http/HttpRequestBuilder.cs:56-66) = {http|https}://{Host}:{Port}{UrlBase}. UrlBase reçoit un / au début s'il n'en a pas. Le point de terminaison, c'est cette URL + /api (SabnzbdProxy.cs:38-44).

  • Les paramètres suffixes arrivent toujours en dernier. Donc apikey (ou ma_username+ma_password) et output=json sont les derniers paramètres de requête (HttpRequestBuilder.cs:82 — QueryParams.Concat(SuffixQueryParams)).

  • Accept: application/json sur chaque appel. output=json sur chaque appel. Il n'existe nulle part de chemin output=xml.

  • La clé API et le nom d'utilisateur/mot de passe sont mutuellement exclusifs : une clé API supprime ma_username/ma_password.

0.2 Répondre toujours HTTP 200, même en cas d'erreur

HttpClient.Execute lève une exception pour tout statut >= 400 (src/NzbDrone.Common/Http/HttpClient.cs:106-121 ; HttpResponse.cs:54 — HasHttpError => (int)StatusCode >= 400 ; un 429 devient TooManyRequestsException). SabnzbdProxy.ProcessRequest (SabnzbdProxy.cs:199-215) transforme cela en DownloadClientException("Unable to connect to SABnzbd, {0}").

Le message de HttpException est "HTTP request failed: [401:Unauthorized] [GET] at [url]" (src/NzbDrone.Common/Http/HttpException.cs:18) — le corps de la réponse n'est pas dans le message. Donc un 401 avec {"error":"API Key Incorrect"} ne sera pas reconnu par TestAuthentication (Sabnzbd.cs:424,429 compare ex.Message), et le test de connexion affiche à la place le message générique "Test was aborted due to an error". Il faut imiter SAB : HTTP 200 + {"status": false, "error": "..."}.

0.3 Paramètres du désérialiseur (gouvernent toutes les questions de noms de champs et de types)

Toutes les charges utiles SAB passent par NzbDrone.Common.Serializer.Json (src/NzbDrone.Common/Serializer/Newtonsoft.Json/Json.cs:21-37), avec Newtonsoft et non System.Text.Json :

DateTimeZoneHandling  = DateTimeZoneHandling.Utc,
NullValueHandling     = NullValueHandling.Ignore,
Formatting            = Formatting.Indented,
DefaultValueHandling  = DefaultValueHandling.Include,
ContractResolver      = new CamelCasePropertyNamesContractResolver()
Converters: StringEnumConverter { NamingStrategy = CamelCaseNamingStrategy }, VersionConverter, HttpUriConverter

Conséquences (comportement de Newtonsoft, pas du code Sonarr) :

Réglage Effet sur un émulateur
CamelCasePropertyNamesContractResolver Les propriétés C# Storage se lient à storage, PP à pp et Misc à misc. Newtonsoft revient aussi à une correspondance de propriété insensible à la casse, donc les vraies clés snake_case ou en minuscules de SAB se lient dans les deux cas.
StringEnumConverter (global) S'applique à SabnzbdDownloadStatus, qui n'a aucun convertisseur par propriété. Les noms d'enum inconnus lèvent JsonSerializationException. Les entiers sont aussi acceptés (AllowIntegerValues vaut true par défaut).
NullValueHandling.Ignore Aussi à la lecture : un null JSON laisse le membre C# à la valeur de son constructeur. Donc "categories": null garde la liste vide du constructeur, mais "misc": null laisse Misc à null (pas de valeur par défaut dans le constructeur), ce qui donne une NRE, voir §3.4.
MissingMemberHandling (par défaut Ignore) Les champs en trop dans ta charge utile sont sans danger. Envoie le corps SAB réel complet.
Culture (par défaut InvariantCulture) Les chaînes numériques comme "1024.00" doivent utiliser . comme séparateur décimal et aucun séparateur de milliers.

Json.Deserialize<T> ne relance que JsonReaderException, avec un message plus clair (Json.cs:39-50) ; Json.TryDeserialize<T> avale uniquement JsonReaderException et JsonSerializationException (Json.cs:99-117). Tout le reste (par exemple une ArgumentException venant du convertisseur timeleft, ou une NRE venant du convertisseur priority) remonte sans être attrapé.

2. SabnzbdDownloadStatus et SabnzbdPriority — membres exacts, gestion des valeurs inconnues et null

2.1 SabnzbdPriority.cs (fichier complet)

namespace NzbDrone.Core.Download.Clients.Sabnzbd
{
    public enum SabnzbdPriority
    {
        Default = -100,
        Paused  = -2,
        Low     = -1,
        Normal  = 0,

JsonConverters/SabnzbdPriorityTypeConverter.cs:14-21:

public override object ReadJson(JsonReader reader, Type objectType, object existingValue, JsonSerializer serializer)
{
    var queuePriority = reader.Value.ToString();

    Enum.TryParse(queuePriority, out SabnzbdPriority output);

    return output;

  • Enum.TryParse<T>(string, out T) est la surcharge sensible à la casse (sémantique .NET). "Normal" fonctionne ; "normal" ne fonctionne pas. En cas d'échec, output vaut default(SabnzbdPriority) == 0 == Normal, donc une mauvaise casse repasse silencieusement en Normal. "Force" compte (§1.9), "force" ne marche pas.

  • Les chaînes numériques marchent aussi : "2" → Force, "-100" → Default. Un nombre JSON 2 marche aussi (reader.Value.ToString() == "2").

  • "priority": null lève une NullReferenceException (reader.Value.ToString() sur null). Ce cas n'est pas intercepté par Json.TryDeserialize. Omets la clé ou envoie une vraie valeur.

  • Omettre priority ne pose pas de problème : le convertisseur n'est pas appelé, le membre reste Normal (0).

  • Le convertisseur n'est enregistré que sur SabnzbdQueueItem.Priority (SabnzbdQueueItem.cs:21) ; les éléments de l'historique n'ont pas de priorité.

  • Ce sont ces mêmes entiers que Sonarr/Radarr renvoient dans &priority= sur mode=addfile (SabnzbdSettings.cs met par défaut Recent*Priority et Older*Priority à (int)SabnzbdPriority.Default = -100).

SabnzbdJsonError (SabnzbdJsonError.cs, complet) :

public string Status { get; set; }
public string Error  { get; set; }

public bool Failed => !string.IsNullOrWhiteSpace(Status) &&
                      Status.Equals("false", StringComparison.InvariantCultureIgnoreCase);

Les règles, précisément :

  • CheckForError s'exécute sur chaque réponse, avant toute désérialisation propre au mode (SabnzbdProxy.cs:217).

  • Status est typé string, mais SAB envoie un booléen JSON. Newtonsoft convertit false en "False", et Failed le reconnaît sans tenir compte de la casse. Donc false (booléen) et "false" (chaîne) fonctionnent tous les deux.

  • Une réponse sans status de premier niveau (par ex. {"version": …}, {"queue": {...}}, {"history": {...}}, {"config": {...}}) laisse Status à null, donc Failed vaut false et il n'y a pas d'erreur.

  • status: true devient "True", donc pas d'échec.

  • Corps non JSON : TryDeserialize renvoie false (il intercepte JsonReaderException et JsonSerializationException, Json.cs:107-116) et la branche texte brut s'exécute. Un corps qui commence par error (sans tenir compte de la casse) donne Status = "false" et lève DownloadClientException("Error response received from SABnzbd: {body with 'error: ' stripped}"). Tout autre corps non JSON donne Status = "true" et est traité comme un succès ; c'est ensuite la désérialisation propre au mode qui échoue, selon ses propres règles.

  • Un corps JSON dont status est un objet (mode=fullstatus) prend aussi la branche texte brut, car un jeton StartObject ne peut pas remplir une propriété string. Status vaut alors "true".

  • Notez la ligne redondante result.Error = … à :239 : Error est défini même dans la branche succès. Cela n'a aucun effet (rien ne lit Error sauf si Failed est vrai).

6.1 DownloadClientRootFolderCheck — le seul endroit où Sonarr et Radarr diffèrent vraiment

IsParentPath (src/NzbDrone.Common/Extensions/PathExtensions.cs:123-140) remonte vers le haut à partir de l'enfant :

public static bool IsParentPath(this string parentPath, string childPath)
{
    var parent = new OsPath(parentPath);
    var child  = new OsPath(childPath);

    while (child.Directory != OsPath.Null)
    {
        if (child.Directory.Equals(parent, true)) { return true; }
        child = child.Directory;
    }

    return false;
}

9. Liste de contrôle de l'implémentation (12 points)

  1. Une seule route : GET|POST {UrlBase}/api, qui dispatche selon mode. Toujours HTTP 200, toujours du JSON.

  2. Implémente version, get_config, queue (lecture + name=delete), history (lecture + name=delete), addfile, fullstatus. Optionnel : retry (code mort pour l'instant). get_cats n'est jamais appelé.

  3. Accepte l'authentification soit par apikey=, soit par ma_username=+ma_password=. Refuse avec 200 + {"status":false,"error":"API Key Incorrect"} / "API Key Required", jamais de 401/403.

  4. Respecte category= sur queue/history (les clients filtrent aussi côté client par correspondance exacte de la chaîne, Sabnzbd.cs:190).

  5. Les tailles de queue sont en MB (mb, mbleft) ; celles de history sont en BYTES (bytes). Ne les mélange jamais. La queue utilise cat, l'historique utilise category.

  6. timeleft est toujours au format h:m:s ou d:h:m:s, jamais vide, jamais absent ou chaîne vide. Aucun champ de date n'est analysé nulle part, donc les champs epoch sont libres.

  7. Les valeurs de status doivent venir de la liste SabnzbdDownloadStatus à 16 membres, casse exacte (un nom inconnu lève une exception et fait tomber tout l'appel queue/history). priority doit être un nom SabnzbdPriority (casse exacte) ou sa valeur entière ; jamais null (NRE dans le convertisseur).

  8. config.misc doit être un objet ; chaque catégorie doit avoir une chaîne dir non nulle qui ne se termine pas par *. categories/sorters/servers peuvent être null ou absents, mais misc et dir ne peuvent pas l'être.

  9. Laisse enable_tv_sorting, enable_movie_sorting, enable_date_sorting et pre_check tous à false, et history_retention_option: "all", pour que le test de connexion et tous les contrôles de santé restent propres.

Attends-toi à ce que les *arr fassent un rm -rf dessus après un import réussi (paramètres par défaut), et à ce que le fichier média en soit déplacé d'abord. Configurer une fenêtre de complétion plus grande

Les deux clients ont 60 comme valeur par défaut pour DownloadClientHistoryLimit. zurg reprend cette fenêtre quand il garde les tâches terminées en trop dans queue. Si tu n'augmentes que la limite du client, certaines tâches apparaîtraient à la fois dans queue et dans l'historique, et c'est queue qui l'emporte.

Si tu as un gros retard, mets sabnzbd.history_limit dans zurg et DownloadClientHistoryLimit des clients à la même valeur, par exemple 500. Cela expose plus de tâches terminées et échouées à chaque interrogation. Si plusieurs clients utilisent des valeurs différentes, laisse zurg à la plus petite limite de client. Ce paramètre avancé du client n'est pas exposé dans la ressource API de configuration du client de téléchargement de Sonarr v4 ; sauvegarde et arrête le client avant de modifier sa configuration enregistrée.

sabnzbd:
  enabled: true
  history_limit: 500

La valeur par défaut reste 60 ; zéro et les valeurs négatives utilisent cette valeur par défaut. Une requête de diagnostic sur l'historique avec une autre limite ne modifie jamais la fenêtre configurée. Les avertissements que le client ne peut pas résoudre demandent toujours une vérification ; une fenêtre plus grande permet aux autres tâches d'arriver jusqu'à l'import pendant que ces avertissements occupent des emplacements dans l'historique.

La vérification de disponibilité avant la fin du téléchargement examine les seize premiers articles et le dernier article de chaque fichier de contenu. Elle attrape un article manquant dans l'en-tête du média, que l'ancien canari du premier article ne détectait pas. Elle télécharge le premier article de chaque fichier de contenu, ce qui vérifie l'identité de l'article et que le corps est toujours servi (un fournisseur peut répondre à STAT pour un article dont il a retiré le corps), plus des articles tirés au hasard jusqu'à seize corps pour une release de moins de seize fichiers, et au maximum soixante-quatre corps au total ; un corps déjà présent dans le cache d'articles n'est pas téléchargé à nouveau. STAT couvre le reste de l'échantillon. Cela ne valide pas chaque article et ne prouve pas que le média se décode. Les requêtes STAT sont regroupées par fichier, pour que l'échantillon ne prenne qu'une réservation du pool au lieu de dix-sept, sans augmenter la limite de connexions du compte. Si un lot n'est pas utilisable, on revient à des STAT individuels. Les échecs serveur laissent la tâche en file d'attente pour une nouvelle tentative ; les articles manquants confirmés produisent un téléchargement échoué avant la première notification de fin.
