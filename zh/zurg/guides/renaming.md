# 重命名发布与文件 {#renaming-releases-and-files}

zurg 的挂载目录只允许一种写操作：你可以**重命名**某个版本文件夹或其中的文件，位置不限。这个功能默认开启。不会复制任何内容，不会下载，也不会动你的网盘账户。新名称会保存在该版本旁边，并优先于 zurg 原本计算出的名称。

你不能**移动**任何东西。在文件管理器里，重命名和换位置看起来是同一个操作，但 zurg 把它们当作相反的操作，原因见[最后一节](#why-a-move-is-refused-when-a-rename-is-not)。

如果你要的是保存下来的*布局*，而不是*名称*，比如你自己整理的文件夹，或者 \*arr 通过移动来导入，请看 [`__magic__`](magic.md)。本页只讲名称。

## 通过挂载点重命名 {#renaming-through-the-mount}

一次在挂载点中的重命名，就是一个 WebDAV `MOVE` 请求，其目标路径与源路径只在最后一段不同。rclone 会把挂载点上的重命名（FUSE `rename(2)`，或 Windows 上对应的 WinFsp）转换成这样的请求，所以 `mv` 或 `Rename-Item`、在 Finder、Explorer 或其他文件管理器里重命名，以及 WebDAV 客户端，最终都会进入同一个处理程序。

+++ Linux 和 macOS

```bash
mv "/mnt/zurg/shows/Show.S01.1080p.WEB-DL/Show.S01E01.mkv" \
   "/mnt/zurg/shows/Show.S01.1080p.WEB-DL/Show - s01e01.mkv"
```

在 macOS 上，除非你改过 `mount_path`，挂载点默认是 `/Volumes/Zurg`。

+++ Windows

```powershell
Rename-Item -LiteralPath "Z:\shows\Show.S01.1080p.WEB-DL\Show.S01E01.mkv" -NewName "Show - s01e01.mkv"
```

+++

两个层级都支持重命名：

| 重命名对象 | 存储为 |
|---|---|
| 一个资源文件夹 | `Torrent.Rename` |
| 资源内的一个文件 | `File.Rename` |

`/dav/` 和 `/infuse/` 端点接受 `MOVE`。`/http/` 不接受，它只是一个只读的浏览器，在 `__magic__` 之外会返回 `405`。

### 文件名需要满足什么 {#what-a-name-has-to-satisfy}

检查新名称时，先去掉首尾空白，然后要满足以下条件才会被接受：不能为空；不能包含 `/` 或 `\`；必须与自身的 `filepath.Clean` 结果相同（这也会拒绝 `.` 和 `..`）；如果是发布文件夹，还不能与*另一个*哈希的访问密钥冲突。文件名在其所属发布内部必须唯一。

| 结果 | 状态码 |
|---|---|
| 已重命名 | `201` |
| 名称为空、包含分隔符，或目标只指定了目录 | `400` |
| 名称已被占用 | `412` |
| 找不到源文件 | `404` |
| 位于压缩包内部，或被拒绝（见下文） | `403` |

*无法重命名压缩包内部的文件。* 压缩包内部的内容是根据压缩包自动生成的，因此没有可以写入名称的地方。zurg 会以 `403` 拒绝此操作，并提示压缩包内的文件无法重命名。

## 从仪表盘和 API 重命名 {#renaming-from-the-dashboard-and-the-api}

这两个重命名操作都是 `POST` 端点，每个都有一个对应的重置操作，用于删除已保存的名称，并把发布项恢复为系统计算出的名称：

```
POST /manage/{torrentHash}/rename
POST /manage/{torrentHash}/clear-rename
POST /manage/{torrentHash}/files/{fileid}/rename
POST /manage/{torrentHash}/files/{fileid}/clear-rename
```

通过挂载点没有与 `clear-rename` 对应的操作。把名称改回原始名称会保存这个名称，而不会删除覆盖设置。

### 季度修复 {#the-season-fix}

`GET /torrents/season-fix/plan` 和 `POST /torrents/season-fix/apply` 是一个批量重命名文件的功能，它依赖 Plex 自己的剧集匹配，适用于文件编号方式无法被任何程序解析的资源。plan 是只读的，会给出每个文件的跳过原因。apply 需要传入一个明确的 hash 列表，而不是一个“全部应用”的开关，这样你能确认自己看过的内容。

## 重命名会保留什么 {#what-a-rename-survives}

存储的名称保存在 release 上，并被序列化到它的 `.zurgtorrent` 中，因此以下情况都不会丢失：

- **库刷新**，包括重新从提供商的列表中构建 release 文件条目的刷新。
- **重启。**
- **修复**，即通过哈希以新 id 重新添加 release。
- **提供商在后台重命名了种子**，Real-Debrid 就会这样做。

它也可以随文件迁移。导出的 `.zurgtorrent` 会带上这些重命名，因此[本地库](local-libraries.md)到了新位置，名称仍然是你设置的那样。

有一种情况下它会失效，就是设置 `ignore_renames: true`，这正是该选项的用途。开启后，zurg 会忽略所有存储的名称，显示计算出的名称，并拒绝通过挂载点进行新的重命名。重命名并没有被删除，只是被忽略了，所以把它改回关闭后，重命名就会重新生效。

## 重命名会连带改变什么 {#what-a-rename-changes-around-it}

重命名只是一个视图，但有好几样东西是基于这个视图构建的，它们也会跟着一起更新：

- **挂载点。** rclone 的目录缓存会对旧路径和新路径做失效处理，所以变化能立即显示，不用等缓存过期。
- **`.strm` 文件**（需要开启 `save_strm_files`）。旧文件会被删除，然后按新名字重新写入。
- **Plex 和 Jellyfin** 会被通知重新扫描这个资源。
- **磁盘上的缓存记录。** 新名字的 `.zurgtorrent` 会被写入，旧文件会被删除。这一步很关键：如果旧文件留着，重启后两份都会被加载，哈希冲突会把结果解析回另一份副本，重命名就会悄悄失效。这是一个真实的 bug，于 2026-08-17 出现过。
- **SABnzbd 和 qBittorrent 接口。** 它们每次轮询时都会重新计算报告给 Sonarr 和 Radarr 的文件夹，所以如果在导入过程中进行重命名，它们告诉 Sonarr 和 Radarr 的导入路径也会跟着更新，而不会让它们卡在旧路径上。

## 三个陷阱 {#three-traps}

**重命名可能会在下一次刷新时让资源被重新归类。** 目录归属是通过对资源名称运行 `directories:` 过滤器来决定的,而过滤器看到的是*重命名后*的名称。重命名操作本身有意不重新评估这些过滤器,它会让资源留在原来所在的目录里,但下一次刷新会重新评估。所以,如果某个过滤器是根据名称中的某些内容来匹配的,而你的新名称不再包含它,那么资源之后会被移到另一个目录,而重命名时没有任何迹象表明会这样。因此,凡是依赖名称的过滤器,重命名时都要先留意。

**更改扩展名就等于改变了文件的类型。** 没有什么能阻止把 `episode.mkv` 改成 `episode.txt`,系统只会拒绝路径分隔符。但可见性是根据客户端看到的文件名来判断的,所以重命名后的文件可能会从 `only_show_the_biggest_file` 中消失,也可能跳出可播放文件的判断逻辑,还可能不再被媒体服务器扫描到。

**已经交给其他程序使用的 `.strm` 链接会失效。** 签名令牌里编码了访问密钥和文件名,所以在重命名之前抓取的链接,在重命名之后会无法解析,并返回 `404`。zurg 自己的 `.strm` 目录树会被重写,但任何从中复制出链接的地方都不会更新。

## 关闭它 {#turning-it-off}

| 键 | 默认值 | 作用 |
|---|---|---|
| `dav_allow_rename` | `true` | `false` 时，挂载点的 `MOVE` 请求会被拒绝并返回 `403`，响应正文中会写明该键名 |
| `ignore_renames` | `false` | `true` 时忽略所有已保存的重命名，改为提供计算出的名称，并通过挂载点拒绝新的重命名请求，返回 `403` |
| `mount_read_only` | `false` | `true` 时以 `--read-only` 启动 rclone，因此内核会在 zurg 收到之前就拒绝写入 |

`dav_allow_rename` 只管挂载点。它不控制仪表盘端点，也不控制 `__magic__` 下的写入操作，因为那些操作不会触及任何 debrid 账户。
镜像是唯一的例外，而且并非因为这个键：`__magic__/__all__` 以及其中直接包含的发布文件夹是资料库自身的结构，所以无论此项如何设置，针对它们的写入都会被拒绝。发布文件夹内部则恢复正常。
`mount_read_only` 在内核层面覆盖一切，也是阻止挂载 `DELETE` 的唯一方法。关于它为何比重命名更重要，请参阅 [config.md](../reference/config.md)。

## 为什么移动会被拒绝而重命名不会 {#why-a-move-is-refused-when-a-rename-is-not}

| 尝试 | 状态 |
|---|---|
| 把 release 文件夹移到另一个目录 | `403` |
| 把文件移到另一个 release 中 | `403` |
| 把文件移到其自身 release 的子文件夹中 | `400` |
| 顶层目录被重命名或移动 | `405` |
| 从 `__magic__` 中移出任何内容 | `403` |
| 写入 `__magic__/__all__`，或写入其直接子项的名称 | `403` |

其背后的规则每次都一样：**重命名有地方可以存储，移动则没有。**

release 的名称是 release 上的一个字符串，所以写入新名称就只是一次字段赋值，之后每次查找都会读回这个值。但顶层目录不是文件夹，它是一个保存的过滤器，其成员关系会在每次刷新时根据 `directories:` 配置重新计算。把 release 移“入” `movies` 不会写入任何内容，因为没有任何东西会读取针对这个问题的已存储答案；下一次刷新会根据过滤器重新计算成员关系，从而把它撤销。拒绝才是诚实的做法。release 内的子文件夹也是同样道理，它的结构来自账户自身的文件列表。

`__magic__` 的存在是因为保存下来的布局确实很有用，而且它正面解决了存储问题，而不是假装问题不存在：在其中移动时，会向一张以内容哈希为键的小表写入一行，这也是为什么修复时即使 release 以新 id 重新添加，这一布局依然能保留。这张表有意只作用于这一个命名空间。

还有第二个理由，不应随意扩大拒绝的范围。[rclone 移动被拒绝的说明](../internals/rclone-move-refusal.md) 记录了被拒绝的 `MOVE` 对一个并未预料到它的客户端会造成什么影响：在 rclone 1.72.0 下，VFS 条目会停留在尝试的目标位置；而如果调用方退回到先复制再删除的方式，它会读到 EOF 并报告成功，最终生成一个它以为已经写入的零字节文件。上面的每一种拒绝，都是某个东西必须能够承受的拒绝。
