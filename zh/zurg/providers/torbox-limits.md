# TorBox 的限制，以及 zurg 如何适应这些限制 {#torbox-limits-and-how-zurg-adapts-to-them}

zurg 的库行为是围绕 Real-Debrid 的限制逐步形成的。TorBox 的限制在性质上就不同,而不只是数量上的差别。如果像对待 Real-Debrid 那样驱动它,首次扫描库时账号几秒钟内就会被限流。下面说明这些限制是什么、数字从哪里来,以及 zurg 针对每一项做了什么。

提供商的限制在代码中以 `debrid.Capabilities` 的形式声明,通用的库代码会读取这些值,而不是假设它们固定不变。添加一个后端,只需要填写这个结构体,不必修改 torrent manager。

## 速率限制 {#rate-limits}

| 限制 | 值 | 来源 |
|---|---|---|
| 所有端点合计，每个 API token | 300/min | [官方文档](https://api-docs.torbox.app/) |
| `POST /torrents/createtorrent`（仅未缓存） | 60/hour | 官方文档 |
| `POST /webdl/createwebdownload`、`POST /usenet/createusenetdownload` | 60/hour | 官方文档 |
| `GET /torrents/requestdl` | **约 100 次调用后返回 429**，这是配额，不是速率 | 实测，2026-08-30 |
| 到同一 CDN 主机的并发连接数 | **正好 20 个**，超过则返回 429 | 实测，2026-08-23 |
| 全局突发上限 | 约 40 个并发时触发，会限制**所有**端点 | 实测 |
| 429 恢复 | `Retry-After: 300`，非此即彼的硬切断 | 实测 |

这些限制以每个 API token 计算，并在 TorBox 的服务器之间同步，不是按 IP 计算。所以其他机器上的额外客户端会共用同一份配额。TorBox 也明确说过这一点：由于限制是按 token 计算的，他们已经不再接受 IP 白名单申请。

有三件事让实际情况比标题里的 300/min 更苛刻：

- **300/min 不是按端点计算的。** 整个 key 共用一份配额，所以把每个端点分别限速，它们加起来就可能超过上限，而单独看它们谁都没超。
- **`requestdl` 比文档写的严格得多，而且它不是速率限制。** 它负责生成下载 URL，结果大约 100 次调用后就被锁了，而在同样的并发下，`user/me`、`mylist` 和 `checkcached` 能处理 500 次以上。

  放慢速度并不能多换来几次调用。2026-08-30 在主账号上测试，共三轮，每轮都从清空锁定状态开始：

  | 节奏 | 429 出现于 | 耗时 |
  |---|---|---|
  | 尽可能快，从 60 逐步升到 240/分钟 | 第 **100** 次调用 | 56 秒 |
  | 每秒一次（60/分钟） | 第 **94** 次调用 | 108 秒 |
  | 每两秒一次（30/分钟） | 第 **101** 次调用 | 198 秒 |
  | 每三秒一次（20/分钟） | **从未出现**，共 241 次调用 | 721 秒，无异常 |

  速率减半只多撑了九十秒，调用次数没有增加；再减半，429 就完全不出现了。账号实际的配额是**滚动五分钟内 100 次调用，即 20/分钟**。只有这种解释能同时吻合四轮结果：它预测前三轮分别在 t≈100 秒、t≈200 秒以及一开始就触发，并预测第四轮恰好卡在临界线上而安然通过。

  这是读本文其余部分时最需要注意的更正。仅靠按分钟的限速器无法让 zurg 保持在配额之内，所以下面的节奏数字换来的是平稳，而不是余量。限速器更快并不能让库扫描更早完成，只会更早触发同样的锁定，而且一旦触发，挂载点会在五分钟内完全无响应。能让扫描走得更远的，只有**减少调用次数**，这也是为什么这里不做预读，以及为什么确定已解析文件的名称时绝不能消耗一次请求。
- **429 是悬崖，不是斜坡。** 一旦触发，所有请求都会失败，大约持续五分钟。不存在可以忍耐过去的部分降速。

CDN 下载单独计量，**不占用** API 配额。流式播放文件从来不消耗链接解析配额。这一点在两个方向上都得到了验证：把 CDN 下载打到 429 后，`requestdl` 仍然正常响应；反过来也一样。

### 两种不同的限制，数字都是 20 {#two-different-limits-both-numbered-20}

表格上面的 20 出现了两次，但这两个数字没有关系。很容易把它们混为一谈，结果去限制错误的东西。

- **`requestdl` 约 20 并发** 是 *API* 限制：大约以这个并发量调用 100 次左右就会出现 429，同时消耗账户的请求配额。
- **每个 CDN 主机 20 个连接** 是 *字节传输路径* 上的限制，是在 2026-08-23 用逐步加压的方式测得的。它完全不需要调用 `requestdl`，复用一个已经生成好的 URL 就能触发它。

字节传输路径的上限正好是 **20**，表现为硬性上限而不是逐渐下降的曲线：无论请求 24、32、40 还是 48 个连接，都稳定在 20 个，超出的部分全部被拒绝。

这个限制是按 **CDN 主机** 计算的，既不是按文件，也不是按 IP。这一点修正了之前"按 IP、在 Cloudflare 层面"的理解：

- 同一个 `nexus-NNN` 主机上提供的两个*不同*文件，共用 20 的总额度，超出的部分同样被拒绝。
- 把同样的负载分到两个主机上，就能正常运行。
- 从同一个 IP 把 32 个并发流分散到 16 个主机上，也没有问题。

为了和用同样方法测过的其他服务商做个对比：Real-Debrid 每个主机上限是 32（在 TCP 层直接拒绝，没有 HTTP 状态码），AllDebrid 是 32（返回 HTTP 429），Premiumize 测到 64 也没有上限。TorBox 的 20 是这四家中最低的。

**TorBox 的全局边缘节点没有这个限制。** 这 20 是 `requestdl` 生成的、按节点划分的 `nexus-NNN.<region>.tb-cdn.st` 主机才有的属性。两个全局边缘节点 `nexus.erth.tb-cdn.earth` 和 `nexus.hare.tb-cdn.earth` 可以提供账户中的任何文件，测试时两者都加压到了 64 个并发连接，且没有任何拒绝。两者的区别只在主机名，路径和 token 仍然是用来验证请求的。目前 zurg 不会改写到这两个节点上（同级的 `debrid` 服务则通过 `TORBOX_CDN_EDGE` 这样做），所以这里适用的是下面的上限。

### zurg 会做什么 {#what-zurg-does}

- **`GetTorrentInfo` 从种子列表中获取数据。** TorBox 的 `mylist` 已经包含每个种子的文件列表，所以刷新一次库只需要一次请求，而不是每个种子一次。这由 `Capabilities.ListIncludesFiles` 声明。对于设置了它的提供商，刷新流程会跳过每个种子的调用，也跳过磁盘上的信息缓存。在一个有 213 个种子的账户上，这就是 213 次请求和 1 次请求的区别。
- **一个限速器管理所有接口**，设置为 240/分钟，而文档上的限制是 300/分钟。这样留出余量，给同一个 key 上的其他东西用，比如 TorBox 控制台、另一个客户端或第二个 zurg。
- **`requestdl` 还有第二个限速器**，设置为 15/分钟。每次解析都会同时消耗两个限速器的额度。这个数字低于实测的 20/分钟，而不是刚好等于它，原因和通用限速器设在 240 而不是文档上的 300 一样：额度会被所有持有这个 key 的东西消耗，而 20/分钟是在上面什么都没有的情况下测出来的。`TestTheRequestdlBudgetCannotBeSpentInsideItsWindow` 保证了真正的约束：整个配额不能在补充它的那个时间窗口内被一次用完，所以这个常量不会悄悄改回超过限制的值。
- **下载客户端每个 CDN 主机最多 20 个连接**（`internal/torbox/client.go` 中的 `maxConnsPerCDNHost`，通过 `rdclient.HTTPClientOptions.MaxConnsPerHost` 传入）。Go 的 `MaxConnsPerHost` 会让第 21 个请求*等待空闲连接*，而不是直接失败，所以这个上限把提供商的拒绝变成了本地排队。没有这个设置时，下载客户端会继承通用传输层的无限制设置，在字节传输路径上可能收到 429，而所有 API 限速器都在正常工作。
- **收到 429 响应时，所有调用方都会暂停**，暂停时长为 `Retry-After` 的时间窗口，而不是让每个调用方各自去发请求、重新摸索限制。这个锁定是整个账户范围的，所以在任何接口上遇到 429，都会让所有接口一起等待。
- **并发上限为 16 个进行中的请求**，低于大约 40 的全局突发上限，给下载客户端留出空间。
- **不做预读。** zurg 在冷读时会预先加载同一个版本中的下一个文件，对于每分钟预算确实有限的后端来说，这没问题。但库扫描会出问题：它只会打开每个文件一次，所以每次打开都是冷读，预热读取的拒绝逻辑永远不会触发，账户就会被要求为每个文件做两次解析。2026-08-30 的测试显示，一次四十个文件的扫描，在四十次读取的同时，还触发了恰好四十次推测性解析，相当于一半的预算都花在了没人请求的文件上。TorBox 将 `Capabilities.SpeculativeResolutionsAffordable` 设为 false，所以不会为此发出任何请求。
- **为解析后的文件取名不需要请求。** 每次解析的最后都会查询该文件的名称和长度，用于下载记录。之前这个查询走的是列表快照，所以一旦 30 秒的新鲜期过去，下一次读取就得先拉取整个种子列表才能回答。扫描期间，每 30 秒就会发生一次，只要扫描还在继续；在一个有 3,700 个种子的库上，这个列表要分四页才能拉完。现在它会直接读取手上已有的列表，不管它有多旧，因为已完成种子的文件名和长度不会改变。
- **链接缓存保留一天，明确被拒绝时会恢复。** 在 2026-08-30 的探测中，重复调用 `requestdl` 返回的是相同的 URL，包括一小时之后；一个 3 小时 25 分钟的 URL 仍然能返回 `206`。这只能证明可以复用，并不代表它的有效期是无限的。2026-09-04，一个认证正确的缓存 URL 返回了 `400`，错误信息是 “Invalid Presigned Token”，而对同一个种子/文件重新解析后，得到的主机和路径都不同，并且能返回 `206`。它的查询参数没有变。只把旧的路径和查询参数换到新主机上，依然返回 `400`。

  24 小时的缓存仍然是出于预算的考虑：扫描以 20/分钟的速度解析，可能要花几个小时。现在，明确的无效 token 拒绝会让这个 URL 失效，并尝试重新解析。并发的读取者共享同一次解析工作，而且较晚到达的拒绝不会把一个更新的缓存 URL 删掉。如果重新解析得到的 URL 也被拒绝，播放会在本地暂停一分钟，但不会判定这个文件有问题。普通的 400 不能证明 URL 过期，只会触发一个短暂的冷却期。CDN 返回的 429 会保留 `Retry-After`，并让对该主机的读取在不同文件和校验调用之间都暂停；API 的预算则保持独立。
- **每次列表调用都带上 `bypass_cache=true`。** TorBox 自己的 `mylist` 缓存有大约 5 分钟的 TTL；如果一直用它的缓存，WebDAV 挂载就会比实际情况慢 5 到 15 分钟。这个参数不占用限速额度，能把同步延迟降到一秒以内。
- **一次轮询只拉取一次列表。** 库变化轮询是唯一会强制刷新的调用方，因为发现变化本来就是它的工作。同一轮里获取活跃数量的调用，以及变化之后的完整刷新，都直接读取它刚刚填充好的快照。如果这两处也强制刷新，每次轮询就要把整个库重复读取两三遍。默认的十秒间隔下，每天就是几千次多余的全库读取，而 zurg 本来就在绕过这个服务自己的列表缓存。
- **列表按每页 1000 条分页读取。** `mylist` 每次响应最多返回 1000 个种子，这是 `limit` 的文档默认值，请求更大的数字也不会提高上限。同时它既不返回总数，也不告诉你是否还有更多。因此，对于更大的账户，单次请求只会返回最新的 1000 个，看起来却和完整的库一模一样。zurg 会通过 `offset` 一直翻页，直到返回的一页不满为止，并在过程中按 id 去重：列表按 id 降序排列，所以在翻页过程中新增的种子会让窗口移动一位，并在分页的交界处重复一条记录。

## 账户限制 {#account-limits}

| 套餐 | 活动槽位 | 做种 | 最大种子大小 | 备注 |
|---|---|---|---|---|
| Free | 1 | 无 | 10 GB | 每 24 小时 1 次添加,每月 10 次添加,不支持私有种子 |
| Essential | 3 | — | 200 GB | 无冷却时间,无限缓存添加 |
| Standard | 5 | 2 周 | — | |
| Pro | 10 | 30 天 | — | 30 天到期 |

来源:[Account Restrictions](https://support.torbox.app/en/articles/9836418-account-restrictions)。

`/user/me` 以数字形式报告套餐,而且这些数字并不按价格排序:**0 Free,1 Essential,2 Pro,3 Standard**。Standard 是在 Pro 之后才加入的。在 2026-10-03 之前,zurg 把套餐 2 当作 Standard 处理,这导致 Pro 账户得到了 5 个槽位以及 Standard 的用量下限。

**活动槽位是 TorBox 最关键的限制**,而 Real-Debrid 的限制则是带宽。种子在下载*或做种*期间都会占用一个槽位,所以在付费套餐上,一个已完成的种子最多可以占用槽位 30 天。

### zurg 会做什么 {#what-zurg-does-1}

- **`GetActiveTorrentCount` 会报告套餐的真实上限**，它从用户记录上的 `plan` 读取。这样修复操作会阻塞并等待，而不是排队添加账户一定会被拒绝的种子。如果服务商没有报告上限，则视为无限制，而不是永远阻塞。
- **添加的种子默认设为不做种。** 做种会长期占用一个名额，还会计入上传流量，而这两点对流媒体挂载都没有帮助。`tb_seed_torrents` 可供需要按分享率计算的私有 tracker 运营者修改：`never` 发送 `seed=3`（默认值），`always` 发送 `seed=2`，`auto` 则不发送该字段。TorBox 对该字段的说明是 "1 is auto. 2 is seed. 3 is don't seed. Optional. Default is 1, or whatever the user has in their settings. Overwrites option in settings"，因此只要发送了任何值（包括 `1`），都会覆盖账户中的 Seeding 设置；只有不发送该字段时，账户设置才会生效。同一模式适用于全部三种添加路径：磁力链接添加、仅缓存添加和 `.torrent` 文件上传。开启做种后，已完成的种子会继续占用名额，一旦做种中的种子占满所有名额，修复操作和下载客户端接口就会被上限卡住。
- **添加前从不检查缓存。** `checkcached` 根本没有调用点。仅缓存模式（`qbittorrent.download_timeout_mins: 0`）原本是唯一的例外，现在改为和其他后端一样先添加种子并监控实例，因为该接口报告的是内容是否在 TorBox 缓存中，而不是这个账户最终是否会持有该内容。未命中时这会带来实际成本：未缓存的添加会消耗每小时 60 次的额度，而探测则不消耗任何额度。缓存添加仍然受每分钟 300 次预算的限制。

## 内容过期 {#content-expiry}

Pro 内容 30 天后过期。过期的种子从 API 返回时状态为 `expired` 或 `reported missing`，同时仍然带着 `download_finished: true` 和 `download_present: false`。

只看 `download_finished` 的话，就会挂载一个每个链接都会 404 的整个种子。zurg 把这两种说法都映射为 `error` 状态，`Capabilities.ContentExpires` 则把这种情况标记为该后端的正常现象，而不是故障。

**单看这两个布尔值，并不能说明数据已经没了。** 一个健康的未缓存下载，在生命周期的最后 9.6 秒里会报告 `download_finished: true` 和 `download_present: false`，同时它依次经过 `processing`、`downloading` 和 `uploading`。这是 2026-08-30 以 0.5 秒轮询间隔测得的，记录在 `docs/torrent-lifecycle.md` 中。以前 zurg 不管状态字符串是什么，都会把这对值当成种子已死，设置了 `delete_error_torrents: true` 的实例就会在下载中途把种子删掉。那一天就有五个探测种子因此被删。现在只有在负载完全没有 `download_state` 时，才由结构性规则来判断。代码还没见过的说法，会被当作仍在进行中的工作来处理，因为 `processing` 在被测量之前也属于这类说法。

如果读取仍然碰到这样的文件，开销就不止一次调用了。服务路径会把已生成投递 URL 的 404 视为链接被撤销，而不是文件缺失。在 Real-Debrid 上就是这样，它的链接会在 downloads 行被删除后失效。所以服务在放弃之前会重新解析，一个过期的 TorBox 文件每次读取最多会花费四次 `requestdl` 调用，而不是一次。这个次数在每次读取内有上限，而且列表已经把该种子标记为 `error`，所以不会有任何东西以这个速率遍历过期的库。但如果客户端反复访问同一个过期路径，成本会是以前的四倍。

### zurg 会做什么 {#what-zurg-does-2}

**没有任何东西会自动重新添加会过期的后端的种子。** 修复（repair）是通过重新添加磁力链接来修好损坏的种子。对于会保留内容的后端，这是修复；对于会让内容过期的后端，这就等于重新下载。如果在整个资料库上定时执行这个操作，TorBox 首先列出的、会导致账号被标记的原因就是这种行为："excessive transfer retention (using tools to artificially keep transfers active)"。而且每次未缓存的重新添加，都会算作一次计入套餐额度的传入传输。

所以，定时扫描会跳过那些可修复副本位于声明了 `ContentExpires` 的提供商上的种子。它们会保持损坏状态，并且仍然显示在面板上。面板上的修复按钮依然可以用。如果某个版本同时保存在 Real-Debrid 上，那么它仍会像往常一样从那个副本修复。区别在于是谁发起的操作，而不是哪里出了问题。

## 使用情况与滥用检测系统 {#usage-and-the-abuse-system}

TorBox 不会审查请求。它会统计滚动的 15 天窗口内传输的字节数，并与根据各套餐等级第 99 百分位数得出的阈值做比较。超过阈值时先警告三次，**每次警告都会轮换 API 密钥**，第四次则封禁。以下是已公布的下限，即这些动态阈值可能降到的最低值：

| 套餐 | 下限 |
|---|---|
| Free | 5 TB/月 |
| Essential | 10 TB/月 |
| Standard | 20 TB/月 |
| Pro | 30 TB/月 |

两个方向都计入：未缓存的添加（下载到 TorBox），以及 TorBox 发出的所有数据，无论是发给你的设备，还是回传给 P2P 节点。已缓存的添加不计入。计量是逐字节精确的，所以一个只读了一部分的文件，只计入实际读取的部分。

**`/user/me` 上的 `cooldown_until` 不是上面那些警告之一，把它当成警告会让你白白损失一天。** 我在 2026-08-12 于一个 plan-2 账户上做过验证，当时冷却刚生效（24 小时后到期，`updated_at` 是一分钟前）：`/user/me`、`checkcached` 和 `mylist` 都返回 `200 success:true`，WebDAV 的 `PROPFIND` 返回 `207`，而带范围的 `bytes=0-0` 读取在 2.8 秒内返回了 **`206`** 和正确的 `Content-Range`。每一层都没有拒绝服务。该账户的累计传输量只有 14.1 GB，远低于 30 TB/月的下限，所以这是 API 速率冷却，而不是流量违规警告。判别依据是**密钥**：真正的警告会轮换密钥，之后所有端点都会返回 `AUTH_ERROR`；而密钥完好的冷却则不会产生任何可观察的影响。另外，`checkcached` 可能会报告某个资源已缓存，而 TorBox 实际上并不会提供它，因此**带范围的读取是唯一能证明服务是否可用的探测方式**。在断定 TorBox 不可用之前，先检查字节读取路径。

来源：[The TorBox Abuse System](https://support.torbox.app/en/articles/10336778-the-torbox-abuse-system)。

### zurg 会做什么 {#what-zurg-does-3}

- **默认情况下，新添加的种子从不做种**，因此对于 zurg 只读取的内容，出站流量不会被计费。`tb_seed_torrents: always`（或在设置为做种的账户上使用 `auto`）是唯一能改变这一点的设置，并且其上传同样会被计费。

- **用量是通过采样并做差值计算的。** API 不提供滚动统计数据，只在 `/user/me` 上提供一个累计计数器，因此账户刷新器每 30 分钟把该计数器记录到 `data/torbox_usage.json`，并对采样结果做差值。当近 30 天的用量超过套餐下限的 80% 时，会记录一条警告。这条警告正是采样的意义所在——仪表盘只显示 zurg 自己代理的流量，从不显示这些差值。全新安装时没有历史数据，程序会明确说明这一点，而不会报告一个让人安心的零。

- **被拒绝的密钥会被报告为可能的滥用警告**，而不是配置拼写错误，也不是内容损坏——因为密钥轮换正是 TorBox 发出这类警告的方式，如果把它当成损坏，就会让整个库都需要修复。

## 刻意未映射 {#deliberately-unmapped}

An无法识别的 `download_state` 会被报告为 `downloading`，而不是 `error`。
当启用 `delete_error_torrents` 时，error 状态会让 zurg 从账户中删除种子，因此 TorBox 在本代码编写之后引入的新状态，绝不能导致删除操作。
