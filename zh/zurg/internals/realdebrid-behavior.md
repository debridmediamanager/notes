# 种子 {#torrents}

Real-Debrid 支持无限制地下载种子文件和磁力链接，你也可以选择要下载其中的哪些文件。
如果某个种子文件或磁力链接已经被其他用户下载过，它就被视为“已缓存”，Real-Debrid 会直接提供已缓存的链接。
如果没有缓存，它会尝试从公共 tracker 或 DHT/PEX 下载该磁力链接。
如果是包含 tracker 信息的种子文件，它会使用其中的 tracker 信息，这对私有 tracker 很有用（遗憾的是，很多私有 tracker 会屏蔽 Real-Debrid 的下载服务器）。
如果种子已经没有做种者或下载者，无法下载种子的全部分片，就会出现错误。
下载完成后，你还会得到类似 https://real-debrid.com/d/DOWNLOADCODE 这样的缓存链接。
DOWNLOADCODE 正好是该文件唯一的 13 位字符 ID（第 13 位之后的内容会被忽略）。

# 选择文件 {#selecting-files}

是的，如前所述，你可以只选择要下载的种子内文件。
如果一个种子包含文件 A、B 和 C，而你选择了 A 和 B，那么它只会下载 A 和 B。
种子的缓存状态其实取决于这种独特的文件选择。
回到包含文件 A、B 和 C 的种子，不同的选择会有不同的缓存状态：A、B、B（单独）、A+B、B+C、A+C（成对）或 A+B+C（全部文件）。
每一种独特的选择都会让种子重新从 tracker 下载，即使是同一个文件，也会返回不同的缓存链接。

# 缓存链接 {#cached-links}

缓存链接其实不能直接下载，它只是一个容器，里面装着 Real-Debrid 的下载代码。
你需要先 "unrestrict"（即把它转换成真正可下载或可串流的链接），这个链接在 Real-Debrid 上 7 天后会过期。
缓存链接的有效期超过 7 天。如果一个种子的缓存链接还能正常 unrestrict，就说明它仍然在 Real-Debrid 里处于缓存状态。
目前还不确定，但很可能是：如果有更多用户 unrestrict 同一个缓存链接，这个种子的缓存状态就可能被延长。

请注意，验证缓存链接是否有效的唯一方法，是先 unrestrict 它，然后用 Range 请求头检查转换后链接的第一个字节。
zurg 支持两种验证方式：默认的 HEAD（速度快），以及基于 Range 的方式（GET bytes=0-0，检查更彻底），通过 use_range_verification 配置项来切换。

# 跨账户共享缓存链接（2026-08-19 实测） {#cached-link-sharing-across-accounts-measured-2026-08-19}

Real-Debrid 返回的链接 ID 有两种长度：13 个字符（约 70%）和 16 个字符（约 30%）。多出来的 3 个字符决定了谁能解开这个链接：
- 截断到前 13 个字符后，一个 /d/ 链接可以被任何高级账户解开，而不只是生成它的那个账户。调用者的种子库不会受影响；唯一的副作用是在调用者的下载历史里多一条记录。
- 如果带着完整的 16 字符 ID 发送，同一个链接只能被生成它的账户解开。其他账户都会收到 "unavailable_file"，即使生成它的种子还在，即使调用者在自己的库里也有相同的 infohash，并且与 ip 参数无关。
所以在解开已保存的缓存链接之前，总是先截断到 13 个字符。用未截断的 ID 做测试，会错误地"证明"链接无法共享。

缓存链接在生成它的账户删除种子后仍然有效，但会因年龄而失效。大规模抽样显示：1 到 2 个月前生成的链接仍然都能跨账户解开；超过约 3 个月的链接则都返回 "hoster_unavailable"。另外，RD 可能会把内容本身从缓存中移除（一个哈希在一个月前被证明已缓存，下个月可能变成 downloading-from-0-seeders）。这时链接对所有人都返回 "unavailable_file"，包括生成它的账户。

解码已保存缓存链接的 unrestrict 错误：
- 13 字符链接 + hoster_unavailable -> 链接已过期；用相同的选择重新添加种子即可生成新链接（见下面的修复部分）
- 13 字符链接 + unavailable_file -> RD 已完全移除该内容；要获得新链接，需要从 seeders 真正重新下载
- 16 字符链接 + unavailable_file -> 这说明不了任何可用性问题：你只是不是生成它的账户；截断后重试即可

解开后的链接（*.download 主机 URL）由服务器端追踪绑定到 IP，而不是靠拒绝来限制。CDN 很乐意为外来 IP 返回 206，但 real-debrid 会记录下载 IP，同一账户的链接被多个 IP 使用会触发账户共享警告。因此请把下载者的 IP 传给 unrestrict/link（ip 参数），让链接为即将拉取数据的那个 IP 生成。

# 修复失效的缓存链接 {#repairing-broken-cached-links}

有时候，种子里某个文件的缓存链接，甚至解除限制后的链接，会突然失效。
这可能是 unrestrict API 报错导致的，也可能是解除限制后的链接返回了 HTTP 错误响应。
要解决这个问题，就得重新下载一次种子，生成新的缓存链接。
你可以先用完全相同的文件选择重新下载种子，看看能不能生成新的缓存链接。
如果还是不行，那就需要在这个种子上换一种文件选择方式。
比如，如果一个包含多个文件的种子里只有一个文件坏了，那就只选中这个坏掉的文件。
如果选中它之后还是返回坏掉的缓存链接，就再往选择里加入另一个文件。
一直这样重复，直到拿到新的、能正常使用的缓存链接为止。

# RAR 行为 {#rar-behavior}

Real-Debrid 有个行为：如果你选择了无法流式播放的不支持文件类型，它会把种子存成 RAR 文件（不压缩）。

已确认的视频文件类型：.avi .flv .m2ts .m4v .mkv .mov .mp4 .mpg .mpeg .ts .webm .wmv
已确认的音频文件类型：.mp3 .flac .m4a

在 Real-Debrid 中选择这些文件类型时，会得到可以流式播放的单独文件链接。
如果选择了其他任何类型，Real-Debrid 肯定会把它存进 RAR 压缩包。
如果你同时选择了 .mkv 视频和 .sub 字幕，它也会被打包成 RAR。
只选一张 .jpg 海报，同样会被打包成 RAR。

即使是多文件的种子，只要被打包成 RAR，也只会返回一个缓存链接（指向 RAR 文件）。
如果你只选择了已确认的视频/音频文件类型，就不会打包成 RAR，你选的每个文件都会得到一个缓存链接。

# 删除下载列表中的一行会撤销它生成的 URL {#deleting-a-downloads-list-row-revokes-the-url-it-minted}

2026-08-22 在测试账号上测得，每个用例只做一次 unrestrict。

一次 unrestrict 会在 /downloads 里生成一行记录，并在某个编号主机上生成一个 URL，例如 https://124-4.download.real-debrid.com/d/<13-char code>/<filename>。这个 code 不绑定主机：在该行被删除之前，同一个 code 在 44-4、125-4 以及它自己的 124-4 上都会返回 200。路径末尾的文件名段是可选的，zurg 会去掉它，两种写法的返回结果完全相同。

DELETE /downloads/delete/<id> 会撤销该 code，而哪些主机还能继续使用，取决于此前哪些主机提供过它：

  - 删除行时该 URL 从未被访问过：所有主机都返回 404，并带 X-Error: invalid_download_code。30 秒后仍然是 404，这个状态不会自行恢复。

  - 通过 44-4 访问过一次后再删除行：44-4 继续返回 200，而生成它的 124-4 和没被访问过的 125-4 都返回 404 invalid_download_code。

所以，访问会在提供服务的那台主机上激活该 code，而行记录则是让其他所有主机继续提供服务的关键。这与 downloads 列表清理功能最初所依据的假设恰好相反。这一点很重要，因为 zurg 会按请求选择下载主机（ensureReachableDownloadServer 会改写为 N 台最快主机之一）：验证用的 HEAD 请求落在哪台主机上，并不代表下一个请求会选中同一台。因此，行被删除后仍留在链接缓存中的解析结果，几乎会在之后的每次请求中返回 404 invalid_download_code。这看起来像链接已失效，于是把一个健康的版本标记为损坏。

删除后再次对同一链接执行 unrestrict，最终会在新主机上生成一个新 id，并且可以正常工作。id 不会被复用。

但并不是立即生效。第一次测量结论是"不受影响"，是因为测量时间离删除已过去几分钟。2026-08-23 在测试账号上重新测量：执行 DELETE /downloads/delete/<id> 之后，unrestrict/link 在 75 秒内持续返回同一个已失效的 id，直到 t+81s 才生成新的 id。

由此得出两点，并且都体现在代码中。downloadsCleanupMinAge 会在行被清理前保留两分钟，因此在这段时间内，另一个实例解析同一链接时仍能拿到有效的 code。而服务路径中的重新 unrestrict 链最多四次尝试、约六秒内完成，全部落在这个窗口之内。所以，即使这条链耗尽，也不能说明文件本身有问题：当每次解析返回的都是刚刚返回 404 的那个 URL 时，zurg 会拒绝这次读取并返回 Retry-After，而不是把该版本标记为损坏。
