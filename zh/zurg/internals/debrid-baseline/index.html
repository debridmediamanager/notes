debrid 基线

zurg 在 debrid 路径上的成本和速度如何，适用于 Real-Debrid、AllDebrid 和 TorBox。这里没有竞争对手。挑战者是之后的 zurg 版本，而这份文件就是它需要超越的基准。

  • 被测版本： 23869fa4（2026.08.18.0140-nightly-48-g23869fa4）
  • 测试时间： 2026-08-19，在 zen 上（2 核，7.6 GB，Ubuntu 22.04）
  • 测试环境： scripts/dbench/，部署在 zen 上的 ~/dbench

如何阅读

这三个服务商也不是三个相互竞争的对手。它们的库大小相差两个数量级：Real-Debrid 上有 3416 个种子，TorBox 上有 479 个，AllDebrid 上只有 14 个。所以单看冷构建耗时的绝对值，说明的更多是账户本身，而不是 zurg。

因此，所有与库大小相关的数字都会同时给出每个种子的平均值。真正有参考价值的比较，始终是同一账户上，这次构建与下一次构建的对比。

真正可以跨服务商比较的，是成本的形态：每个种子后端需要多少次 API 调用，是否需要为链接验证付出开销，以及它的变更轮询是按页还是按令牌进行的。

配置

每个实例运行一个 provider，使用自己的端口和自己的数据目录。与发布默认值的差异，只有隔离所需的那些：

Setting Bench Why
host / port 127.0.0.1, 9991-9994 四个实例跑在同一台主机上
providers 每个实例一个 把开销归到某个后端上
rclone_enabled false 通过 HTTP 测量，从不经过 FUSE
directories 一个 all，不加过滤 列表开销就只取决于库的大小
enable_repair false 另一个 zurg 加载了同一个 TorBox 账号，而一个账号只能由一个实例负责修复

其余设置都保持发布默认值，这是刻意的，其中包括两项会严重影响数字的设置，它们本身也是测试结论的一部分：

  • log_level: DEBUG，即发布默认值（pkg/logutil/factory.go）。
  • torrents_rate_limit_per_minute: 75，即发布默认值，也是冷启动 Real-Debrid 构建时真正的瓶颈。

语料库

十二个资源,三个账号上的信息哈希完全相同,所以不同服务商之间的差异来自服务商本身,而不是文件。大小从一集 1.5 GB 到 334 GB 的 remux 合集不等。形式包括单文件电影、整季合集,以及一个 349 个文件的剧集合集。条目 0 The Shawshank Redemption (1994) DS4K(7.31 GB,单文件)是延迟和吞吐量测试阶段用来串流的对象。

组装这批数据比较麻烦,值得记录下来。TorBox 的缓存和 Real-Debrid 库大约有 2% 的重叠(136 次探测里命中 3 次),所以语料必须从 TorBox 那边入手,而不是 Real-Debrid。AllDebrid 上一个都没有,但磁力链接都是立即接收的,16 个里成功了 14 个。Real-Debrid 每次添加之间需要等 20 到 45 秒,否则会触发 451 限流。它还拒绝了两个:一个是文档中记录的确定性名称屏蔽(Supergirl…WEB-DL…),在安静了三分钟之后第一次尝试就被干净地拒绝;另一个则一直处于限流状态。

测量 API 成本

zurg 不会记录出站请求计数，而 log_requests 有意跳过了两个 Real-Debrid 端点——torrents/activeCount 和 torrents?limit=1&…——它们合起来正是整个变更检测轮询。如果从日志统计，就会把 Real-Debrid 的空闲开销报告为零。

所以计数要在进程之外进行。mitmproxy 负责终止 TLS，一个插件会为每个请求写入一行 JSONL，实例启动时设置 HTTPS_PROXY 和 SSL_CERT_FILE，指向用于拦截的 CA。Go 的 x509 加载器会遵循 SSL_CERT_FILE，因此信任范围仅限该进程，宿主机上的任何内容都不会被修改。请求会被分类为 api、nettest、content 或 other。

代理位于请求路径上，所以只在 API 开销阶段使用；计时阶段则直连运行。在 TorBox 上——整个构建只有四次调用——走代理的运行和直连运行分别为 3.0 秒和 4.0 秒，所以在这个规模下，代理的开销已经淹没在误差范围内。

结果

All numbers from build 23869fa4 on zen, 2026-08-19. Latency and throughput come from one interleaved run over the same 7.31 GB file — same infohash on all three accounts, and ffprobe reports the identical 8552.574 s duration through each, so the content really is byte-identical.

失败的是什么

第二次运行保留了流程日志，所以这 699 次有一份细分：

状态 次数 端点
429 589 unrestrict/link
503 85 unrestrict/link
404 22 downloads/delete/{id}
451 3 unrestrict/link

这是两个各自独立的问题，都不是"服务商不稳定"那么简单。

  • 589 次限流拒绝，全部发生在 unrestrict/link 上。api_rate_limit_per_minute 默认为 250，但它无法把 unrestrict 的请求控制在 Real-Debrid 实际允许的范围内，所以冷构建中大约 8% 的请求都是被拒绝后再重试。
  • 23 次 downloads/delete 调用中有 22 次返回 404。 本来用来抵消 3,992 次 unrestrict 的清理操作，不只是偶尔失败，而是每次运行都会失败，它删除的是不存在的 id。每次 unrestrict 都会在账户的 downloads 列表里留下一条持久记录，经过这些扫描后，测试账户上已经积累了 12,469 条。

有一个数字在两次运行之间发生了变化，目前还没有解释清楚：对 *.download.real-debrid.com 的 HEAD 探测，第一次构建是 88 次，第二次是 3,426 次（大约每个种子一次）。它与 downloads 列表的增长相关，而且第二次运行调用 /downloads 的次数是第一次的八倍（8 次对 1 次），但这只是相关性，不是原因。在进行优化之前，值得先把它弄清楚。

热重读的速度和冷读一样。 在 Usenet 路径上，重复读取从 512 MB 的 LRU 缓存中返回，只需 0.05-0.17 秒；而这里每次都要完整拉取一遍，因为 debrid 路径是代理 CDN 的，本身不做任何缓存。 当 rclone_enabled: false 时，这就是 zurg 独自在干活。在常规安装中，rclone 的 VFS 缓存会把这部分吸收掉；但就 zurg 本身而言，根本没有热路径。

提供商中断，CDN 正常

ca/outage.py 会让每个服务商 API 调用都返回 503，同时放行内容请求，然后在这种状态下启动 zurg。

  故障前读取 故障期间编译的库 故障期间读取
Real-Debrid 206, 1.60 s 从不（180 s） 120 s 超时
AllDebrid 206, 0.44 s 从不（180 s） 120 s 超时
TorBox 206, 1.53 s 从不（180 s） 0.035 s 内返回 400

在服务商宕机时启动 zurg，会得到一个空挂载。 这是运维中最需要关注的场景，比如主机在 Real-Debrid 出现 503 期间重启。八月份在 fun 上导致数万个 Plex 条目被删除，正是这种情况：扫描时挂载短暂为空，Plex 会误以为"所有文件都被删除了"。针对这种情况的防护措施在 Plex 里（autoEmptyTrash 0），而不在 zurg 中。

此外，Real-Debrid 和 AllDebrid 会让读取端一直等到自身超时，而不是快速失败；TorBox 则在 35 ms 内就返回了响应。

瞬时 503 会让发布变成空文件夹

这次运行里最明显的问题是我偶然发现的。

在 Real-Debrid 的冷构建中，3,316 个 torrent 里有 85 次响应为 503，84 个 torrent 最终进入 broken_torrent 状态。处于这种状态的资源仍会显示在挂载中，但其目录是空的。我用 PROPFIND 验证了其中两个，它们的存储记录里分别有 10 个和 3 个已选文件，但目录里一个都没有。

这个问题不会自己消失。测试台运行时设置了 enable_repair: false，这些资源在超过一小时、重启了好几次之后仍然是损坏状态。

开启修复（出厂默认值）确实能处理它们，但速度很慢。手动触发一轮修复后：

已用时间 损坏数 正在修复
0 分钟 85 0
约 2 分钟 77 2
约 15 分钟 73 4

十五分钟只修复了 12 个资源，而且头几分钟之后速度明显下降。照这个趋势，一次冷构建产生的损坏资源要一个多小时才能清完，而在此期间，每个还没轮到的资源都是一个空文件夹。

所以严重程度取决于设置：

  • 开启修复（默认）时，扫描期间出现的一次 503 会让资源丢失文件，直到修复轮次处理到它为止。对于完整的库，大约需要一小时。
  • 关闭修复时，资源会一直是空文件夹。

TorBox 的情况更严重。它返回 StoredLinksCanRot: false，所以刷新永远不会重新验证它的链接。除了修复，没有任何途径能清除损坏状态。在故障测试中被标记为损坏的那一个 TorBox 资源，在 68 分钟和好几次重启之后仍然是损坏状态，但服务商那边显示它是 cached、download_present，只有一个文件，大小 7.31 GB。

读取完整性

在第一轮吞吐量测试中，一次 AllDebrid 读取对 268,435,456 字节的范围只返回了 263,798,425 字节，但返回的是 206，也没有报错。这个问题没有复现：Real-Debrid 和 AllDebrid 各重复了八次，每次都返回了完整范围。我把它记为偶发情况，而不是缺陷，但值得留意。

Plex 负载下的表现

我们前面测的都是单个读取者，但媒体服务器的实际工作方式并非如此。Plex 会一边扫描——成千上万个文件，每个只读一点——一边播放，两者是同时进行的。这些阶段测的就是挂载点在这两种负载下的表现。

请把总吞吐量数字理解为 zen 主机的特性，而不是 zurg 的特性。 无论使用哪个服务商、哪种模式，每个目标都稳定在 73–78 MB/s，这是主机的网络带宽上限。真正具有普遍参考价值的是完成率以及各服务商特有的失败模式；吞吐上限是本地环境造成的。

AllDebrid 在四个并发的不同文件上就停止完成读取了。 数据仍在传输，它的总量也稳定在主机上限，但单个流无法结束。在八个和十二个流时，单流 TTFB 中位数超过 3 秒，单流中位数降到零。其他服务商一直到十二个流才有问题，那时四家都会丢掉一两个。

2026-08-23 撤回。这不是服务商的并发限制。 我们改为直接请求各家 API，并使用受速率限制的播放码率重测，而不是通过 zurg 满速拉取。这次 AllDebrid 对 4/8/12/16/24 个并发的不同链接 都解析成功，成功率 100%，并稳定维持 24/24 个实时流。上面的失败其实来自 三个空路由的 AllDebrid CDN 主机：l4m5n6.debrid.it、o7p8q9.debrid.it、c1uw74.debrid.it。它们都解析到 0.0.0.0，承载了 15.6% 的已解析链接。第一个主机，就是本文后面记录为一次性失效链接的那台，它并不是偶发的。

只有当失效主机上的文件出现在批次里时才会失败，因此失败数会随 N 增加而上升，表现得就像并发上限。任何随着并发增加而抽取更多不同文件的测试阶梯，都会复现这个错误结论。

这一整列完成率也受测试方法限制，原因相同：这些测试是在 73–78 MB/s 的饱和链路上满速拉取的，所以它衡量的是带宽份额，而不是服务商限制。真正的单主机上限（目前都没有公开文档）是：Real-Debrid 32（在 TCP 层被断开）、AllDebrid 32（HTTP 429）、TorBox 每个 nexus-NNN 主机 20（HTTP 429，按主机计，而不是按 IP 计），Premiumize 在 64 时未发现上限。

对于撤回结论也不要过度解读：空路由主机大约 0.1 秒就失败，而上面的 TTFB 中位数超过了 3 秒。这是一种表现不同的慢失败，所以带宽饥饿很可能也存在。两种情况都说明问题不在服务商的上限。

由此得出的修复方法： 把 AllDebrid CDN 主机上的连接级失败当作可重试的错误，重新解锁链接，因为新的 /link/unlock 会返回不同的主机，而不是降低并发。DNS 查询发现 0.0.0.0 时直接拒绝，就能覆盖这里看到的所有情况，而且几乎没有额外成本。

多个读取者，同一文件

同样的并发数，同一个文件，不同的偏移量，也就是预读加跳转的模式。

流数 Real-Debrid AllDebrid TorBox
4 4/4 4/4 4/4
8 8/8 8/8 8/8
12 10/12 9/12 10/12

AllDebrid 在这里没问题，4/4 和 8/8 都正常，而在不同文件时它是 2/4 和 3/8。 这种反转就是诊断结果：它的限制不是带宽，也不是单个种子的上限， 而是并发的链接解析。不同文件意味着不同的解锁；同一个文件只解析一次，之后就只管播放。

2026-08-23 已撤回：这种反转有更简单的解释。不同文件会分到不同的 CDN 主机，而 AllDebrid 的其中三台被 null-routed 了；同一个文件只会解析到一台主机，要么能用，要么不能。链接解析本身在 24 个并发下测试是正常的。参见上面的说明。

多个读取者跨越不同提供商

这是混合提供商的情况，它需要一个 matched 语料无法提供的语料库。由于合并后的实例会从 Sources[0] 提供一个多账号的版本，matched 语料的每次读取最终都会落到 Real-Debrid 上。因此这里的池是 provider-exclusive（独占）：8 个文件只有 Real-Debrid 有，7 个只有 AllDebrid 有，8 个只有 TorBox 有。

流数（每个提供商） 总吞吐 MB/s 完成 RD AD TB
3（每个 1 个） 55.3 2/3 28.8 — 27.9
6（每个 2 个） 66.9 5/6 16.1 13.3 21.5
12（每个 4 个） 75.9 11/12 7.4 8.4 9.0

每个提供商列都是每条流的中位数，单位为 MB/s。

不同账号上的读取确实会并行运行，但它们都会遇到同一个 76 MB/s 的主机上限，而单个提供商自己就能达到这个速度。在这台主机上，混合后端并不能增加带宽。 在其他地方是否能增加，取决于是否有一条比单个提供商能跑满的更粗的链路，而 zen 没有。混合后端带来的是可用性，而且只是部分的，下面的故障转移一节会说明。

始终复现的那一个故障是一个 AllDebrid 文件，它的 CDN 主机名 l4m5n6.debrid.it 解析到 0.0.0.0。这是 AllDebrid 给出了一个失效的链接，不是 zurg 的问题。但 zurg 会在三次重试上花大约 4 秒，然后返回 500。由于这个文件不在其他任何账号上，没有可以回退的地方。

故障转移：仅单向

由于合并后的实例无法分担负载，它真正要解决的是某个账号出问题时的生存能力。ca/cdnfail.py 只会屏蔽某个账号的 CDN，其他 API 和其他账号都不受影响，所以库依然能加载，受影响的只是文件数据。读取的内容是匹配的语料，三个账号都有这些内容。

CDN 被屏蔽 成功的读取 读取的结果
Real-Debrid 2/2 回退到 AllDebrid，耗时 0.6 秒
AllDebrid 0/3 对 AllDebrid 尝试了一次，返回 503，然后在 0.1 秒内向客户端返回 500

只有当出问题的账号是 Real-Debrid 时才会发生故障转移，原因是其他后端没有设置某个能力。只有 StoredLinksCanRot 为 true 时，刷新才会主动验证链接，而这一点只有 Real-Debrid 满足：

Link verification failed during refresh for /A.Business.Proposal…: (code: 503)

正是这一步把源降级，之后读取才会干净地切换到其他账号。AllDebrid 和 TorBox 从不被探测，所以它们的 CDN 失效时没人会注意到，源不会被降级，该内容的每次读取都会返回 500，直到问题解决为止。

这还说明了另外两件事：

  • 读取路径完全没有内联回退。 所选账号的 CDN 返回的 503 会在 0.1 秒内直接变成给客户端的 500，同一文件所在的其他账号根本不会去尝试。恢复完全依赖后台刷新，所以即使是 Real-Debrid 的情况，也存在一段读取失败的时间窗口。
  • 这和那个卡在 broken_torrent 状态 68 分钟的 TorBox 内容是同一个缺失机制导致的。没有任何东西会重新验证 TorBox 或 AllDebrid 的链接，因此既不会清除错误状态，也不会察觉恢复过来的状态。

提供商返回的失效链接

一个在独占池（exclusive pool）里的 AllDebrid 文件，每次被访问都失败了，每轮扫描和每次 mixed-reader 运行都是如此。它的 CDN 主机名被解析到一个空路由：

$ getent hosts l4m5n6.debrid.it
::              l4m5n6.debrid.it
0.0.0.0

AllDebrid 给出的链接指向 0.0.0.0。这部分是服务商的问题，不是 zurg 的问题。zurg 的部分是它之后的处理：大约 4 秒内尝试三次，然后返回 500。这个文件在其他账户上也没有，所以无处可退。不过上面的故障转移结果表明，即使有其他选择，它也不会切换过去。

2026-08-23：不是一个主机，也不是一个文件。 同一时间有三个 AllDebrid CDN 主机名被设为空路由：l4m5n6.debrid.it、o7p8q9.debrid.it、c1uw74.debrid.it。在一个样本里它们占了 32 个链接中的 5 个，在另一个样本里占了 32 个中的 4 个，而且涉及的内容彼此无关。AllDebrid 会把同样的失效主机分给不同的文件，直到这次运行之后好几天仍是如此。这是它服务器群里一个持续存在的漏洞，也正是导致上面那条（已撤回的）并发结论的原因。

三次尝试加一个 500 是错误的做法。改为重新解锁：/link/unlock 会返回另一个主机。并且在发起请求前先做一次 DNS 查询预检，拒绝解析到 0.0.0.0 的结果。这样做没有额外成本，就能拦住目前观察到的每一种情况。

扫描

ffprobe 作用于整个 23 个文件的混合池，这相当于 Plex 的分析过程。

concurrency files/min per-file median per-file max CPU s
1 43.7 1.16 s 3.11 s 2.22
4 112.0 1.67 s 4.19 s 1.29
8 142.3 1.87 s 6.67 s 1.16

扫描非常适合并行处理：从 1 个线程增加到 8 个线程，速度提升了 3.3 倍，而单文件延迟只增加了 60%。对于 3,316 个 release 的 Real-Debrid 库，在 1 个线程时大约需要 76 分钟，8 个线程时大约需要 23 分钟，这还不包括 Plex 自身的处理时间。

扫描时的串流

最需要担心的情况，是一次扫描撞上了暂时不正常的挂载点。fun 上丢失的数万个 Plex 条目，就是这样造成的。

scan concurrency stream alone stream during scan kept scan wall
4 57.7 MB/s 66.5 MB/s 115% 11.8 s
8 67.8 MB/s 66.8 MB/s 98.5% 9.7 s

扫描不会饿死串流。 观看者几乎保留了全部吞吐量，而且首字节时间（time-to-first-byte）反而更好了，从 1.18 秒降到 0.15 秒，因为那时链路已经预热好了。这是 debrid 路径表现比预期好的唯一一处。

本次运行发现的缺陷

  1. 瞬时的 503 会让一个发布变成空文件夹。 一次冷启动构建中，85 个 503 把 84 个发布放进了 broken_torrent，而损坏的发布会显示为没有任何文件。关闭修复时，它永远不会恢复；开启修复时，只有修复任务轮到它时才会恢复。TorBox 完全没有重新校验的途径（StoredLinksCanRot: false），那里唯一损坏的发布在 68 分钟后仍然损坏，而服务商却报告它已缓存且存在。

  2. 下载条目的清理坏了，代价还在不断累积。 unrestrict/link 调用了 3,992 次，downloads/delete 只调用了 23 次，其中 有 22 次返回 404，也就是清理删的都是不存在的 id。在另外两次冷启动构建中，账户里的条目从 12,469 涨到了 18,768。而 zurg 启动时会每次分页拉取 5,000 条整个列表，所以泄漏最终变成了启动开销，并且随着条目增多而越来越大。

  3. 一次冷启动构建里有 589 次限速拒绝。 全部发生在 unrestrict/link 上，约占整个任务的 8%。默认的 api_rate_limit_per_minute: 250 无法把 unrestrict 控制在 Real-Debrid 的真实限制之内。这些限速拒绝和前面的 503 是同一件事，也正是缺陷 1 的成因。

  4. 在服务商故障期间启动，会得到一个空挂载点。 之后对 Real-Debrid 或 AllDebrid 的读取会一直挂起，直到客户端自己的超时才结束，而不是快速失败。TorBox 则在 35 毫秒内就返回 400。

  5. AllDebrid 在并发读取不同文件时会停止完成。 2026-08-23 撤回，请参阅上面"Multiple readers, different files"部分中的说明。 原因是有三个被空路由的 AllDebrid CDN 主机承载了 15.6% 的链接，而不是并发限制；我直接重新测试后发现，AD 能以 100% 的成功率同时解析 24 个不同的链接，并能持续维持 24/24 路流。下面保留原文以作记录。

    2 of 4, 3 of 8, 4 of 12。在单个文件上，同样的并发数量是正常的（4/4、8/8），所以限制来自并发的链接解析，而不是带宽或单个种子的上限。对一个家庭来说，同时播放四个文件是再普通不过的晚上了。

  6. 多账户发布总是从同一个账户提供服务。 File.PrimarySource 返回的是 Sources[0]，所以选中的总是最先出现的那个账户。验证结果是：语料库中的 7 个发布全部由 Real-Debrid 提供服务，而 AllDebrid 和 TorBox 明明各有一份完全相同的副本。它从不会挑选更快或负载更轻的账户。

  7. 故障转移只在一个方向上有效，而且从不在请求过程中进行。 当 Real-Debrid 的 CDN 拒绝服务时，读取会切换到 AllDebrid；但当 AllDebrid 拒绝服务时，3 次读取中有 0 次成功，每次都在 0.1 秒内返回 500，却不会去尝试另外两个持有同一文件的账户。只有 Real-Debrid 设置了 StoredLinksCanRot，所以只有它的链接会在刷新时被重新校验，也只有它的失败会把某个来源降级。读取路径中，没有任何一处会在出错时尝试第二个账户。

  8. 启动时的网络测试会对每个后端都运行一次。 在只使用 TorBox 和只使用 AllDebrid 的实例上，它都会对 Real-Debrid 下载主机发出 88 次 HEAD 请求，而这些实例根本用不到这个结果。

  9. 集合自身的 PROPFIND href 返回 404。 zurg 输出的是 <d:href>/all/…</d:href>，漏掉了 /dav 前缀；访问该路径会返回 404。子项则以裸的相对 href 输出，所以只有自身条目是错的。RFC 4918 要求 href 是客户端能够解析的，而 rclone 和 Plex 之所以还能用，只是因为它们没有用到这个值。

  10. user/user/me 在每次启动时都会被调用三次，无论冷启动还是热启动，TorBox 和 AllDebrid 都是如此。

并非缺陷，但值得了解

  • Real-Debrid 不会按 infohash 去重。 如果添加一个账号里已有的磁力链接，会生成一条新的条目。这就是为什么 3,416 个种子只对应 3,318 个唯一发布版本。这也让第一次删除检测测试失效了：它删掉了刚刚创建的重复条目，于是得出结论说从来没有检测到任何删除。
  • torrents_rate_limit_per_minute 默认为 75，这是限制冷启动 Real-Debrid 构建速度的参数。这是一个有意设定的默认值，不是 bug，但它决定了 29 分钟这个数字。
