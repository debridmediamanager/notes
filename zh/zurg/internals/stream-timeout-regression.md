# 代理流超时回归 {#proxied-stream-timeout-regression}

## 摘要 {#summary}

zurg 把 `download_timeout_secs` 当成代理 HTTP 下载的总时长上限来用。它的默认值是 15 秒，所以只要某个上游响应的正文超过 15 秒才传完，就会被截断，哪怕数据一直在正常传输。

这个问题在 2026-08-21 于 Discord 上报，版本是 `2026.08.21.0151-nightly`（`fc2a21f`）。通过 zurg 反复请求 2 GB 的范围数据时，在传过去约 1.26 GB、速度约 84 MB/s 的时候，于 15.001 秒被切断。同一段范围直接从 Real-Debrid 下载是能完成的。把 `download_timeout_secs` 调到 3600 后，通过 zurg 的请求 25.8 秒就完成了。

这是 zurg 自身的回归问题，不是内容过滤、CDN 故障，也不是 `fc2a21f` 引入的回归。提交 `6edeaa8c`（`Optimize client`，2024-11-17）引入了它。普通的代理播放路径已经由 `41db7245` 修复，之后 `eff972b8` 又让同样的错误在提供商 API 边界处难以再次出现。

## 对用户的影响 {#user-impact}

受影响的路径是：zurg 从基于 HTTP 的 debrid 提供商代理的任何响应体，只要其连接保持打开的时间超过 `download_timeout_secs`。Real-Debrid 从 2024 年 11 月起受到影响。TorBox 和 AllDebrid 在被添加时也继承了同样的行为。本地提供的 NZB 读取从未经过 HTTP 下载客户端，因此不受影响。

用户能看到的症状包括：

- Infuse 或其他直连 WebDAV 客户端在播放时卡住；
- 拖动进度条后，发出新的范围请求，播放随之失败；
- 尽管收到了 HTTP `206 Partial Content`，下载仍提前结束；以及
- 客户端报错，看起来像是媒体文件或 CDN 的问题，但直接请求却能正常完成。

播放器不一定在播放开始 15 秒后就失败。按报告中的 84 MB/s 计算，截止时间前 zurg 大约传输了 1.26 GB。播放器可能要消耗这些缓冲数据好几分钟才会耗尽，所以原本精确的 15 秒网络截止时间，看起来就变成了时长不定的播放卡顿。

## 根本原因 {#root-cause}

Go 的 `http.Client.Timeout` 是整个请求生命周期的截止时间，不是空闲或停滞超时。计时从请求开始时就启动，并且在读取响应正文期间一直持续，不管这期间是否有数据在传输。

在 `6edeaa8c` 之前，下载客户端本身没有整个请求的超时设置：

```go
client: &http.Client{}
```

`download_timeout_secs` 通过传输层的拨号器和 `ResponseHeaderTimeout` 限制连接和响应头阶段。响应正文到达之后，服务端可以按下游客户端的需要一直读取下去。

`6edeaa8c` 重组了 HTTP 传输层，把配置的超时加到了客户端本身上，同时移除了 `ResponseHeaderTimeout`：

```go
client.client = &http.Client{
    Transport: transport,
    Timeout:   time.Duration(timeoutSecs) * time.Second,
}
```

这改变了原有 15 秒这个值的含义。它依然保护连接阶段，但现在也对响应正文施加了一个绝对截止时间。服务端本来就通过这个客户端获取媒体，所以这个回归在改动合并的那一刻就生效了。

这个故障很隐蔽。zurg 先把成功的上游状态码和响应头发给了 zurg 的下游，然后才把正文复制给播放器。当客户端的截止时间打断了正文传输时，复制操作返回了错误，但服务端代码丢弃了这个错误：

```go
n, _ = copyBuffered(resp, body)
```

到这时，`206` 响应已经提交，无法再换成错误状态码。日志记录关闭时，没有任何地方报告正文为什么提前结束。因此，下游客户端看到的是一个成功的部分内容响应，但正文在声明的长度之前就结束了。

## 回归历史 {#regression-history}

相关提交组成了一条比报告问题的那个 nightly 更长的链条：

| 日期 | 提交 | 影响 |
|---|---|---|
| 2024-06-28 | `c3aea427` | 将现有的服务读取改为经由 `DownloadFile`。这一改动保持了原有行为，因为下载客户端当时还没有整个请求的超时设置。 |
| 2024-11-17 | `6edeaa8c` | 为下载客户端添加了 `http.Client.Timeout`。正是这个回归开始截断普通的代理响应体。 |
| 2026-02-26 | `dea98d34` | 正确诊断出 RAR 压缩包读取遇到了同样的 15 秒截断，添加了一个无超时的流式客户端，并且只把 RAR 路径迁移到了它。普通文件服务仍然保留在 `DownloadFile` 上。 |
| 2026-08-02 | `e9318e66` | 将下载功能移到了多提供商的 `debrid.Provider` 接口后面，并原样保留了普通服务的调用。它并没有引入 Real-Debrid 的这个 bug，但新的基于 HTTP 的提供商继承了这个不安全的方法。 |
| 2026-08-21 | `fc2a21f` | 报告中使用的那个 nightly。它包含这个 bug，但并不是它引入的。 |
| 2026-08-21 | `41db7245` | 将普通代理播放改为使用 `DownloadFileStreaming`，并添加了第一个端到端的超时回归测试。 |
| 2026-08-21 | `eff972b8` | 将每个 HTTP 提供商的 `DownloadFile` 都改为无超时，作为结构性的防护措施，并把覆盖范围扩展到 Real-Debrid、AllDebrid、TorBox 以及一个 NZB 对照组。 |

二月那次 RAR 修复是一次很重要的险些漏掉的情况。它的提交信息明确写到，`http.Client.Timeout` 会覆盖响应体，而 15 秒的默认值正在杀掉 RAR 流。诊断本身是正确的，但修复只限于 RAR 读取器。由于 `DownloadFile` 和 `DownloadFileStreaming` 两个方法并存，普通服务路径又保留了这个不安全的选择，一直持续了六个月。

## 为何长期未被发现 {#why-it-stayed-hidden}

以下几个因素让这个回归问题隐藏了大约 21 个月:

1. 大多数媒体服务器部署通过 rclone 而不是直接使用 WebDAV 读取 zurg。rclone 使用有界的范围请求。当前托管挂载的默认值从 4 MB 起步,最高增长到 512 MB 上限,因此在网速快的情况下,许多单独的上游请求都能在 15 秒内完成。这降低了问题暴露的概率,但并没有让这条路径变得安全,在较慢的网络上尤其如此。
2. 像 Infuse 这样直接使用 WebDAV 的客户端可能会发出很大的或不设上限的范围请求。这些请求会让一个上游响应保持打开足够长的时间,从而稳定地触发超时。这也是 Discord 上的复现在三个不同偏移量下都完全一致的原因。
3. 播放缓冲掩盖了原因和现象。上游请求在 15 秒时断开,但播放器要等到已经收到的字节被消耗完,才会真正停止。可见的卡顿时长会随码率、缓冲和拖动进度而变化。
4. 响应看起来是成功的。CDN 返回了有效的 `206`,zurg 将其转发出去,而在响应头已经发送之后,正文复制时的错误被忽略了。直接测试 CDN 时一切正常,普通日志中也没有超时错误。
5. 调高设置似乎解决了问题。这让缺陷看起来像是一个设得太小的调优值,而不是一个绑定在错误抽象层上的超时。
6. 现有测试使用的正文或范围都能在配置的超时时间内完成。没有任何测试刻意让响应正文在超过截止时间后继续传输,然后通过服务路径断言完整的长度和校验和。
7. 针对 RAR 的那个小修复消除了之前最明显的表现,但并没有去掉普通下载中那个不安全的默认值。

## 为何提高超时看似能解决问题 {#why-a-higher-timeout-appeared-to-fix-it}

把设置改为 3600 秒，并没有改变这个超时所覆盖的范围。它只是把整体的截止时间推迟到足够远，让报告中那次 25.8 秒的传输能够完成：

```text
15 seconds   < 25.8-second transfer < 3600 seconds
```

这只是一个变通办法，不是安全的修复。任何有限长度的整请求超时，仍然可能切断足够长的响应体，比如客户端很慢或连接被暂停的情况。这个设置还会用于下载客户端的拨号超时以及有界的验证请求，所以把它调到一小时，会让一个无法连接的主机要花更长时间才会失败。修复后的版本应使用正常的配置值；它不再限制代理的媒体响应体。

## 修复与防护措施 {#fix-and-guardrails}

`41db7245` 中的临时修复把 `streamFileToResponse` 改为通过 `Provider.DownloadFileStreaming` 获取内容。这个客户端与原来共用同一个传输层，但没有 `http.Client.Timeout`，所以响应体的存活时间不再受 `download_timeout_secs` 限制。请求仍然使用下游请求的 context，因此播放器断开连接时会取消上游读取。建立连接和 TLS 握手仍然由传输层设置的超时来限制。

`eff972b8` 随后去掉了对调用方通过方法名中是否带有 "Streaming" 来选择方法的依赖：

- Real-Debrid 的 `DownloadFile` 现在使用 `DoStreaming`。
- 共享的 `debrid.DownloadRanged` 辅助函数接收 `StreamingDoer`，它只暴露 `DoStreaming`。AllDebrid 和 TorBox 都使用这个辅助函数。
- 因此，两个提供方的下载方法都可以安全地返回较长的响应体。
- 对于有界的非播放读取，例如计算 OpenSubtitles 哈希时读取的两次 64 KiB，现在会使用各自显式设置的 context 截止时间，而不再借用不安全的客户端级响应体超时。

回归测试位于 `internal/universal/stream_timeout_test.go`。测试使用一个本地服务器，在大约 1.6 秒内分 16 个块发送 1.6 MB 的响应体，而配置的超时时间是 1 秒。测试同时检查完整长度和校验和：

- 直接调用 Real-Debrid、AllDebrid 和 TorBox 这两个提供方的下载方法；
- 通过 `streamFileToResponse` 端到端测试三个基于 HTTP 的提供方；
- 通过一个类 NZB 的本地提供方作为不受影响的对照组进行测试。

这条不变量现在被明确写下来：返回下载响应体的方法绝不能使用整个请求的超时。短时探测和元数据读取应该在各自的 context 上设置截止时间；流式响应体则应一直保持，直到传输完成、下游取消或出现真正的传输错误为止。

## 按进度而非时间设限 {#bounded-by-progress-not-by-time}

只要请求没完成，就还留着一种读取永远不会结束的情况：分发节点保持响应连接不断，却不再继续发数据，或者干脆一直不回应。2026 年 9 月，一次 Plex 扫描在一个 Real-Debrid 文件上卡了十一个小时，而那次读取从未报错。这个客户端没有任何超时上限可以放弃它，而 rclone 的 `--timeout` 是空闲超时：zurg 以 256 KiB 为单位写入数据体，所以一个每五分钟才发 256 KiB、速度低于 1 KB/s 的节点，会不断重置这个计时器，永远不会触发。速度更慢的节点确实会触发超时，但 rclone 随后会对同一个节点重发同样的请求，每三次超时只记录一条错误。2026 年 10 月 3 日在 zen 上使用 rclone 1.75 和挂载自带的参数测量，遇到这类节点的读取在 30 分钟后仍处于阻塞状态。

`internal/universal/starved_read.go` 现在会在节点 30 秒内送来的数据不足 1 MiB 时切断代理读取，计时只算 zurg 在等待该节点的时间。这包括从请求建立连接到响应头到达的时间，以及读取数据体时每次读取的时间。写入客户端的时间不计入，所以上面的保证依然成立，暂停或慢速的客户端可以无限期保持流打开。被切断的文件会在两分钟内返回 `503`，这样 rclone 的重试会立即结束，而不是每次又等满一个窗口。本地提供的 NZB 读取不受监控。

压缩包内文件的读取从未经过 `streamFileToResponse`，所以在卡片 204 之前没有受这个上限约束。它们的字节来自每个分卷的部分区段，通过同一个客户端由 `providerDoer.Do` 获取，再由 RAR 解析器读取，因此只要节点保持连接，它就可以无限期占用这些读取。现在每次分卷获取都由同样的下限监控，一旦被切断，该条目会被拒绝两分钟。如果在列出压缩包时被切断，列表会直接失败，而不是让解析器把这个分卷当作损坏分卷而略过。在一个真实的五分卷集合上，之前就是这样，条目按完整长度返回，但第二个分卷之后的字节是错的。

卡片 222 发现，节点导致分卷读取失败的其他各种方式也有同样的问题：5xx、429、响应头中途断开的连接。解析器把这些都当成损坏的分卷，于是列出的压缩包缺了这个分卷，而且这个列表会被缓存。在同一个集合上，第 3 个分卷返回 503，会从偏移 16,057 处开始返回错误的字节，即使节点恢复之后仍一直这样。现在解析器会区分"字节没能解析"和"字节根本没有到达"的分卷。后者用 `rarstream.ErrVolumeUnavailable` 表示，`HTTPSrc` 会为它看到的状态码打上标记，`providerDoer` 会为远程读取失败的所有情况打上标记，NZB 数据体则会为其读取器归类为传输错误的情况打上标记。遇到后者，列表会失败，包括嵌套集合和分卷头分组的情况，失败时返回带 `Retry-After` 的 `503`，不会被缓存为压缩包失败，不会被记为结论，也不会在浏览时用原始分卷代替压缩包内容返回。损坏或缺失的分卷仍像以前一样被跳过列出。

上面提到的 256 KiB 写入也在卡片 204 中改掉了。节点快的时候，复制仍会把缓冲区填满，所以快速的数据体仍像以前一样以整块缓冲区发送；但首批字节一到达就会立刻发出，并且任何字节都不会被保留超过 250 ms（`internal/universal/downloader.go` 中的 `defaultCopyFlushAfter`），同时刷新响应。慢速节点不会再阻止客户端拿到响应头。在此之前，在 zen 上通过 rclone 和挂载自带的参数测试时，一个压缩包条目所在的节点每四分钟先发 64 KiB 再发 16 KiB，而 rclone 恰好在五分钟时放弃，连续三次，结果 rclone 什么都没收到：节点已发送的所有数据都还留在缓冲区里。
