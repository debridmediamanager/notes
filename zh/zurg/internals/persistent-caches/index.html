持久化读取缓存

导入的 NZB、Real-Debrid、AllDebrid 和 TorBox 条目的库状态都保存在 data/*.zurgtorrent 里。这些文件描述的是库本身。读取准备数据和字节缓存都放在它们旁边，所以修改或清除派生缓存时，不会改写库，也不会丢失标签、名称和账户关联。

重启后仍保留的内容

缓存 位置 避免的工作
NZB 文档清单 data/nzb-manifests/ 为获取名称、大小、修复类型、密码和分段数而重复解析未变化的 XML
NZB 文章索引 data/nzb-index/ 重新构建文章引用;mmap 和 resident 两种模式都会使用
已解码的 Usenet 文章 data/bytecache/articles/ 重新获取并 yEnc 解码已经读过的文章
压缩包布局 data/archive-layouts/ 重新读取压缩包头,以重建分卷范围、嵌套条目和已学习的 ZIP 偏移量
已解压的压缩包块 data/bytecache/decoded/ 重启或向后跳转后,为了读到已保留的字节范围而再次解码
提供方状态 data/provider-cache/ 为了重建未变化的 RD 下载窗口,或为了获取新的 TorBox 区域表
下载链接 data/linkcache/ 重新解析仍然有效的 URL

压缩包布局支持存储式和压缩式的 RAR/ZIP 条目、嵌套源、加密范围以及支持的分卷压缩包。它们只保存源引用和偏移量,不保存实时的 HTTP 读取器。恢复时会重新附加当前的提供方 URL。缺少分卷的不完整布局会从源重新构建。在目录列表期间不会为每个条目预先获取文件头,而是在第一次读取后持久化已学习的 ZIP 载荷偏移量。

NZB 清单会与源文件的大小、纳秒级修改时间和解析器版本进行比对。mmap 会立即恢复元数据,并在需要时映射文章索引。resident 会把该索引加载到堆内存中。reparse 会立即恢复元数据,但在需要文章引用时仍会解析 XML。现有的库会在此版本下的首次扫描时构建清单;启动时的保存操作会在之后的扫描和重启时生效。

AllDebrid 和 TorBox 对同一未缓存账户/文件的并发请求现在共享同一次解析。取消一个调用者不会取消另一个调用者的解析。RD 保留其现有的合并机制。TorBox 在解析文件时会使用已知的目录名称和大小,而不再重新获取这些详细信息。

data/info/ 中的提供方详情记录在每个进程中首次 JSON 解码后会被记忆。每次复用都会检查文件标识、大小和修改时间,并返回一份独立的副本。库文件和详情文件都会以原子方式替换。

存储预算

这些可选的顶层设置以 MiB 为单位,重启后生效:

nzb_article_disk_cache_mb: 512
archive_decoded_disk_cache_mb: 512

每个缓存默认为整个实例 512 MiB。设为 0 会关闭该缓存;负值会按 0 处理。预算计算的是记录字节数,包括校验和,而不是文件系统的分配开销。有新记录写入时,最久未使用的记录会被清除。把预算调小后,初始化时会修剪现有缓存。关闭缓存后,已有文件会保留,需要你手动删除。

文章缓存是对现有 RAM 缓存的补充。归档缓存保留 64 KiB 的解码块,是对每个解码器 64 MiB 滚动 RAM 窗口的补充。两个缓存都不会预先下载整个库。如果读取的位置不在已保留的解码块内,仍然需要从压缩条目的开头开始解码。Rclone 的 VFS 缓存是独立的,它会继续直接提供已缓存的完整范围,不会经过这些路径;这些缓存同样对直接的 HTTP/WebDAV 读取有帮助。

压缩条目只能从开头解码,所以读取位置靠后时,实际上需要先把整个归档取回来。zurg 会把这类读取挂起 20 秒,之后返回 503,而不是让客户端一直没有回应。解码已经进行到的位置会被保留,因此播放器每次重试向前跳转时都会更近一步。如果读取靠近条目末尾而被拒绝,zurg 会对该条目启动一次后台解码,一次只处理一个条目,并把该条目的最后 8 MiB 保存在 data/bytecache/decoded-tails/ 中。之后文件末尾就能立即读取,这正是媒体服务器分析文件时会请求的内容。该存储占用的预算与 archive_decoded_disk_cache_mb 相同,并会随它一起关闭。

派生的元数据会随着库的增长而增加,并且不计入这些字节预算。NZB 扫描会删除已移除文档的清单和文章索引。过时的归档布局版本可以在实例停止时删除;它们可以安全丢弃,需要时会重新生成。

校验与恢复

新的元数据记录和字节数据块都带有校验和。损坏的记录和写入失败的缓存会回退到源站读取。文章记录只有在完整抓取成功后才会进入磁盘缓存。写入是在文章已经交给抓取它的读取操作之后进行的，所以读取操作从不需要等待缓存。如果一阵突发的文章写入数量超过同时运行的上限，多出来的记录会被直接丢弃，而不是卡住读取操作。被丢弃的记录会在下次需要时重新抓取。文章的标识包含 NZB 版本、服务器配置、文件和分段；归档的标识包含当前的源引用、大小、账户配置、密码和格式版本。替换 NZB 源时，归档布局和已解码的字节也会一并失效。

本地源的指纹假设替换后大小或修改时间会发生变化。它特意不在每次启动时对整个 XML 做哈希，以免拖慢启动。如果替换后两者都保持不变，就必须删除相关的派生缓存。

RD 快照只有在满足以下条件时才会被采用：令牌和配置的下载上限相同、在一小时内，并且实时探测确认最新条目和总数一致。列表一旦发生变化，就会触发全量对账。TorBox 区域表保持原有的六小时有效期。交付 URL 的有效期和提供方的失败处理方式都没有改变：已预热的布局会先打开负载，然后才确认 HTTP 成功，这样被撤销的 URL 就能走正常的重新解析/重试流程。

交付链接的变更会在大约一秒后触发一次合并的磁盘刷新。五分钟的重试刷新和关闭时的刷新仍然保留。原子替换可以防止读取方看到写了一半的记录，但它不是 fsync 保证，无法防止断电。在 Unix 上，新的缓存文件使用 0600 权限，因为链接和加密的归档布局可能包含凭据或派生密钥。Windows 则使用所在目录的 ACL，而不是 Unix 权限位。

带热缓存的备份

默认备份仍然只保存权威状态。如果要把派生缓存和实例本地的 rclone VFS 缓存也包含进去:

./zurg backup --include-caches --out warm.zurgbackup

这份备份可能比标准备份大得多。它包括上面列出的各个根目录、NZB 的命名、大小和 PAR2 缓存,以及网络测试状态。日志和 Plex 数据库快照仍然会被排除。data/rclone-cache/ 之外的 rclone 缓存不会被包含。如果你需要活动缓存在某个一致的时间点上的快照,请先停止实例。

请在实例停止的状态下,使用 ./zurg restore-backup warm.zurgbackup 进行还原。备份会保留纳秒级的源文件时间戳,因此没有变化的 NZB 可以保留它们的索引和清单。还原后的缓存仍然会经过正常的验证和过期检查。备份中包含配置文件里的 token 和缓存的凭据。

可复现的检查

BenchmarkParsedDocumentStartup 比较了 XML 解析与每种 manifest 恢复模式的耗时，测试用的是 60 个文件、30,000 个分段。BenchmarkDetailJSONRefresh 比较了 JSON 读取路径与带 memo 缓存的访问方式，测试用的是一条 1,000 个文件的记录。两个基准都是本地、缓存已预热的文件系统测试，不是端到端的生产启动测量。

测试环境为 Apple M3 Pro，2026-09-05 跑了三轮 500 ms（每个操作取中位数）：

操作 耗时 分配字节数
解析 NZB XML 43.49 ms 20.27 MB
以 mmap 模式恢复元数据 0.224 ms 59 KB
恢复元数据和常驻文章索引 0.577 ms 1.79 MB
以 reparse 模式恢复元数据 0.199 ms 59 KB
读取并解码 provider 详情记录 0.538 ms 784 KB
复用详情记录（stat 检查加复制） 0.0084 ms 59 KB

详情解码这一项在每次调用前都会清空新的 memo，所以包含了填充 memo 的成本。这些数字只是在比较两条当前的访问路径，不代表网络延迟，也不能推算整个媒体库的启动时间。

回归测试覆盖了这些场景：重启后复用、损坏、源文件变化、账号隔离、并发解析、开头/中间/结尾的字节一致性、超出 RAM 窗口的向后 seek，以及布局恢复后 URL 被撤销的情况。

go test ./...
go test -race ./internal/debrid ./internal/nzb ./internal/rarstream ./internal/universal ./pkg/cachefile ./pkg/diskcache
go test ./internal/nzb ./internal/torrent -run '^$' -bench 'Benchmark(ParsedDocumentStartup|DetailJSONRefresh)$' -benchmem
make integration-test

集成测试目标需要其文档中列出的真实测试账号和主机依赖。被跳过的集成脚本并不能验证缓存改动。
