# Identidade da requisição de saída {#outbound-request-identity}

`user_agent` controla o User-Agent HTTP compartilhado usado nas APIs dos serviços de debrid e nas leituras de CDN, nas buscas Newznab, nos downloads de NZB, no OpenSubtitles, nas sondagens do ffprobe, nas integrações com servidores de mídia, nos downloads de dependências, nas atualizações e nas exportações opcionais de compartilhamento/logs.
O padrão é um agente genérico de navegador. Deixar em branco restaura esse padrão. Um valor personalizado explícito é enviado exatamente como você digitou, mesmo que identifique o aplicativo.

`omit_user_agent: true` impede que os clientes HTTP do Go enviem o cabeçalho User-Agent e faz o ffprobe usar um agente vazio, substituindo a string configurada. Alguns serviços podem rejeitar requisições sem agente. O GitHub recusa todas com um 403, então as requisições ao GitHub (`zurg update` e os downloads do rclone e do ffprobe) continuam enviando o agente configurado, ou o agente genérico de navegador se nenhum for definido.

Plex, Jellyfin e Emby também exigem metadados de cliente/dispositivo. Configure-os com `outbound_client_name`, `outbound_client_id`, `outbound_client_version`, `outbound_device_name`, `outbound_device_id` e `outbound_platform`. Os padrões são `Media Client`, `media-client`, `1.0`, `Media Client`, `media-client` e `Desktop`, nessa ordem. O Plex usa o ID do cliente para autenticação, escaneamento e requisições de metadados; o Jellyfin/Emby usa o ID do dispositivo nos metadados de autenticação. Os campos só são usados onde o protocolo oferece suporte. Mudar os IDs pode fazer o servidor de mídia mostrar um cliente/dispositivo diferente.

Todas essas configurações estão disponíveis em Network & Connectivity no painel. O painel mostra os valores salvos com os padrões resolvidos. O Restart aplica as configurações juntas; salvar não muda a identidade em execução. Os valores devem ser ASCII imprimível, com no máximo 2048 caracteres; os campos de cliente/dispositivo não podem conter aspas nem barras invertidas. Tokens de autenticação e nomes de cabeçalhos do protocolo continuam inalterados, incluindo a credencial `X-Zurg-Token` exigida pelo DMM.

Os clientes de provedores/indexadores removem os cabeçalhos `Referer`, `Origin` e `X-Zurg*` antes de enviar as requisições, inclusive em redirecionamentos. Assim, os redirecionamentos não conseguem expor caminhos privados de URLs anteriores nem parâmetros de chave de API na query por meio de um Referer. A autenticação, as requisições de range, os cookies dos provedores e os limites de redirecionamento continuam funcionando. Nenhum identificador de cliente/dispositivo do aplicativo é adicionado a essas requisições.

O NNTP envia `AUTHINFO USER`, `AUTHINFO PASS`, `BODY`, `STAT`, `DATE` e `QUIT` conforme necessário, sem nenhum comando de identificação do software. Não há ID de software NNTP para configurar. Nomes de usuário e senhas continuam na configuração NNTP de cada provedor. Testes de transcrição TLS e em texto puro cobrem autenticação, acesso a artigos, keep-alive e encerramento.

Isso minimiza os identificadores explícitos do aplicativo; não oferece anonimato. Os serviços remotos continuam vendo credenciais, IPs de origem, conteúdo solicitado e horários. O comportamento de TLS/HTTP, identidades personalizadas, chaves de API registradas pelo aplicativo e padrões de acesso (incluindo os links de teste de rede do Real-Debrid) ainda podem permitir correlação.
URLs fornecidas externamente, metadados de torrents, IDs de artigos, payloads de compartilhamento e o conteúdo dos logs/configurações exportados não são reescritos. As URLs de download de software identificam o software solicitado. Players externos e ferramentas abertas separadamente usam as próprias configurações.

Testes de regressão no nível de socket cobrem os padrões, agentes personalizados e omitidos, redirecionamentos, autenticação preservada e metadados de servidores de mídia. Testes de configuração e do painel cobrem validação, ida e volta no YAML e aplicação das configurações no Restart.
